# 1. Мета PHASE A.8

PHASE A.8 присвячена одному з найважливіших механізмів шахового двигуна — системі ідентифікації позицій та повторного використання результатів пошуку.

У шахах одна й та сама позиція може виникнути різними послідовностями ходів.

Наприклад:

- спочатку розвивається кінь, потім слон;
- спочатку розвивається слон, потім кінь.

Якщо в обох випадках отримано однакову шахову позицію, двигун може повторно використати вже обчислений результат.

Це називається транспозицією.

Transposition Table (TT) зберігає інформацію про раніше досліджені позиції, щоб уникати повторного обчислення однакових або еквівалентних станів.

Однак тут виникає фундаментальна проблема:

**Не кожна однакова конфігурація фігур означає однакову шахову позицію.**

Для правильної ідентифікації можуть мати значення:

- розташування фігур;
- сторона, яка ходить;
- права на рокіровку;
- можливість en passant;
- лічильник напівходів;
- історія повторень;
- контекст пошуку;
- параметри оцінювання;
- глибина пошуку;
- тип збереженої межі.

Якщо ці характеристики не враховуються належним чином, TT може повертати результат, який був правильним для іншого стану, але неправильний для поточного.

# 2. Фундаментальна відмінність: Position, Hash та Search State

Необхідно розділити три поняття.

## 2.1. Position

Position — фактичний стан шахової системи.

Позначимо:

P = (B, S, C, E, H, R)

де:

- B — Board;
- S — сторона, яка ходить;
- C — Castling Rights;
- E — En Passant State;
- H — Halfmove Clock;
- R — Position History або релевантний історичний контекст.

Це концептуальна модель. Конкретна реалізація може зберігати ці характеристики в різних структурах.

## 2.2. Position Hash

Position Hash — компактний ідентифікатор, отриманий із певних характеристик позиції.

Наприклад:

Hash(P) = Zobrist(P)

Хеш не є самою позицією.

Він є її ймовірнісним представленням.

## 2.3. Search State

Search State містить додаткову інформацію, необхідну для пошуку:

SearchState = (P, d, α, β, ply, mode, history, context)

де:

- d — глибина;
- α, β — межі Alpha-Beta;
- ply — відстань від кореня;
- mode — тип пошуку;
- history — історія пошуку;
- context — контекст оцінювання та пошуку.

### Ключовий висновок

Position Hash ≠ Search State Identity.

Однакова шахова позиція може досліджуватися:

- на різній глибині;
- з різними Alpha-Beta bounds;
- у різному режимі;
- з різним історичним контекстом.

Тому TT повинна правильно розрізняти:

1. ідентичність позиції;
2. придатність збереженого результату для повторного використання.

# 3. AUDIT A8-001
## Zobrist Hashing Integrity

Zobrist Hashing — механізм формування хешу позиції шляхом XOR-комбінації псевдовипадкових значень.

Для кожної фігури та поля існує відповідний ключ.

Додаткові ключі можуть представляти:

- сторону ходу;
- права на рокіровку;
- en passant;
- інші характеристики, які входять до визначеної моделі ідентичності.

Спрощена формула:

H(P) = K₁ ⊕ K₂ ⊕ ... ⊕ Kₙ

де Kᵢ — ключі відповідних характеристик позиції.

### 3.1. Основні ризики

- пропущений компонент;
- дубльований XOR;
- неправильний індекс;
- неправильна орієнтація кольорів;
- неправильне оновлення після спеціального ходу;
- невідповідність між повним та інкрементальним хешем.

### 3.2. Вимога

Zobrist Hash повинен бути детермінованим.

Для однакової позиції та однакової таблиці ключів:

Hash(P) = Hash(P)

Це тривіальна на вигляд умова, але вона повинна зберігатися після будь-якої послідовності легальних трансформацій.

### Статус

**OPEN — необхідна перевірка реалізації та незалежна верифікація хешу.**

# 4. AUDIT A8-002
## Position Identity

Один із найважливіших пунктів цієї фази.

Потрібно визначити, що саме SUBIT-CHESS вважає однаковою позицією.

Розташування фігур саме по собі недостатнє.

Наприклад, дві позиції можуть мати:

- однакові фігури;
- однакове розташування;
- однакову сторону ходу;

але різні права на рокіровку.

Такі позиції не є повністю еквівалентними, оскільки множина доступних легальних ходів може відрізнятися.

Аналогічно, різний En Passant State може змінювати множину легальних ходів.

### 4.1. Мінімальна модель позиційної ідентичності

Для звичайного шахового пошуку доцільно використовувати:

PositionIdentity = (Board, Side, Castling, EnPassant)

Це основа для шахового хешу.

Однак для правил завершення партії цього може бути недостатньо.

### 4.2. Розширена модель

PositionContext = (PositionIdentity, HalfmoveClock, RepetitionContext)

Ця модель важлива для коректного трактування:

- 50-ходового правила;
- 75-ходового правила;
- триразового повторення;
- п'ятиразового повторення;
- інших історично залежних станів.

### Важливе розмежування

Не обов'язково включати всю історію партії безпосередньо в Zobrist Hash.

Але система повинна мати окремий механізм, який не дозволяє повторно використати TT score, якщо історичний контекст змінює результат.

# 5. AUDIT A8-003
## Hash Collision

Хешування не забезпечує абсолютної унікальності.

Різні позиції теоретично можуть мати однаковий хеш.

Hash(P₁) = Hash(P₂)

але:

P₁ ≠ P₂

Це називається hash collision.

### 5.1. Типи колізій

**Index Collision**

Різні хеші потрапляють в одну комірку TT.

**Full Hash Collision**

Різні позиції мають однаковий повний хеш.

**Key Truncation Collision**

Повний хеш обрізається до коротшого значення, і різні позиції стають нерозрізненними.

Ці явища мають різні наслідки.

### 5.2. Index Collision

Зазвичай не є проблемою, якщо TT зберігає достатню частину ключа та перевіряє відповідність запису.

### 5.3. Full Hash Collision

Може спричинити використання результату іншої позиції.

### 5.4. Рекомендація

TT Entry повинна зберігати достатню інформацію для перевірки відповідності ключа.

Потрібно розрізняти:

- індекс комірки;
- повний ключ;
- збережений verification key;
- фактичну перевірку відповідності.

### Критерій

Index Collision не повинен автоматично перетворюватися на прийняття чужого TT Entry.

# 6. AUDIT A8-004
## Incremental Hash Update

Інкрементальне оновлення хешу дозволяє не перераховувати всю позицію після кожного ходу.

Якщо хід змінює певні характеристики, відповідні ключі додаються або видаляються через XOR.

У спрощеній формі:

Hₙ₊₁ = Hₙ ⊕ RemovedKeys ⊕ AddedKeys

Це ефективно, але створює ризик накопичення помилок.

### 6.1. Основні трансформації

Необхідно перевірити:

- звичайний хід;
- захоплення;
- захоплення з en passant;
- рокіровку;
- promotion;
- capture-promotion;
- зміну сторони ходу;
- зміну castling rights;
- зміну en passant square.

### 6.2. Критичний принцип

Інкрементальний хеш повинен відповідати повному перерахунку:

IncrementalHash(P) = RecomputedHash(P)

Ця рівність повинна перевірятися після кожної трансформації у спеціальному тестовому режимі.

### 6.3. Make/Unmake

Після виконання та скасування ходу:

Hash(make(P, m)) → H₁

Hash(unmake(H₁, m)) → H₀

Повинно виконуватися:

H₀ = OriginalHash(P)

Необхідно перевіряти не тільки звичайні ходи, але й усі спеціальні трансформації.

# 7. AUDIT A8-005
## Full Hash Recalculation

Інкрементальний хеш потребує незалежного контрольного механізму.

Пропонується реалізувати або використовувати в тестовому режимі незалежну функцію:

recomputeHash(P)

Вона повинна обчислювати хеш без використання поточного інкрементального значення.

### Чому це важливо?

Якщо обидві функції використовують однакову помилкову логіку, порівняння може не виявити дефект.

Тому контрольний алгоритм повинен мати незалежний шлях обчислення.

### Рекомендована перевірка

Для кожної тестової позиції:

1. обчислити початковий хеш;
2. виконати легальний хід;
3. перевірити інкрементальний хеш;
4. незалежно перерахувати хеш;
5. порівняти результати;
6. скасувати хід;
7. повторити перевірку.

### Статус

**OPEN — незалежність контрольного механізму потребує підтвердження.**

# 8. AUDIT A8-006
## Transposition Table Architecture

TT — це структура зберігання результатів попередніх пошуків.

Типова концептуальна модель:

TTEntry = (Key, Move, Score, Depth, Bound, Age)

Додатково можуть зберігатися:

- evaluation;
- generation;
- node type;
- flags;
- контекстні характеристики;
- інформація про режим пошуку.

### Основні вимоги

1. Запис повинен відповідати позиції.
2. Глибина повинна зберігатися коректно.
3. Score повинен мати правильну перспективу.
4. Bound повинен правильно трактуватися.
5. Move повинен проходити перевірку легальності.
6. Replacement Policy не повинна безконтрольно знищувати корисні записи.
7. Застарілі записи не повинні трактуватися як актуальні без перевірки.

### Архітектурна проблема

TT — не просто кеш.

Це кеш результатів пошуку, які мають математичну семантику.

Тому неправильне повторне використання TT Entry може вплинути на коректність Alpha-Beta.

---

# 9. AUDIT A8-007
## TT Entry Layout

Формат запису повинен бути узгоджений із фактичними типами даних.

Потрібно перевірити:

- розмір ключа;
- розмір score;
- розмір depth;
- тип Bound;
- формат Move;
- generation;
- age;
- alignment;
- memory layout.

### Потенційні ризики

- переповнення;
- обрізання значень;
- помилка знакового типу;
- неправильне пакування полів;
- змішування прапорців;
- некоректне читання неповного запису.

### Особлива увага

Якщо TT використовує TypedArray або ручне пакування в числові слова, необхідно перевірити межі кожного поля.

Наприклад:

score ∈ [−MAX_SCORE, MAX_SCORE]

depth ∈ [0, MAX_DEPTH]

bound ∈ {EXACT, LOWER, UPPER}

Усі значення повинні бути представлені без втрати інформації.

# 10. AUDIT A8-008
## Depth Integrity

Глибина є одним із найважливіших параметрів TT.

Результат пошуку на глибині 8 не завжди придатний для заміни результату на глибині 12.

Типова умова використання:

TTDepth ≥ RequiredDepth

Але навіть вона не є достатньою.

Потрібно також враховувати:

- тип вузла;
- Bound;
- поточне вікно;
- режим пошуку;
- контекст;
- статус завершення попереднього пошуку.

### Ризик

TT Entry із достатньою глибиною може мати лише LOWER або UPPER bound.

Його не можна автоматично трактувати як точне значення.

### Вимога

Depth Integrity та Bound Integrity повинні перевірятися разом.

---

# 11. AUDIT A8-009
## Score Integrity

Score у TT повинен відповідати позиції, а не випадковому контексту вузла.

Особливо важливо правильно трактувати:

- сторону оцінювання;
- знак score;
- mate scores;
- дистанцію до мату;
- значення Infinity;
- спеціальні terminal scores.

### 11.1. Perspective Integrity

Якщо пошук використовує Negamax, score повинен мати визначену перспективу.

Наприклад:

Score(P, sideToMove)

Якщо TT зберігає score з іншої перспективи, його використання без коректного перетворення призведе до помилки знака.

### 11.2. Mate Score Integrity

Матова оцінка часто залежить від ply.

Наприклад:

MATE_SCORE − ply

Якщо TT зберігає таке значення без нормалізації, одна й та сама позиція, досягнута на різній відстані від кореня, може отримати некоректну матову оцінку.

Це потребує окремого механізму.

---

# 12. AUDIT A8-010
## EXACT / LOWERBOUND / UPPERBOUND

Це критичний елемент TT.

TT Entry повинна зберігати не тільки score, але й семантику цього score.

### EXACT

Оцінка є точною для відповідного пошукового контексту.

### LOWERBOUND

Справжнє значення не менше збереженого.

### UPPERBOUND

Справжнє значення не більше збереженого.

### Приклад

Якщо:

Score ≥ Beta

то пошук може отримати fail-high.

Збережений результат може бути LOWERBOUND.

Якщо:

Score ≤ Alpha

може бути збережений UPPERBOUND.

Якщо результат знаходиться всередині початкового вікна, він може бути EXACT.

### Критична вимога

Bound Classification повинна використовувати початкові межі вузла, а не некоректно оновлені проміжні значення.

Позначимо:

α₀ — початковий alpha;

β₀ — початковий beta.

Тоді класифікація повинна бути узгоджена саме з цими межами.

### Потенційний дефект

Якщо TT Entry із LOWERBOUND використовується як EXACT, engine може повертати неправильну оцінку.

Тому Bound — не другорядний прапорець, а частина семантики запису.

---

# 13. AUDIT A8-011
## Mate Score Normalization

Матова оцінка має спеціальну семантику.

Розглянемо:

MATE_SCORE − ply

Це дозволяє віддавати перевагу швидшому мату та відкладати неминучий мат.

Але позиція може бути досягнута з різною глибиною ply.

Тому TT не повинна безпосередньо зберігати коренево залежне значення без нормалізації.

### Рекомендований механізм

Перед записом:

scoreToTT(score, ply)

Перед використанням:

scoreFromTT(score, ply)

Ці функції повинні бути взаємно узгодженими.

### Тест

Для одного й того самого матового стану, досягнутого на різній відстані від кореня:

- відстань до мату повинна зберігатися;
- знак повинен бути правильним;
- перевага швидшого мату не повинна зникати.

---

# 14. AUDIT A8-012
## Replacement Policy

TT має обмежений обсяг пам'яті.

Коли комірка зайнята, система повинна вирішити, який запис залишити.

Можливі критерії:

- глибина;
- вік;
- generation;
- exactness;
- корисність ходу;
- частота повторного використання.

### Проблема

Якщо система завжди залишає найглибший запис, вона може блокувати оновлення актуальної інформації.

Якщо завжди залишає найновіший, може втрачати цінні глибокі результати.

### Рекомендований принцип

Replacement Policy повинна балансувати:

**Depth Value**

Цінність глибокого пошуку.

**Freshness**

Актуальність запису.

**Information Quality**

Якість bound.

**Reuse Probability**

Імовірність повторного використання.

### Вимога

Replacement Policy не повинна створювати систематичне блокування оновлення записів.

---

# 15. AUDIT A8-013
## TT Aging

Aging дозволяє поступово зменшувати цінність застарілих записів.

Це особливо важливо під час тривалого пошуку та між різними пошуковими ітераціями.

### Потенційні проблеми

- generation overflow;
- некоректне порівняння віку;
- надмірне збереження старих записів;
- передчасне видалення корисних записів;
- неправильне трактування generation після reset.

### Вимога

Aging повинен бути детермінованим і мати визначені правила переходу.

---

# 16. AUDIT A8-014
## Generation Integrity

Generation — механізм позначення актуальності TT Entry.

Потрібно розділити:

- generation пошукового циклу;
- age запису;
- generation конкретного запису;
- загальний стан TT.

### Ризик

Якщо generation оновлюється в неправильний момент, система може:

- вважати актуальні записи застарілими;
- використовувати старі записи як нові;
- некоректно працювати після reset;
- порушувати Replacement Policy.

### Критерій

Generation transition повинна мати формальну послідовність і контрольоване переповнення.

# 17. AUDIT A8-015
## Hash Move Validation

TT Move часто використовується для покращення ordering.

Але він може бути:

- застарілим;
- пошкодженим;
- некоректно закодованим;
- отриманим через hash collision;
- нелегальним у поточній позиції.

### Вимога

TT Move повинен пройти перевірку перед виконанням.

Наявність Move у TT Entry не є доказом його легальності.

### Додатковий тест

Якщо TT Move є нелегальним:

- пошук не повинен аварійно завершуватися;
- позиція не повинна змінюватися;
- інші легальні ходи повинні залишатися доступними;
- некоректний запис повинен бути безпечно проігнорований.

# 18. AUDIT A8-016
## Repetition vs Transposition

Це один із найскладніших пунктів A.8.

Транспозиція означає, що однакова позиція досягнута різними послідовностями ходів.

Повторення означає, що відповідна позиція знову з'явилася в історії партії.

Це не тотожні поняття.

### Приклад

Позиція P може бути досягнута:

- без попереднього повторення;
- після одного повторення;
- після двох повторень.

Фізична конфігурація фігур може бути однаковою.

Але статус щодо правила триразового повторення буде різним.

### Критична проблема

Якщо TT повертає score, отриманий у позиції без повторення, для тієї самої позиції з історією, яка вже наближається до автоматичної нічиєї або дає право вимагати її, результат може бути непридатним.

### Принцип

Position Identity ≠ Repetition Context.

### Рекомендація

Repetition Detection повинна мати окремий механізм, який враховує історію поточного шляху.

TT не повинна автоматично замінювати цей механізм.

# 19. AUDIT A8-017
## Draw Context

Нічия може залежати від історії або поточного матеріального стану.

Потрібно розрізняти:

- stalemate;
- insufficient material;
- триразове повторення;
- п'ятиразове повторення;
- 50-ходове правило;
- 75-ходове правило;
- інші завершальні стани, визначені правилами гри.

### Ризик

TT Entry може містити оцінку, отриману в контексті, де позиція була нічиєю через історію.

Повторне використання такого score у позиції з іншою історією може бути неправильним.

### Рекомендація

Потрібно розділити:

**Position-Dependent Draw**

Нічия, яка випливає з поточного стану позиції.

**History-Dependent Draw**

Нічия, яка залежить від історії ходів.

**Search-Dependent Draw**

Нічия, яка виникає внаслідок конкретного пошукового шляху або правил пошукової процедури.

Ці категорії не повинні змішуватися в одному неідентифікованому TT score.

# 20. AUDIT A8-018
## Halfmove Clock Context

Halfmove Clock впливає на правила 50 та 75 ходів.

Тому дві позиції з однаковим розташуванням фігур можуть мати різний статус щодо наближення до автоматичної нічиєї.

Наприклад:

P₁: HalfmoveClock = 10

P₂: HalfmoveClock = 99

Якщо інші характеристики однакові, звичайна позиційна оцінка може бути схожою.

Але пошуковий контекст суттєво відрізняється.

### Критична вимога

TT повинна враховувати цю різницю там, де вона впливає на придатність score.

Необхідно визначити:

1. чи Halfmove Clock включається в TT Key;
2. чи використовується окремий verification mechanism;
3. чи обмежується використання score за певних значень;
4. чи перевіряється Draw Context перед TT Cutoff.

Не можна автоматично вважати, що однаковий Zobrist Hash означає однакову можливість завершення партії.

# 21. AUDIT A8-019
## TT Context Collision

Цей пункт об'єднує декілька попередніх ризиків.

Дві позиції можуть мати однаковий основний хеш, але різні додаткові умови.

Наприклад:

- різний Halfmove Clock;
- різна історія повторень;
- різні evaluation parameters;
- різний режим пошуку;
- різні умови terminal detection.

### Формалізація

Нехай:

K(P) — основний Position Hash.

А:

C(P) — контекст позиції.

Тоді:

K(P₁) = K(P₂)

не гарантує:

C(P₁) = C(P₂)

### Вимога

Перед використанням TT Score потрібно перевірити не лише збіг основного ключа, а й придатність збереженого результату в поточному контексті.

# 22. AUDIT A8-020
## Search State Reuse

TT зберігає результат попереднього пошуку.

Але результат може бути:

- точним;
- нижньою межею;
- верхньою межею;
- неповним;
- отриманим після перерваного пошуку;
- залежним від селективних евристик.

### Проблема

Не всі завершення пошуку створюють придатний TT Entry.

Наприклад, якщо пошук був перерваний через:

- time limit;
- node limit;
- user abort;
- worker termination;

неповний результат не повинен автоматично записуватися як точний.

### Рекомендація

Кожен результат пошуку повинен мати Completion Status:

**COMPLETED**

Вузол завершено.

**ABORTED**

Пошук перервано.

**INCOMPLETE**

Результат не є повністю визначеним.

**FAILED**

Сталася помилка обчислення або стану.

TT повинна мати чіткі правила запису для кожної категорії.

# 23. AUDIT A8-021
## Cache Integrity

TT є спеціалізованим кешем.

Тому необхідно розрізняти:

- правильність ключа;
- правильність запису;
- правильність зчитування;
- придатність score;
- придатність move;
- актуальність запису.

### Основний інваріант

TTReuse(P, Entry) є допустимим лише тоді, коли:

1. Entry відповідає позиції;
2. її глибина придатна;
3. bound дозволяє відповідне використання;
4. score має правильну перспективу;
5. контекст не робить результат непридатним;
6. запис завершений;
7. move, якщо використовується, проходить перевірку.

### Диференційний тест

Для контрольованої множини позицій:

SearchWithoutTT(P)

порівнюється із:

SearchWithTT(P)

За вимкнених селективних механізмів та однакових умов результат повинен бути узгодженим.

Різниця у кількості вузлів очікувана.

Різниця в математичному результаті контрольованого пошуку потребує розслідування.

# 26. Особливий аудит: адитивне комбінування Hash і Halfmove Bucket

У попередньому аудиті v3.0.11 було зафіксовано потенційний ризик у схемі, де ключ формується через додавання:

`key = baseHash + bucket * 1048576`

Цей пункт потребує повторної перевірки фактичної реалізації.

### Чому це важливо?

Додавання до основного хешу не гарантує унікальності комбінованого ключа.

Різні пари:

(baseHash₁, bucket₁)

та:

(baseHash₂, bucket₂)

можуть дати однаковий результат.

Тобто:

baseHash₁ + bucket₁ · C  
=  
baseHash₂ + bucket₂ · C

при різних значеннях компонентів.

### Потенційний наслідок

Два різні контексти можуть потрапити до одного ключа.

Це створює ризик неправильного TT Hit.

### Рекомендоване рішення

Необхідно розділити:

- Position Hash;
- Context Hash;
- TT Index;
- Verification Key.

Можливі підходи:

**Підхід A — окремі поля**

Зберігати основний ключ і контекстний ідентифікатор окремо.

**Підхід B — незалежне змішування**

Використовувати визначену функцію змішування з перевіркою результату.

**Підхід C — context-aware verification**

Зберігати основний ключ, а перед використанням score перевіряти додатковий контекст.

Жоден із підходів не усуває всі можливі колізії автоматично. Потрібно визначити точну семантику ключа та механізм перевірки.

**Статус:** CANDIDATE RISK — потребує повторного source-level підтвердження.

# 29. SUBIT Transposition Integrity Protocol — STIP

Додатково пропонується протокол:

## STIP — SUBIT Transposition Integrity Protocol

Його функція — визначити послідовність перевірок перед повторним використанням TT Entry.

### Етап 1 — Lookup

Визначити індекс комірки.

### Етап 2 — Key Verification

Перевірити збережений ключ.

### Етап 3 — Position Compatibility

Перевірити відповідність позиційної ідентичності.

### Етап 4 — Context Compatibility

Перевірити історичний та пошуковий контекст.

### Етап 5 — Depth Validation

Перевірити достатність глибини.

### Етап 6 — Bound Validation

Перевірити EXACT, LOWERBOUND або UPPERBOUND.

### Етап 7 — Score Validation

Перевірити перспективу та нормалізацію score.

### Етап 8 — Completion Validation

Переконатися, що запис отримано з допустимого завершеного пошуку.

### Етап 9 — Move Validation

Перевірити легальність TT Move.

### Етап 10 — Reuse Decision

Дозволити:

- повний TT Cutoff;
- використання лише TT Move;
- використання лише Evaluation;
- ігнорування запису.

### Основний принцип

TT Hit не повинен автоматично означати TT Cutoff.

Це два різні стани.

# 33. Архітектурний висновок: TT як система контекстуального знання

Для SUBIT-CHESS важливо не трактувати Transposition Table лише як швидку пам'ять.

TT зберігає не просто відповідь на запит:

«Якою є оцінка цієї позиції?»

Вона зберігає результат певного обчислювального процесу, який відбувся за конкретних умов.

Тому TT Entry фактично має структуру:

**Knowledge = State + Context + Provenance + Dynamics + Rule + Meta-Rule**

У цьому контексті:

- State — позиція;
- Context — історичні та пошукові умови;
- Provenance — походження результату;
- Dynamics — глибина й характеристики пошуку;
- Rule — семантика bound та шахових правил;
- Meta-Rule — умови допустимості повторного використання.

Це дає змогу сформулювати важливий принцип:

> Однакова позиція не гарантує однакової придатності всіх попередніх результатів пошуку.

SUBIT-CHESS повинен не просто впізнавати повторення структури.

Він повинен перевіряти, чи є попередній результат релевантним для поточного контексту.

Саме це відрізняє механічне кешування від контекстуального повторного використання знань.

# 34. Загальний висновок PHASE A.8

Transposition Table здатна істотно прискорити шаховий двигун.

Але її ефективність залежить від правильності трьох фундаментальних механізмів:

1. ідентифікації позиції;
2. збереження результату;
3. перевірки придатності результату для повторного використання.

Основні ризики:

- неповна Position Identity;
- некоректне інкрементальне хешування;
- hash collision;
- неправильне трактування bound;
- помилка нормалізації mate score;
- повторне використання результатів із несумісним історичним контекстом;
- неправильне трактування Halfmove Clock;
- stale TT entries;
- некоректна Replacement Policy;
- запис неповного результату пошуку.

Головна вимога:

**TT Hit ≠ TT Cutoff.**

Спочатку система повинна встановити, що запис відповідає позиції та контексту.

Лише після цього вона може вирішити, чи дозволено використовувати score, move або bound.

У термінах SUBIT:

**POSITION → IDENTITY → CONTEXT → VERIFICATION → REUSE**

а не:

**HASH MATCH → AUTOMATIC CUTOFF**
