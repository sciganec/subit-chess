# 1. МЕТА PHASE A.15

Попередні фази досліджували внутрішню логіку шахового двигуна: від представлення позиції до адаптивного пошуку.

Однак повноцінний шаховий двигун повинен взаємодіяти із зовнішнім середовищем.

Це середовище може включати:

- шаховий графічний інтерфейс;
- UCI-сумісний клієнт;
- автоматизований тестовий стенд;
- консольний інтерфейс;
- систему аналізу партій;
- зовнішній контролер;
- інструменти налагодження.

Між зовнішньою системою та внутрішнім ядром існує межа відповідальності.

Якщо ця межа реалізована неправильно, двигун може:

- отримати некоректну позицію;
- втратити історію ходів;
- неправильно інтерпретувати команду;
- продовжувати пошук після команди зупинки;
- повернути застарілий хід;
- видати результат незавершеного пошуку;
- змішати результати двох пошукових завдань;
- неправильно обробити зміну налаштувань;
- порушити формат протоколу.

Отже, A.15 досліджує не шахову силу як таку, а **цілісність взаємодії між шаховим ядром і зовнішнім керуванням**.

Основне питання:

**Чи може SUBIT-CHESS гарантувати, що кожна зовнішня команда однозначно перетворюється на коректну внутрішню дію, а кожен результат пошуку повертається в правильному контексті?**

# 2. SUBIT ENGINE INTERFACE MODEL

## 2.1. Архітектурне визначення

Пропонується:

**SEIM — SUBIT Engine Interface Model.**

SEIM — архітектурний шар між зовнішнім протоколом і внутрішнім шаховим ядром.

Його функції:

1. приймати зовнішні команди;
2. перевіряти синтаксис;
3. перевіряти семантику;
4. визначати допустимість команди в поточному стані;
5. перетворювати команду на внутрішню операцію;
6. передавати операцію відповідному модулю;
7. контролювати виконання;
8. формувати коректну відповідь;
9. зберігати контекст операції;
10. забезпечувати відновлення після помилок.

SEIM не повинен містити шахову логіку, яка дублює ядро.

Він повинен керувати взаємодією з ядром.

## 2.2. Формальна модель

Нехай:

`I = (C, S, P, O, E)`

де:

- `C` — отримана команда;
- `S` — стан протоколу;
- `P` — контекст позиції;
- `O` — конфігурація двигуна;
- `E` — контекст виконання.

Тоді:

`SEIM(I) → (A, R, S′)`

де:

- `A` — внутрішня дія;
- `R` — зовнішня відповідь;
- `S′` — новий стан протоколу.

Важливо: не кожна синтаксично коректна команда є семантично допустимою.

Наприклад, команда `stop` має різне практичне значення залежно від того, чи виконується пошук.

# 3. UCI PROTOCOL COMPLIANCE

## 3.1. Загальна вимога

UCI — Universal Chess Interface — визначає стандартний спосіб взаємодії шахового двигуна з графічними інтерфейсами та іншими клієнтами.

SUBIT-CHESS повинен коректно реалізовувати ті команди та можливості UCI, які він заявляє як підтримувані.

Офіційна специфікація UCI повинна бути еталоном протокольної відповідності.

Архітектурно необхідно перевірити такі команди:

- `uci`;
- `debug`;
- `isready`;
- `setoption`;
- `register`;
- `ucinewgame`;
- `position`;
- `go`;
- `stop`;
- `ponderhit`;
- `quit`.

Також потрібно перевірити інформаційні повідомлення:

- `id`;
- `option`;
- `uciok`;
- `readyok`;
- `info`;
- `bestmove`.

## 3.2. Принцип відповідності

Необхідно розрізняти:

1. повну підтримку команди;
2. часткову підтримку;
3. допустиме ігнорування непідтримуваних опцій відповідно до протоколу;
4. помилкову інтерпретацію;
5. відсутність реалізації.

Не можна вважати двигун UCI-сумісним лише тому, що він розпізнає кілька основних команд.

## 3.3. UCI Output Integrity

Протокольний вихід повинен бути структурно коректним.

Особливо важливо:

- одна команда — один передбачений результат;
- відсутність стороннього тексту в протокольному потоці;
- коректне завершення рядків;
- правильна послідовність відповідей;
- відсутність змішування повідомлень різних пошукових завдань.

Діагностичні повідомлення повинні відокремлюватися від протокольного каналу, якщо використовується середовище, де це можливо.

# 4. COMMAND PARSING ARCHITECTURE

## 4.1. Проблема парсингу

Зовнішні команди надходять як текст.

Текст повинен перетворюватися на структуровані операції.

Небезпечно використовувати фрагментарну обробку, за якої різні частини команди інтерпретуються незалежно без перевірки загальної структури.

## 4.2. Command Pipeline

Пропонується:

`Raw Input → Tokenization → Parsing → Validation → Semantic Resolution → Dispatch`

### Stage 1 — Raw Input

Отримання повного рядка команди.

### Stage 2 — Tokenization

Розділення рядка на токени з урахуванням структури протоколу.

### Stage 3 — Parsing

Формування структурованого представлення команди.

### Stage 4 — Validation

Перевірка синтаксичної коректності.

### Stage 5 — Semantic Resolution

Перевірка значень, меж і контексту.

### Stage 6 — Dispatch

Передавання операції відповідному модулю.

## 4.3. Parser Invariants

Парсер повинен гарантувати:

- відсутність неоднозначного трактування;
- контроль некоректних токенів;
- контроль відсутніх параметрів;
- контроль повторюваних параметрів;
- коректне розпізнавання числових значень;
- контроль переповнення;
- контроль надмірно довгого вводу;
- відсутність часткового виконання некоректної команди.

## 4.4. Atomic Command Processing

Команда повинна або успішно пройти необхідні перевірки та бути переданою на виконання, або бути відхиленою без часткового пошкодження стану.

Це особливо важливо для `position`, `setoption` та `go`.

Принцип:

**VALIDATE FIRST — MUTATE SECOND.**

# 5. POSITION COMMAND INTEGRITY

## 5.1. Мета

Команда `position` встановлює позицію, з якої двигун повинен виконувати аналіз.

Вона може задавати:

- початкову позицію;
- позицію через FEN;
- послідовність ходів після початкової позиції.

## 5.2. Position Context

Пропонується:

`PositionContext = (B, T, C, E, H, M)`

де:

- `B` — розташування фігур;
- `T` — сторона, яка ходить;
- `C` — права рокірування;
- `E` — доступність взяття на проході;
- `H` — лічильник напівходів;
- `M` — номер повного ходу.

Для коректного пошуку додатково необхідно зберігати історію, потрібну для повторень і контексту правил.

## 5.3. Position Command Failure Modes

Потрібно перевірити:

1. неправильний ключ `startpos`;
2. некоректний FEN;
3. некоректний формат `moves`;
4. незаконний хід у послідовності;
5. неправильний порядок ходів;
6. неповну історію;
7. помилку відновлення стану;
8. невідповідність сторони, яка ходить;
9. некоректні права рокірування;
10. неправильне трактування en passant.

## 5.4. Atomic Position Reconstruction

Найбезпечніша архітектура:

1. створити тимчасовий стан;
2. встановити базову позицію;
3. перевірити її;
4. послідовно застосувати ходи;
5. перевірити кожен хід;
6. перевірити кінцевий стан;
7. лише після успіху замінити активний контекст двигуна.

Таким чином некоректна команда не повинна залишати двигун у частково зміненому стані.

## 5.5. Position History Preservation

Важливо не ототожнювати:

- поточну позицію;
- історію ходів;
- історію повторень;
- стан пошуку.

Дві однакові дошки можуть мати різні контексти повторення.

Тому `position` не повинна зводитися до встановлення лише розташування фігур.

# 6. FEN INPUT VALIDATION

## 6.1. FEN як зовнішнє джерело стану

FEN є текстовим представленням шахової позиції.

Двигун повинен перевіряти не лише формат, а й внутрішню узгодженість даних.

## 6.2. Validation Layers

Пропонується п'ять рівнів:

**FEN-L1 — Syntax**

Перевірка кількості полів і структури рядка.

**FEN-L2 — Board Encoding**

Перевірка восьми горизонталей, допустимих символів та коректної кількості клітинок.

**FEN-L3 — Piece Constraints**

Перевірка фігур, королів, пішаків і допустимих обмежень представлення.

**FEN-L4 — Rights Consistency**

Перевірка сторони, яка ходить, прав рокірування, en passant і лічильників.

**FEN-L5 — Position Plausibility**

Перевірка базової логічної узгодженості позиції.

## 6.3. Syntax vs Legality

Необхідно розрізняти:

- синтаксично некоректний FEN;
- структурно некоректний FEN;
- позицію з неможливими властивостями;
- позицію, яка є незвичайною, але може бути допустимою для аналізу.

Не слід автоматично відхиляти всі позиції, які не могли виникнути в звичайній партії, якщо формат або призначення двигуна дозволяє аналіз довільних позицій.

Водночас двигун повинен мати чітку політику для позицій, що порушують фундаментальні правила шахового стану.

# 7. GO COMMAND SEMANTICS

## 7.1. Значення команди

`go` запускає пошук.

Однак ця команда може містити різні обмеження:

- `depth`;
- `nodes`;
- `movetime`;
- `wtime`;
- `btime`;
- `winc`;
- `binc`;
- `movestogo`;
- `infinite`;
- `ponder`;
- `searchmoves`.

Двигун повинен правильно інтерпретувати підтримувані параметри.

## 7.2. Search Limits Model

Пропонується:

`SearchLimits = (D, N, T, C, P, I)`

де:

- `D` — обмеження глибини;
- `N` — обмеження вузлів;
- `T` — часові обмеження;
- `C` — параметри контролю часу;
- `P` — обмеження кандидатних ходів;
- `I` — режим нескінченного пошуку.

## 7.3. Conflicting Limits

Потрібно перевірити поведінку за наявності кількох параметрів одночасно.

Наприклад:

- `depth` разом із `nodes`;
- `movetime` разом із параметрами годинника;
- `infinite` разом з іншими обмеженнями;
- `ponder` разом із часовими параметрами.

Двигун повинен мати передбачувану політику пріоритетів відповідно до протоколу.

## 7.4. Searchmoves

Якщо задано `searchmoves`, пошук повинен обмежуватися дозволеною множиною кандидатів.

Необхідно перевірити:

- легальність кожного ходу;
- дублікати;
- порожню множину;
- некоректну нотацію;
- ходи, які не відповідають поточній позиції.

Якщо обмеження не залишає жодного допустимого ходу, двигун повинен коректно обробити цю ситуацію відповідно до протоколу та правил завершення партії.

# 8. STOP COMMAND AND SEARCH CANCELLATION

## 8.1. Критичність

`stop` — одна з найважливіших команд зовнішнього керування.

Вона повинна припинити активний пошук і забезпечити коректне завершення пошукового завдання.

Простого встановлення прапорця недостатньо, якщо пошук не перевіряє його в усіх потрібних точках.

## 8.2. Cancellation Model

Пропонується:

`SearchControl = (Active, StopRequested, Completed, Aborted)`

Ці стани повинні мати чіткі переходи.

## 8.3. Stop Invariants

1. Команда stop не повинна пошкоджувати дошку.
2. Не повинна залишати незавершені зміни make/unmake.
3. Не повинна дозволяти старому пошуку змінювати результат нового.
4. Не повинна повертати випадковий або незаконний хід.
5. Повинна забезпечувати передбачуване завершення.
6. Повинна зберігати останній завершений результат, якщо він існує.
7. Повинна коректно обробляти stop до завершення першої ітерації.

## 8.4. Cancellation Latency

Потрібно вимірювати час між отриманням `stop` і фактичним припиненням пошуку.

Надмірна затримка може означати, що пошуковий цикл рідко перевіряє прапорець переривання.

Однак перевірка повинна бути достатньо частою, щоб не створювати надмірних накладних витрат.

## 8.5. Stop Race Conditions

Особливу увагу потрібно приділити таким сценаріям:

- stop одночасно із завершенням пошуку;
- stop під час QSearch;
- stop під час make/unmake;
- stop під час TT-запису;
- stop перед початком наступної ітерації;
- stop після завершення пошуку, але до видачі bestmove.

# 9. PONDERING AND PONDERHIT

## 9.1. Pondering

Pondering дозволяє двигуну аналізувати можливу позицію суперника до фактичного отримання наступного ходу.

Це може підвищувати ефективність використання часу.

## 9.2. Ponder State

Пропонується:

`PonderContext = (BasePosition, PredictedMove, PredictedPosition, SearchState)`

Необхідно зберігати зв'язок між:

- позицією до прогнозованого ходу;
- прогнозованим ходом;
- очікуваною позицією;
- активним пошуковим завданням.

## 9.3. Ponderhit

Команда `ponderhit` означає, що прогнозований хід підтверджено.

Потрібно перевірити:

1. чи відповідає реальна позиція прогнозованій;
2. чи може поточний пошук продовжитися;
3. чи потрібно змінити часовий режим;
4. чи не втрачено історичний контекст;
5. чи не використовується застарілий пошуковий результат.

## 9.4. Ponder Mismatch

Якщо реальний хід не відповідає прогнозу, двигун повинен коректно завершити або відкинути попередній пошук і перейти до нової позиції.

Не можна переносити результат старої позиції в нову без перевірки відповідності контексту.

# 10. BESTMOVE CORRECTNESS

## 10.1. Основна вимога

`bestmove` є остаточною відповіддю двигуна на пошукове завдання.

Це не просто перший хід із внутрішнього масиву кандидатів.

Він повинен відповідати:

- актуальній позиції;
- актуальному пошуковому завданню;
- легальному ходу;
- завершеному або коректно перерваному процесу.

## 10.2. Bestmove Provenance

Пропонується:

`BestmoveResult = (Move, Ponder, PositionId, SearchId, CompletionState)`

Додатково:

- джерело вибору ходу;
- глибина;
- оцінка;
- статус завершення;
- причина зупинки.

Ця інформація може бути внутрішньою, навіть якщо не вся вона передається через UCI.

## 10.3. Bestmove Invariants

- Хід повинен бути легальним у відповідній позиції.
- Хід повинен належати актуальному пошуковому завданню.
- Після завершення партії не можна повертати звичайний хід як найкращий.
- Якщо немає легальних ходів, потрібно коректно обробити мат або пат.
- Якщо пошук перервано до першої завершеної ітерації, потрібен безпечний fallback.
- `ponder` повинен бути узгоджений із вибраним `bestmove`.

## 10.4. Stale Bestmove

Особливий ризик — повернення результату попереднього пошуку після того, як користувач уже встановив нову позицію.

Пропонується використовувати:

`SearchId = monotonically_increasing_identifier`

Кожен пошуковий запит повинен мати власний ідентифікатор.

Результат може бути опублікований лише тоді, коли його контекст відповідає актуальному завданню.

- currmove;
- currmovenumber.

## 11.2. Reporting Integrity

Необхідно перевірити:

- правильність типу оцінки;
- коректність mate score;
- узгодженість depth і seldepth;
- правильність PV;
- коректність node count;
- коректність часу;
- відповідність multipv;
- відсутність застарілих повідомлень.

## 11.3. Score Semantics

Необхідно чітко розрізняти:

- оцінку в centipawns;
- оцінку мату;
- нижню межу;
- верхню межу;
- точне значення в межах пошукового протоколу.

Fail-high та fail-low результати не можна представляти як точні оцінки.

## 11.4. Information Provenance

Кожне повідомлення `info` повинно походити від актуального пошукового завдання.

Після заміни позиції повідомлення старого пошуку не повинні змішуватися з новими.

# 12. MULTIPV OUTPUT

## 12.1. MultiPV Consistency

Якщо двигун підтримує MultiPV, він повинен правильно формувати кілька альтернативних ліній.

Потрібно перевірити:

- кількість PV;
- їхню нумерацію;
- узгодженість оцінок;
- легальність ходів;
- повноту варіантів;
- поведінку при зміні MultiPV під час пошуку.

## 12.2. PV Ordering

Потрібно встановити, чи відповідає порядок PV фактичному ранжуванню варіантів.

Не можна допускати ситуацію, коли PV 1 має гіршу оцінку за PV 2 через помилку сортування або змішування результатів.

Винятки можуть виникати через різні типи меж і неповністю завершені пошукові ітерації. Вони повинні бути враховані в логіці представлення.

## 12.3. PV Legality

Кожен хід у PV повинен бути легальним у позиції, що виникає після попередніх ходів цього варіанта.

Перевірка лише першого ходу недостатня.

# 13. SETOPTION AND CONFIGURATION INTEGRITY

## 13.1. Мета

`setoption` дозволяє зовнішній системі змінювати параметри двигуна.

Можливі налаштування:

- Hash;
- Threads;
- MultiPV;
- Ponder;
- Clear Hash;
- параметри власних евристик.

Підтримувані опції повинні бути задекларовані.

## 13.2. Option Registry

Пропонується:

`Option = (Name, Type, Default, Min, Max, State, Mutability)`

де:

- `Name` — назва;
- `Type` — тип;
- `Default` — значення за замовчуванням;
- `Min` і `Max` — межі;
- `State` — поточне значення;
- `Mutability` — умови зміни.

## 13.3. Configuration Validation

Необхідно перевірити:

- невідому опцію;
- некоректний тип;
- значення поза межами;
- повторне встановлення;
- зміну під час пошуку;
- несумісні конфігурації;
- переповнення пам'яті;
- часткове застосування конфігурації.

## 13.4. Configuration Atomicity

Налаштування повинні застосовуватися атомарно там, де це необхідно.

Якщо зміна опції вимагає перебудови внутрішньої структури, нова конфігурація повинна бути повністю підготовлена до того, як стане активною.

## 13.5. Runtime Mutability

Не всі параметри безпечно змінювати під час активного пошуку.

Потрібно розділити:

- runtime-safe options;
- search-boundary options;
- new-game-only options;
- restart-required options.

# 14. UCINEWGAME AND STATE RESET

## 14.1. Призначення

`ucinewgame` сигналізує про початок нової партії.

Це не обов'язково означає, що всі налаштування двигуна повинні повністю скидатися.

Необхідно визначити, які компоненти очищуються, а які зберігаються.

## 14.2. Reset Model

Пропонується:

`NewGameReset = (H, TT, History, Search, Stats, Config)`

де:

- `H` — історичний контекст;
- `TT` — транспозиційна таблиця;
- `History` — історичні евристики;
- `Search` — активний пошук;
- `Stats` — лічильники;
- `Config` — конфігурація.

## 14.3. Reset Policy

Необхідно визначити:

- чи очищується TT;
- чи очищуються історичні евристики;
- чи скидається repetition history;
- чи завершується активний пошук;
- чи зберігаються параметри;
- чи скидається статистика.

Найважливіше — не допустити перенесення контексту попередньої партії, який може спотворювати нову.

# 15. PROTOCOL STATE MACHINE

## 15.1. Необхідність

Команди UCI мають різне значення залежно від стану двигуна.

Тому пропонується формальна машина станів.

## 15.2. Engine Protocol States

`EPS = {INITIALIZING, IDLE, READY, SEARCHING, PONDERING, STOPPING, TERMINATED, ERROR}`

Це запропонована внутрішня модель, а не перелік офіційних станів UCI.

### INITIALIZING

Ініціалізація двигуна.

### IDLE

Двигун очікує команду.

### READY

Двигун готовий до виконання наступного завдання.

### SEARCHING

Активний пошук.

### PONDERING

Пошук у режимі прогнозування.

### STOPPING

Процес завершення пошуку.

### TERMINATED

Двигун завершив роботу.

### ERROR

Виявлено помилку, яка потребує контрольованого відновлення або завершення.

## 15.3. State Transition Rules

Приклади:

`INITIALIZING → READY`

Після завершення ініціалізації.

`READY → SEARCHING`

Після коректної команди `go`.

`SEARCHING → STOPPING`

Після команди `stop`.

`STOPPING → READY`

Після завершення активного пошукового завдання.

`READY → TERMINATED`

Після `quit`.

Переходи повинні бути явно визначені.

## 15.4. Illegal Transitions

Необхідно перевірити:

- повторний `go`;
- `position` під час активного пошуку;
- `setoption` під час пошуку;
- `stop` у стані IDLE;
- `ponderhit` без pondering;
- `quit` під час активного пошуку;
- команди після TERMINATED.

Двигун повинен мати передбачувану політику для кожної ситуації.

# 16. ASYNCHRONOUS SEARCH CONTROL

## 16.1. Проблема

У браузерному або асинхронному середовищі пошук може виконуватися паралельно з обробкою зовнішніх команд.

Це створює ризики конкурентного доступу.

## 16.2. Search Task Identity

Пропонується:

`Task = (SearchId, PositionId, ConfigId, Status)`

Кожне завдання повинно мати ідентифікатор.

Результат пошуку повинен бути пов'язаний із:

- позицією;
- конфігурацією;
- обмеженнями;
- поколінням завдання.

## 16.3. Race Conditions

Потрібно перевірити:

1. нова позиція під час активного пошуку;
2. новий `go` до завершення попереднього;
3. stop і новий go;
4. зміна Hash під час пошуку;
5. зміна MultiPV;
6. завершення старого асинхронного завдання після запуску нового;
7. повторна видача bestmove.

## 16.4. Stale Result Protection

Результат може бути прийнятий лише за умови:

`Result.SearchId = ActiveSearchId`

І додатково:

`Result.PositionId = ActivePositionId`

Якщо конфігурація є частиною пошукового контексту:

`Result.ConfigId = ActiveConfigId`

Ці перевірки повинні відбуватися перед публікацією результату.

# 17. ERROR RECOVERY

## 17.1. Категорії помилок

Пропонується розділити:

- INPUT_ERROR;
- PARSE_ERROR;
- POSITION_ERROR;
- MOVE_ERROR;
- SEARCH_ERROR;
- RESOURCE_ERROR;
- PROTOCOL_ERROR;
- INTERNAL_ERROR.

## 17.2. Recovery Policy

Для кожної категорії потрібно визначити:

- чи можна продовжити роботу;
- чи потрібно відхилити команду;
- чи потрібно скинути поточне завдання;
- чи потрібно перебудувати позицію;
- чи потрібно завершити двигун.

## 17.3. Error Isolation

Помилка одного пошукового завдання не повинна автоматично пошкоджувати глобальний стан двигуна.

Особливо важливо відокремити:

- тимчасовий Search State;
- активний Position State;
- глобальну конфігурацію;
- протокольний стан.

## 17.4. Error Logging

Діагностика повинна зберігати:

- тип помилки;
- команду;
- стан протоколу;
- SearchId;
- PositionId;
- час;
- місце виникнення;
- результат відновлення.

У протокольному каналі не повинні з'являтися довільні повідомлення, які порушують очікуваний формат UCI.

# 19. INPUT FUZZING AND ROBUSTNESS

## 19.1. Мета

Протокольний парсер повинен витримувати некоректний і несподіваний ввід.

Це не означає, що він повинен приймати будь-яку команду.

Він повинен безпечно відхиляти те, що не може коректно інтерпретувати.

## 19.2. Fuzzing Categories

- порожні рядки;
- надмірно довгі рядки;
- невідомі команди;
- невідомі параметри;
- повторювані токени;
- відсутні значення;
- некоректні числа;
- від'ємні ліміти;
- дуже великі ліміти;
- некоректний FEN;
- неправильна нотація ходів;
- випадкові комбінації команд.

## 19.3. Robustness Invariants

1. Парсер не повинен зависати.
2. Некоректний ввід не повинен пошкоджувати пам'ять.
3. Не повинно виникати неконтрольованої рекурсії.
4. Не повинно відбуватися часткового застосування некоректної позиції.
5. Не повинно виникати випадкового запуску пошуку.
6. Двигун повинен зберігати можливість коректного відновлення, якщо протокол це допускає.

# 20. SUBIT ENGINE INTERFACE MODEL — SEIM

## 20.1. Архітектурні рівні

Пропонується розділити SEIM на сім рівнів.

### SEIM-L1 — Input Layer

Отримання зовнішніх повідомлень.

### SEIM-L2 — Parsing Layer

Перетворення тексту на структуровані команди.

### SEIM-L3 — Validation Layer

Перевірка синтаксису та семантики.

### SEIM-L4 — Protocol State Layer

Контроль допустимості команд у поточному стані.

### SEIM-L5 — Execution Dispatch Layer

Передавання операцій відповідним модулям.

### SEIM-L6 — Result Management Layer

Контроль результатів, ідентифікаторів та завершення завдань.

### SEIM-L7 — Output Layer

Формування коректних протокольних повідомлень.

## 20.2. SEIM Context Model

Пропонується:

`SEIMContext = (Protocol, Position, Search, Config, Output, History)`

де:

- `Protocol` — стан протоколу;
- `Position` — активний шаховий стан;
- `Search` — активне пошукове завдання;
- `Config` — конфігурація;
- `Output` — стан вихідного каналу;
- `History` — історія команд і переходів.

## 20.3. Context Integrity

Ключова вимога:

**Жоден результат не повинен відриватися від контексту, в якому він був отриманий.**

Це стосується:

- позиції;
- пошукового завдання;
- конфігурації;
- обмежень;
- історії;
- причини завершення.

## 20.4. SEIM and SACM Interaction

SEIM і SACM повинні мати чітке розмежування.

SEIM відповідає за зовнішнє керування.

SACM відповідає за адаптивний розподіл обчислювальних ресурсів.

Їхня взаємодія:

`External Command → SEIM → Search Request → SACM → Search Core`

Результат:

`Search Core → SACM → Search Result → SEIM → UCI Output`

SEIM не повинен самостійно змінювати глибину пошуку, обходячи SACM.

SACM не повинен самостійно генерувати протокольні відповіді.

# 25. АРХІТЕКТУРНІ РИЗИКИ

### RISK A15-R1 — Parser Ambiguity

Різні частини команди можуть інтерпретуватися неоднаково.

### RISK A15-R2 — Partial Position Mutation

Некоректна команда може залишити частково змінену позицію.

### RISK A15-R3 — History Loss

Встановлення позиції може втратити контекст повторень.

### RISK A15-R4 — Search Cancellation Failure

Пошук може продовжуватися після stop.

### RISK A15-R5 — Stale Bestmove

Двигун може повернути результат попереднього пошуку.

### RISK A15-R6 — Output Interleaving

Повідомлення різних пошукових завдань можуть змішуватися.

### RISK A15-R7 — Ponder Context Mismatch

Результат прогнозного пошуку може бути застосований до іншої позиції.

### RISK A15-R8 — Configuration Mutation

Зміна параметрів може пошкодити активний пошуковий стан.

### RISK A15-R9 — Incorrect Score Semantics

Fail-high або fail-low може бути представлений як точна оцінка.

### RISK A15-R10 — State Machine Inconsistency

Двигун може приймати команди, несумісні з поточним станом.

### RISK A15-R11 — Protocol Deadlock

Взаємодія між читанням команд, пошуком і виведенням може спричинити зависання.

### RISK A15-R12 — Resource Exhaustion

Некоректні або надмірні ліміти можуть призвести до виснаження ресурсів.

# 26. ПІДСУМКОВИЙ ВИСНОВОК PHASE A.15

PHASE A.15 визначає зовнішню архітектурну межу SUBIT-CHESS.

Основний висновок:

**Шаховий інтелект не може вважатися надійним, якщо зовнішнє керування не зберігає цілісність його внутрішнього стану.**

SEIM повинен забезпечити:

- однозначний парсинг;
- коректну валідацію;
- атомарне встановлення позицій;
- контроль пошукових завдань;
- безпечне переривання;
- правильне формування bestmove;
- узгоджений інформаційний вихід;
- контроль конфігурації;
- відновлення після помилок;
- захист від застарілих асинхронних результатів.

Важливо також зберегти архітектурне розділення:

- шахове ядро відповідає за правила та аналіз;
- SACM відповідає за адаптивне керування обчисленнями;
- SEIM відповідає за зовнішній протокол і керування завданнями.

Жоден із цих шарів не повинен непомітно підміняти відповідальність іншого.

**Статус PHASE A.15: ARCHITECTURAL AUDIT COMPLETE / SOURCE VALIDATION OPEN.**

Підтверджених дефектів реалізації не встановлено. Вихідний код цільового commit у межах цієї фази повторно не перевірявся. Runtime-тести не виконувалися.
