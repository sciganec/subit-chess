# 1. МЕТА PHASE A.17

Попередні фази сформували концептуальну архітектуру шахового двигуна та визначили вимоги до його ключових компонентів.

Однак наявність специфікацій, алгоритмічних моделей та архітектурних інваріантів сама по собі не доводить правильності реалізації.

Потрібна незалежна система, яка дозволить відповісти на такі питання:

1. Чи відповідає реалізація заявленій специфікації?
2. Чи правильно працюють окремі функції?
3. Чи зберігаються інваріанти під час послідовних операцій?
4. Чи правильно взаємодіють незалежні модулі?
5. Чи витримує двигун граничні та патологічні сценарії?
6. Чи можна відтворити знайдену помилку?
7. Чи можна встановити, яка саме зміна спричинила регресію?
8. Чи не погіршується якість пошуку після оптимізації?
9. Чи не виникають приховані помилки після тривалого виконання?
10. Чи можна незалежно перевірити результати самонавчання та self-play?

PHASE A.17 формує відповідну методологію.

Її центральна теза:

**Якість програмного забезпечення повинна бути не декларативною характеристикою, а системою перевірюваних властивостей.**

# 2. SUBIT VERIFICATION ENGINEERING MODEL

## 2.1. Визначення SVEM

Пропонується:

**SVEM — SUBIT Verification Engineering Model.**

Це концептуальна система верифікації, призначена для незалежної перевірки:

- шахової коректності;
- алгоритмічної коректності;
- структурної цілісності;
- пошукової поведінки;
- ресурсної стабільності;
- протокольної відповідності;
- відтворюваності;
- якості експериментальних результатів.

SVEM не повинен бути частиною механізму прийняття шахових рішень.

Його функція — перевіряти двигун, а не підказувати йому ходи.

## 2.2. Формальна модель

Пропонується:

`SVEM = (S, T, O, I, E, P, R)`

де:

- `S` — специфікації;
- `T` — тестові сценарії;
- `O` — очікувані результати;
- `I` — інваріанти;
- `E` — виконання перевірок;
- `P` — provenance доказів;
- `R` — звіт про результати.

Кожна перевірювана властивість повинна мати:

1. формулювання;
2. область застосування;
3. метод перевірки;
4. критерій проходження;
5. критерій відмови;
6. ідентифікатор;
7. зв'язок із відповідною специфікацією.

## 2.3. Незалежність перевірки

Критично важливо, щоб тестова система не відтворювала ті самі помилки, що й основна реалізація.

Наприклад, якщо генератор ходів містить помилку, а тестовий oracle використовує той самий генератор, перевірка може помилково підтвердити некоректну поведінку.

Тому необхідно розділяти:

**Implementation Under Test (IUT)** — тестована реалізація.

**Verification Oracle (VO)** — незалежний механізм перевірки очікуваної властивості.

**Test Harness (TH)** — середовище виконання тестів.

**Evidence Store (ES)** — сховище результатів та доказів.

# 3. SOFTWARE QUALITY MODEL

## 3.1. Якість як багатовимірна характеристика

Якість шахового двигуна не можна зводити лише до сили гри або швидкості пошуку.

Пропонується модель:

`Q = (C, A, S, P, M, R, V)`

де:

- `C` — Correctness;
- `A` — Architectural Integrity;
- `S` — Stability;
- `P` — Performance;
- `M` — Maintainability;
- `R` — Reproducibility;
- `V` — Verifiability.

### Correctness

Правильність реалізації правил, алгоритмів і результатів.

### Architectural Integrity

Відповідність архітектурним контрактам та межам відповідальності.

### Stability

Стійкість під час тривалого виконання, переривань та граничних навантажень.

### Performance

Швидкість, ефективність пошуку та використання ресурсів.

### Maintainability

Можливість безпечно змінювати та розширювати систему.

### Reproducibility

Можливість повторити експеримент та отримати порівнюваний результат.

### Verifiability

Можливість незалежно перевірити заявлені властивості.

## 3.2. Незалежність вимірів

Необхідно уникати помилкового ототожнення:

- швидкий двигун ≠ коректний двигун;
- сильний двигун ≠ стабільний двигун;
- великий test coverage ≠ доведена правильність;
- відсутність аварій ≠ відсутність логічних помилок;
- однаковий результат ≠ незалежна верифікація;
- проходження тестів ≠ відсутність невиявлених дефектів.

## 3.3. Quality Gates

Пропонується запровадити послідовні контрольні рівні.

**QG-0 — Build Integrity**

Проєкт збирається або завантажується без критичних помилок.

**QG-1 — Static Integrity**

Немає невирішених критичних статичних проблем.

**QG-2 — Unit Correctness**

Базові функції проходять незалежні тести.

**QG-3 — Integration Correctness**

Міжмодульні сценарії проходять перевірку.

**QG-4 — Chess Rule Correctness**

Правила та переходи позицій перевірені.

**QG-5 — Search Integrity**

Пошук зберігає коректність результатів та стану.

**QG-6 — Runtime Stability**

Система витримує тривалі та граничні сценарії.

**QG-7 — Performance Acceptance**

Продуктивність відповідає зафіксованим критеріям.

**QG-8 — Release Verification**

Відповідний commit має повний набір доказів.

Жоден Quality Gate не повинен автоматично вважатися пройденим на підставі проходження попереднього.

# 4. STATIC CODE ANALYSIS

## 4.1. Призначення

Статичний аналіз досліджує програмний код без необхідності повноцінного виконання двигуна.

Його завдання — виявляти потенційні дефекти, структурні проблеми та порушення правил реалізації.

## 4.2. Основні категорії

Необхідно перевіряти:

1. синтаксичні помилки;
2. недосяжний код;
3. невикористані змінні;
4. невикористані функції;
5. неініціалізовані значення;
6. некоректні типи;
7. небезпечні перетворення;
8. потенційні переповнення;
9. неконтрольовані мутації;
10. приховані глобальні залежності;
11. дублювання логіки;
12. надмірну складність;
13. неправильну обробку помилок;
14. неочікувані побічні ефекти;
15. некоректне використання асинхронних операцій.

## 4.3. Особливості JavaScript

Якщо цільова реалізація використовує JavaScript, окремо потрібно дослідити:

- неявні перетворення типів;
- `NaN`;
- `undefined`;
- `null`;
- переповнення беззнакових та знакових представлень;
- побітові оператори;
- точність Number;
- переповнення лічильників;
- змінюваність об'єктів;
- прототипне успадкування;
- затінення змінних;
- замикання;
- асинхронні побічні ефекти.

Особливо важливі побітові операції.

JavaScript використовує 32-бітне представлення для багатьох побітових операцій, навіть якщо початкові значення представлені як Number.

Тому шахові Hash, індекси, маски та кодування станів повинні перевірятися з урахуванням фактичної семантики мови.

## 4.4. Static Analysis Acceptance

Статичний аналіз не повинен просто генерувати список попереджень.

Кожне попередження необхідно класифікувати:

- CONFIRMED DEFECT;
- POTENTIAL DEFECT;
- ACCEPTED DESIGN;
- FALSE POSITIVE;
- NEEDS REVIEW.

# 5. CODE COMPLEXITY ANALYSIS

## 5.1. Мета

Складність коду не є автоматично дефектом.

Однак надмірна складність збільшує ймовірність:

- логічних помилок;
- пропущених умов;
- неправильних граничних переходів;
- труднощів тестування;
- регресій після змін.

## 5.2. Метрики

Пропонується аналізувати:

**Cyclomatic Complexity**

Кількість незалежних шляхів виконання.

**Cognitive Complexity**

Складність розуміння структури функції.

**Nesting Depth**

Глибина вкладеності умов та циклів.

**Function Length**

Кількість рядків або операцій у функції.

**Dependency Count**

Кількість зовнішніх залежностей.

**Branch Density**

Щільність умовних переходів.

**Mutation Surface**

Кількість змінюваних структур, до яких функція має доступ.

## 5.3. Особлива увага

Першочергово перевіряти складні функції:

- move generation;
- legal move filtering;
- make/unmake;
- castling;
- en passant;
- Zobrist hashing;
- TT probe/store;
- negamax;
- alpha-beta;
- PVS;
- LMR;
- null move pruning;
- quiescence search;
- evaluation;
- UCI command processing.

## 5.4. Complexity Risk

Функція з великою кількістю умовних переходів потребує більшого тестового покриття.

Але автоматичне розділення складної функції на менші не завжди покращує якість.

Потрібно зберегти цілісність алгоритмічного контексту.

# 6. DEAD CODE AND UNREACHABLE CODE

## 6.1. Dead Code

Dead Code — код, який не впливає на жоден можливий результат виконання.

Можливі причини:

- застарілі функції;
- невикористані алгоритми;
- залишки попередніх версій;
- дубльовані реалізації;
- відключені експериментальні модулі.

## 6.2. Unreachable Code

Unreachable Code — код, до якого неможливо дійти за наявних умов виконання.

Потенційні причини:

- неправильні умови;
- суперечливі гілки;
- некоректна структура переходів;
- передчасні `return`;
- неправильні стани керування.

## 6.3. Особлива проблема шахового двигуна

Не можна автоматично видаляти код лише тому, що він не активується у звичайних партіях.

Рідкісні ситуації можуть вимагати окремих гілок:

- en passant;
- promotion;
- castling;
- stalemate;
- repetition;
- mate-distance handling;
- zugzwang;
- terminal search states.

## 6.4. Acceptance

Видалення Dead Code допустиме лише після перевірки:

1. чи не використовується функція динамічно;
2. чи не викликається вона через протокол;
3. чи не є вона частиною тестового API;
4. чи не потрібна вона в рідкісному шаховому стані;
5. чи не впливає на побічні ефекти.

# 7. TYPE AND DATA VALIDATION

## 7.1. Типова цілісність

Кожна важлива структура повинна мати чіткі допустимі значення.

Особливо:

- piece type;
- color;
- square;
- move encoding;
- castling rights;
- en passant square;
- depth;
- alpha;
- beta;
- score;
- hash;
- TT flags;
- search status.

## 7.2. Domain Constraints

Недостатньо перевірити, що значення є числом.

Необхідно перевіряти, чи належить воно допустимій області.

Наприклад:

`0 ≤ square < 64`

якщо використовується індексація 0–63.

Для глибини пошуку:

`0 ≤ depth ≤ MAX_DEPTH`

Для меж:

`alpha < beta`

за умови, що саме такий контракт визначено відповідною функцією.

## 7.3. Sentinel Values

Особливо небезпечне використання спеціальних числових значень.

Наприклад:

- `-1` як відсутня клітинка;
- `0` як відсутній хід;
- велике число як Infinity;
- спеціальне значення як невідомий score.

Потрібно перевірити, чи не конфліктують sentinel values із допустимими значеннями.

## 7.4. Numeric Safety

Окремо перевірити:

- NaN propagation;
- Infinity;
- signed/unsigned conversion;
- bitwise truncation;
- integer overflow;
- precision loss;
- mate score normalization.

Некоректне числове значення може непомітно поширитися через весь пошуковий цикл.

# 8. FUNCTION CONTRACT VERIFICATION

## 8.1. Формальна модель

Для кожної критичної функції:

`F: X → Y`

потрібно визначити:

- допустимі X;
- допустимі Y;
- передумови;
- післяумови;
- побічні ефекти;
- інваріанти.

## 8.2. Pure Functions

Функції без побічних ефектів бажано відокремлювати від функцій, які змінюють стан.

Наприклад:

- attack detection;
- score conversion;
- move decoding;
- position feature extraction.

Якщо функція повинна лише читати позицію, її контракт не повинен дозволяти змінювати її.

## 8.3. Stateful Functions

Особливий контроль потрібен для:

- makeMove;
- unmakeMove;
- search;
- TT store;
- history update;
- reset;
- initialization.

## 8.4. Contract Violation

Порушення контракту повинно мати конкретний тест.

Наприклад:

якщо `unmakeMove` повинна відновити початкову позицію, то тест має порівняти не лише дошку, а весь відповідний контекст.

# 9. UNIT TESTING ARCHITECTURE

Unit Testing перевіряє окремі функції або невеликі компоненти ізольовано.

Його головна перевага — точне визначення місця помилки.

## 9.2. Position Core

Необхідні перевірки:

- координати;
- кодування клітинок;
- доступ до фігур;
- представлення кольорів;
- списки фігур;
- ініціалізація;
- копіювання позиції.

## 9.3. Move Generation

Перевірити:

- рухи кожного типу фігур;
- блокування;
- атаки;
- напрямки;
- межі дошки;
- шахові обмеження;
- спеціальні ходи.

## 9.4. Search

Перевірити:

- базові terminal conditions;
- negamax sign inversion;
- alpha-beta bounds;
- mate score;
- depth handling;
- stop conditions;
- score propagation;
- PV construction.

## 9.5. Evaluation

Перевірити:

- матеріальні значення;
- симетрію;
- колірну інверсію;
- phase interpolation;
- оцінювання термінальних станів;
- узгодженість компонентів.

## 9.6. Unit Test Independence

Unit-тест не повинен залежати від усієї системи, якщо його властивість можна перевірити ізольовано.

# 10. INTEGRATION TESTING

## 10.1. Призначення

Integration Testing перевіряє контракти між компонентами.

Для SUBIT-CHESS це особливо важливо, оскільки шахова коректність залежить від послідовної взаємодії багатьох модулів.

## 10.2. Основні інтеграційні ланцюги

**IT-01 — Position → Move Generation**

Генератор отримує актуальний стан.

**IT-02 — Move Generation → Legality**

Псевдолегальні ходи правильно фільтруються.

**IT-03 — Move → Make/Unmake**

Перетворення позиції та відновлення узгоджені.

**IT-04 — Position → Hash**

Hash відповідає фактичній позиції.

**IT-05 — Hash → TT**

TT використовує правильний ключ.

**IT-06 — Search → Evaluation**

Оцінка відповідає поточному вузлу.

**IT-07 — Search → QSearch**

Перехід до Quiescence Search зберігає коректність.

**IT-08 — Search → Time Management**

Зупинка не пошкоджує результат останньої завершеної ітерації.

**IT-09 — Engine → Protocol**

Команди та результати відповідають протокольному контракту.

**IT-10 — Engine → UI**

Відображений стан відповідає актуальному результату.

# 12. REGRESSION TESTING

## 12.1. Призначення

Regression Testing повинно виявляти випадки, коли нова зміна руйнує раніше підтверджену поведінку.

## 12.2. Regression Corpus

Пропонується створити власний корпус тестових позицій.

Він повинен містити:

- початкові позиції;
- тактичні позиції;
- шахи;
- мати;
- пат;
- рокірування;
- en passant;
- promotion;
- repetition;
- складні ендшпілі;
- zugzwang;
- fortress;
- позиції з великою кількістю легальних ходів;
- позиції з малою кількістю легальних ходів.

Усі позиції можуть бути створені внутрішньо за правилами шахів.

Не потрібно використовувати зовнішні партії або PGN як джерело навчальних прикладів.

## 12.3. Regression Record

Кожен тест повинен мати:

`RegressionRecord = (ID, Position, Context, Expected, Actual, Version, Evidence)`

## 12.4. Golden Tests

Golden Tests зберігають раніше підтверджений результат.

Однак важливо не перетворювати їх на безумовний механізм прийняття старої поведінки.

Якщо старий результат був неправильним, тест повинен бути переглянутий із документуванням причини.

---

# 13. PROPERTY-BASED TESTING

## 13.1. Основна ідея

Property-Based Testing перевіряє загальні властивості системи на великій множині автоматично створених вхідних даних.

На відміну від звичайного тесту, який перевіряє один конкретний приклад, property-based тест перевіряє клас станів.

## 13.2. Position Properties

Приклади:

**PBT-01 — Make/Unmake Identity**

`Unmake(Make(P, m), m) = P`

для кожного допустимого ходу `m` у позиції `P`.

Порівняння повинно охоплювати повний відповідний стан, а не лише розташування фігур.

**PBT-02 — Hash Restoration**

Після make/unmake Hash повинен відповідати початковому значенню.

**PBT-03 — Side Alternation**

Після звичайного ходу сторона ходу змінюється.

**PBT-04 — Legal Move Safety**

Легальний хід не повинен залишати власного короля під шахом.

**PBT-05 — Board Bounds**

Жодна фігура не повинна потрапляти за межі представлення дошки.

## 13.3. Search Properties

- завершений пошук повертає допустимий результат;
- перерваний пошук не видає непідтверджений результат за завершений;
- повторний пошук без зміни контексту зберігає визначені гарантії;
- зміна позиції не повинна використовувати старий Search State.

## 13.4. Generator Design

Генератор тестових позицій повинен:

1. починати з коректного стану;
2. виконувати лише допустимі перетворення;
3. зберігати історію;
4. підтримувати відтворення;
5. реєструвати seed;
6. вміти зменшувати знайдений приклад до мінімального контрприкладу.

# 14. DIFFERENTIAL TESTING

## 14.1. Призначення

Differential Testing порівнює результати двох незалежних реалізацій однієї властивості.

Для SUBIT-CHESS найважливіше — незалежна перевірка правил та переходів позицій.

## 14.2. Незалежний Chess Oracle

Можна створити власний мінімальний перевірочний модуль, який реалізує правила незалежно від основного двигуна.

Наприклад:

- повільніший генератор атак;
- незалежна перевірка легальності;
- окреме представлення дошки;
- незалежний розрахунок Hash;
- незалежна перевірка термінальних станів.

Він не повинен використовувати внутрішні функції тестованого модуля.

## 14.3. Важливе обмеження

Необхідно розрізняти:

**Differential Correctness Testing**

Порівняння двох незалежних реалізацій правил.

**Playing Strength Comparison**

Порівняння сили гри двох шахових двигунів.

Перше може використовуватися для перевірки SUBIT-CHESS.

Друге не повинно перетворювати зовнішній двигун на компонент, джерело знань або вчителя SUBIT-CHESS.

У межах автономної архітектури SUBIT-CHESS не повинен отримувати зовнішні шахові рішення для навчання.

## 14.4. Differential Testing Limits

Дві реалізації можуть містити однакову концептуальну помилку.

Тому differential testing необхідно доповнювати:

- формальними правилами;
- відомими шаховими інваріантами;
- ручними граничними сценаріями;
- metamorphic testing;
- незалежними перевірками.

---

# 15. METAMORPHIC TESTING

## 15.1. Основна ідея

Metamorphic Testing перевіряє, як повинен змінюватися результат після контрольованого перетворення вхідних даних.

Це особливо корисно там, де немає простого еталонного результату.

## 15.2. Шахова симетрія

Наприклад, вертикальне відображення дошки разом із заміною кольорів повинно зберігати відповідні шахові властивості.

Якщо:

`T(P)` — симетрично перетворена позиція,

то множини легальних ходів повинні відповідати одна одній після застосування того самого перетворення до координат.

## 15.3. Evaluation Symmetry

Для оцінки з погляду сторони, яка ходить:

`Eval(T(P)) ≈ Eval(P)`

якщо T змінює кольори та координати відповідно до визначеної симетрії.

Точна рівність може залежати від:

- округлення;
- позиційних таблиць;
- асиметричних евристик;
- історичних параметрів.

Будь-яке відхилення потрібно класифікувати.

## 15.4. Move Ordering Invariance

Зміна порядку перебору ходів не повинна змінювати математично правильне значення повного minimax-пошуку за однакової глибини та однакової моделі оцінювання.

Однак у реальному двигуні з обмеженим часом, selective search і різними евристиками результат може змінюватися.

Це не можна автоматично трактувати як помилку.

## 15.5. Metamorphic Properties

Пропонується перевірити:

- симетрію кольорів;
- дзеркальну відповідність;
- еквівалентність незалежних представлень;
- make/unmake;
- повторне завантаження тієї самої позиції;
- стабільність оцінки;
- відповідність легальних ходів після трансформації.

---

# 16. FUZZ TESTING

## 16.1. Призначення

Fuzz Testing генерує велику кількість різноманітних входів для пошуку аварій, порушень інваріантів та неочікуваної поведінки.

## 16.2. Категорії

**Valid Fuzzing**

Автоматичне створення коректних шахових позицій.

**Invalid Fuzzing**

Некоректні FEN, ходи, команди та конфігурації.

**State Transition Fuzzing**

Випадкові послідовності допустимих ходів.

**Protocol Fuzzing**

Некоректні та граничні протокольні повідомлення.

**Resource Fuzzing**

Граничні значення глибини, часу, пам'яті та кількості вузлів.

## 16.3. FEN Fuzzing

Перевірити:

- відсутні поля;
- зайві поля;
- некоректні символи;
- неправильну кількість клітинок;
- недопустимі значення;
- некоректні права рокірування;
- некоректні en passant;
- граничні лічильники;
- надмірну кількість фігур;
- суперечливі стани.

## 16.4. Move Fuzzing

Перевірити:

- клітинки поза дошкою;
- однакові початкову та кінцеву клітинки;
- неправильні типи фігур;
- некоректні promotion;
- неіснуючі ходи;
- спроби зробити хід із порожньої клітинки;
- спроби змінити стан після terminal state.

## 16.5. Fuzz Reproducibility

Кожен знайдений дефект повинен зберігати:

- seed;
- початковий стан;
- послідовність операцій;
- версію;
- параметри;
- очікуваний результат;
- фактичний результат.

# 17. BOUNDARY TESTING

## 17.1. Чому це важливо

Більшість складних помилок проявляється на межах допустимих значень.

Для шахового двигуна межі існують на кількох рівнях.

## 17.2. Board Boundaries

Перевірити:

- a1;
- h1;
- a8;
- h8;
- крайні файли;
- крайні ранги;
- рухи біля меж;
- діагоналі біля меж.

## 17.3. Search Boundaries

Перевірити:

- depth = 0;
- depth = 1;
- мінімальну допустиму глибину;
- максимальну допустиму глибину;
- alpha = beta;
- граничні alpha/beta;
- негайне переривання;
- переривання під час пошуку;
- відсутність легальних ходів.

## 17.4. Numeric Boundaries

Перевірити:

- мінімальні та максимальні score;
- mate scores;
- Infinity;
- NaN;
- великі Hash;
- граничні індекси;
- переповнення лічильників.

## 17.5. Resource Boundaries

Перевірити:

- нульовий бюджет вузлів;
- мінімальний часовий бюджет;
- максимальний бюджет;
- порожню TT;
- мінімальний розмір TT;
- максимальне допустиме навантаження.

# 18. STATE INVARIANT TESTING

## 18.1. Призначення

Цей рівень перевіряє властивості, які повинні залишатися істинними протягом усього життєвого циклу двигуна.

## 18.2. Position Invariants

- кожна фігура має допустиме представлення;
- клітинка не може містити дві фігури;
- списки фігур відповідають дошці;
- king count відповідає контракту позиції;
- Hash відповідає позиції;
- side-to-move допустимий.

## 18.3. Move Invariants

- кожен згенерований легальний хід відповідає правилам;
- кожен виконаний хід може бути відновлений;
- спеціальні ходи правильно змінюють відповідний стан;
- незаконний хід не повинен непомітно змінювати позицію.

## 18.4. Search Invariants

- Search Stack не виходить за межі;
- рекурсивний стан відновлюється;
- PV містить допустимі ходи;
- переривання не залишає пошкоджений стан;
- завершені та незавершені результати розрізняються.

## 18.5. System Invariants

Після кожного пошукового завдання повинні перевірятися:

`SystemInvariant(P, H, S, T, R)`

де:

- P — Position;
- H — Hash;
- S — Search State;
- T — TT;
- R — Resource State.

# 19. SEARCH CORRECTNESS TESTING

## 19.1. Особлива складність

Пошукові алгоритми важко тестувати, оскільки їхня поведінка залежить від:

- дерева ходів;
- порядку перебору;
- глибини;
- pruning;
- extensions;
- reductions;
- TT;
- оцінювання;
- часових обмежень.

## 19.2. Search Test Modes

Пропонується розділити перевірки на режими.

**MODE A — Full Minimax**

Без selective pruning на малих контрольованих деревах.

**MODE B — Alpha-Beta**

Перевірка еквівалентності minimax-значень.

**MODE C — PVS**

Перевірка правильності null-window search та re-search.

**MODE D — TT Enabled**

Порівняння результатів із пошуком без TT за однакових умов, де це математично обґрунтовано.

**MODE E — Selective Search**

Перевірка евристик та допустимих відхилень.

**MODE F — Interrupted Search**

Перевірка безпечного завершення.

**MODE G — Quiescence**

Перевірка тактичної стабілізації.

## 19.3. Exact vs Approximate Results

Необхідно розділяти:

- exact minimax result;
- alpha-beta bound;
- selective search estimate;
- incomplete iteration;
- interrupted search result;
- heuristic evaluation.

Ці результати не повинні мати однаковий статус.

## 19.4. Search Oracle

Для малих штучно створених шахових дерев можна реалізувати незалежний повний minimax oracle.

Його завдання — перевіряти базові пошукові алгоритми на контрольованих деревах.

Це не є зовнішнім шаховим двигуном і не порушує автономності SUBIT-CHESS.

# 20. PROTOCOL TESTING

## 20.1. Мета

Протокольна коректність повинна перевірятися незалежно від шахового інтелекту.

## 20.2. UCI Scenarios

# 21. PERFORMANCE REGRESSION TESTING

## 21.1. Основна проблема

Після оптимізації код може стати швидшим на одному сценарії, але повільнішим на іншому.

Тому потрібна окрема система performance regression.

## 21.2. Метрики

- Nodes Per Second;
- Total Nodes;
- Search Time;
- Completed Depth;
- Effective Branching Factor;
- TT Hit Rate;
- TT Cutoff Rate;
- QNodes;
- Evaluation Calls;
- Move Generation Calls;
- Memory Usage;
- Search Completion Rate.

## 21.3. Performance Corpus

Потрібно створити власний контрольований набір позицій:

- opening;
- middlegame;
- tactical;
- quiet positional;
- king attack;
- endgame;
- zugzwang;
- promotion race;
- high branching;
- low branching.

## 21.4. Controlled Benchmarking

Порівняння повинно проводитися за однакових:

- позицій;
- апаратних умов;
- конфігурацій;
- часових бюджетів;
- лімітів вузлів;
- параметрів TT;
- версій середовища.

## 21.5. Performance vs Correctness

Зростання NPS не є доказом покращення шахової сили.

Зменшення кількості вузлів не є автоматично покращенням пошуку.

Прискорення може бути наслідком надмірного pruning.

Тому performance regression потрібно аналізувати разом із correctness regression.

# 23. DETERMINISTIC TESTING

## 23.1. Призначення

Відтворюваність є необхідною умовою якісного аудиту.

Без неї складно визначити, чи спричинена зміна поведінки:

- зміною коду;
- випадковістю;
- іншим порядком виконання;
- різним seed;
- різними ресурсними умовами.

## 23.2. Deterministic Search

Для контрольованого тестового режиму необхідно фіксувати:

- позицію;
- конфігурацію;
- seed;
- глибину;
- node limit;
- TT state;
- порядок ініціалізації;
- версію коду.

## 23.3. Determinism Levels

**D0 — Input Determinism**

Однакові вхідні дані.

**D1 — Configuration Determinism**

Однакові параметри.

**D2 — Search Determinism**

Однакова послідовність пошукових рішень за контрольованого виконання.

**D3 — Result Determinism**

Однаковий кінцевий результат.

**D4 — Trace Determinism**

Однаковий або еквівалентний журнал виконання.

## 23.4. Nondeterminism

Якщо система використовує паралельне виконання або випадкові евристики, потрібно явно документувати джерела недетермінованості.

Не слід заявляти повну детермінованість, якщо фактичне середовище її не гарантує.

# 24. TEST COVERAGE

## 24.1. Обмеження Coverage

Високий відсоток покриття коду не доводить правильність.

Функція може бути виконана тестом, але її результат не перевірений.

Тому необхідно розрізняти:

- Line Coverage;
- Function Coverage;
- Branch Coverage;
- Condition Coverage;
- Path Coverage;
- State Coverage;
- Requirement Coverage;
- Invariant Coverage.

## 24.2. Requirement Traceability

Кожна вимога повинна мати зв'язок із тестами.

Пропонується:

`Requirement → Implementation → Test → Result → Evidence`

Це дозволить виявляти вимоги, які:

- не реалізовані;
- не тестуються;
- тестуються частково;
- мають невизначений статус.

- special moves;
- terminal conditions;
- abort paths;
- error paths;
- TT replacement;
- null move;
- pruning boundaries;
- repetition;
- draw rules;
- promotion.

# 25. VERIFICATION PROVENANCE

## 25.1. Призначення

Кожен результат тестування повинен мати доказове походження.

Пропонується:

`VerificationRecord = (TestId, Commit, Environment, Input, Expected, Actual, Status, Evidence)`

## 25.2. Evidence Classes

**E0 — NOT CHECKED**

Перевірка не виконувалася.

**E1 — STATIC REVIEW**

Виконано аналіз коду.

**E2 — UNIT TEST**

Функція перевірена ізольовано.

**E3 — INTEGRATION TEST**

Перевірено взаємодію модулів.

**E4 — SYSTEM TEST**

Перевірено повний сценарій.

**E5 — REPRODUCIBLE EXPERIMENT**

Результат повторений у контрольованих умовах.

**E6 — FORMAL PROOF**

Властивість доведена формально в межах конкретної моделі та припущень.

Ці класи не є універсальною лінійною шкалою істинності.

Наприклад, формальний доказ окремої функції не доводить правильність усієї системи.

## 25.3. Evidence Integrity

Для кожного доказу необхідно зберігати:

- commit hash;
- тестову версію;
- середовище;
- конфігурацію;
- дату;
- результат;
- лог;
- seed;
- ідентифікатор тесту.

# 26. AUTONOMOUS VERIFICATION POLICY

Цей розділ принципово важливий для автономної концепції SUBIT-CHESS.

## 26.1. Незалежність шахового інтелекту

Тестова інфраструктура може використовувати незалежні перевірочні реалізації правил.

Однак вона не повинна передавати основному двигуну готові шахові рішення як навчальні цілі.

## 26.2. Дозволені методи

- формальні шахові правила;
- незалежна реалізація перевірки легальності;
- власні тестові позиції;
- контрольовані шахові дерева;
- property-based генерація;
- metamorphic testing;
- self-play;
- внутрішньо створені регресійні сценарії;
- перевірка інваріантів;
- аналіз відтворюваності.

## 26.3. Недопустиме змішування

Необхідно розділяти:

**Verification Knowledge**

Знання про правила, інваріанти та очікувані властивості.

**Playing Knowledge**

Внутрішні оцінки, стратегії та рішення двигуна.

Тестова система може перевіряти, чи відповідає хід правилам.

Але вона не повинна автоматично підміняти власну оцінку SUBIT-CHESS оцінкою стороннього двигуна.

## 26.4. Self-Play Validation

Самостійно створені партії можуть використовуватися для дослідження поведінки двигуна.

Проте self-play не є незалежним доказом сили.

Якщо одна й та сама систематична помилка присутня в обох сторонах, результати можуть виглядати переконливо, залишаючись некоректними.

Тому self-play необхідно поєднувати з незалежними тестами правил, інваріантів та пошукової коректності.

# 33. ФІНАЛЬНИЙ ВИСНОВОК PHASE A.17

PHASE A.17 формує основу незалежної системи перевірки SUBIT-CHESS.

Головний результат — визначення переходу від програмної реалізації до системи доказів її властивостей.

Тепер кожна важлива характеристика повинна мати три складові:

**1. Specification**

Що саме повинно бути правильним?

**2. Verification Method**

Як саме це перевіряється?

**3. Evidence**

Який відтворюваний результат підтверджує проходження перевірки?

Це дозволяє відокремити:

- заявлену функціональність;
- фактично реалізовану функціональність;
- перевірену функціональність;
- формально доведену функціональність.

Особливо важливо, що SVEM не повинен ставати зовнішнім шаховим інтелектом для SUBIT-CHESS.

Його роль — забезпечувати незалежну перевірку правил, інваріантів, структурної цілісності та результатів експериментів.

**Статус PHASE A.17: VERIFICATION ARCHITECTURE PROPOSED / SOURCE VALIDATION OPEN.**

Підтверджених дефектів реалізації не встановлено. Цільовий commit повторно не перевірявся. Статичний аналіз та runtime-тести не виконувалися. Усі наведені тестові ідентифікатори є специфікацією майбутньої перевірки, а не звітом про вже пройдені тести.
