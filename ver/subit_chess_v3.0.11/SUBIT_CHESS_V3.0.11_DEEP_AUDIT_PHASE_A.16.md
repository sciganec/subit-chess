# 2. SUBIT SYSTEM INTEGRITY MODEL

## 2.1. Архітектурне визначення

Пропонується:

**SSIM — SUBIT System Integrity Model.**

SSIM — архітектурна модель, призначена для контролю структурної та операційної цілісності всього двигуна.

Вона охоплює:

1. модульну структуру;
2. межі відповідальності;
3. залежності;
4. володіння даними;
5. життєвий цикл компонентів;
6. синхронізацію стану;
7. поширення помилок;
8. використання ресурсів;
9. взаємодію із зовнішнім середовищем;
10. збереження інваріантів.

## 2.2. Формальна модель

Нехай:

`ENGINE = (M, D, S, C, R, L)`

де:

- `M` — множина модулів;
- `D` — множина залежностей;
- `S` — множина станів;
- `C` — контракти взаємодії;
- `R` — ресурси;
- `L` — життєві цикли.

Тоді:

`SSIM(ENGINE) = (I, O, V, P)`

де:

- `I` — системні інваріанти;
- `O` — модель володіння станом;
- `V` — механізми верифікації;
- `P` — походження та простежуваність даних.

## 2.3. Основна вимога

Кожен модуль повинен мати:

- визначену відповідальність;
- визначений вхід;
- визначений вихід;
- визначені залежності;
- власні інваріанти;
- правила доступу до стану;
- визначений життєвий цикл;
- передбачувану поведінку при помилках.

Модуль без чіткої межі відповідальності створює ризик прихованого зв'язування компонентів.

# 3. GLOBAL ENGINE ARCHITECTURE

## 3.1. Принцип багаторівневої архітектури

Пропонується розглядати SUBIT-CHESS як систему з такими логічними рівнями:

**L0 — Chess Domain**

Правила шахів, геометрія дошки, фігури, ходи, термінальні стани.

**L1 — Position Core**

Представлення позиції, історія, легальні ходи, make/unmake.

**L2 — Search Core**

Negamax, Alpha-Beta, PVS, iterative deepening, Quiescence Search.

**L3 — Evaluation Intelligence**

Матеріал, позиційні характеристики, королівська безпека, стратегічні та ендшпільні оцінки.

**L4 — Search Intelligence**

Move Ordering, Selective Search, Adaptive Depth, SACM.

**L5 — State and Memory Infrastructure**

Hashing, TT, історичні евристики, кешування.

**L6 — Engine Control**

UCI, SEIM, управління пошуковими завданнями.

**L7 — Application Interface**

UI, налаштування, візуалізація, користувацька взаємодія.

Це логічна модель для аудиту, а не твердження про фактичну структуру файлів v3.0.11.

## 3.2. Архітектурна ізоляція

Рівень не повинен безконтрольно залежати від усіх інших рівнів.

Наприклад:

- Position Core не повинен залежати від UI;
- Evaluation не повинна самостійно змінювати Position;
- Search не повинен керувати DOM;
- UCI не повинен реалізовувати шахові правила;
- UI не повинен безпосередньо змінювати внутрішній Search State;
- TT не повинна самостійно визначати легальність ходу.

## 3.3. Dependency Direction

Пропонується правило:

**Залежності повинні спрямовуватися до стабільніших доменних абстракцій, а не до зовнішніх інтерфейсів.**

Наприклад:

`UI → Engine API → Search → Position`

а не:

`Position → UI → Search`

Це дозволяє зберігати незалежність шахового ядра.

# 4. MODULE DEPENDENCY GRAPH

## 4.1. Модель залежностей

Архітектуру необхідно представляти як орієнтований граф:

`G = (V, E)`

де:

- `V` — модулі;
- `E` — залежності між модулями.

Ребро:

`A → B`

означає, що модуль A залежить від функціональності B.

## 4.2. Dependency Classification

Необхідно розрізняти:

**Direct Dependency**

Безпосереднє використання іншого модуля.

**Indirect Dependency**

Залежність через проміжні модулі.

**Runtime Dependency**

Залежність, яка виникає під час виконання.

**Initialization Dependency**

Залежність, необхідна під час ініціалізації.

**State Dependency**

Залежність від даних, які змінюються іншим модулем.

**Protocol Dependency**

Залежність від зовнішнього контракту взаємодії.

## 4.3. Circular Dependencies

Циклічна залежність:

`A → B → C → A`

створює потенційні проблеми:

- складний порядок ініціалізації;
- приховане взаємне володіння;
- важке тестування;
- непередбачувані побічні ефекти;
- складність ізоляції помилок.

Циклічні залежності не завжди автоматично означають дефект, але кожна така структура потребує обґрунтування.

## 4.4. Dependency Audit

Для кожної залежності потрібно встановити:

1. хто є споживачем;
2. хто є постачальником;
3. який контракт використовується;
4. чи є залежність необхідною;
5. чи є вона односторонньою;
6. чи передає вона змінюваний стан;
7. чи створює циклічність;
8. чи може бути замінена стабільною абстракцією.

# 5. STATE OWNERSHIP MODEL

Це один із найважливіших напрямів A.16.

## 5.1. Проблема володіння станом

У складному двигуні одна й та сама інформація може використовуватися багатьма модулями.

Наприклад:

- дошка використовується генератором ходів;
- пошук використовує дошку;
- оцінювання читає дошку;
- Hash залежить від дошки;
- TT використовує Hash;
- UI відображає дошку.

Але це не означає, що всі ці компоненти повинні мати право змінювати один і той самий стан.

## 5.2. Ownership Principle

Для кожної змінюваної структури потрібно визначити єдиного відповідального власника.

Інші модулі можуть отримувати:

- read-only доступ;
- контрольовану копію;
- незмінний snapshot;
- доступ через визначений API.

Пропонується принцип:

**ONE STATE — ONE OWNER — EXPLICIT ACCESS.**

## 5.3. State Ownership Registry

Необхідно визначити власника для:

- Board State;
- Position History;
- Search Stack;
- Evaluation Context;
- Transposition Table;
- Search Heuristics;
- Engine Configuration;
- Protocol State;
- UI State;
- Resource State.

## 5.4. Mutable State Risk

Найнебезпечніша ситуація — коли модуль змінює дані, які інший модуль вважає незмінними.

Наприклад:

1. Search отримує позицію.
2. Evaluation читає її.
3. UI змінює активну дошку.
4. Search продовжує роботу зі зміненими даними.

Це створює порушення контекстної цілісності.

Необхідно забезпечити ізоляцію активного пошукового стану від зовнішніх змін.

# 6. POSITION STATE ISOLATION

## 6.1. Position Snapshot

Пропонується створювати контрольований snapshot позиції для кожного пошукового завдання.

`PositionSnapshot = (Board, Side, Rights, EP, Counters, HistoryContext)`

Snapshot повинен залишатися незмінним з погляду зовнішніх модулів протягом відповідного пошукового завдання.

Внутрішній пошук може створювати робочі копії або змінювати власний Search Position через make/unmake.

## 6.2. Position Identity

Необхідно розрізняти:

- Position Identity;
- Position Hash;
- Search Position;
- Position Snapshot;
- Position History.

Ці поняття не повинні використовуватися як взаємозамінні.

## 6.3. Position Mutation Rules

Зміна позиції повинна відбуватися лише через визначені операції.

Наприклад:

- makeMove;
- unmakeMove;
- loadPosition;
- resetPosition;
- validatePosition.

Пряме неузгоджене редагування окремих полів повинно бути виключене або суворо контрольоване.

## 6.4. Position Consistency Invariant

Після кожної зміни позиції повинні залишатися узгодженими:

- дошка;
- списки фігур;
- сторона ходу;
- права рокірування;
- en passant;
- лічильники;
- Hash;
- матеріальний баланс;
- історичний контекст.

# 7. SEARCH STATE ISOLATION

## 7.1. Search State

Пошуковий стан містить тимчасову інформацію, яка не повинна автоматично переноситися між незалежними пошуковими завданнями.

Пропонується:

`SearchState = (Position, Stack, Alpha, Beta, Depth, PV, Counters, Control)`

## 7.2. Search Ownership

Search Core повинен володіти:

- рекурсивним стеком;
- поточними межами пошуку;
- локальними кандидатами;
- станом переривання;
- поточними ітераціями;
- локальними результатами.

SACM може визначати параметри пошуку, але не повинен безконтрольно змінювати внутрішні структури Search Core.

## 7.3. Search State Leakage

Можливі ризики:

- перенесення alpha/beta між непов'язаними завданнями;
- збереження старої PV;
- використання старого stop flag;
- перенесення лічильників;
- використання застарілих обмежень;
- неправильне відновлення після переривання.

## 7.4. Search Isolation Invariant

Кожен SearchId повинен мати ізольований контекст виконання.

Завершення або скасування одного завдання не повинно пошкоджувати інше.

# 8. EVALUATION STATE ISOLATION

## 8.1. Evaluation Context

Оцінювання може використовувати дані, які залежать від поточної позиції:

- матеріал;
- фігурна активність;
- пішакова структура;
- королівська безпека;
- фаза партії;
- позиційні характеристики;
- історичні або контекстні ознаки.

Необхідно визначити, які дані обчислюються безпосередньо, а які кешуються.

## 8.2. Evaluation Cache

Якщо оцінка кешується, потрібно визначити:

- ключ;
- залежності;
- умови інвалідації;
- життєвий цикл;
- сумісність із поточною позицією.

## 8.3. Evaluation Consistency

Оцінка не повинна використовувати дані попередньої позиції.

Особливо важливо перевірити кешовані:

- матеріальні значення;
- фазу;
- mobility;
- pawn structure;
- king safety;
- positional terms.

## 8.4. Evaluation Provenance

Для діагностики необхідно мати можливість визначити, які компоненти сформували остаточну оцінку.

Пропонується:

`EvalProvenance = (Material, PST, Mobility, Pawns, King, Structure, Endgame, Other)`

Це не вимагає обов'язкового виведення всіх компонентів у GUI.

Йдеться про внутрішню простежуваність.

# 9. TRANSPOSITION TABLE OWNERSHIP

## 9.1. Власність TT

TT є спільною інфраструктурою пошуку, але це не означає, що будь-який модуль може змінювати її записи.

Необхідно визначити:

- власника;
- API читання;
- API запису;
- політику очищення;
- правила заміни;
- правила generation;
- правила інвалідації.

## 9.2. TT and Search Isolation

TT може містити результати попередніх пошуків.

Це допустимо, але контекст запису повинен бути сумісним із поточним використанням.

Необхідно розрізняти:

- position hash;
- search depth;
- score;
- bound;
- best move;
- generation;
- draw context.

## 9.3. Shared TT Risks

Особливі ризики:

- частково записані entries;
- конкурентне читання і запис;
- неправильна заміна;
- застарілі записи;
- некоректна оцінка mate distance;
- повторне використання несумісного історичного контексту.

## 9.4. TT Ownership Invariant

Тільки визначений TT API повинен змінювати записи.

Інші модулі повинні працювати через контрольовані операції.

# 10. SHARED MUTABLE STATE

## 10.1. Визначення

Shared Mutable State — дані, які можуть змінюватися одним компонентом і читатися або змінюватися іншим.

Це одна з головних причин складних міжмодульних помилок.

## 10.2. Потенційні Shared Structures

Необхідно перевірити:

- глобальні лічильники;
- поточну дошку;
- Hash;
- TT;
- History Heuristics;
- Killer Moves;
- Search Control Flags;
- Configuration;
- UI State;
- Protocol Buffers або повідомлення.

## 10.3. Контроль доступу

Пропонується класифікувати кожну структуру:

- IMMUTABLE;
- SINGLE_OWNER_MUTABLE;
- SHARED_READ_ONLY;
- SHARED_SYNCHRONIZED;
- TASK_LOCAL;
- DERIVED_CACHE.

Класифікація повинна бути явною.

## 10.4. Immutable Snapshot Strategy

Для зовнішніх модулів доцільно використовувати незмінні представлення.

Це дозволяє уникати ситуацій, коли зовнішній компонент змінює внутрішній стан без відома його власника.

# 11. MODULE CONTRACTS

## 11.1. Контракт модуля

Кожен модуль повинен мати контракт:

`Contract = (Preconditions, Operations, Postconditions, Invariants, Errors)`

де:

- Preconditions — передумови;
- Operations — доступні операції;
- Postconditions — очікувані результати;
- Invariants — властивості, які зберігаються;
- Errors — визначені помилки.

## 11.2. Приклад: Position Core

Передумови:

- коректно ініціалізована позиція;
- допустимий формат ходу.

Операція:

- застосування ходу.

Післяумови:

- нова позиція сформована;
- історія оновлена;
- Hash узгоджений.

Інваріанти:

- не порушено структуру дошки;
- сторона ходу відповідає правилам;
- make/unmake взаємно узгоджені.

## 11.3. Приклад: Search Core

Передумови:

- валідна позиція;
- коректні межі пошуку;
- доступний контроль виконання.

Операція:

- пошук найкращого ходу.

Післяумови:

- результат пов'язаний із початковим контекстом;
- пошуковий стан відновлений;
- статус завершення визначений.

## 11.4. Contract Violation

Порушення контракту повинно бути виявлене якомога ближче до місця виникнення.

Не слід дозволяти помилці поширюватися через кілька рівнів, перш ніж вона стане помітною.

# 12. INVARIANT PRESERVATION

## 12.1. Системні інваріанти

Пропонується визначити набір глобальних властивостей.

**INV-01 — Board Integrity**

Дошка має узгоджене представлення.

**INV-02 — Legal State Integrity**

Позиція відповідає встановленим правилам представлення.

**INV-03 — Hash Consistency**

Hash відповідає поточному стану.

**INV-04 — History Consistency**

Історія відповідає послідовності виконаних ходів.

**INV-05 — Search Restoration**

Після пошуку робочий стан відновлений.

**INV-06 — Evaluation Isolation**

Оцінювання не використовує застарілі позиційні дані.

**INV-07 — TT Integrity**

Записи TT мають коректний формат і походження.

**INV-08 — Search Task Isolation**

Результати різних завдань не змішуються.

**INV-09 — Protocol Consistency**

Зовнішній стан відповідає внутрішньому стану керування.

**INV-10 — Resource Safety**

Ресурси звільняються або повторно використовуються контрольовано.

## 12.2. Local vs Global Invariants

Потрібно розрізняти:

- локальні інваріанти модуля;
- міжмодульні інваріанти;
- системні інваріанти.

Локальна правильність не гарантує системної правильності.

# 13. INITIALIZATION ORDER

## 13.1. Проблема

Порядок ініціалізації може впливати на поведінку системи.

Наприклад:

- конфігурація ще не створена;
- TT ще не виділена;
- пошукові структури вже використовуються;
- UI звертається до неініціалізованого Engine API;
- протокол приймає команди до готовності ядра.

## 13.2. Initialization Graph

Пропонується формувати граф:

`InitGraph = (Modules, Dependencies, Order)`

Для кожного модуля необхідно визначити:

- prerequisites;
- initialization operation;
- success state;
- failure state;
- cleanup operation.

## 13.3. Initialization Safety

Система не повинна приймати пошукові команди до завершення обов'язкової ініціалізації.

Часткова ініціалізація повинна мати контрольований стан помилки.

## 13.4. Reinitialization

Окремо потрібно перевірити повторну ініціалізацію:

- після нової партії;
- після зміни Hash;
- після помилки;
- після зміни конфігурації;
- після завершення пошукового завдання.

# 14. MODULE LIFECYCLE

## 14.1. Життєвий цикл

Для кожного модуля пропонується визначити:

`Lifecycle = (Created, Initialized, Active, Suspended, Reset, Destroyed)`

Не всі модулі повинні використовувати всі стани.

## 14.2. Lifecycle Consistency

Необхідно перевірити:

- повторну ініціалізацію;
- очищення ресурсів;
- зупинку активних операцій;
- звільнення пам'яті;
- збереження необхідної конфігурації;
- неможливість використання знищеного об'єкта.

## 14.3. Reset vs Recreate

Важливо розрізняти:

- reset state;
- clear cache;
- recreate component;
- full engine restart.

Це різні операції.

Наприклад, очищення TT не повинно автоматично означати скидання всього шахового стану.

# 16. ERROR PROPAGATION

## 16.1. Проблема

Помилки можуть виникати на будь-якому рівні.

Якщо механізм поширення помилок не визначений, система може:

- приховувати критичні помилки;
- продовжувати роботу з пошкодженими даними;
- багаторазово обробляти одну помилку;
- втрачати причину початкового збою;
- залишати ресурси незвільненими.

## 16.2. Error Propagation Model

Пропонується:

`Error = (Origin, Type, Severity, Context, Recovery)`

## 16.3. Error Severity

- INFO — інформаційна подія;
- WARNING — відхилення без негайної втрати коректності;
- RECOVERABLE — помилка, після якої можливе відновлення;
- CRITICAL — порушення важливого інваріанта;
- FATAL — безпечне продовження неможливе.

## 16.4. Recovery Boundaries

Необхідно визначити межі відновлення:

- команда;
- пошукове завдання;
- позиція;
- партія;
- конфігурація;
- весь двигун.

Помилка локальної команди не повинна автоматично завершувати весь двигун.

Водночас критичне пошкодження внутрішнього стану не можна маскувати звичайним повідомленням про помилку вводу.

# 17. MEMORY OWNERSHIP AND RESOURCE LIFECYCLE

## 17.1. Пам'ять

SUBIT-CHESS повинен мати зрозумілу модель використання пам'яті.

Особливо важливі:

- TT;
- Search Stack;
- Move Buffers;
- Position History;
- Evaluation Cache;
- UI Structures;
- протокольні буфери.

## 17.2. Memory Ownership

Для кожної структури потрібно визначити:

- хто виділяє пам'ять;
- хто нею володіє;
- хто може змінювати;
- хто очищує;
- хто звільняє;
- як контролюється повторне використання.

## 17.3. Memory Risks

- подвійне звільнення;
- витік пам'яті;
- повторне використання застарілих буферів;
- переповнення;
- неузгоджені розміри;
- необмежене зростання історії;
- надмірне виділення пам'яті під TT;
- накопичення завершених пошукових завдань.

## 17.4. Browser Runtime Considerations

Якщо двигун працює в браузері, необхідно окремо перевірити:

- обмеження пам'яті;
- поведінку Garbage Collector;
- затримки головного потоку;
- великі масиви;
- передачу даних між Worker;
- копіювання буферів;
- припинення Worker;
- звільнення тимчасових об'єктів.

Ці ризики є умовними до підтвердження фактичної архітектури виконання.

# 18. BROWSER RUNTIME ARCHITECTURE

## 18.1. Принцип розділення

Якщо SUBIT-CHESS використовує браузерний інтерфейс, шахове ядро та UI повинні мати чіткі межі.

UI відповідає за:

- відображення;
- введення;
- взаємодію;
- візуалізацію;
- керування параметрами.

Engine відповідає за:

- позицію;
- генерацію ходів;
- пошук;
- оцінювання;
- результати.

## 18.2. Main Thread Blocking

Тривалий синхронний пошук у головному потоці браузера може блокувати:

- анімацію;
- взаємодію;
- оновлення інтерфейсу;
- обробку подій.

Потрібно перевірити, чи не виконується основна обчислювальна робота в критичному UI-потоці.

## 18.3. Worker Architecture

Якщо застосовуються Web Workers, необхідно дослідити:

- межі відповідальності;
- передачу позицій;
- передачу команд;
- передачу результатів;
- cancellation;
- завершення Worker;
- передачу великих буферів;
- синхронізацію конфігурації.

## 18.4. Worker Isolation

Worker не повинен використовувати застарілий контекст після заміни позиції або перезапуску пошуку.

Для цього потрібні ідентифікатори завдань і контроль версій стану.

---

# 19. UI AND ENGINE SEPARATION

## 19.1. Separation of Concerns

UI не повинен бути власником шахової логіки.

Він може відображати стан двигуна, але не повинен самостійно визначати легальність ходів через дубльовані правила.

## 19.2. Engine API

Пропонується єдиний внутрішній API:

`EngineAPI = (Initialize, SetPosition, Configure, Search, Stop, GetStatus, Shutdown)`

Це концептуальна модель.

Кожна операція повинна мати визначені вхідні дані, вихідні дані та помилки.

## 19.3. UI State vs Engine State

Необхідно розділяти:

- відображену дошку;
- внутрішню позицію;
- вибраний користувачем хід;
- результат пошуку;
- останній завершений результат;
- історію партії.

UI може відображати позицію, яка ще не була прийнята двигуном.

Це не повинно автоматично змінювати внутрішній стан ядра.

## 19.4. UI Consistency

Після кожного прийнятого результату UI повинен відображати актуальну позицію та результат відповідного пошукового завдання.

Застарілі повідомлення не повинні перезаписувати актуальний інтерфейс.

# 20. EVENT LOOP INTERACTION

## 20.1. Event Loop

Якщо система використовує асинхронну модель JavaScript, необхідно перевірити взаємодію між:

- event loop;
- пошуковим циклом;
- Promise;
- timers;
- UI events;
- Worker messages;
- cancellation events.

## 20.2. Event Ordering

Можлива ситуація:

1. запускається Search A;
2. користувач змінює позицію;
3. запускається Search B;
4. Search A завершується пізніше;
5. старий результат надходить після нового.

Без контролю ідентифікаторів це може пошкодити актуальний стан інтерфейсу.

## 20.3. Event Integrity

Кожна подія повинна мати:

- тип;
- контекст;
- джерело;
- ідентифікатор завдання;
- час або порядковий номер;
- умову допустимості.

## 20.4. Cancellation Semantics

Скасування асинхронної операції повинно бути узгоджене з фактичним припиненням обчислень.

Скасування Promise саме по собі не гарантує припинення синхронного пошукового циклу.

# 21. MODULE COUPLING AND COHESION

## 21.1. Coupling

Coupling — ступінь залежності модулів один від одного.

Надмірне зв'язування створює:

- складність змін;
- складність тестування;
- приховані залежності;
- побічні ефекти;
- ризик регресій.

## 21.2. Cohesion

Cohesion — наскільки відповідальність усередині модуля є логічно цілісною.

Модуль, який одночасно:

- генерує ходи;
- оцінює позиції;
- керує UI;
- обробляє UCI;
- змінює конфігурацію;

має потенційно надмірну кількість відповідальностей.

## 21.3. Architectural Metrics

Для аудиту пропонується вимірювати:

- кількість залежностей;
- кількість циклічних залежностей;
- кількість зовнішніх станів, які змінює модуль;
- кількість відповідальностей;
- кількість побічних ефектів;
- кількість контрактів;
- складність тестування.

Не слід трактувати ці метрики як універсальні числові критерії якості.

Їх потрібно інтерпретувати в контексті призначення модулів.

# 22. CROSS-MODULE INTEGRATION TESTING

Перевірити, що Evaluation отримує коректний контекст кожного вузла.

Перевірити, що записи TT відповідають позиціям і пошуковим параметрам.

Перевірити, що адаптивний контролер не порушує інваріанти Search Core.

## 22.5. SEIM → Engine API

Перевірити, що зовнішні команди перетворюються на коректні внутрішні операції.

## 22.6. Engine → UI

Перевірити, що зовнішнє відображення відповідає актуальному результату.

## 22.7. Full System Cycle

Повний сценарій:

`Initialize → Position → Search → Evaluate → Result → Output → New Position → Search`

На кожному етапі необхідно перевірити системні інваріанти.

# 29. ПІДСУМКОВИЙ ВИСНОВОК PHASE A.16

PHASE A.16 формує основу системного архітектурного аудиту SUBIT-CHESS.

Її головний результат — перехід від перевірки ізольованих функцій до перевірки взаємної узгодженості всіх компонентів.

Основний висновок:

**Коректність двигуна є не просто сумою коректних модулів. Вона залежить від того, чи зберігають ці модулі спільні інваріанти під час взаємодії.**

SSIM повинен забезпечити:

- явні архітектурні межі;
- контрольовані залежності;
- однозначне володіння станом;
- ізоляцію пошукових завдань;
- узгодженість позиції та Hash;
- контрольоване використання TT;
- модульні контракти;
- простежуваність даних;
- контроль життєвого циклу;
- безпечне управління ресурсами;
- системну перевірку інваріантів.

Особливо важливим є розмежування трьох рівнів:

**Локальна коректність:** модуль виконує власну функцію правильно.

**Інтеграційна коректність:** модулі правильно взаємодіють.

**Системна коректність:** двигун зберігає необхідні властивості впродовж повного життєвого циклу.

Лише поєднання цих трьох рівнів дає підстави говорити про архітектурну надійність SUBIT-CHESS.

**Статус PHASE A.16: ARCHITECTURAL AUDIT COMPLETE / SOURCE VALIDATION OPEN.**

Підтверджених дефектів реалізації не встановлено. Вихідний код цільового commit у межах цієї фази повторно не перевірявся. Runtime-тести не виконувалися.
