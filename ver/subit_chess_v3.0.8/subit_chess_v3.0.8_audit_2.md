# SUBIT-CHESS v3.0.8 — Аудит repetition, Null Move та Draw Rules

## 1. Repetition history: звичайний пошук реалізований послідовно

У Root Search:

```js
pos.pushRep();
const undo = pos.makeMove(m);

// пошук

pos.unmakeMove(undo);
pos.popRep();
```

У звичайному Negamax:

```js
pos.pushRep();
const undo = pos.makeMove(m);
```

Після перевірки легальності ходу, якщо він незаконний:

```js
pos.unmakeMove(undo);
pos.popRep();
continue;
```

Після завершення дочірнього пошуку:

```js
pos.unmakeMove(undo);
pos.popRep();
```

### Висновок

Звичайна історія повторень має послідовний цикл:

**додавання позиції → виконання ходу → пошук → відновлення позиції → видалення історії.**

Явної помилки балансування `pushRep()` / `popRep()` у показаних фрагментах не виявлено.

## 2. Null Move — потенційний дефект із реальними підставами

Поточна реалізація:

```js
const undo = pos.makeNullMove();
const score = -this.negamax(
  pos,
  depth - R,
  -beta,
  -beta + 1,
  ply + 1
);
pos.unmakeNullMove(undo);
```

Null Move змінює позицію, але не ізолює історію повторень.

У дочірньому Negamax є:

```js
if (ply > 0) {
  if (pos.repetitionCount() >= 5) return 0;
  if (pos.repetitionCount() >= 3) return 0;
}
```

### Чому це небезпечно

Після Null Move пошук продовжується в позиції, яка не могла виникнути в реальній партії.

Якщо подальші легальні ходи утворять позицію, хеш якої збігається з позицією в історії реальної партії, `repetitionCount()` може трактувати це як повторення, хоча траєкторія містить штучний Null Move.

Це може створити хибну нічию.

Водночас тут є нюанс: Null Move зазвичай використовується для оцінки можливості пропустити хід, а не для побудови реального варіанта. Тому repetition history у цій гілці має особливий статус.

### Статус дефекту

🟠 **Потенційна логічна помилка, яка потребує цільового тесту.**

Ми поки не довели, що вона реально впливає на вибір ходу. Але механізм, який може спричинити хибне виявлення повторення, існує.

## 3. Найсерйозніша проблема — неправильна семантика claimable draws

У коді:

```js
if (pos.halfmove >= 150) return 0;

if (ply > 0) {
  if (pos.repetitionCount() >= 5) return 0;
  if (pos.repetitionCount() >= 3) return 0;
  if (pos.halfmove >= 100) return 0;
}
```

Автор пояснює це так:

```js
// The 50-move rule (9.3) and threefold
// repetition (9.2) are claimable, which in practice means the opponent will
// claim them. Both are therefore scored as 0...
```

Це **неправильне спрощення моделі шахової гри**.

### Автоматичні нічиї

- 75 ходів без взяття або ходу пішака.
- П'ятикратне повторення позиції.

Ці випадки автоматично завершують гру відповідно до правил, якщо не відбувається мат, який має пріоритет.

### Нічиї за заявою

- 50 ходів без взяття або ходу пішака.
- Трикратне повторення позиції.

Ці випадки дають право заявити нічию, але не зобов'язують гравця це робити.

Пошуковий алгоритм не повинен автоматично трактувати право на заяву нічиєї як безумовний результат 0 у кожній позиції.

### Чому це критично для SUBIT-CHESS

Уявімо, що рушій має позицію з перевагою +8.00, але в поточній позиції можна заявити трикратне повторення.

Якщо алгоритм повертає:

```js
if (pos.repetitionCount() >= 3) return 0;
```

він може не розглядати можливість продовжити боротьбу та реалізувати виграш.

З іншого боку, якщо рушій програє, право заявити нічию може бути стратегічно найкращим рішенням.

Отже, право на заяву нічиєї повинно моделюватися як **доступна дія або альтернатива продовженню гри**, а не як автоматичний terminal score.

Статус: 🔴 **підтверджена концептуальна помилка в моделі draw rules пошуковим алгоритмом.**

## 4. Futility pruning — підтверджена помилка знака

Поточний код:

```js
const staticScore = this.ev.evaluate(pos, depth);

if (staticScore + futility.margin <= alpha) {
  pruned++;
  pos.unmakeMove(undo);
  pos.popRep();
  continue;
}
```

До цього моменту вже виконано хід:

```js
const undo = pos.makeMove(m);
```

А `evaluate()` повертає оцінку з погляду сторони, яка тепер ходить.

Отже:

- `staticScore` — оцінка для опонента;
- `alpha` — межа батьківського вузла, тобто оцінка для попередньої сторони.

Ці величини мають протилежну перспективу.

Якщо оцінка після ходу становить +500 для опонента, це приблизно −500 для батьківської сторони, а не +500.

Тому поточна умова:

```js
staticScore + margin <= alpha
```

неправильно зіставляє оцінки.

Очікувана форма, яку треба буде перевірити математично та тестами:

```js
-staticScore + futility.margin <= alpha
```

Але поки що це **не патч**. Спочатку потрібно перевірити межі застосування pruning, величину margin, `bestScore`, обробку шаху та поведінку при різних глибинах.

Статус: 🔴 **підтверджена помилка знака в futility pruning.**

## 5. Qsearch — три серйозні проблеми залишаються

З попереднього аналізу коду:

### 5.1. Stand-pat у шаху

Поточний алгоритм у стані шаху використовує статичну оцінку як `best` і допускає beta cutoff.

У шаху сторона не може просто «залишити позицію без змін». Вона повинна зробити легальний хід, який усуває шах.

Статичне stand-pat оцінювання в такому вузлі некоректне.

🔴 Підтверджений дефект.

### 5.2. Qsearch depth cap у шаху

При досягненні ліміту qdepth пошук може повернути статичну оцінку, навіть якщо сторона перебуває під шахом.

Це може оцінити позицію, в якій шах фактично не усунуто.

🔴 Підтверджений дефект.

### 5.3. Stalemate на глибині qsearch

Перевірка пату виконується лише в початковому qsearch-вузлі при `qdepth === 0`.

Пат може виникнути глибше, після серії тактичних ходів.

У такому випадку пошук може повернути матеріальну або статичну оцінку замість 0.

🔴 Підтверджений дефект.

# 6. Root Search — ще один пробіл у термінальних правилах

У Root Search:

```js
const rootMoves = pos.legalMoves();

if (rootMoves.length === 0) {
  return {
    move: 0,
    score: pos.inCheck() ? -MATE : 0,
    ...
  };
}
```

Перевіряється мат або пат.

Але не видно перевірки:

- `halfmove >= 150`;
- `repetitionCount() >= 5`;
- `insufficientMaterial()`.

Отже, кореневий пошук може продовжувати аналіз позиції, яка вже є автоматично завершеною нічиєю.

🔴 **Підтверджений пробіл у root terminal detection.**
