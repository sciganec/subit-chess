# 1. Анотація

SUBIT-CHESS Integrated Execution & Control Architecture визначає загальну архітектуру виконання шахового двигуна, у якій окремі аналітичні, пошукові, структурні, стратегічні, мнемонічні та дослідницькі компоненти координуються єдиною системою керування.

Попередні специфікації SUBIT-CHESS сформували окремі теоретичні модулі:

- представлення шахової позиції;
- структурний і реляційний аналіз;
- структурна динаміка;
- функція позиційної цінності;
- стратегічне планування;
- пошук і прийняття рішень;
- причинний аналіз;
- аналіз потенційності та контрфактичних можливостей;
- оцінювання невизначеності;
- метарозмірковування;
- автономне навчання;
- автономні дослідження;
- керування обчислювальними ресурсами;
- обчислювальна пам’ять;
- інкрементальні обчислення.

Проте наявність цих компонентів сама по собі ще не створює цілісного двигуна. Необхідно визначити механізм, який:

1. координує виконання компонентів;
2. контролює залежності між обчисленнями;
3. визначає пріоритети;
4. розподіляє ресурси;
5. забезпечує узгодженість стану;
6. контролює достовірність проміжних результатів;
7. обробляє помилки;
8. керує завершенням пошуку;
9. формує відтворюване рішення;
10. зберігає історію обчислювального процесу.

Ця специфікація вводить інтегрований контур виконання SUBIT-CHESS.

Основна теза:

**Шаховий двигун повинен бути не набором незалежних алгоритмів, а узгодженою системою перетворення позиційної інформації на перевірене рішення.**

# 3. Основна архітектурна модель

Введемо інтегровану систему:

**IECA = (C, O, S, G, M, R, V, L, E, X)**

де:

- C — Controller: центральний контролер;
- O — Orchestrator: координатор виконання;
- S — State Manager: керування станом;
- G — Computational Graph: обчислювальний граф;
- M — Memory: система пам’яті;
- R — Resource Scheduler: планувальник ресурсів;
- V — Validation: перевірка результатів;
- L — Logging: журналювання;
- E — Error Recovery: обробка помилок і відновлення;
- X — Execution Engine: виконання пошукових та аналітичних операцій.

Загальна функція:

**IECA(P, B, Θ) → (D, T, Eᵣ)**

де:

- P — поточна шахова позиція;
- B — доступний обчислювальний бюджет;
- Θ — зафіксована конфігурація параметрів;
- D — рішення;
- T — трасування обчислювального процесу;
- Eᵣ — набір доказів, результатів перевірки та оцінок невизначеності.

Важливо: результатом роботи системи є не просто хід.

Результатом є:

**рішення + його обчислювальне походження + межі достовірності.**

# 4. Два рівні системи: Control Plane і Data Plane

Архітектура розділяється на два логічні рівні.

## 4.1. Control Plane

Контрольний рівень керує процесом.

До нього належать:

- центральний контролер;
- оркестратор;
- планувальник ресурсів;
- диспетчер завдань;
- менеджер станів;
- механізм зупинки;
- обробник помилок;
- система журналювання.

Control Plane визначає:

- які завдання потрібно виконати;
- у якій послідовності;
- які завдання можуть виконуватися паралельно;
- які результати необхідно перевірити;
- коли потрібно повторити обчислення;
- коли необхідно завершити пошук.

## 4.2. Data Plane

Рівень даних виконує безпосередні обчислення.

До нього належать:

- генерація легальних ходів;
- геометричний аналіз;
- структурний аналіз;
- реляційний аналіз;
- тактичний аналіз;
- оцінювання позиції;
- генерація стратегічних цілей;
- пошук;
- контрфактичний аналіз;
- причинний аналіз;
- формування пояснення.

Data Plane отримує завдання від Control Plane і повертає результати відповідно до визначених контрактів.

## 4.3. Принцип розділення

Контрольний рівень не повинен довільно змінювати результати аналітичних компонентів.

Аналітичні компоненти не повинні самостійно змінювати глобальний стан системи.

Взаємодія відбувається через формалізовані повідомлення та результати виконання.

Це забезпечує контрольованість і відтворюваність.

# 5. Центральний контролер

Центральний контролер є головним координатором обчислювального циклу.

Позначення:

**C₀ = Controller(P, State, Budget, Configuration)**

Його функції:

1. отримати нову позицію;
2. перевірити цілісність вхідного стану;
3. ініціювати аналітичний процес;
4. сформувати набір завдань;
5. передати завдання оркестратору;
6. контролювати виконання;
7. оцінювати достатність результатів;
8. запускати додаткові перевірки;
9. отримувати результати пошуку;
10. затверджувати фінальне рішення в межах встановленої ієрархії повноважень.

Контролер не повинен перетворюватися на ще один евристичний оцінювач.

Його основне завдання — забезпечення коректного виконання.

## 5.1. Обмеження повноважень

Контролер не має права:

- змінювати правила шахів;
- приймати нелегальний хід;
- ігнорувати шах королю;
- замінювати точний результат завершеної партії евристикою;
- використовувати неперевірені результати як точні факти;
- змінювати параметри активного пошуку;
- приховувати неповноту пошукового процесу.

# 7. Граф залежностей виконання

Окремі аналітичні завдання утворюють орієнтований граф.

**DG = (Vₜ, Eₜ)**

де:

- Vₜ — множина завдань;
- Eₜ — залежності між завданнями.

Приклад:

```text
POSITION INPUT
      │
      ▼
STATE VALIDATION
      │
      ▼
LEGAL MOVE GENERATION
      │
      ├───────────────┐
      ▼               ▼
GEOMETRY          TERMINAL CHECK
      │
      ▼
STRUCTURAL ANALYSIS
      │
      ├───────────────┐
      ▼               ▼
TACTICAL ANALYSIS  RELATIONAL ANALYSIS
      │               │
      └───────┬───────┘
              ▼
       POSITION EVALUATION
              │
              ▼
       STRATEGIC ANALYSIS
              │
              ▼
            SEARCH
              │
              ▼
       DECISION VALIDATION
              │
              ▼
           OUTPUT
```

Це концептуальна схема, а не обов’язкова послідовність кожного обчислення.

Деякі операції можуть виконуватися паралельно.

Наприклад, геометричний аналіз і перевірка термінального стану можуть бути незалежними після отримання узгодженого знімка позиції.

## 7.1. Типи залежностей

Визначаються:

- DATA_DEPENDENCY — потрібні дані;
- STATE_DEPENDENCY — потрібна конкретна версія стану;
- LOGICAL_DEPENDENCY — потрібен попередній логічний результат;
- VALIDATION_DEPENDENCY — потрібне підтвердження;
- RESOURCE_DEPENDENCY — потрібен доступний ресурс;
- TEMPORAL_DEPENDENCY — результат має часову актуальність;
- VERSION_DEPENDENCY — потрібна конкретна версія параметрів.

## 7.2. Заборона передчасного виконання

Завдання не може використовувати результат залежного компонента, якщо цей результат:

- ще не сформований;
- належить іншій версії позиції;
- не пройшов необхідну перевірку;
- був анульований;
- втратив актуальність.

# 8. Менеджер стану

Менеджер стану забезпечує єдине джерело актуального шахового стану.

Повна позиція:

**P = (B, s, CR, EP, H, N, 𝓗)**

де:

- B — шахівниця;
- s — сторона, що ходить;
- CR — права на рокіровку;
- EP — можливість взяття на проході;
- H — лічильник напівходів;
- N — номер повного ходу;
- 𝓗 — необхідна історія позиції для перевірки історично залежних правил.

## 8.1. Незмінність знімка позиції

Кожний пошуковий процес отримує власний логічно незмінний знімок:

**Snapshot(P, vₚ)**

де vₚ — версія позиції.

Під час виконання пошуку цей знімок не змінюється.

Якщо надходить нова позиція, створюється новий знімок.

Старі завдання:

- завершуються;
- скасовуються;
- або ізолюються від нового стану.

Вони не повинні непомітно змішувати результати різних позицій.

## 8.2. Узгодженість версій

Кожний аналітичний результат повинен містити:

```text
AnalysisResult = {
    position_id,
    position_version,
    parameter_version,
    module_version,
    result,
    evidence,
    timestamp,
    validity
}
```

Результат може бути використаний лише після перевірки сумісності версій.

# 9. Контракт обчислювального компонента

Кожний компонент SUBIT-CHESS повинен мати визначений контракт.

Загальна модель:

**Module = (Input, Preconditions, Operation, Output, Invariants, FailureModes)**

де:

- Input — вхідні дані;
- Preconditions — передумови;
- Operation — операція;
- Output — результат;
- Invariants — властивості, які повинні зберігатися;
- FailureModes — можливі помилки.

Наприклад, контракт генератора легальних ходів:

```text
Module:
    LEGAL_MOVE_GENERATOR

Input:
    ValidatedPosition

Preconditions:
    Position state is internally consistent.

Operation:
    Generate every legal move.

Output:
    CompleteLegalMoveSet

Invariants:
    Every returned move is legal.
    No legal move is omitted.
    Special chess rules are respected.

FailureModes:
    Invalid state.
    Incomplete generation.
    Incorrect special-move handling.
```

Цей контракт є принциповим.

Евристичний модуль може помилятися в оцінюванні позиції, але генератор легальних ходів не повинен підміняти точну операцію приблизною.

# 10. Ієрархія повноважень

Інтегрована архітектура встановлює чітку ієрархію.

## Рівень 1. Правила шахів

Найвищий рівень.

Включає:

- легальність ходів;
- правила шаху;
- правила мату;
- пат;
- рокіровку;
- взяття на проході;
- перетворення пішака;
- правила нічиєї;
- завершення партії.

Ці правила не можуть бути змінені навчанням.

## Рівень 2. Точні результати

Якщо стан однозначно визначає завершення партії або примусову тактичну ситуацію в межах перевіреного дерева, ці результати мають пріоритет над евристичними міркуваннями.

Важливо відрізняти:

- математично доведений результат;
- результат повного пошуку в конкретному дереві;
- результат обмеженого пошуку;
- евристичне припущення.

## Рівень 3. Повна множина легальних ходів

Нехай:

**L(P) = {m₁, m₂, ..., mₙ}**

Пошукова система повинна працювати з усіма легальними ходами, якщо не застосовує окремо визначений і контрольований механізм скорочення пошуку.

Стратегічний аналіз не має права видаляти легальні ходи з множини.

## Рівень 4. Пошук

Пошук оцінює наслідки ходів і визначає перевагу серед кандидатів.

Базова модель:

**V(P,d) = maxₘ∈L(P) [−V(T(P,m),d−1)]**

де:

- P — позиція;
- d — глибина;
- T(P,m) — результат легального ходу;
- V — оцінка з перспективи сторони, що ходить.

## Рівень 5. Структурна та стратегічна аналітика

Ці компоненти можуть:

- змінювати порядок ходів;
- формувати цілі;
- визначати важливі структурні елементи;
- пропонувати додаткові варіанти аналізу;
- рекомендувати збільшення глибини;
- визначати необхідність перевірки.

Але вони не можуть скасовувати точні правила або підміняти результати пошуку.

## Рівень 6. Евристичні та навчальні параметри

Навчальні параметри впливають на:

- оцінювання;
- порядок пошуку;
- розподіл ресурсів;
- контекстуальні ваги;
- вибір додаткових аналітичних процедур.

Вони не змінюють правила шахів.

# 11. Інтеграція обчислювального графа

Обчислювальний граф представляє не тільки залежності між модулями, а й походження результатів.

Позначення:

**CG(P) = (V꜀, E꜀, L꜀)**

де:

- V꜀ — обчислювальні вузли;
- E꜀ — залежності;
- L꜀ — типи операцій та зв’язків.

Кожний вузол має:

```text
ComputeNode = {
    node_id,
    operation_type,
    input_versions,
    dependencies,
    output,
    status,
    evidence,
    cost,
    provenance
}
```

## 11.1. Основні типи вузлів

- STATE_NODE;
- RULE_NODE;
- GEOMETRY_NODE;
- STRUCTURE_NODE;
- RELATION_NODE;
- TACTIC_NODE;
- VALUE_NODE;
- STRATEGY_NODE;
- SEARCH_NODE;
- UNCERTAINTY_NODE;
- MEMORY_NODE;
- VALIDATION_NODE;
- DECISION_NODE.

## 11.2. Правило походження результату

Кожний результат повинен мати простежуваний шлях до первинних даних.

Наприклад:

```text
Position
   ↓
Piece Configuration
   ↓
Attack Relations
   ↓
King Safety Features
   ↓
Evaluation Component
   ↓
Search Result
   ↓
Decision
```

Якщо один із проміжних вузлів виявляється некоректним, система повинна визначити всі залежні результати, які необхідно повторно обчислити.

Це пов’язує Integrated Execution із Computational Graph та Incremental Computation.

---

# 12. Інтеграція пам’яті

Модуль Computational Memory забезпечує збереження результатів, але інтегрована архітектура визначає правила їх використання.

## 12.1. Принцип

**Stored ≠ Valid**

Збережений результат не обов’язково є актуальним.

Перед використанням результат перевіряється за:

- ідентичністю позиції;
- історичним контекстом;
- версією алгоритму;
- версією параметрів;
- походженням;
- залежностями;
- умовами застосування;
- часовою актуальністю.

## 12.2. Процедура отримання з пам’яті

```text
MEMORY REQUEST
      ↓
IDENTITY CHECK
      ↓
CONTEXT CHECK
      ↓
VERSION CHECK
      ↓
PROVENANCE CHECK
      ↓
DEPENDENCY CHECK
      ↓
VALIDITY CHECK
      ↓
REUSE / RECOMPUTE / REJECT
```

## 12.3. Категорії використання

- DIRECT_REUSE — безпосереднє використання після перевірки;
- CONDITIONAL_REUSE — використання за виконання умов;
- CONTEXTUAL_REUSE — контекстуально обмежене використання;
- ANALOGICAL_GUIDANCE — аналогічний випадок лише як підказка;
- RECOMPUTATION_REQUIRED — потрібне повторне обчислення;
- INVALID_FOR_CURRENT_STATE — результат непридатний.

## 12.4. Заборона змішування версій

Результати різних версій позиції, параметрів або алгоритму не можуть об’єднуватися без явної процедури сумісності.

---

# 13. Планувальник ресурсів

Планувальник отримує бюджет:

**B = (Bₜ, Bₙ, Bₘ, B꜀, Bₚ)**

де:

- Bₜ — часовий бюджет;
- Bₙ — бюджет вузлів пошуку;
- Bₘ — бюджет пам’яті;
- B꜀ — обчислювальна потужність;
- Bₚ — паралельність.

Кожне завдання має:

- пріоритет;
- прогнозовану вартість;
- фактичну вартість;
- залежності;
- критичність;
- очікувану користь;
- граничний час.

## 13.1. Категорії пріоритетів

**P0 — обов’язкові операції**

- перевірка стану;
- перевірка правил;
- визначення завершення партії;
- генерація легальних ходів.

**P1 — тактична безпека**

- перевірка шаху;
- аналіз примусових відповідей;
- пошук матових загроз;
- перевірка критичних тактичних варіантів.

**P2 — основний пошук**

- iterative deepening;
- alpha-beta;
- principal variation;
- quiescence search;
- перевірка кандидатів.

**P3 — структурний аналіз**

- реляційна структура;
- активність фігур;
- слабкості;
- контроль простору;
- структурні зміни.

**P4 — стратегічний аналіз**

- цілі;
- плани;
- альтернативні маршрути;
- причинні залежності;
- стійкість плану.

**P5 — додаткові дослідження**

- контрфактичні сценарії;
- розширене пояснення;
- додаткові перевірки невизначеності;
- дослідницькі експерименти.

Ця ієрархія не означає, що структурний аналіз завжди виконується після пошуку. Частина структурної інформації може бути потрібна для ефективного впорядкування ходів.

Вона визначає насамперед те, які завдання не можна пожертвувати заради необов’язкового аналізу.

## 13.2. Резерв тактичних ресурсів

Система повинна резервувати обчислювальні ресурси для тактичної перевірки.

Не можна витрачати весь бюджет на стратегічне моделювання, залишаючи недостатньо ресурсів для перевірки безпосередніх загроз.

## 13.3. Відсутність голодування

Низькопріоритетні завдання можуть відкладатися, але не повинні нескінченно залишатися невиконаними.

Планувальник повинен враховувати:

- старіння завдання;
- його актуальність;
- залежності;
- доступний бюджет;
- ризик втрати результату.

Основний цикл IECA:

4. CHECK TERMINAL CONDITIONS
        ↓

        ↓

        ↓
8. VALIDATE MEMORY
        ↓
9. ANALYZE STRUCTURE
        ↓
10. ANALYZE TACTICS
        ↓
11. ANALYZE CONTEXT
        ↓

        ↓
13. GENERATE STRATEGIC GOALS
        ↓

        ↓

        ↓

        ↓

- виявлена помилка структурного графа може ініціювати його перебудову;
- висока невизначеність може викликати додатковий аналіз.

Отже, це не лінійний конвеєр, а керований цикл.

# 15. Механізм зупинки пошуку

Пошук не повинен зупинятися лише тому, що отримано першу оцінку.

Він завершується відповідно до бюджету та критеріїв достатності.

Позначимо:

**Stop(P,t,n,u,q)**

де:

- t — витрачений час;
- n — кількість вузлів;
- u — профіль невизначеності;
- q — якість та стабільність результату.

Можливі причини зупинки:

1. завершено задану глибину;
2. вичерпано часовий бюджет;
3. вичерпано бюджет вузлів;
4. знайдено точний термінальний результат;
5. досягнуто граничного ресурсу;
6. пошук скасовано через новий стан;
7. отримано достатньо стабільний результат у межах встановленої політики.

## 15.1. Anytime-поведінка

Система повинна бути здатна повертати найкращий доступний результат після кожної завершеної ітерації.

Наприклад:

```text
Depth 1 → provisional result
Depth 2 → updated result
Depth 3 → updated result
Depth 4 → updated result
Depth 5 → updated result
```

Проміжний результат не повинен видаватися за остаточний.

Він має бути позначений як:

- PROVISIONAL;
- INCOMPLETE;
- VALIDATED_WITHIN_DEPTH;
- FINAL_WITHIN_BUDGET.

## 15.2. Безпечні точки зупинки

Пошук може бути перерваний лише в контрольованому стані.

Система повинна зберегти:

- завершені ітерації;
- найкращий відомий хід;
- principal variation;
- параметри пошуку;
- позицію;
- версію стану;
- доступні результати перевірки.

Незавершена ітерація не повинна підміняти собою останню завершену.

---

# 16. Інтеграція невизначеності

Невизначеність не є одним числом.

Вона може мати різні джерела:

- неповнота пошуку;
- нестабільність оцінювання;
- невизначеність тактичного варіанта;
- невизначеність структурної інтерпретації;
- невизначеність стратегічного плану;
- невідповідність контексту;
- обмеження моделі.

Вектор:

**U(P) = (Uₛ, Uₜ, Uₑ, Uᵣ, Uₚ, Uₕ, Uₘ, U𝚌)**

Контролер використовує цей вектор для визначення потреби в додаткових обчисленнях.

Наприклад:

- висока Uₜ → додаткова тактична перевірка;
- висока Uₛ → збільшення глибини або перевірка альтернатив;
- висока Uₑ → повторне оцінювання;
- висока Uᵣ → перебудова структурного представлення;
- висока Uₚ → перегляд планів;
- висока Uₘ → перевірка відповідності моделі.

Принцип:

**Невизначеність повинна керувати обсягом перевірки, а не автоматично погіршувати оцінку позиції.**

# 17. Паралельне виконання

Архітектура допускає паралельне виконання незалежних завдань.

Можливі паралельні операції:

- структурний аналіз різних зон;
- аналіз окремих кандидатних ходів;
- обчислення незалежних оцінювальних компонентів;
- підготовка стратегічних альтернатив;
- перевірка окремих причинних залежностей.

## 17.1. Умови безпечного паралелізму

Паралельні завдання повинні мати:

- узгоджені знімки позиції;
- зафіксовану версію параметрів;
- визначені вхідні дані;
- ізольовані робочі області;
- контрольований механізм повернення результатів.

## 17.2. Заборона спільної неконтрольованої мутації

Два потоки не повинні одночасно змінювати один і той самий логічний стан без синхронізації.

Особливо це стосується:

- шахового стану;
- таблиці транспозицій;
- пам’яті;
- журналу змін;
- параметрів навчання;
- глобального пошукового контексту.

## 17.3. Детермінованість

Детермінованість бажана для:

- генерації легальних ходів;
- застосування ходів;
- оцінювання за фіксованої конфігурації;
- перевірки структурних інваріантів;
- тестування.

Паралельний пошук може мати недетермінований порядок завершення завдань. Тому для відтворюваних експериментів необхідно фіксувати:

- конфігурацію;
- seed;
- бюджет;
- версії;
- порядок об’єднання результатів, якщо він впливає на рішення.

# 18. Обробка помилок і відновлення

Система повинна розрізняти помилки за походженням.

## 18.1. Категорії помилок

**E1 — STATE_ERROR**

Некоректний шаховий стан.

**E2 — RULE_ERROR**

Порушення правил або неправильна генерація легальних ходів.

**E3 — GRAPH_ERROR**

Пошкодження обчислювального графа.

**E4 — VERSION_ERROR**

Змішування несумісних версій.

**E5 — MEMORY_ERROR**

Некоректне або застаріле використання пам’яті.

**E6 — RESOURCE_ERROR**

Вичерпання ресурсів або порушення бюджету.

**E7 — SEARCH_ERROR**

Некоректний пошуковий результат.

**E8 — VALIDATION_ERROR**

Невдале проходження перевірки.

**E9 — CONCURRENCY_ERROR**

Конфлікт паралельного виконання.

**E10 — PERSISTENCE_ERROR**

Помилка збереження або відновлення.

## 18.2. Загальна процедура

```text
ERROR DETECTED
      ↓
CLASSIFY ERROR
      ↓
IDENTIFY AFFECTED COMPONENTS
      ↓
ISOLATE INVALID RESULTS
      ↓
CHECK LAST VALID SNAPSHOT
      ↓
REBUILD / RECOMPUTE / RESTORE
      ↓
VALIDATE RECOVERED STATE
      ↓
RESUME OR TERMINATE
```

## 18.3. Принцип локалізації

Помилка одного евристичного компонента не повинна автоматично руйнувати весь двигун.

Якщо стратегічний аналіз недоступний, базовий пошук може продовжитися без нього.

Однак якщо неможливо підтвердити легальність ходів, система не має права повертати рішення як коректне.

## 19.1. Вимоги до журналу

- Які обмеження залишилися?

## 19.2. Принцип прозорості

Пояснення рішення повинно спиратися на фактичний журнал і результати пошуку.

Заборонено генерувати після завершення пошуку причинне пояснення, яке не відповідає реальному процесу прийняття рішення.

# 20. Формування фінального рішення

Результат пошуку проходить процедуру перевірки.

Нехай:

**D(P) = (m*, V*, PV, d, N, U, E)**

де:

- m* — обраний хід;
- V* — його оцінка;
- PV — principal variation;
- d — завершена глибина;
- N — кількість вузлів;
- U — профіль невизначеності;
- E — докази та обчислювальне походження.

## 20.1. Перевірка рішення

Перед поверненням ходу система перевіряє:

1. чи належить хід множині легальних ходів;
2. чи відповідає він актуальній позиції;
3. чи не змінилася версія стану;
4. чи є пошуковий результат валідним;
5. чи правильно визначена перспектива оцінки;
6. чи не використано застарілі параметри;
7. чи не порушено обчислювальний бюджет;
8. чи відомий статус завершеності пошуку.

## 20.2. Decision Certificate

Для кожного рішення формується внутрішній сертифікат:

```text
DecisionCertificate = {
    position_identity,
    position_version,
    selected_move,
    legal_validation,
    search_depth,
    completed_iteration,
    node_count,
    principal_variation,
    evaluation,
    uncertainty_profile,
    parameter_version,
    algorithm_version,
    validation_status,
    provenance
}
```

Сертифікат не є математичним доказом найкращого ходу.

Він є структурованим свідченням того, як система отримала та перевірила своє рішення.

# 21. Інтеграція автономного навчання

Навчальний процес не повинен втручатися в активний пошук.

Визначаються два різні контури.

## 21.1. Контур гри

```text
POSITION
   ↓
ANALYSIS
   ↓
SEARCH
   ↓
DECISION
   ↓
MOVE
```

## 21.2. Контур розвитку

```text
EXPERIENCE
   ↓
DATA GENERATION
   ↓
HYPOTHESIS
   ↓
CANDIDATE CHANGE
   ↓
CONTROLLED TESTING
   ↓
VALIDATION
   ↓
ACCEPT / REJECT / INCONCLUSIVE
   ↓
VERSIONED RELEASE
```

Навчання може змінювати:

- параметри оцінювання;
- порядок пошуку;
- контекстуальні ваги;
- розподіл ресурсів;
- стратегії дослідження;
- окремі алгоритмічні компоненти.

Навчання не може змінювати:

- правила шахів;
- вимоги до легальності;
- критерії коректності;
- вимоги до незалежної перевірки.

## 21.3. Ізоляція параметрів

Кожний активний пошук використовує незмінний знімок параметрів:

**Θₜ = Snapshot(Θ, version)**

Навіть якщо паралельно відбувається навчання, активний пошук продовжує працювати з Θₜ.

Нові параметри застосовуються лише в наступному контрольованому запуску.

## 21.4. Автономність

SUBIT-CHESS повинен самостійно формувати та перевіряти свої рішення.

У межах цієї архітектури заборонено використовувати як складові двигуна або джерела навчальних оцінок:

- сторонні шахові рушії;
- запозичені шахові бібліотеки;
- зовнішні бази шахових партій;
- готові зовнішні оцінки позицій;
- сигнали зовнішніх рушіїв як учителя.

Допускаються:

- внутрішньо згенеровані позиції;
- контрольований self-play;
- власні алгоритмічні тести;
- незалежні регресійні набори;
- математичні та формальні перевірки.

# 22. Інтегрована архітектура станів

Уся система має власний стан виконання.

Позначимо:

**ES = (P, A, Q, B, Θ, M, T, F)**

де:

- P — шахова позиція;
- A — аналітичний стан;
- Q — черга завдань;
- B — залишковий бюджет;
- Θ — конфігурація параметрів;
- M — стан пам’яті;
- T — журнал виконання;
- F — стан помилок.

Глобальні стани системи:

```text
IDLE
INITIALIZING
VALIDATING
ANALYZING
SEARCHING
VERIFYING
DECIDING
OUTPUTTING
LEARNING
RECOVERING
CANCELLED
COMPLETED
FAILED
```

Не всі ці стани є взаємовиключними на рівні окремих паралельних завдань. Це стани загального контролера.

## 22.1. Перехід між станами

Наприклад:

```text
IDLE
  ↓
INITIALIZING
  ↓
VALIDATING
  ↓
ANALYZING
  ↓
SEARCHING
  ↓
VERIFYING
  ↓
DECIDING
  ↓
OUTPUTTING
  ↓
COMPLETED
```

Якщо виявлено помилку:

```text
ANY ACTIVE STATE
       ↓
ERROR
       ↓
RECOVERING
       ↓
VALIDATING
       ↓
RESUME / FAILED
```

# 23. Формальні інваріанти

Нижче наведено інваріанти інтегрованої архітектури.

Вони є нормативними вимогами специфікації. Їхня фактична гарантія потребує реалізації та тестування.

**IECA-INV-001 — State Integrity**

Стан позиції повинен відповідати визначеній моделі шахів.

**IECA-INV-002 — Snapshot Immutability**

Активний пошуковий процес не змінює власний знімок позиції.

**IECA-INV-003 — Version Consistency**

Результати одного рішення повинні мати сумісні версії стану та параметрів.

**IECA-INV-004 — Legal Move Authority**

Жодний нелегальний хід не може бути повернений як рішення.

**IECA-INV-005 — Complete Legal Move Generation**

Генератор легальних ходів повинен повертати повну множину легальних ходів.

**IECA-INV-006 — Rule Immutability**

Навчання не може змінювати правила шахів.

**IECA-INV-007 — Tactical Priority**

Евристичні стратегічні результати не можуть скасовувати підтверджені тактичні обмеження.

**IECA-INV-008 — Search Evidence**

Кожне пошукове рішення повинно мати відомі параметри та статус завершеності.

**IECA-INV-009 — Memory Revalidation**

Результат пам’яті не може використовуватися без перевірки актуальності.

**IECA-INV-010 — Dependency Integrity**

Завдання не може використовувати недійсний результат своєї залежності.

**IECA-INV-011 — Resource Bound**

Виконання повинно дотримуватися визначених ресурсних обмежень.

**IECA-INV-012 — Tactical Reserve**

Необов’язкові аналітичні операції не повинні повністю витісняти необхідні тактичні перевірки.

**IECA-INV-013 — Safe Interruption**

Переривання пошуку не повинно пошкоджувати останній завершений результат.

**IECA-INV-014 — Parallel Isolation**

Паралельні завдання не повинні неконтрольовано змінювати спільний стан.

**IECA-INV-015 — Provenance Preservation**

Кожний важливий результат повинен мати походження.

**IECA-INV-016 — Error Isolation**

Помилка окремого евристичного модуля не повинна автоматично пошкоджувати базову коректність системи.

**IECA-INV-017 — Decision Validation**

Фінальний хід повинен пройти перевірку перед поверненням.

**IECA-INV-018 — No Unsupported Certainty**

Неповний пошук не може представлятися як математично доведений результат.

**IECA-INV-019 — Learning Isolation**

Навчання не повинно змінювати параметри активного пошуку.

**IECA-INV-020 — Reproducibility**

Система повинна зберігати достатньо інформації для відтворення контрольованих обчислювальних експериментів.

**IECA-INV-021 — No Heuristic Rule Override**

Евристики не можуть змінювати або обходити точні шахові правила.

**IECA-INV-022 — Context Preservation**

Під час об'єднання результатів не можна втрачати контекст їх отримання.

**IECA-INV-023 — Atomic State Transition**

Зміна основного шахового стану повинна бути атомарною з погляду спостерігачів системи.

**IECA-INV-024 — Trace Consistency**

Журнал виконання повинен відповідати фактично виконаним операціям.

Вимірювання вартості перевірки пам’яті.

Порівняння різних стратегій розподілу обчислювального бюджету.

**IECA-EXP-007 — Tactical Reserve**

Перевірка впливу резервування ресурсів на виявлення тактичних загроз.

Порівняння послідовного та паралельного виконання.

Перевірка відновлення після переривання пошуку.

Перевірка ізоляції паралельних пошуків із різними параметрами.

Перевірка того, чи допомагає профіль невизначеності ефективніше розподіляти ресурси.

Вимірювання стабільності вибору ходу при збільшенні бюджету.

Контрольоване введення помилок для перевірки механізмів відновлення.

**IECA-EXP-014 — End-to-End Execution**

Перевірка всього циклу від отримання позиції до повернення ходу.

## 25.1. Критерії оцінювання

Необхідно вимірювати:

- час до першого результату;
- час до завершення пошуку;
- кількість вузлів;
- використання пам’яті;
- кількість повторних обчислень;
- частку валідних повторно використаних результатів;
- кількість помилок узгодженості;
- частоту успішного відновлення;
- стабільність рішення;
- ефективність розподілу ресурсів.

Покращення швидкості саме по собі не доводить покращення сили гри.

Ці властивості потрібно перевіряти окремо.

# 26. Метрики інтегрованої системи

## 26.1. Execution Latency

**EL = T_output − T_input**

Час від отримання позиції до повернення результату.

## 26.2. Task Completion Rate

**TCR = N_completed / N_created**

Частка успішно завершених завдань.

## 26.3. Validation Success Rate

**VSR = N_validated / N_validation_attempts**

Частка успішно валідованих результатів.

## 26.4. Resource Utilization

**RU = B_used / B_available**

Частка використаного бюджету.

## 26.5. Reuse Efficiency

**RE = N_valid_reused / N_memory_requests**

Частка запитів до пам’яті, які завершилися коректним повторним використанням.

## 26.6. Recovery Rate

**RR = N_successful_recoveries / N_recovery_attempts**

Частка успішних відновлень.

## 26.7. Version Conflict Rate

**VCR = N_version_conflicts / N_result_merges**

Частота конфліктів версій.

## 26.8. Decision Stability

Вимірюється частота зміни найкращого ходу між послідовними завершеними ітераціями або контрольованими запусками.

Ця метрика не є безпосереднім показником сили двигуна.

# 28. Ризики архітектури

## 28.1. Надмірна складність керування

Велика кількість компонентів може створити витрати на координацію, які перевищуватимуть користь від додаткового аналізу.

Відповідь: мінімальний контролер, явні контракти, вимірювання накладних витрат.

## 28.2. Надмірна кількість повторних обчислень

Часті перевірки можуть знищити переваги інкрементальної архітектури.

Відповідь: перевіряти лише ті залежності, які дійсно змінилися, за умови доведеної коректності інкрементального оновлення.

## 28.3. Помилкове повторне використання пам’яті

Схожі позиції можуть мати різні права на рокіровку, історію або інші критичні параметри.

Відповідь: розділяти ідентичність дошки, повний шаховий стан та аналітичну подібність.

## 28.4. Надмірна паралельність

Паралельне виконання може збільшити конкуренцію за ресурси й ускладнити відтворюваність.

Відповідь: починати з послідовної реалізації та додавати паралельність лише після профілювання.

## 28.5. Конфлікт між стратегічним аналізом і пошуком

Стратегічний компонент може рекомендувати план, який спростовується тактикою.

Відповідь: пошук і точні правила мають вищий рівень повноважень.

## 28.6. Ілюзія автономності

Наявність модулів пам’яті, навчання та метаконтролю ще не означає, що система стала автономним інтелектуальним агентом.

Відповідь: автономність потрібно визначати через перевірювані функції — самостійне генерування кандидатів, аналіз, перевірку, адаптацію та оцінювання власних змін.

# 32. Основні принципи IECA

Інтегрована архітектура встановлює такі принципи.

**1. DO NOT EXECUTE WITHOUT VALID STATE**

Не починати обчислення без перевіреного стану.

**2. DO NOT MIX VERSIONS**

Не об’єднувати результати несумісних версій.

**3. DO NOT TRUST WITHOUT VALIDATION**

Не використовувати результат лише тому, що його сформував внутрішній компонент.

**4. DO NOT REUSE WITHOUT CONTEXT**

Не повторно використовувати пам’ять без перевірки контексту.

**5. DO NOT OVERRIDE RULES WITH HEURISTICS**

Не дозволяти евристикам змінювати точні правила.

**6. DO NOT CONFUSE COMPLETION WITH CORRECTNESS**

Завершене обчислення не обов’язково є правильним.

**7. DO NOT CONFUSE SEARCH DEPTH WITH PROOF**

Глибина пошуку сама по собі не є математичним доказом.

**8. DO NOT LEARN DURING ACTIVE SEARCH**

Не змінювати параметри активного пошукового процесу.

**9. DO NOT HIDE UNCERTAINTY**

Не приховувати обмеження результатів.

**10. DO NOT COLLAPSE — CONTEXTUALIZE**

Не зводити складну обчислювальну систему до одного числа, одного евристичного показника або одного непрозорого рішення.

# 33. Висновок

SUBIT-CHESS Integrated Execution & Control Architecture v1.0 формалізує перехід від набору теоретичних аналітичних компонентів до єдиної системи координованого виконання.

Її головний внесок полягає в тому, що вона визначає:

- єдиний контур керування;
- розподіл повноважень між компонентами;
- контракти виконання;
- узгодженість станів;
- граф залежностей;
- інтеграцію пам’яті;
- керування ресурсами;
- правила зупинки;
- механізми перевірки;
- ізоляцію помилок;
- відтворюваність;
- контроль автономного навчання.

Особливе значення має розділення трьох понять:

**Обчислення — результат — доказ.**

Обчислення може бути завершене, але його результат може бути помилковим.

Результат може бути корисним, але не мати достатніх доказів.

Доказ може бути коректним у визначених межах, але не поширюватися на всю шахову партію.

Саме тому SUBIT-CHESS повинен зберігати походження, контекст і межі застосування кожного важливого результату.

Інтегрований двигун має не лише знаходити ходи, а й контролювати процес, завдяки якому ці ходи були знайдені.

**Ключова архітектурна теза:**

SUBIT-CHESS — це система, у якій позиція перетворюється на структуроване знання, структуроване знання — на контрольований пошук, а пошук — на перевірене рішення з відомим походженням та обмеженнями.

**DO NOT COLLAPSE — CONTEXTUALIZE.**
