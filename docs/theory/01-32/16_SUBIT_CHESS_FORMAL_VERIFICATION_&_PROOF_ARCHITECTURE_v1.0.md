# 1. Анотація

SUBIT-CHESS FORMAL VERIFICATION & PROOF ARCHITECTURE (FVPA) визначає систему формальної перевірки, яка має забезпечити логічну, математичну та програмну коректність шахового двигуна.

SUBIT-CHESS розробляється як автономна система, що самостійно:

- представляє шахові позиції;
- визначає легальні ходи;
- аналізує структурні відношення;
- оцінює позиції;
- генерує стратегічні плани;
- виконує пошук;
- навчається на власному досвіді;
- проводить дослідницькі експерименти;
- змінює власні алгоритми.

Така архітектура створює особливу проблему: система, яка самостійно вдосконалює власні компоненти, повинна мати механізм перевірки того, що ці зміни не руйнують базові властивості системи.

FVPA розв'язує цю проблему через розділення двох категорій:

**Незмінні властивості:**

- правила шахів;
- коректність представлення позиції;
- легальність ходів;
- коректність переходів між позиціями;
- точність визначення термінальних станів;
- цілісність історії, необхідної для визначення повторень і нічиїх.

**Змінні властивості:**

- евристики;
- функції оцінювання;
- порядок ходів;
- параметри пошуку;
- структурні моделі;
- стратегічні механізми;
- алгоритми навчання;
- дослідницькі процедури.

Першу категорію необхідно захищати формальними інваріантами. Другу — перевіряти через формальні контракти, тести, експерименти та контрольоване порівняння.

Основна теза:

**Автономна еволюція допустима лише за умови збереження формально визначених властивостей шахового ядра.**

# 2. Мета та межі специфікації

FVPA повинен забезпечити:

1. Формальне визначення шахового стану.
2. Формальне визначення допустимих ходів.
3. Перевірку переходів між позиціями.
4. Перевірку коректності структурного представлення.
5. Перевірку узгодженості структурних відношень.
6. Перевірку пошукового алгоритму.
7. Перевірку функції оцінювання.
8. Перевірку навчальних процедур.
9. Перевірку автономної еволюції.
10. Перевірку дослідницьких експериментів.
11. Контроль збереження інваріантів між версіями.

FVPA не повинен доводити, що SUBIT-CHESS завжди обирає найкращий шаховий хід.

Це принципово важливо.

Коректність алгоритму та сила гри — різні властивості.

Можна побудувати математично коректний пошуковий алгоритм, який грає слабко через недосконалу функцію оцінювання.

Так само можна отримати сильні результати на обмеженому наборі позицій, маючи дефекти в окремих правилах або граничних випадках.

Тому:

**FORMAL CORRECTNESS ≠ PLAYING STRENGTH.**

# 3. Архітектура формальної верифікації

Визначимо FVPA:

FVPA = (S, R, T, G, C, V, A)

де:

- S — State Specification;
- R — Rule Specification;
- T — Transition Verification;
- G — Structural Verification;
- C — Search and Computation Verification;
- V — Validation and Evidence;
- A — Autonomous Evolution Assurance.

Архітектура складається з семи рівнів.

## LEVEL 0 — MATHEMATICAL FOUNDATIONS

Формальні типи, множини, функції, відношення та логічні аксіоми.

## LEVEL 1 — CHESS STATE VERIFICATION

Перевірка представлення шахової позиції.

## LEVEL 2 — RULE AND TRANSITION VERIFICATION

Перевірка шахових правил та переходів.

## LEVEL 3 — STRUCTURAL VERIFICATION

Перевірка структурного представлення позиції та його відношень.

## LEVEL 4 — SEARCH VERIFICATION

Перевірка пошукових алгоритмів та їхніх контрактів.

## LEVEL 5 — LEARNING AND RESEARCH VERIFICATION

Перевірка навчальних та експериментальних процедур.

## LEVEL 6 — AUTONOMOUS EVOLUTION ASSURANCE

Перевірка того, що зміни архітектури не порушують обов'язкових властивостей.

Кожен наступний рівень спирається на попередні, але не повинен автоматично вважатися доведеним лише тому, що нижчий рівень перевірено.

# 4. Формальна модель шахового стану

## 4.1. Множини

Нехай:

C = {WHITE, BLACK}

— множина кольорів.

Q = {a1, a2, ..., h8}

— множина 64 шахових полів.

K = {KING, QUEEN, ROOK, BISHOP, KNIGHT, PAWN}

— множина типів фігур.

Piece = C × K × Q

— базовий тип шахової фігури з кольором, типом та полем.

## 4.2. Представлення дошки

Board — часткова функція:

B : Q ⇀ C × K

Вона визначає, яка фігура займає конкретне поле.

Введемо:

Occupied(B) = dom(B)

Empty(B) = Q \ Occupied(B)

## 4.3. Сторона ходу

s ∈ C

Сторона, яка повинна зробити наступний хід.

## 4.4. Право рокіровки

CastlingRights — множина дозволів на рокіровку:

CR ⊆ {
  WHITE_KINGSIDE,
  WHITE_QUEENSIDE,
  BLACK_KINGSIDE,
  BLACK_QUEENSIDE
}

## 4.5. Поле en passant

EP ∈ Option(Q)

Містить поле, на яке може бути здійснено взяття en passant, або відсутнє значення.

## 4.6. Лічильники

halfmove_clock ∈ ℕ

fullmove_number ∈ ℕ⁺

Вони потрібні для обробки відповідних правил завершення гри та коректного запису стану.

## 4.7. Історія

History — послідовність релевантних попередніх станів або їхніх достатніх представлень.

Вона необхідна для перевірки повторення позицій.

Важливо: поточна шахова дошка не завжди містить усю інформацію, потрібну для визначення нічиєї за повторенням.

## 4.8. Повний стан

Визначимо:

P = (B, s, CR, EP, H, N, 𝓗)

де:

- B — дошка;
- s — сторона ходу;
- CR — права рокіровки;
- EP — поле en passant;
- H — лічильник напівходів;
- N — номер повного ходу;
- 𝓗 — історія.

Це базова модель стану для формальної верифікації.

# 5. Інваріанти шахового стану

Визначимо предикат:

ValidPosition(P)

Він повинен включати набір обов'язкових умов.

## 5.1. Унікальність зайнятості

Кожне поле може містити не більше однієї фігури.

Це забезпечується самою моделлю часткової функції B.

## 5.2. Межі дошки

Для кожної фігури:

square(piece) ∈ Q

## 5.3. Королі

У звичайній легальній позиції повинно існувати рівно по одному королю кожного кольору.

CountKing(B, WHITE) = 1

CountKing(B, BLACK) = 1

## 5.4. Неможливість одночасного шаху обом королям

У позиції, яка досягається легальною послідовністю ходів, не повинно бути ситуації, коли королі обох сторін одночасно перебувають під шахом.

Це обмеження стосується досяжних легальних позицій.

Для довільних синтетичних конфігурацій, які не є легальними шаховими позиціями, такі перевірки повинні мати окремий статус.

## 5.5. Пішакова структура

Пішаки не можуть перебувати на першій або восьмій горизонталі у звичайному завершеному стані ходу.

Перетворення пішака повинно виконуватися як частина ходу на останню горизонталь.

## 5.6. Права рокіровки

Право рокіровки не може зберігатися після того, як відповідний король або тура здійснили хід за правилами шахів.

## 5.7. En passant

Поле en passant повинно відповідати попередньому подвійному ходу пішака та відповідній геометрії позиції.

## 5.8. Лічильники

H ≥ 0

N ≥ 1

## 5.9. Історична узгодженість

Історія повинна бути сумісною з поточним станом.

Якщо історія неповна, система повинна явно позначити, що деякі правила повторення або нічиєї не можуть бути повністю перевірені.

# 6. Формальна модель шахового ходу

## 6.1. Хід

Визначимо:

Move = (
  from,
  to,
  promotion,
  special
)

де:

- from — початкове поле;
- to — кінцеве поле;
- promotion — тип перетворення або None;
- special — додаткова інформація про спеціальний хід.

Спеціальні типи:

- NORMAL;
- CAPTURE;
- CASTLING;
- EN_PASSANT;
- PROMOTION.

У реальній реалізації ці типи повинні мати точніші структуровані визначення, щоб уникнути неоднозначностей.

## 6.2. Псевдолегальні ходи

PseudoLegal(P) — множина ходів, які відповідають геометрії руху фігур та локальним умовам, але ще не перевірені на те, чи залишають власного короля під шахом.

## 6.3. Легальні ходи

Legal(P) = {
  m ∈ PseudoLegal(P)
  | KingSafe(ApplyRaw(P,m))
}

Тут ApplyRaw — попереднє застосування кандидата з відповідною перевіркою спеціальних умов.

Це формальне визначення повинно бути уточнене для кожного спеціального ходу.

## 6.4. Перехід

Визначимо:

T : Position × Move ⇀ Position

Це часткова функція переходу.

Вона визначена лише для легальних ходів.

Якщо:

m ∈ Legal(P)

то:

T(P,m) = P'

## 6.5. Обов'язкова властивість

Якщо позиція коректна та хід легальний, результат переходу повинен залишатися коректним:

ValidPosition(P) ∧ m ∈ Legal(P)

⇒ ValidPosition(T(P,m))

Це одна з центральних теорем шахового ядра.

Вона повинна бути доведена або розкладена на менші доведені леми.

# 7. Верифікація спеціальних правил

Кожне спеціальне правило повинно мати окремий набір доказових зобов'язань.

## 7.1. Рокіровка

Потрібно перевірити:

1. Король не здійснював попереднього ходу.
2. Відповідна тура не здійснювала попереднього ходу.
3. Між королем і турою немає фігур.
4. Король не перебуває під шахом.
5. Поля проходження короля не атакуються суперником.
6. Кінцеве поле короля не атаковане.
7. Перехід правильно змінює розташування короля і тури.
8. Права рокіровки оновлюються.

## 7.2. En passant

Потрібно перевірити:

1. Попередній хід був подвійним ходом пішака.
2. Поле en passant визначене правильно.
3. Хід виконується відповідним пішаком.
4. Пішак суперника видаляється з правильного поля.
5. Власний король не залишається під шахом після видалення пішака.
6. Право en passant після переходу скидається або оновлюється відповідно до нового ходу.

Особливо важливо перевіряти випадок, коли взяття en passant відкриває вертикальну або діагональну атаку на власного короля.

## 7.3. Перетворення пішака

Потрібно перевірити:

1. Пішак досягає останньої горизонталі.
2. Вибирається дозволений тип фігури.
3. Новий тип фігури правильно записується в позиції.
4. Пішак більше не існує на цьому полі як пішак.
5. Усі права та лічильники оновлюються.
6. Наступний аналіз використовує новий тип фігури.

## 7.4. Взяття

Потрібно перевірити:

- видалення захопленої фігури;
- оновлення зайнятості поля;
- оновлення лічильника напівходів;
- правильне оновлення історії;
- відсутність некоректних станів після переходу.

# 8. Формальна перевірка термінальних станів

Визначимо:

Terminal(P) ∈ {
  CHECKMATE,
  STALEMATE,
  DRAW,
  NON_TERMINAL
}

## 8.1. Мат

Мат має місце, якщо:

- король сторони ходу перебуває під шахом;
- сторона не має жодного легального ходу.

## 8.2. Пат

Пат має місце, якщо:

- король сторони ходу не перебуває під шахом;
- сторона не має жодного легального ходу.

## 8.3. Нічия

До необхідних механізмів визначення нічиєї належать:

- пат;
- недостатній матеріал для мату;
- повторення позиції відповідно до правил;
- правило 50 ходів;
- інші передбачені правилами випадки.

Правило 75 ходів та п'ятикратне повторення потребують окремої обробки як автоматичні підстави нічиєї відповідно до правил FIDE, з урахуванням передбачених винятків.

Також необхідно відрізняти автоматичну нічию від можливості заявити нічию.

## 8.4. Історична залежність

Terminal(P) не завжди можна визначити лише за B.

Потрібні також:

- сторона ходу;
- права рокіровки;
- поле en passant;
- лічильник напівходів;
- історія позицій.

Це повинно бути враховано у формальному ключі стану та відповідних процедурах.

# 9. Верифікація генератора ходів

Генератор ходів є критичним компонентом.

Якщо він пропускає легальний хід або створює нелегальний, усі наступні рівні можуть працювати на неправильному просторі можливостей.

Визначимо:

G(P) — результат реалізованого генератора ходів.

L(P) — математично визначена множина легальних ходів.

Основна вимога:

G(P) = L(P)

Це означає одночасно:

**Soundness**

Кожен згенерований хід легальний:

G(P) ⊆ L(P)

**Completeness**

Кожен легальний хід згенерований:

L(P) ⊆ G(P)

Разом:

G(P) = L(P)

Це одна з найважливіших цілей формальної верифікації.

## 9.1. Перевірка через незалежну реалізацію

Для додаткової перевірки допускається створити незалежний, простіший еталонний генератор.

Він не повинен використовувати код основного генератора.

Обидві реалізації порівнюються на однакових позиціях.

Це не є використанням стороннього шахового двигуна: обидва компоненти належать SUBIT-CHESS.

## 9.2. Perft

Perft(P,d) визначає кількість вузлів, досяжних за d напівходів із позиції P.

Стандартні контрольні значення для початкової позиції:

- perft(1) = 20;
- perft(2) = 400;
- perft(3) = 8902;
- perft(4) = 197281.

Ці значення можна використовувати як контрольні математичні результати.

Perft перевіряє генерацію та застосування ходів, але не оцінює шахову силу двигуна.

Він також не замінює формального доказу коректності.

# 10. Верифікація структурного аналізу

SUBIT-CHESS не обмежується класичним представленням дошки.

Він створює структурну модель позиції.

Нехай:

Ω(P) = (F, R, A, D, M, K, T)

де:

- F — фігури;
- R — структурні відношення;
- A — атаки;
- D — захист;
- M — мобільність;
- K — критичні властивості;
- T — тактичні та стратегічні можливості.

FVPA повинен перевіряти, що структурне представлення не суперечить первинному шаховому стану.

## 10.1. Відповідність фігур

Кожна фігура структурного представлення повинна відповідати фігурі на дошці.

PieceSet(Ω(P)) = PieceSet(P)

## 10.2. Відповідність полів

Кожне поле, приписане фігурі у структурній моделі, повинно відповідати її фактичному розташуванню.

## 10.3. Відповідність геометричних атак

Якщо структурна модель позначає геометричну атаку, вона повинна відповідати геометрії фігури та стану перешкод на дошці.

При цьому необхідно розрізняти:

- геометричну атаку;
- псевдолегальну можливість;
- легальний хід;
- фактичну загрозу.

Це різні поняття.

Наприклад, фігура може геометрично атакувати поле, але не мати права здійснити відповідний хід через відкриття шаху власному королю.

## 10.4. Відповідність структурних відношень

Для кожного відношення SRA повинна бути визначена семантика.

Наприклад:

ATTACK_GEOM — геометрична атака.

DEFEND — захист власної фігури.

BLOCK — блокування лінії або доступу.

PIN — зв'язування фігури відносно важливішого об'єкта.

SUPPORT — підтримка фігури іншою фігурою відповідно до визначеної семантики.

Не можна вважати ці відношення взаємозамінними.

## 10.5. Типова коректність

Кожне відношення повинно з'єднувати об'єкти дозволених типів.

Наприклад, відношення між фігурою та полем не повинно випадково трактуватися як відношення між двома фігурами.

## 10.6. Походження

Кожне структурне твердження повинно мати provenance:

- джерело;
- алгоритм виведення;
- версію;
- позицію;
- рівень достовірності;
- статус.

Структурна інтерпретація не повинна видаватися за безпосередній факт шахової дошки.

# 11. Інкрементальне оновлення структури

SUBIT-CHESS повинен мати можливість оновлювати структурне представлення після ходу без повної перебудови.

Позначимо:

Build(P) — повна побудова структури.

Update(Ω(P),m) — інкрементальне оновлення після ходу m.

Основна властивість:

Build(T(P,m)) ≡ Update(Build(P),m)

Це означає, що повна перебудова та інкрементальне оновлення повинні давати еквівалентний структурний результат.

## 11.1. Що потрібно порівнювати

- набір фігур;
- зайнятість полів;
- геометричні атаки;
- захист;
- мобільність;
- структурні залежності;
- тактичні відношення;
- контекстні характеристики.

## 11.2. Допустимі відмінності

Якщо система використовує наближені або контекстні оцінки, їх не можна вимагати побітово ідентичними без спеціальної причини.

Для таких компонентів повинні бути визначені:

- межі похибки;
- допустимий діапазон;
- стабільність;
- умови еквівалентності.

Точні факти та евристичні оцінки перевіряються окремо.

# 12. Верифікація структурної динаміки

Для переходу:

Pₜ → Pₜ₊₁

визначимо:

Ωₜ → Ωₜ₊₁

Структурна динаміка повинна описувати:

- CREATED;
- PRESERVED;
- REMOVED;
- TRANSFORMED.

Для кожної зміни повинно бути встановлено походження.

Наприклад, якщо тура втрачає доступ до вертикалі через переміщення пішака, система повинна визначити, що зміна виникла внаслідок конкретного переходу.

## 12.1. Temporal Consistency

Структурні зміни повинні відповідати реальному переходу:

ΔΩ(P,m) = Ω(T(P,m)) − Ω(P)

Тут віднімання є концептуальним позначенням різниці структур, а не обов'язково числовою операцією.

## 12.2. Відсутність хибних причин

Система не повинна стверджувати, що відношення було зруйноване ходом, якщо воно фактично залишилося незмінним.

## 12.3. Контрфактичні операції

Видалення фігури для аналізу її внеску — це аналітична операція.

Вона не повинна трактуватися як легальний шаховий хід.

Це розмежування має бути закріплене на рівні типів операцій.

# 13. Верифікація функції оцінювання

Позначимо:

E(P,s;θ)

— функцію оцінювання позиції.

Вона повинна мати визначений контракт.

## 13.1. Типова коректність

Вхід:

- коректна позиція;
- сторона перспективи;
- валідний набір параметрів.

Вихід:

- числове значення;
- статус оцінки;
- за потреби — невизначеність;
- походження компонентів оцінки.

## 13.2. Color Symmetry

Якщо позиція повністю відображена зі зміною кольорів, сторін та відповідних шахових координат, оцінка повинна змінити знак.

Позначимо ColorSwap(P) — симетрично відображену позицію.

Тоді для оцінки в абсолютній перспективі:

E(ColorSwap(P), WHITE;θ) = −E(P, BLACK;θ)

Це вимагає відповідного перетворення всіх компонентів позиції.

## 13.3. Terminal Exactness

Мат, пат та інші термінальні стани повинні оброблятися відповідно до правил.

Евристична функція не може скасувати результат мату.

## 13.4. Bounded Evaluation

Оцінка повинна мати контрольовані числові межі.

Це необхідно для:

- стабільності пошуку;
- уникнення переповнення;
- коректної роботи alpha-beta;
- правильного розмежування матових та нематових оцінок.

## 13.5. No Double Counting

Одна й та сама структурна властивість не повинна неконтрольовано враховуватися декілька разів.

Наприклад, активність фігури, контроль поля та просторовий вплив можуть частково описувати той самий феномен.

AREE повинен досліджувати такі залежності.

## 13.6. Розділення оцінки та невизначеності

Оцінка позиції та впевненість у ній — різні величини.

Позначимо:

V(P) — оцінка.

U(P) — невизначеність.

Не можна автоматично трактувати високу невизначеність як низьку цінність позиції.

Невизначеність може вимагати додаткового пошуку, але сама по собі не повинна змінювати знак оцінки.

# 14. Верифікація пошукового алгоритму

SUBIT-SEARCH повинен зберігати математично визначену поведінку.

Для нульової суми шахової гри використовується рекурсивна модель:

V(P,d) = maxₘ [−V(T(P,m),d−1)]

де:

m ∈ Legal(P)

Базовий випадок:

V(P,0) = E(P,s)

Для термінальних позицій застосовується точний результат.

## 14.1. Повнота множини ходів

Пошуковий алгоритм не повинен непомітно вилучати легальні ходи з повного дерева пошуку.

Якщо використовується селективний пошук, він повинен мати окремий статус і контрольовані умови.

## 14.2. Alpha-Beta

Alpha-beta повинен повертати те саме значення, що й відповідний повний minimax, за однакової глибини та однакової функції оцінювання.

Це стосується коректної реалізації вікон та граничних умов.

## 14.3. Transposition Table

Таблиця транспозицій повинна враховувати всі параметри, що впливають на результат.

Ключ позиції повинен відображати:

- дошку;
- сторону ходу;
- права рокіровки;
- поле en passant відповідно до обраної семантики;
- релевантну інформацію про історію для правил нічиєї.

Не можна використовувати ключ, який об'єднує стани з різними правами або різними наслідками історії.

## 14.4. Типи записів

Записи TT:

- EXACT;
- LOWERBOUND;
- UPPERBOUND.

Їхня інтерпретація повинна відповідати правилам alpha-beta.

## 14.5. Quiescence Search

У стані шаху алгоритм не має права застосовувати звичайну stand-pat оцінку так, ніби сторона може пропустити відповідь.

Якщо король під шахом, потрібно розглядати всі легальні відповіді.

Це окрема критична властивість.

## 14.6. Selective Search

Null-move pruning, LMR, futility pruning та інші вибіркові методи можуть впливати на результат.

Тому вони не повинні вважатися еквівалентними повному minimax без окремого доказу або обґрунтованої оцінки похибки.

Null move не є легальним шаховим ходом.

Його використання — внутрішній обчислювальний прийом.

# 15. Верифікація стратегічного планування

Стратегічний план SUBIT-CHESS:

Π(P) = (G,O,A,C,R,H,U)

де:

- G — ціль;
- O — бажаний структурний результат;
- A — можливі дії;
- C — умови;
- R — ризики;
- H — горизонт;
- U — невизначеність.

FVPA повинен гарантувати, що планувальник не отримує повноважень змінювати правила шахів або вилучати легальні ходи.

## 15.1. План не є ходом

Стратегічна ціль не повинна безпосередньо трактуватися як легальний хід.

Вона лише впливає на генерацію кандидатів, порядок розгляду або розподіл обчислювального бюджету.

## 15.2. Tactical Override

Якщо пошук виявляє форсовану тактичну необхідність, стратегічний план не повинен її ігнорувати.

## 15.3. Feasibility

Кожна стратегічна ціль повинна мати статус:

- FEASIBLE;
- INFEASIBLE;
- UNKNOWN.

Невідоме не повинно автоматично перетворюватися на можливе.

## 15.4. Plan Consistency

План повинен бути сумісним із:

- поточною позицією;
- легальними ходами;
- структурними відношеннями;
- тактичними обмеженнями;
- ресурсами пошуку.

# 16. Верифікація навчання

Навчальний механізм може змінювати параметри, але не повинен змінювати шахові правила.

Позначимо:

θₜ — параметри поточної версії.

LearningUpdate(θₜ, D) = θₜ₊₁

## 16.1. Bounded Parameters

Для кожного параметра повинні існувати допустимі межі.

θᵢ ∈ [θᵢ_min, θᵢ_max]

## 16.2. Immutable Rules

Навчальний процес не має права змінювати:

- геометрію руху фігур;
- умови легальності;
- правила шаху;
- правила мату;
- правила спеціальних ходів;
- правила завершення партії.

## 16.3. Snapshot Isolation

Під час активного пошуку параметри повинні залишатися незмінними.

Оновлення застосовується лише до нової версії конфігурації.

## 16.4. Training–Validation Separation

Навчальні та валідаційні позиції повинні бути розділені.

Якщо позиції використовуються для налаштування параметрів, вони не можуть одночасно вважатися незалежним доказом узагальнення.

## 16.5. No Self-Confirmation

Власна оцінка двигуна не є незалежною істиною.

Навчальні сигнали, отримані з власного пошуку, повинні мати окрему категорію походження.

## 16.6. Reproducibility

Для кожного оновлення необхідно зберігати:

- початкові параметри;
- кінцеві параметри;
- дані;
- версію алгоритму;
- seed;
- умови;
- результати;
- рішення про прийняття.

# 17. Верифікація AREE

Автономний дослідницький механізм повинен бути перевірений окремо від шахового пошуку.

## 17.1. Гіпотеза

Кожна гіпотеза повинна мати:

- визначене твердження;
- область застосування;
- умови перевірки;
- умови спростування;
- альтернативні пояснення.

## 17.2. Експеримент

Експеримент повинен мати:

- baseline;
- candidate;
- контрольні умови;
- визначені метрики;
- обчислювальний бюджет;
- процедуру повторення.

## 17.3. Результат

Результат повинен мати:

- походження;
- невизначеність;
- обмеження;
- статус.

## 17.4. Незалежність перевірки

AREE не повинен бути єдиним компонентом, який визначає правильність власного експерименту.

Критичні експерименти повинні перевірятися окремим механізмом, який не залежить від того самого алгоритму прийняття рішення.

# 18. Верифікація автономної еволюції

ADE відповідає за створення та прийняття нових версій.

FVPA встановлює обмеження для цього процесу.

## 18.1. Candidate Isolation

Кандидатна версія не повинна змінювати активну стабільну версію до завершення перевірки.

## 18.2. Immutable Baseline

Базова версія повинна зберігатися для відтворення порівняння.

## 18.3. Mandatory Verification

Кожна зміна проходить відповідний набір перевірок.

Масштаб перевірки залежить від типу зміни.

Наприклад:

- зміна ваги оцінювання не потребує повторного доведення геометрії шахових ходів;
- зміна генератора ходів вимагає повної перевірки коректності генерації;
- зміна структури позиції вимагає повторної перевірки залежних компонентів.

## 18.4. Dependency Graph

Введемо граф залежностей:

DG = (V,E)

Кожен вузол — компонент системи.

Ребро A → B означає, що B залежить від властивостей A.

Якщо змінюється A, система повинна визначити, які перевірки для B необхідно повторити.

## 18.5. Rollback

Якщо нова версія порушує обов'язковий інваріант, вона не може бути прийнята.

Попередня стабільна версія повинна залишатися доступною.

## 18.6. Заборона автоматичного злиття

Формальна специфікація не надає двигуну дозволу самостійно змінювати віддалений репозиторій, створювати коміти або зливати pull request.

Такі дії залишаються окремими операціями з відповідним дозволом користувача.

# 19. Класи доказів

FVPA повинен розрізняти рівні підтвердження.

## LEVEL P0 — SPECIFICATION

Властивість визначена формально.

## LEVEL P1 — TESTED

Властивість перевірена тестами.

## LEVEL P2 — PROPERTY TESTED

Властивість перевірена набором генеративних або метаморфних тестів.

## LEVEL P3 — PROOF ASSISTANT CHECKED

Формальний доказ перевірений ядром proof assistant.

## LEVEL P4 — REFINED IMPLEMENTATION

Доведено відповідність конкретної реалізації формальній моделі в межах визначених припущень.

## LEVEL P5 — SYSTEM ASSURANCE

Перевірено інтеграцію компонентів, межі довіри, конфігурацію та критичні властивості всієї системи.

Ці рівні не є взаємозамінними.

Наприклад, P3 не означає автоматично P4.

Доведення математичної моделі не доводить, що конкретний JavaScript або Rust-код реалізує цю модель.

# 21. Основні цільові теореми

Нижче наведено перелік пріоритетних доказових цілей.

## FV-001 — Board Domain

Усі зайняті поля належать множині 64 полів.

## FV-002 — King Uniqueness

У валідній досяжній позиції існує рівно один король кожного кольору.

## FV-003 — Legal Move Soundness

Кожний хід, повернений генератором, є легальним.

## FV-004 — Legal Move Completeness

Кожний легальний хід присутній у результаті генератора.

## FV-005 — Transition Preservation

Легальний хід із валідної позиції породжує валідну позицію.

## FV-006 — Side Alternation

Після звичайного завершеного ходу сторона ходу змінюється.

## FV-007 — Castling Correctness

Рокіровка відповідає всім необхідним умовам.

## FV-008 — En Passant Correctness

Взяття en passant відповідає історії та геометрії.

## FV-009 — Promotion Correctness

Перетворення пішака формує правильний тип фігури.

## FV-014 — Relation Type Safety

Структурні відношення використовують допустимі типи об'єктів.

## FV-015 — Structural Update Equivalence

Інкрементальне оновлення еквівалентне повній перебудові.

## FV-016 — Evaluation Color Symmetry

## FV-017 — Terminal Evaluation Priority

## FV-020 — Quiescence Check Safety

Quiescence search не використовує stand-pat у позиції шаху.

## FV-021 — Transposition Key Adequacy

Ключ таблиці транспозицій не об'єднує стани, які мають різні релевантні наслідки.

Навчальні параметри залишаються в допустимих межах.

## FV-023 — Rule Immutability

Навчання не змінює правила шахів.

Активний пошук використовує незмінний знімок конфігурації.

Кожний експеримент має відтворюване походження.

## FV-028 — Dependency-Aware Verification

Зміна компонента запускає перевірки залежних компонентів.

# 22. Метаморфне тестування

Не всі властивості легко перевірити через відомі очікувані результати.

Для таких випадків використовуються метаморфні тести.

## 22.1. Color Swap

Якщо позицію симетрично відобразити та поміняти кольори, структура легальних ходів повинна відповідно відобразитися.

## 22.2. Move Reversal

Для оборотного ходу в позиції без спеціальних історичних змін можна перевірити відповідність відновленої дошки.

Однак це не означає, що будь-який шаховий хід можна формально скасувати без урахування прав рокіровки, en passant та історії.

## 22.3. Independent Rebuild

Після кожного тестового переходу:

- інкрементально оновити структуру;
- повністю перебудувати структуру;
- порівняти результати.

## 22.4. Deterministic Replay

Однаковий стан, конфігурація та seed повинні давати відтворюваний результат там, де алгоритм заявлений як детермінований.

Якщо використовується стохастичний компонент, його випадковість повинна бути контрольованою та задокументованою.

## 22.5. Search Budget Monotonicity

Не можна безумовно вимагати, щоб збільшення глибини пошуку завжди покращувало оцінку або силу гри.

Однак для повного minimax із фіксованою функцією оцінювання можна формально досліджувати властивості значень на визначеній моделі.

Для реального пошукового двигуна з обрізаннями та евристиками це окреме питання.

# 23. Довіра до обчислювального середовища

Формальна верифікація програмного компонента не означає автоматичної довіри до всього середовища.

Необхідно розрізняти:

- математичне визначення;
- proof assistant kernel;
- компілятор;
- runtime;
- операційну систему;
- апаратне забезпечення;
- зовнішні залежності.

Для SUBIT-CHESS бажано мінімізувати критичну довірену базу.

Особливо важливо:

1. Не вводити сторонні шахові бібліотеки.
2. Не використовувати зовнішні двигуни.
3. Не використовувати зовнішні шахові оцінки як еталон.
4. Не приховувати критичні залежності.
5. Зберігати відтворюваність збірки.
6. Перевіряти відповідність між специфікацією та реалізацією.

Lean може перевірити математичний доказ, але сам факт використання Lean не доводить коректність усієї програми.

# 26. Принципи формальної дисципліни

Для запобігання хибним твердженням у документації та звітах вводяться такі статуси:

**SPECIFIED**

Властивість формально визначена.

**IMPLEMENTED**

Властивість реалізована в коді.

**TESTED**

Властивість перевірена тестами.

**PROVED**

Для властивості існує перевірений формальний доказ.

**REFINED**

Доведено відповідність реалізації формальній моделі в межах визначених припущень.

**UNVERIFIED**

Перевірка ще не виконана.

Ці статуси не можна використовувати як синоніми.

Наприклад, наявність функції в коді не означає, що її коректність доведена.

Наявність тестів не означає повноти перевірки.

Наявність математичного доказу не означає автоматичної коректності програмної реалізації.

# 27. Наукові гіпотези

**H-FVPA-01 — Formal Core Stability**

Формальна специфікація незмінного шахового ядра може зменшити ризик регресій під час автономної еволюції.

**H-FVPA-02 — Structural Consistency**

Формальна перевірка структурного представлення може зменшити кількість помилок, які виникають через некоректну інтерпретацію позиції.

**H-FVPA-03 — Incremental Equivalence**

Еквівалентність інкрементального оновлення та повної перебудови може забезпечити надійнішу оптимізацію структурного аналізу.

**H-FVPA-04 — Proof-Guided Evolution**

Використання формальних контрактів може дозволити змінювати евристичні компоненти без порушення базових властивостей двигуна.

**H-FVPA-05 — Layered Assurance**

Розділення формальних доказів, тестування та емпіричної оцінки може підвищити достовірність висновків про якість системи.

Це дослідницькі гіпотези. Їхня практична ефективність має бути перевірена.

# 28. Обмеження

FVPA не гарантує шахової непереможності.

Формальний доказ коректності генератора ходів не доводить сили оцінювання.

Формальний доказ alpha-beta не доводить, що обмежена глибина пошуку достатня для конкретної позиції.

Формальна узгодженість структурної моделі не гарантує, що її евристична інтерпретація стратегічно корисна.

Доведення окремих компонентів не гарантує автоматично коректності інтегрованої системи.

Тому загальна гарантія повинна бути обмежена конкретними властивостями, припущеннями та версіями компонентів.

# 30. Заключний принцип

SUBIT-CHESS повинен розвиватися як система, яка не тільки здатна змінювати власні алгоритми, а й має формально визначені межі допустимих змін.

У цьому контексті формальна верифікація виконує роль не зовнішнього обмежувача інтелекту, а внутрішнього механізму збереження цілісності.

Шахові правила визначають простір допустимих переходів.

Структурний аналіз визначає відношення всередині позиції.

Пошук досліджує наслідки можливих переходів.

Навчання змінює параметри інтерпретації.

AREE визначає, які гіпотези необхідно перевірити.

ADE керує розвитком системи.

FVPA перевіряє, чи зберігаються обов'язкові властивості на всіх цих рівнях.

Фінальна формула:

**SPECIFICATION → IMPLEMENTATION → PROOF → EXPERIMENT → EVIDENCE → EVOLUTION → ASSURANCE.**

Автономність не означає відсутності обмежень.

Навпаки: чим більш автономною стає система, тим важливішими є чіткі, формально визначені та відтворювані умови її власної коректності.
