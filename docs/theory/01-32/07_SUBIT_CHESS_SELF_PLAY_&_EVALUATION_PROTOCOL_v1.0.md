# SUBIT-CHESS SELF-PLAY & EVALUATION PROTOCOL v1.0

## Протокол автономної самогри, порівняння версій та оцінювання шахової сили

**Статус:** концептуальна технічна специфікація  
**Версія:** 1.0  
**Система:** SUBIT-CHESS  
**Залежності:** SPVT, SRA, SUBIT-SEARCH, SUBIT-CHESS LEARNING ARCHITECTURE v1.0  
**Принцип:** DO NOT COLLAPSE — CONTEXTUALIZE

# 1. Анотація

Цей документ визначає протокол автономного тестування та вдосконалення SUBIT-CHESS через власну шахову практику.

Основне завдання — створити відтворювану систему, яка дозволяє:

- генерувати внутрішні шахові партії;
- порівнювати різні версії двигуна;
- перевіряти вплив окремих алгоритмічних компонентів;
- виявляти регресії;
- оцінювати стабільність результатів;
- визначати, чи покращила нова версія якість гри;
- не допускати хибного самопідтвердження.

Протокол не передбачає використання сторонніх шахових рушіїв, зовнішніх партій, імпортованих шахових баз або зовнішніх оцінок позицій.

Він спирається на три джерела внутрішніх доказів:

1. Точну коректність шахових правил.
2. Відтворювані результати контрольованої самогри.
3. Незалежно сформовані контрольні позиції та тести.

Важливе обмеження: результати самогри дозволяють порівнювати конфігурації двигуна, але не встановлюють його абсолютну шахову силу.

# 2. Мета та межі протоколу

## 2.1. Основна мета

Визначити, чи є нова конфігурація SUBIT-CHESS кращою за попередню за однакових умов.

Позначимо:

- C — чинна версія, Champion;
- N — нова версія, Challenger.

Потрібно оцінити:

`ΔS = S(N) − S(C)`

де S — показник результативності.

Але ця різниця має сенс лише за контрольованих умов.

Якщо N отримує більше часу, більшу глибину пошуку або інші початкові позиції, безпосереднє порівняння стає некоректним.

## 2.2. Що протокол не доводить

Протокол не може самостійно довести:

- що двигун грає на рівні конкретного шахового рейтингу;
- що його оцінювання відповідає об'єктивній теорії шахів;
- що обрана стратегія є оптимальною;
- що нова версія сильніша за всі можливі альтернативи;
- що перемога в самогрі означає правильність усіх її рішень.

Він дозволяє отримувати обмежені, але відтворювані свідчення про відносну ефективність конфігурацій.

# 3. Одиниця оцінювання

Основною одиницею оцінювання є не окремий хід і не окрема позиція, а контрольований матч.

## 3.1. Матч

Матч складається з однієї або декількох партій між двома конфігураціями.

`Match = (C, N, P₀, K, R)`

де:

- C — Champion;
- N — Challenger;
- P₀ — початкова позиція;
- K — набір контрольованих умов;
- R — результат.

## 3.2. Парний матч

Для зменшення впливу кольору використовуються дві партії:

**Партія A:**

- Champion — білі;
- Challenger — чорні.

**Партія B:**

- Challenger — білі;
- Champion — чорні.

Обидві партії починаються з однакової позиції.

Такий матч утворює парну одиницю порівняння.

## 3.3. Серія матчів

Оцінювання не повинно залежати від однієї позиції.

Тому формується набір:

`M = {m₁, m₂, ..., mₙ}`

Позиції можуть бути розподілені за структурними категоріями:

- початкові;
- відкриті;
- закриті;
- тактичні;
- позиційні;
- матеріально нерівні;
- ендшпільні;
- позиції з високою королівською напругою;
- позиції з обмеженою мобільністю.

Це дозволяє оцінювати не лише загальний результат, але й поведінку двигуна в різних контекстах.

# 4. Генератор контрольних позицій

## 4.1. Принцип

Контрольні позиції повинні створюватися власним генератором SUBIT-CHESS.

Вони не імпортуються з шахових баз.

Основний спосіб генерації:

`P₀ → m₁ → P₁ → m₂ → P₂ → ... → Pₙ`

Тобто позиція формується через послідовність легальних ходів від коректного початкового стану.

## 4.2. Профілі генерації

Потрібно реалізувати кілька профілів.

### PROFILE-OPENING

Позиції з ранньої фази партії.

Досліджувані характеристики:

- розвиток фігур;
- контроль центру;
- безпека короля;
- мобільність;
- зв'язність;
- просторові обмеження.

### PROFILE-MIDDLEGAME

Позиції середини гри.

Характеристики:

- тактична напруга;
- атаки;
- захист;
- структурна стійкість;
- контроль критичних полів;
- взаємодія фігур.

### PROFILE-ENDGAME

Позиції завершальної фази.

Характеристики:

- активність короля;
- прохідні пішаки;
- матеріальна перевага;
- обмеження мобільності;
- перетворення пішаків;
- координація фігур.

### PROFILE-TACTICAL

Позиції з тактичними можливостями.

Генератор повинен створювати ситуації, у яких можливі:

- шахи;
- взяття;
- зв'язування;
- подвійні напади;
- відкриті атаки;
- відволікання;
- матові загрози.

### PROFILE-STRUCTURAL

Позиції з вираженими структурними характеристиками:

- ізольовані пішаки;
- здвоєні пішаки;
- пішакові ланцюги;
- слабкі поля;
- відкриті лінії;
- обмежені фігури;
- просторові переваги.

Ці категорії описують генераційні цілі, а не наперед визначають оцінку позиції.

## 4.3. Контроль легальності

Кожна позиція повинна проходити перевірку:

`ValidatePosition(P) = TRUE`

Перевірка включає:

- наявність рівно одного короля кожного кольору;
- коректність розташування фігур;
- відсутність неможливих станів;
- відповідність прав на рокіровку;
- коректність en passant;
- допустимість сторони, що ходить;
- можливість походження позиції через легальні ходи.

Окремо потрібно перевіряти, що генератор не створює позиції, які формально мають правильне розташування фігур, але не можуть виникнути в легальній партії.

# 5. Формування контрольних наборів

Для уникнення витоку даних необхідно розділити три множини.

## 5.1. Training Set

`D_train`

Використовується для:

- самонавчання;
- оптимізації параметрів;
- аналізу помилок;
- налаштування контексту;
- корекції функції оцінювання.

## 5.2. Validation Set

`D_val`

Використовується для:

- порівняння Champion і Challenger;
- відбору кандидатів;
- перевірки результатів оптимізації.

Цей набір не повинен безпосередньо використовуватися для корекції параметрів.

## 5.3. Regression Set

`D_reg`

Незмінний набір позицій і тестових випадків.

Використовується для перевірки:

- правил шахів;
- генерації ходів;
- спеціальних ходів;
- пошукових інваріантів;
- стабільності оцінювання;
- відсутності програмних регресій.

Цей набір не є навчальним матеріалом.

## 5.4. Захист від витоку

Якщо позиція з D_val використовується для оптимізації параметрів, вона повинна бути вилучена з поточного контрольного набору.

Не можна нескінченно використовувати один і той самий набір для вибору параметрів, а потім називати його незалежною перевіркою.

Потрібна періодична ротація контрольних наборів.

---

# 6. Стандартизація умов матчу

Кожне порівняння повинно використовувати однакові обмеження.

## 6.1. Часовий бюджет

Можливі режими:

- однаковий час на хід;
- однаковий загальний час на партію;
- однаковий бюджет обчислювальних вузлів.

Для первинного тестування рекомендовано фіксований бюджет вузлів.

Це дозволяє краще відокремити якість пошуку від швидкості виконання.

Окремо потрібно проводити тести з однаковим часовим бюджетом, оскільки швидкість двигуна також має практичне значення.

## 6.2. Глибина пошуку

Якщо використовується фіксована глибина, вона повинна бути однаковою для обох версій.

Якщо використовується адаптивний пошук, потрібно фіксувати його правила та максимальний бюджет.

## 6.3. Апаратні умови

Для порівняння швидкодії повинні бути однаковими:

- процесор;
- кількість потоків;
- доступна пам'ять;
- умови виконання;
- обмеження CPU;
- режим оптимізації;
- середовище виконання.

## 6.4. Відтворюваність

Кожен матч повинен мати ідентифікатор і запис умов.

`MatchConfig = (Seed, Position, Budget, Threads, VersionA, VersionB)`

Якщо конфігурація не може бути відтворена, результат не повинен використовуватися як надійний доказ покращення.

# 7. Алгоритм Champion–Challenger

## 7.1. Ініціалізація

Зберігаються:

`Champion = C₀`

`Challenger = N₀`

Champion є останньою прийнятою конфігурацією.

Challenger містить одну або декілька змін.

## 7.2. Проведення матчів

Для кожної позиції:

1. Запустити Champion білими.
2. Запустити Challenger чорними.
3. Зафіксувати результат.
4. Поміняти кольори.
5. Повторити матч.
6. Зберегти обидва результати.

## 7.3. Розрахунок результату

Визначимо:

- W — перемоги Challenger;
- D — нічиї Challenger;
- L — поразки Challenger.

Тоді:

`Score_N = (W + 0.5D) / (W + D + L)`

Для Champion:

`Score_C = 1 − Score_N`

Якщо результати зібрані в парних матчах, потрібно також зберігати результат кожної пари окремо.

## 7.4. Рішення

Кандидат може бути:

- прийнятий;
- відхилений;
- залишений на додаткову перевірку.

Необхідно уникати бінарного рішення на основі недостатньої кількості партій.

---

# 8. Статистичне оцінювання

## 8.1. Чому кількості перемог недостатньо

У шахах велика кількість нічиїх може приховувати відмінності між двигунами.

Наприклад, дві конфігурації можуть мати однаковий відсоток очок, але різну поведінку:

- одна грає стабільно;
- інша часто виграє або програє;
- одна краще грає в ендшпілі;
- інша краще реалізує тактичні переваги.

Тому потрібно зберігати розподіл результатів, а не лише сумарний бал.

## 8.2. Парні результати

Нехай результат кожної пари:

`xᵢ ∈ {0, 0.5, 1}`

де значення визначається результатом двох партій із перестановкою кольорів.

Середній результат:

`μ = (Σxᵢ) / n`

Розкид результатів:

`σ² = Σ(xᵢ − μ)² / (n − 1)`

Це дає змогу оцінити середню ефективність і варіативність.

## 8.3. Довірчі інтервали

Оцінка повинна супроводжуватися довірчим інтервалом.

Якщо інтервал надто широкий, результат є невизначеним.

Для частки очок можна використовувати інтервали, що враховують обмежений діапазон показника та невелику вибірку.

Оскільки результати партій можуть бути залежними, особливо коли вони походять з одних і тих самих початкових позицій, простий аналіз усіх партій як незалежних спостережень може завищувати впевненість.

Тому для парного протоколу доцільно аналізувати саме пари як одиниці порівняння.

## 8.4. Послідовне тестування

Не можна запускати матчі та зупиняти їх у момент, коли результат випадково став сприятливим.

Потрібно заздалегідь визначити:

- мінімальну кількість пар;
- максимальну кількість пар;
- критерій статистичної достатності;
- правило дострокового завершення;
- критерій прийняття.

Інакше виникає ризик статистичного самонавіювання.

# 9. Оцінювання за контекстами

Загальний результат не повинен приховувати локальні слабкості.

SUBIT-CHESS повинен оцінювати поведінку в різних контекстах.

## 9.1. Контекстна модель

Використовується:

`C = I × Z × Φ`

де:

`I = {QUIET, DEFENCE, ATTACK, PRESSURE}`

`Z = {GLOBAL, QUEENSIDE, KING, CENTER}`

`Φ = {OPENING, MIDDLEGAME, ENDGAME, TRANSITION}`

Отримуємо 64 комбінації.

Ця модель є шаховою прикладною системою контекстів і не замінює канонічні координати SUBIT ISA.

## 9.2. Контекстні результати

Для кожного контексту можна визначати:

- частоту перемог;
- частоту нічиїх;
- частоту поразок;
- середню кількість вузлів;
- середню глибину;
- частоту тактичних помилок;
- стабільність оцінки;
- зміну структурної якості.

## 9.3. Важливе застереження

Контексти можуть перекриватися.

Одна позиція може одночасно мати:

- атакувальну функцію;
- контроль центру;
- ознаки мітельшпілю;
- захисну необхідність.

Тому не потрібно примусово призначати кожну позицію лише одному контексту.

Контекстні метрики можуть бути багатозначними та мати різну інтенсивність.

## 9.4. Виявлення слабких зон

Якщо Challenger загалом покращив результат, але значно погіршив гру в певному контексті, це потрібно відобразити у звіті.

Загальний бал не повинен приховувати структурні регресії.

---

# 10. Тактична перевірка

Результат партії не завжди дозволяє встановити причину успіху або невдачі.

Тому необхідний окремий набір тактичних тестів.

## 10.1. Власні тактичні задачі

SUBIT-CHESS повинен створювати тестові ситуації алгоритмічно.

Наприклад:

- мат в один хід;
- мат у два ходи;
- захист від неминучого мату;
- виявлення незахищеної фігури;
- пошук виграшу матеріалу;
- виявлення вилки;
- пошук зв'язування;
- уникнення тактичної пастки.

## 10.2. Перевірка відповіді

У випадках, де існує точно відомий тактичний факт, можна перевіряти його безпосередньо.

Наприклад, якщо генератор створив позицію з легальним матом в один хід, тест повинен перевірити, чи здатний двигун знайти принаймні один такий хід.

Не потрібно вимагати конкретного ходу, якщо існує декілька еквівалентних матових рішень.

## 10.3. Відмінність між тактикою та оцінкою

Виявлення мату — точна задача.

Вибір між двома позиційними ходами — евристична задача.

Протокол повинен зберігати цю відмінність.

---

# 11. Аналіз якості окремого ходу

Для поглибленого аналізу можна використовувати внутрішню діагностику.

Нехай:

`P' = T(P,m)`

Після виконання ходу система зберігає:

- зміну матеріалу;
- створені та втрачені відносини;
- зміну мобільності;
- зміну безпеки короля;
- тактичні наслідки;
- зміну контексту;
- пошукову стабільність.

Структурна зміна:

`ΔΩ(P,m) = Ω(P') − Ω(P)`

Це не арифметичне віднімання довільних об'єктів, а узагальнене представлення змін структурних компонентів.

## 11.1. Діагностичні категорії

Хід можна позначити як:

- тактично спростований;
- матеріально невигідний;
- структурно ризикований;
- позиційно обґрунтований;
- невизначений;
- підтверджений подальшим аналізом.

Ці категорії не повинні автоматично вважатися об'єктивними оцінками якості.

Вони є результатами внутрішньої діагностики.

## 11.2. Причинний аналіз

Якщо після певного ходу партія завершилася поразкою, не можна автоматично вважати цей хід причиною поразки.

Потрібно аналізувати всю послідовність:

`P₀ → m₁ → P₁ → m₂ → ... → Pₙ`

Причинна відповідальність може бути розподілена між кількома рішеннями.

# 12. Тестування структурних компонентів

## 12.1. Базова конфігурація

`A = Material + Mobility + Basic Search`

## 12.2. Структурна конфігурація

`B = A + SRA`

## 12.3. Контекстуальна конфігурація

## 12.4. Динамічна конфігурація

## 12.5. Повна конфігурація

3. Чи покращує окремі контексти?

5. Чи зберігає стабільність?

# 13. Контроль самопідтвердження

Цей розділ встановлює захист від циклічного навчання.

## 13.1. Проблема

Двигун може створити навчальну систему, яка винагороджує саме ті рішення, які відповідають його поточним упередженням.

У результаті система може стати більш послідовною, але не сильнішою.

## 13.2. Протидія

Потрібно використовувати:

- різні конфігурації двигуна;
- різні глибини пошуку;
- окремі генератори позицій;
- незалежні seeds;
- парні матчі;
- фіксовані регресійні тести;
- контрольні позиції, що не використовувалися під час навчання;
- аналіз окремих компонентів;
- порівняння з незмінною базовою версією.

## 13.3. Незалежність без зовнішнього вчителя

Незалежність у цьому протоколі означає незалежність процедур генерації та оцінювання від конкретного навчального процесу.

Вона не означає наявності зовнішнього абсолютного критерію шахової істини.

Це принципове обмеження автономної системи.

# 16. Архітектурний цикл

Повний цикл розвитку:

`GENERATE → PLAY → RECORD → ANALYZE → LEARN → CHALLENGE → VALIDATE → ACCEPT`

У більш формальному вигляді:

`Dₜ = Generate(θₜ, Gₜ)`

`θ' = Optimize(θₜ, Dₜ)`

`R = Evaluate(θ', θₜ, D_val)`

`θₜ₊₁ = Select(θₜ, θ', R)`

де:

- θₜ — поточні параметри;
- Gₜ — генератор позицій;
- Dₜ — навчальний досвід;
- θ' — кандидат;
- D_val — контрольний набір;
- R — результат оцінювання;
- Select — процедура прийняття або відхилення.

Цей цикл не повинен змінювати шахові правила або порушувати точність легальних трансформацій.

**H-SP-002.** Контекстно стратифікована генерація позицій допоможе виявляти слабкості, приховані загальним результатом.

**H-SP-003.** Розділення навчальних і контрольних генераторів зменшить ризик надмірного пристосування.

**H-SP-004.** Абляційне тестування дозволить встановити фактичний внесок структурних компонентів SUBIT.

**H-SP-005.** Поєднання самогри та алгоритмічної генерації тактичних позицій покращить діагностичні можливості двигуна.

**H-SP-006.** Контроль різноманітності позицій зменшить ризик структурного звуження.

Усі гіпотези потребують емпіричної перевірки.

# 18. Фінальна теза

SUBIT-CHESS повинен оцінювати власний розвиток не за кількістю зіграних партій, не за складністю алгоритму і не за кількістю параметрів.

Критерієм є відтворюване покращення поведінки за контрольованих умов.

Самогра формує досвід.

Структурний аналіз пояснює, що змінилося.

Навчання коригує параметри.

Валідація перевіряє, чи справді зміна принесла користь.

Ці процеси повинні залишатися розділеними.

**Автономний шаховий інтелект не повинен плутати власний досвід із доказом власної правильності.**

Саме ця вимога перетворює самогру з простого механізму накопичення партій на контрольований процес розвитку SUBIT-CHESS.
