# 1. Анотація

SUBIT-CHESS AUTONOMOUS REASONING ARCHITECTURE визначає єдину обчислювальну архітектуру, яка об'єднує всі попередньо сформовані підсистеми SUBIT-CHESS у цілісний цикл аналізу шахової позиції та вибору ходу.

Архітектура ґрунтується на взаємодії дев'яти основних компонентів:

1. SUBIT POSITION VALIDATION — перевірка позиції та шахових правил.
2. SUBIT POSITION VECTOR — структурне представлення позиції.
3. SUBIT RELATIONAL ANALYSIS — аналіз відношень між фігурами, полями та структурами.
4. SUBIT STRUCTURAL DYNAMICS — аналіз змін і потенційних трансформацій.
5. SUBIT STRATEGIC PLANNING — генерація цілей і стратегічних планів.
6. SUBIT SEARCH — пошук наслідків можливих ходів.
7. SUBIT VALUE FUNCTION — оцінювання позицій.
8. SUBIT LEARNING — вдосконалення параметрів на основі внутрішньо створеного досвіду.
9. SUBIT VALIDATION — незалежна перевірка якості змін.

Головна архітектурна теза:

**SUBIT-CHESS не повинен обирати хід лише тому, що він відповідає певній стратегічній ідеї. Він повинен сформувати структурну гіпотезу, перевірити її наслідки шаховим пошуком і прийняти рішення на основі результатів аналізу легальних продовжень.**

Стратегічне планування не замінює шахового пошуку. Воно формує гіпотези, визначає перспективні напрями дослідження та допомагає ефективніше розподіляти обчислювальні ресурси.

Пошук перевіряє ці гіпотези в просторі можливих ходів.

# 3. Основний архітектурний принцип

## 3.1. Від позиції до рішення

Шахова позиція — не просто розташування фігур на дошці.

Вона містить:

- геометричну конфігурацію;
- правовий статус фігур і ходів;
- систему атак і захистів;
- взаємозалежності;
- обмеження мобільності;
- тактичні можливості;
- стратегічні можливості;
- історичний контекст;
- потенціал майбутніх трансформацій.

SUBIT-CHESS має розглядати ці компоненти як взаємопов'язані аспекти одного стану.

Однак взаємопов'язаність не означає взаємозамінність.

Наприклад:

- структурна перевага не є доказом виграшу;
- активність фігури не гарантує її тактичної безпеки;
- стратегічна ціль не є легальним ходом;
- структурна трансформація не обов'язково покращує позицію;
- висока оцінка позиції на обмеженій глибині не є доказом оптимальності.

Звідси випливає головне правило:

**Кожен рівень аналізу має власний тип істинності та власні межі повноважень.**

## 3.2. Принцип непідміни

Позначимо:

- ℒ — множина легальних ходів;
- Ω — структурне представлення;
- ℛ — система відношень;
- ΔΩ — структурна динаміка;
- Γ — множина стратегічних цілей;
- Π — множина стратегічних планів;
- 𝒮 — шаховий пошук;
- 𝒱 — функція оцінювання.

Тоді:

Ω(P) → ℛ(P) → ΔΩ(P) → Γ(P) → Π(P) → 𝒮(P) → 𝒱(P)

Це не проста послідовність незалежних обчислень. Результати різних рівнів можуть повертатися до попередніх рівнів і змінювати їхні гіпотези.

Водночас жоден евристичний рівень не може змінити правила легальності.

# 4. Загальна архітектура

## 4.1. Компоненти

### A. SPVT — SUBIT POSITION VECTOR

Вхідний стан:

- розташування фігур;
- сторона, що ходить;
- права на рокіровку;
- можливість взяття на проході;
- лічильник напівходів;
- номер повного ходу;
- необхідна історія позицій.

SPVT створює формалізоване представлення позиції.

### B. SPV — SUBIT POSITION VALIDATION

Перевіряє:

- коректність представлення;
- відповідність шаховим правилам;
- можливість завершення партії;
- наявність шаху;
- мат;
- пат;
- спеціальні правила нічиєї;
- допустимість переходу до наступного стану.

Цей компонент має найвищий нормативний авторитет.

### C. SRA — SUBIT RELATIONAL ANALYSIS

Визначає відношення:

- ATTACK;
- DEFEND;
- SUPPORT;
- PROTECT;
- BLOCK;
- PIN;
- DISCOVER;
- RESTRICT;
- CONTROL;
- CONNECT;
- THREATEN;
- ENABLES;
- DISABLES;
- DEPENDS_ON;
- CONFLICTS_WITH.

SRA формує структурний граф позиції.

### D. STRUCTURAL DYNAMICS

Визначає, як зміниться структура після можливого ходу:

- які відношення виникнуть;
- які зникнуть;
- які збережуться;
- які змінять функціональну роль;
- які нові можливості з'являться;
- які обмеження будуть створені.

### E. SPG — SUBIT STRATEGIC PLAN GENERATION

Формує:

- стратегічні цілі;
- залежності між цілями;
- потенційні плани;
- умови виконання;
- ризики;
- можливі відповіді суперника;
- критерії завершення або перегляду плану.

### F. SUBIT-SEARCH

Перевіряє наслідки легальних ходів за допомогою шахового пошуку.

Використовує:

- Negamax;
- Alpha-Beta;
- Iterative Deepening;
- Principal Variation;
- Quiescence Search;
- Transposition Table;
- Move Ordering;
- контрольовані механізми вибіркового пошуку.

### G. SUBIT VALUE FUNCTION

Оцінює позицію за сукупністю характеристик:

- матеріал;
- активність;
- структурні відношення;
- безпека короля;
- тактичний стан;
- простір;
- потенціал трансформації.

### H. SUBIT LEARNING

Аналізує результати внутрішніх партій та алгоритмічно створених позицій.

Може вдосконалювати:

- параметри оцінювання;
- порядок ходів;
- розподіл обчислювального бюджету;
- ваги структурних ознак;
- механізми генерації стратегічних цілей.

Не може змінювати правила шахів.

### I. SUBIT VALIDATION

Перевіряє, чи справді нові параметри або алгоритмічні зміни покращують систему.

Навчання не має права самостійно оголошувати власний результат успішним.

# 5. Формальна модель вхідного стану

## 5.1. Повний стан партії

Позначимо позицію:

P = (B, s, C, E, H, N, 𝓗)

де:

- B — конфігурація шахівниці;
- s — сторона, яка має ходити;
- C — права на рокіровку;
- E — стан взяття на проході;
- H — лічильник напівходів;
- N — номер повного ходу;
- 𝓗 — необхідна історія попередніх позицій.

Історія потрібна для коректного визначення повторень та інших правил, залежних від попереднього перебігу партії.

Не можна вважати дві позиції повністю еквівалентними лише тому, що їхні фігури розташовані однаково.

Наприклад, різні права на рокіровку можуть означати різні множини легальних ходів.

## 5.2. Функції представлення

Для кожної позиції визначаються:

Ω(P) — структурне представлення;

C(P) — контекстуальний профіль;

D(P) — профіль структурної динаміки;

G(P) — множина потенційних цілей;

Π(P) — множина кандидатних планів;

L(P) — повна множина легальних ходів.

Важливо:

L(P) визначається правилами шахів, а не стратегічною оцінкою.

Ніяка стратегічна модель не має права виключати легальний хід із множини L(P) лише через те, що він здається нецікавим або структурно небажаним.

# 6. Типи інформації та рівні достовірності

Одна з головних небезпек складної архітектури полягає в тому, що евристичні висновки можуть непомітно перетворитися на нібито точні факти.

SUBIT-CHESS повинен зберігати тип інформації для кожного твердження.

## 6.1. RULE FACT

Точний факт, визначений правилами шахів.

Приклади:

- хід легальний;
- король перебуває під шахом;
- рокіровка недоступна;
- позиція є матом;
- позиція є патом.

Такі факти не повинні залежати від навчальних параметрів.

## 6.2. STRUCTURAL FACT

Факт, безпосередньо отриманий із конфігурації позиції та формальних відношень.

Приклади:

- кінь атакує поле;
- тура заблокована власною пішаковою структурою;
- фігура захищена іншою фігурою;
- вертикаль відкрита;
- поле контролюється кількома фігурами.

Структурні факти мають бути відтворюваними та перевірними.

## 6.3. HEURISTIC INTERPRETATION

Евристична інтерпретація структурного факту.

Наприклад:

«Кінь має обмежену мобільність».

Сам факт кількості доступних полів може бути обчислений точно, але характеристика «обмежена мобільність» потребує інтерпретаційного критерію.

## 6.4. STRATEGIC HYPOTHESIS

Гіпотеза про можливий розвиток позиції.

Наприклад:

«Переведення коня на центральне поле може посилити контроль центру».

Це не факт і не гарантія.

## 6.5. SEARCH-BACKED CONCLUSION

Висновок, отриманий у результаті шахового пошуку.

Він має містити:

- глибину;
- кількість досліджених вузлів;
- оцінку;
- principal variation;
- параметри пошуку;
- відомості про обрізання дерева;
- інформацію про використані евристики.

Такий висновок є обмеженим результатом конкретного обчислення, а не абсолютним доказом оптимальності.

## 6.6. LEARNED PARAMETER

Параметр, отриманий у результаті навчання або оптимізації.

Він повинен містити:

- ідентифікатор параметра;
- версію моделі;
- метод отримання;
- навчальний набір;
- валідаційний набір;
- критерій прийняття;
- історію змін.

Навчений параметр не є шаховим фактом.

# 7. Єдиний цикл автономного міркування

## 7.1. Загальна схема

Основний цикл:

OBSERVE  
→ VALIDATE  
→ REPRESENT  
→ RELATE  
→ EVALUATE  
→ DETECT EVENTS  
→ GENERATE GOALS  
→ GENERATE PLANS  
→ SEARCH  
→ COMPARE  
→ SELECT  
→ EXECUTE / OUTPUT  
→ UPDATE  
→ LEARN / LOG

Кожен етап має окрему відповідальність.

## 7.2. OBSERVE

Отримання поточної позиції.

Система повинна:

- прочитати стан дошки;
- отримати сторону, що ходить;
- отримати спеціальні права;
- відновити необхідний контекст історії;
- перевірити повноту вхідних даних.

## 7.3. VALIDATE

Перевірка коректності позиції.

Якщо позиція некоректна, процес прийняття рішення не повинен продовжуватися так, ніби дані правильні.

## 7.4. REPRESENT

Формування SPVT і структурного опису Ω(P).

Структурне представлення повинно містити не тільки розташування фігур, а й характеристики їхньої взаємодії.

## 7.5. RELATE

Побудова графа відношень.

G(P) = (V, E, L)

де:

- V — множина вузлів;
- E — множина відношень;
- L — множина типізованих міток і атрибутів.

Кожне відношення повинно мати чітку семантику.

Наприклад, ATTACK не можна автоматично ототожнювати з LEGAL_CAPTURE.

Геометрична атака, легальна можливість взяття та фактична можливість безпечно взяти фігуру — різні поняття.

## 7.6. EVALUATE

Початкове оцінювання позиції.

Система визначає:

- матеріальний баланс;
- активність;
- безпеку королів;
- структурні переваги та недоліки;
- тактичні ознаки;
- мобільність;
- потенціал трансформації.

Це попереднє оцінювання, а не остаточне рішення.

## 7.7. DETECT EVENTS

Виявлення критичних подій:

- шах;
- матова загроза;
- незахищена фігура;
- перевантаження захисника;
- відкриття лінії;
- створення зв'язки;
- виникнення вилки;
- зміна пішакової структури;
- поява прохідного пішака;
- зміна ролі фігури.

Система повинна відокремлювати точні тактичні факти від евристичних сигналів.

## 7.8. GENERATE GOALS

Генерація стратегічних цілей.

Приклади:

- покращити активність фігури;
- посилити контроль центру;
- створити слабкість у позиції суперника;
- відкрити лінію;
- забезпечити безпеку короля;
- підтримати просування пішака;
- спростити позицію;
- зберегти матеріальну перевагу;
- перейти до виграшного або нічийного закінчення.

Цілі можуть конфліктувати.

Наприклад, прагнення спростити позицію може суперечити потребі зберегти атакувальний потенціал.

## 7.9. GENERATE PLANS

Для кожної перспективної цілі формується один або кілька планів.

План повинен містити:

- бажаний структурний результат;
- передумови;
- можливі дії;
- ризики;
- очікувану тривалість;
- можливі відповіді суперника;
- умови перегляду.

План не повинен бути жорсткою послідовністю ходів.

Він є моделлю можливого розвитку позиції.

## 7.10. SEARCH

Пошукова система перевіряє кандидатні ходи та їхні наслідки.

Стратегічні плани можуть впливати на порядок дослідження ходів, але не можуть підміняти пошук.

## 7.11. COMPARE

Порівнюються:

- результати пошуку;
- альтернативні продовження;
- стратегічні цілі;
- ризики;
- стійкість позиції;
- невизначеність;
- ресурсна вартість аналізу.

## 7.12. SELECT

Вибирається хід із множини легальних ходів на основі результатів пошуку.

## 7.13. EXECUTE / OUTPUT

У реальній партії система видає один обраний хід.

У внутрішньому самонавчанні система може виконувати хід у власному симульованому середовищі.

Ці режими повинні бути розділені.

## 7.14. UPDATE

Після переходу:

Pₜ → Pₜ₊₁

система оновлює:

- структурний граф;
- відношення;
- динаміку;
- контекст;
- стратегічні плани;
- історію позицій;
- кешовані дані, які більше не є актуальними.

## 7.15. LEARN / LOG

Система записує:

- початкову позицію;
- вибраний хід;
- альтернативи;
- результати пошуку;
- версії параметрів;
- результати партії;
- помилки прогнозування;
- інформацію для майбутньої оптимізації.

Навчання відбувається окремо від активного пошуку.

# 8. Робочий простір міркування

## 8.1. Мета

SUBIT-CHESS повинен мати формалізований робочий простір, у якому зберігаються проміжні результати аналізу.

Це дозволить:

- відтворювати рішення;
- перевіряти походження висновків;
- виявляти помилки;
- порівнювати версії алгоритмів;
- відокремлювати факти від гіпотез.

## 8.2. Типізований запис доказу

Кожне твердження має бути представлене окремим записом:

EvidenceRecord = (
  id,
  type,
  proposition,
  source,
  method,
  position_id,
  parent_ids,
  search_depth,
  parameter_version,
  confidence_class,
  timestamp,
  seed
)

Де:

- id — унікальний ідентифікатор;
- type — тип твердження;
- proposition — зміст;
- source — джерело даних;
- method — метод отримання;
- position_id — позиція, до якої належить запис;
- parent_ids — записи, на яких він ґрунтується;
- search_depth — глибина пошуку, якщо застосовно;
- parameter_version — версія параметрів;
- confidence_class — категорія достовірності;
- timestamp — час створення;
- seed — випадкове зерно, якщо використовувалася стохастична процедура.

## 8.3. Походження висновків

Наприклад:

Твердження:

«Поле d5 є стратегічно перспективним для білого коня».

Походження:

1. STRUCTURAL FACT: поле d5 контролюється білими фігурами.
2. STRUCTURAL FACT: чорні мають обмежену кількість засобів витіснення коня.
3. HEURISTIC INTERPRETATION: кінь на d5 може підвищити контроль центру.
4. STRATEGIC HYPOTHESIS: маневр коня на d5 може покращити позицію.
5. SEARCH-BACKED CONCLUSION: конкретні варіанти перевірені на заданій глибині.

Ці записи не можна зливати в одне нерозрізнене твердження.

## 8.4. Принцип аудитовності

Система повинна бути здатна відповісти:

- Який факт спричинив цю гіпотезу?
- Який алгоритм отримав цей факт?
- Які альтернативні гіпотези існували?
- Які варіанти були перевірені?
- Які варіанти залишилися неперевіреними?
- Яка версія параметрів використовувалася?
- Чому було обрано саме цей хід?

Пояснення повинні відображати реальні обчислювальні дані, а не створювати постфактум правдоподібну історію.

# 9. Ієрархія повноважень

## 9.1. Нормативний рівень

Правила шахів визначають:

- легальність ходів;
- можливість переходів;
- завершення партії;
- спеціальні права;
- правила нічиєї.

Цей рівень не може змінюватися внаслідок навчання.

## 9.2. Рівень тактичних обмежень

Система повинна виявляти:

- шах;
- матові загрози;
- вимушені відповіді;
- форсовані комбінації;
- безпосередні матеріальні втрати.

Але навіть тактичний детектор не повинен замінювати повний механізм перевірки пошуком.

Виявлена тактична загроза є підставою для аналізу, а не автоматичним доказом конкретного результату.

## 9.3. Рівень пошуку

Пошук оцінює наслідки ходів із використанням дерева можливих продовжень.

Він є основним механізмом перевірки рішень.

## 9.4. Рівень стратегічного планування

Стратегічне планування формує довгострокові цілі та гіпотези.

Воно може:

- рекомендувати перспективні ходи для раннього дослідження;
- визначати важливі структурні переходи;
- пропонувати альтернативні плани;
- спрямовувати додатковий пошуковий бюджет.

Воно не може:

- оголошувати нелегальний хід допустимим;
- видаляти легальні ходи;
- ігнорувати форсований тактичний варіант;
- підміняти результат пошуку власною оцінкою.

## 9.5. Рівень структурних переваг

Структурні переваги можуть допомагати розрізняти позиції, але не мають автоматичного пріоритету над конкретними тактичними наслідками.

Наприклад, покращення структури не виправдовує хід, який допускає неминучий мат.

# 10. Інтеграція стратегічного планування з пошуком

## 10.1. Повнота легальних ходів

Для позиції P:

L(P) = {m₁, m₂, ..., mₙ}

Стратегічний модуль може встановити пріоритети:

Priority(mᵢ)

Але початковий повний набір легальних ходів має залишатися доступним пошуковій системі.

Стратегічний пріоритет не є дозволом на видалення ходів.

## 10.2. Порядок ходів

Рекомендований порядок пріоритетів може враховувати:

1. Хід із попередньої principal variation.
2. Хід із transposition table.
3. Тактичні ходи.
4. Взяття.
5. Перетворення пішака.
6. Захисні та вимушені ходи.
7. Ходи, що відповідають стратегічним цілям.
8. Ходи з високою структурною перспективністю.
9. Інші легальні ходи.

Цей порядок є початковою евристикою, а не універсальним законом.

## 10.3. Мінімакс

Базове рекурсивне визначення:

V(P,d) = maxₘ [−V(T(P,m),d−1)]

де:

- P — поточна позиція;
- d — глибина пошуку;
- m — легальний хід;
- T(P,m) — позиція після виконання ходу.

Формула описує стандартний принцип Negamax.

Вона не є новою математичною теорією SUBIT. Особливість SUBIT-CHESS полягає в тому, як структурне представлення, контекст і стратегічні гіпотези інтегруються з пошуком.

## 10.4. Alpha-Beta

Alpha-Beta може скорочувати кількість досліджуваних вузлів, не змінюючи результат повного мінімаксного пошуку за відповідних умов.

Якість порядку ходів безпосередньо впливає на ефективність обрізання.

Тут структурна аналітика може дати практичну перевагу.

## 10.5. Quiescence Search

У позиції шаху не можна використовувати звичайний stand-pat як підставу для завершення аналізу.

Якщо сторона перебуває під шахом, пошук повинен розглядати всі легальні відповіді на шах.

Це правило є обов'язковим.

## 10.6. Transposition Table

Ключ позиції повинен враховувати всі характеристики, що впливають на доступні ходи та результат.

Необхідно окремо враховувати історично залежні правила нічиєї.

Транспозиційна таблиця не повинна створювати хибну еквівалентність позицій із різними правами на рокіровку або різним станом взяття на проході.

## 10.7. Вибірковий пошук

Null Move Pruning, Late Move Reductions, Futility Pruning та інші вибіркові методи можуть бути додані лише після створення надійного базового пошуку.

Кожен такий метод повинен мати:

- окремий параметр увімкнення;
- контрольований режим;
- тести на помилкове відкидання критичних ходів;
- можливість відключення;
- порівняння з базовим пошуком.

Стратегічний модуль не повинен маскувати втрату коректності вибіркового пошуку.

# 11. Модель остаточного рішення

## 11.1. Основне визначення

Остаточне рішення:

Decision(P) = argmaxₘ RobustSearchValue(P,m)

за умови:

m ∈ L(P)

Тобто система вибирає хід із множини легальних ходів, орієнтуючись на результати пошуку.

Стратегічний план може впливати на те, як система досліджує ходи, але не повинен підміняти їхній пошуковий результат.

## 11.2. Три різні поняття

Необхідно розрізняти:

**Expected Value**

Очікувана оцінка за певної моделі можливих відповідей.

**Minimax Value**

Оцінка за припущення, що суперник обиратиме найсильнішу відповідь у межах дослідженого дерева.

**Robustness**

Стійкість рішення до зміни припущень, глибини пошуку та параметрів оцінювання.

Ці поняття не тотожні.

## 11.3. Обмежена глибина

Результат пошуку на глибині d:

V(P,d)

не обов'язково дорівнює:

V(P,d+1)

Збільшення глибини може змінити оцінку та порядок ходів.

Тому система повинна зберігати інформацію про глибину та стабільність результату.

## 11.4. Відсутність гарантії оптимальності

Якщо дерево пошуку не досліджене повністю, система не повинна заявляти, що знайдений хід математично оптимальний.

Коректне формулювання:

«Найкращий хід серед досліджених кандидатів за поточних параметрів і заданого обчислювального бюджету».

# 12. Множинність гіпотез

## 12.1. Чому потрібна множинність

Позиція може підтримувати кілька стратегічних напрямів.

Наприклад:

- атака на королівському фланзі;
- боротьба за центр;
- покращення найгіршої фігури;
- перехід у вигідне закінчення.

Система не повинна передчасно зводити ці варіанти до одного плану.

## 12.2. Граф гіпотез

Нехай:

H(P) = {h₁, h₂, ..., hₙ}

Між гіпотезами можуть існувати відношення:

- SUPPORTS;
- CONFLICTS_WITH;
- DEPENDS_ON;
- ENABLES;
- BLOCKS;
- REPLACES.

Це дозволяє моделювати не лише окремі цілі, а й систему взаємозалежних можливостей.

## 12.3. Парето-порівняння

Плани можуть оцінюватися за вектором:

J(π) = (
  material_risk,
  king_safety,
  activity,
  structural_quality,
  tactical_risk,
  transformation_potential
)

Не кожен план має бути примусово зведений до одного скалярного рейтингу.

Якщо один план кращий за активністю, а інший — за безпекою короля, вони можуть бути непорівнянними без додаткового контексту.

Такі альтернативи слід зберігати до отримання результатів пошуку.

## 12.4. Перегляд гіпотез

Після кожної суттєвої зміни позиції система повинна перевірити актуальність попередніх цілей.

План може мати статус:

- PRESERVE;
- MODIFY;
- SUSPEND;
- REPLACE;
- ABANDON;
- COMPLETE.

Виконання одного проміжного кроку не означає, що початкова стратегічна гіпотеза залишається правильною.

# 13. Контрфактичний аналіз

## 13.1. Мета

Контрфактичний аналіз досліджує, наскільки важливим є певний структурний елемент для загальної конфігурації.

Наприклад:

- що зміниться, якщо прибрати захисника;
- як зміниться контроль поля;
- чи зберігається захист короля без конкретної фігури;
- чи залежить пішакова структура від одного захисного ресурсу.

## 13.2. Відмінність від шахового ходу

Аналітичне вилучення фігури:

P \ x

не є легальним шаховим ходом.

Воно не повинно передаватися пошуковій системі як реальний перехід.

Це окрема процедура дослідження структурної залежності.

## 13.3. Контрфактична залежність

Можна визначити:

ΔF(x,P) = F(P) − F(P \ x)

де F — структурна характеристика.

Це дозволяє оцінити внесок елемента x у певну характеристику.

Однак така різниця не є безпосередньою оцінкою шахової позиції.

Вона може бути використана для генерації гіпотез, які надалі перевіряються легальним пошуком.

---

# 14. Модель невизначеності

## 14.1. Джерела невизначеності

SUBIT-CHESS повинен враховувати:

- обмежену глибину пошуку;
- неповністю досліджені варіанти;
- нестабільність оцінки;
- залежність від параметрів;
- евристичність структурних характеристик;
- можливі помилки вибіркового пошуку.

## 14.2. Категорії

Рекомендовані класи:

- EXACT — точний факт;
- PROVEN_BY_RULES — результат безпосередньо випливає з правил;
- SEARCH_CONFIRMED — підтверджено в межах дослідженого дерева;
- HEURISTIC — евристична оцінка;
- HYPOTHETICAL — гіпотеза;
- UNKNOWN — недостатньо даних.

Ці класи не потрібно трактувати як універсальну числову шкалу ймовірності.

## 14.3. Невизначеність і бюджет пошуку

Невизначеність може бути підставою для додаткового аналізу.

Наприклад, система може збільшити бюджет, якщо:

- два найкращі ходи мають близькі оцінки;
- principal variation нестабільна;
- результат сильно залежить від параметрів;
- позиція містить складні тактичні взаємодії;
- різні стратегічні гіпотези суперечать одна одній.

Водночас невизначеність не повинна автоматично змінювати оцінку позиції.

Потрібно розрізняти:

- значення оцінки;
- невизначеність оцінки;
- обчислювальний бюджет, необхідний для зменшення невизначеності.

# 15. Контекстуальна інтеграція SUBIT

## 15.1. Контекстуальний простір

Для шахової аналітики використовується контекстуальна модель:

I × Z × Φ

де:

I = {QUIET, DEFENCE, ATTACK, PRESSURE}

Z = {GLOBAL, QUEENSIDE, KING, CENTER}

Φ = {OPENING, MIDDLEGAME, ENDGAME, TRANSITION}

Кількість можливих контекстуальних комбінацій:

4 × 4 × 4 = 64

Ця модель є шаховою прикладною системою контекстів.

Вона не повинна ототожнюватися з канонічними координатами WHO × WHERE × WHEN у SUBIT ISA.

## 15.2. Контексти не є взаємовиключними

Одна позиція може одночасно містити:

- атакувальний контекст;
- захисний контекст;
- тиск у центрі;
- локальну боротьбу на королівському фланзі.

Тому контексти повинні мати інтенсивність або ступінь актуальності.

## 15.3. Контекст не змінює факти

Контекст може змінювати значущість певної ознаки, але не її шахову семантику.

Наприклад, ATTACK залишається ATTACK незалежно від того, чи перебуває партія у дебюті, мітельшпілі або ендшпілі.

# 16. Внутрішні пояснення та аудит

## 16.1. Мета

SUBIT-CHESS повинен мати можливість формувати зрозумілий звіт про вибір ходу.

Це не означає, що пояснення є буквальним відображенням людського мислення.

Воно має бути звітом про фактичні обчислення та залежності.

## 16.2. Структура пояснення

Для кожного вибраного ходу бажано зберігати:

1. Початкову позицію.
2. Вибраний хід.
3. Повну множину легальних ходів або її перевірний ідентифікатор.
4. Оцінки найкращих альтернатив.
5. Principal variation.
6. Глибину пошуку.
7. Кількість досліджених вузлів.
8. Термінальний або тактичний статус.
9. Ключові структурні факти.
10. Активну стратегічну ціль.
11. Статус відповідного плану.
12. Відхилені альтернативи.
13. Причини відхилення.
14. Рівень невизначеності.
15. Версію параметрів.
16. Ідентифікатори джерел доказів.

## 16.3. Приклад звіту

**Вибраний хід:** умовний хід M.

**Структурні факти:**
- покращує мобільність фігури;
- створює додатковий контроль центрального поля;
- зберігає захист короля.

**Стратегічна гіпотеза:**
- посилити центральний контроль і підготувати наступну трансформацію структури.

**Результат пошуку:**
- хід залишається найкращим серед досліджених кандидатів;
- основна відповідь суперника включена до principal variation;
- пошук завершено на зазначеній глибині.

**Невизначеність:**
- глибші продовження не досліджені;
- оцінка залежить від поточної версії параметрів.

Такий звіт повинен бути автоматично сформований із журналу обчислень.

# 17. Навчання та оновлення системи

## 17.1. Відокремлення пошуку від навчання

Під час активного пошуку параметри повинні залишатися незмінними.

Інакше одна й та сама позиція може оцінюватися різними моделями в межах одного дерева.

Тому:

ActiveSearch(θᵥ)

повинен використовувати одну зафіксовану версію параметрів θᵥ.

Після завершення пошуку система може передати результати навчальному модулю.

## 17.2. Джерела внутрішнього досвіду

Дозволені джерела:

- контрольований самограй;
- алгоритмічно згенеровані позиції;
- внутрішні тактичні тести;
- власні результати пошуку;
- результати власних партій;
- помилки прогнозування;
- порівняння версій власної системи.

Не використовуються як навчальні джерела:

- зовнішні шахові партії;
- імпортовані PGN-колекції;
- оцінки сторонніх шахових двигунів;
- ходи, рекомендовані сторонніми двигунами;
- сторонні модулі, які приймають рішення замість SUBIT-CHESS.

## 17.3. Обмеження самонавчання

Самограй не є незалежним доказом сили.

Якщо одна й та сама система генерує позиції, оцінює їх і перевіряє власні результати, вона може закріплювати власні помилки.

Тому необхідні:

- окремі навчальні позиції;
- окремі валідаційні позиції;
- незмінний регресійний набір;
- незалежні тести коректності;
- порівняння Champion і Challenger;
- можливість відкату параметрів.

## 17.4. Прийняття нової версії

Нова версія параметрів може бути прийнята лише після проходження визначених критеріїв.

Можливі результати:

- ACCEPT;
- REJECT;
- INCONCLUSIVE.

Якщо результат статистично або методологічно недостатній, правильним рішенням є INCONCLUSIVE.

# 18. Автономність SUBIT-CHESS

## 18.1. Визначення

SUBIT-CHESS має бути самостійною програмною системою, яка:

- самостійно реалізує правила шахів;
- самостійно генерує легальні ходи;
- самостійно будує структурне представлення;
- самостійно визначає відношення;
- самостійно генерує стратегічні гіпотези;
- самостійно здійснює пошук;
- самостійно оцінює результати;
- самостійно навчається на власному досвіді.

## 18.2. Заборона сторонніх шахових компонентів

Архітектура не передбачає використання сторонніх шахових двигунів як компонентів системи.

Також не передбачається запозичення сторонніх шахових бібліотек або модулів для виконання основних функцій двигуна.

Усі критичні алгоритми повинні мати власну реалізацію.

## 18.3. Незалежність навчання

Система не повинна отримувати зовнішні оцінки позицій або рекомендації ходів як навчальні цілі.

Внутрішній досвід формується самостійно.

Загальні математичні, алгоритмічні та шахові знання можуть використовуватися для теоретичного проєктування, але це не повинно перетворюватися на імпорт стороннього шахового коду або зовнішнього вчителя.

# 19. Захист від самопідтвердження та циклічних помилок

## 19.1. Проблема

Автономна система може потрапити в замкнений цикл:

1. Вона генерує гіпотезу.
2. Обирає ходи відповідно до гіпотези.
3. Оцінює результат власними параметрами.
4. Використовує власну оцінку як підтвердження гіпотези.
5. Посилює параметри, які породили початкову гіпотезу.

Такий цикл не гарантує реального покращення.

## 19.2. Захисні механізми

Потрібно реалізувати:

- незалежний регресійний набір;
- перевірку різноманітності стратегічних планів;
- виявлення повторюваних циклів;
- контроль за надмірним повторенням одного типу ходів;
- аналіз позицій, у яких попередній план не дав очікуваного результату;
- Champion–Challenger;
- відкат до попередньої стабільної версії.

## 19.3. Виявлення стратегічної петлі

Система повинна відстежувати, чи не повторює вона одну й ту саму стратегічну дію без вимірюваного прогресу.

Наприклад:

- багаторазове переведення тієї самої фігури;
- повторне створення та усунення однакових структурних відношень;
- циклічне перемикання між двома планами;
- систематичне відкладання критичної дії.

При цьому необхідно розрізняти стратегічну петлю та легальне повторення позиції, яке може бути тактично або позиційно виправданим.

# 20. Інваріанти архітектури

## AR-INV-001 — LEGALITY

Кожен хід, виданий як рішення, повинен належати L(P).

## AR-INV-002 — RULE AUTHORITY

Правила шахів мають пріоритет над евристиками, планами та навчальними параметрами.

## AR-INV-003 — STRUCTURAL SEPARATION

Структурний факт не можна автоматично ототожнювати з оцінкою позиції.

## AR-INV-004 — HYPOTHESIS SEPARATION

Стратегічна гіпотеза не є доведеним результатом.

## AR-INV-005 — SEARCH INTEGRITY

Стратегічне планування не повинно непомітно змінювати семантику пошуку.

## AR-INV-006 — MOVE COMPLETENESS

Повна множина легальних ходів повинна зберігатися в базовому пошуковому режимі.

## AR-INV-007 — TERMINAL EXACTNESS

Термінальні результати повинні визначатися правилами шахів, а не евристичним оцінюванням.

## AR-INV-008 — PROVENANCE

Кожен важливий висновок повинен мати простежуване походження.

## AR-INV-009 — PARAMETER IMMUTABILITY

Параметри не змінюються всередині активного пошукового циклу.

## AR-INV-010 — COLOR SYMMETRY

Алгоритмічні властивості повинні проходити перевірку на симетричних позиціях із переставленими кольорами.

## AR-INV-011 — DETERMINISM

Однакові вхідні дані, версії алгоритмів, параметри та випадкові зерна повинні давати відтворювані результати там, де алгоритм заявлений як детермінований.

## AR-INV-012 — NO EXTERNAL TEACHER

Рішення та навчальні сигнали не повинні залежати від зовнішніх шахових двигунів або імпортованих шахових партій.

## AR-INV-013 — COUNTERFACTUAL SEPARATION

Аналітичне вилучення елемента не можна трактувати як легальний шаховий хід.

## AR-INV-014 — UNCERTAINTY SEPARATION

Невизначеність повинна зберігатися окремо від оцінки позиції.

## AR-INV-015 — VALIDATION INDEPENDENCE

Навчальна система не може бути єдиним критерієм успішності власного навчання.

# 21. Протокол тестування

## 21.1. Тести правил

Перевіряються:

- генерація легальних ходів;
- шах;
- мат;
- пат;
- рокіровка;
- взяття на проході;
- перетворення пішака;
- повторення позицій;
- правила нічиєї.

Perft використовується для перевірки генератора ходів.

Стандартні значення для початкової позиції:

- perft(1) = 20;
- perft(2) = 400;
- perft(3) = 8902;
- perft(4) = 197281.

Ці значення перевіряють коректність генерації ходів, але самі по собі не доводять силу двигуна.

## 21.2. Модульні тести

Окремо перевіряються:

- SPVT;
- SPV;
- SRA;
- STRUCTURAL DYNAMICS;
- SPG;
- SUBIT-SEARCH;
- SUBIT VALUE FUNCTION;
- SUBIT LEARNING;
- SUBIT VALIDATION.

## 21.3. Інтеграційні тести

Перевіряється повний цикл:

OBSERVE → VALIDATE → REPRESENT → RELATE → EVALUATE → PLAN → SEARCH → SELECT.

Важливо перевіряти не лише успішний сценарій, а й помилкові вхідні дані, неповні позиції та суперечливі гіпотези.

## 21.4. Симетричні тести

Для кожної вибраної тестової позиції створюється кольорово-симетрична пара.

Перевіряється:

- коректність генерації ходів;
- симетрія структурних характеристик;
- відповідність оцінок із протилежною перспективою;
- відсутність систематичної переваги одного кольору через помилку реалізації.

## 21.5. Тактичні тести

Тестові позиції можуть створюватися алгоритмічно.

Вони повинні охоплювати:

- матові загрози;
- вилки;
- зв'язки;
- відкриті напади;
- перевантаження;
- відволікання;
- проміжні ходи;
- захисні ресурси;
- вимушені послідовності.

Такі позиції не повинні залежати від імпортованих колекцій шахових партій.

## 21.6. Порівняння версій

Champion і Challenger повинні грати контрольовані матчі:

- з однаковими ресурсними обмеженнями;
- зі зміною кольорів;
- на однакових початкових позиціях;
- з фіксованими умовами;
- із заздалегідь визначеними критеріями.

Потрібно аналізувати не лише перемоги та поразки, а й:

- тактичні помилки;
- втрати матеріалу;
- якість пошуку;
- стабільність оцінок;
- ефективність структурного аналізу;
- витрати часу та вузлів.

## 21.7. Ablation Testing

Потрібно окремо вимірювати внесок:

- структурного графа;
- контекстуальної моделі;
- структурної динаміки;
- стратегічного планування;
- адаптивного порядку ходів;
- навченої функції оцінювання.

Якщо відключення компонента не погіршує результат або навіть покращує його, це є підставою переглянути компонент.

Не можна вважати кожен складний модуль корисним лише тому, що він теоретично узгоджується з SUBIT.

# 23. Наукові гіпотези

Наведені положення є дослідницькими гіпотезами. Їх не слід представляти як доведені результати.

## H-AR-01 — Structural Guidance Hypothesis

Структурний аналіз може покращити порядок ходів і зменшити кількість вузлів, необхідних для знаходження якісного рішення.

## H-AR-02 — Multi-Plan Hypothesis

Одночасне збереження кількох стратегічних гіпотез може зменшити ризик передчасного вибору хибного плану.

## H-AR-03 — Dynamic Context Hypothesis

Контекстуальна оцінка структурних відношень може бути ефективнішою за використання однакових ваг для всіх фаз гри.

## H-AR-04 — Structural Dynamics Hypothesis

Аналіз структурних змін може допомогти виявляти позиційні можливості, які недостатньо представлені статичною оцінкою.

## H-AR-05 — Evidence-Based Reasoning Hypothesis

Збереження походження висновків може полегшити діагностику помилок та вдосконалення алгоритмів.

## H-AR-06 — Adaptive Search Budget Hypothesis

Розподіл обчислювального бюджету на основі невизначеності може покращити ефективність пошуку.

## H-AR-07 — Autonomous Improvement Hypothesis

Контрольований самограй у поєднанні з незалежною внутрішньою валідацією може забезпечити поступове покращення власної системи.

Жодна з цих гіпотез не вважається підтвердженою без експериментальних результатів.

# 24. Обмеження та ризики

## 24.1. Надмірна складність

Надмірна кількість структурних рівнів може збільшити обчислювальну вартість без покращення гри.

Тому кожен модуль повинен довести свою практичну користь.

## 24.2. Подвійний облік

Одна й та сама позиційна перевага може бути врахована в кількох характеристиках.

Наприклад, контроль поля може впливати одночасно на активність, простір і структурні відношення.

Потрібна система виявлення корельованих ознак і контролю подвійного обліку.

## 24.3. Хибна впевненість

Велика кількість структурних фактів не означає, що стратегічний висновок правильний.

Потрібно зберігати відмінність між фактом, інтерпретацією та результатом пошуку.

## 24.4. Обмеженість самограю

Система може навчитися ефективно грати проти власних недоліків, не набувши достатньої стійкості до інших стилів гри.

Тому внутрішні тести повинні охоплювати різні типи алгоритмічно згенерованих позицій і різні режими поведінки самої системи.

## 24.5. Обмеженість пошуку

Жодна евристика не усуває фундаментальної проблеми комбінаторного зростання шахового дерева.

Тому архітектура повинна бути орієнтована на ефективне використання обмежених ресурсів, а не на обіцянку повного аналізу кожної позиції.

# 26. Заключний принцип

SUBIT-CHESS повинен не просто оцінювати шахову позицію як набір незалежних ознак.

Він має встановлювати структуру, досліджувати відношення, виявляти можливі трансформації, формувати альтернативні стратегічні гіпотези та перевіряти їх через наслідки легальних ходів.

Проте складність структурного опису не повинна перетворюватися на самоціль.

Структура потрібна для кращого аналізу.  
Контекст потрібен для правильної інтерпретації.  
Динаміка потрібна для розуміння можливих змін.  
Стратегічний план потрібен для формування напрямку.  
Пошук потрібен для перевірки наслідків.  
Навчання потрібне для вдосконалення системи.  
Валідація потрібна для того, щоб відрізнити реальне покращення від самопідтвердження.

Отже, остаточний принцип архітектури:

**OBSERVE STRUCTURE → CONTEXTUALIZE RELATIONS → GENERATE HYPOTHESES → SEARCH CONSEQUENCES → SELECT A LEGAL MOVE → RECORD EVIDENCE → LEARN THROUGH INDEPENDENT VALIDATION.**

SUBIT-CHESS має залишатися автономним двигуном, який самостійно створює власне представлення шахового світу, самостійно аналізує його та самостійно приймає рішення.

**DO NOT COLLAPSE — CONTEXTUALIZE.**
