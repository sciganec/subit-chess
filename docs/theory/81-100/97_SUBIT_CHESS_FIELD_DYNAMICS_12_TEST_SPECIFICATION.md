# 1. ПРИЗНАЧЕННЯ

FD-12 визначає повну систему перевірки SUBIT-CHESS FIELD DYNAMICS.

Мета документа — перетворити математичні, структурні, обчислювальні та пошукові вимоги FD-01—FD-11 на перевірювані властивості, тестові сценарії та критерії приймання.

FD-12 повинен відповісти на такі питання:

1. Чи правильно побудовані польові структури з шахової позиції?
2. Чи зберігають оператори визначену математичну семантику?
3. Чи коректно поля взаємодіють між собою?
4. Чи правильно оновлюються поля після легального ходу?
5. Чи збігаються інкрементальні обчислення з повними?
6. Чи не спотворює FIELD DYNAMICS шахову легальність?
7. Чи коректно інтегровано поля з оцінюванням і пошуком?
8. Чи зберігається правильність після оптимізації?
9. Чи можна відтворити результати тестування?
10. Чи підтверджується продуктивність вимірюваннями?

Основний принцип:

**EVERY STRUCTURAL CLAIM MUST HAVE A TESTABLE INVARIANT.**

Тестування не повинно обмежуватися перевіркою того, що програма не завершується помилкою. Воно має перевіряти відповідність реалізації визначеній семантиці.

# 2. ТЕСТОВА ФІЛОСОФІЯ

## 2.1. Розділення правильності та продуктивності

FD-12 розділяє два незалежні критерії:

**Correctness:** результат обчислення правильний.

**Performance:** результат отримано з прийнятними обчислювальними витратами.

Швидка реалізація з неправильним результатом не проходить тестування.

Повільна реалізація з правильним результатом може пройти перевірку коректності, але не пройти перевірку продуктивності.

## 2.2. Незалежність тестового оракула

Тест не повинен перевіряти алгоритм виключно за допомогою іншого виклику того самого алгоритму.

Для критичних властивостей необхідно передбачити незалежні способи перевірки:

- ручні еталонні позиції;
- прості контрольні реалізації;
- математичні інваріанти;
- повне обчислення як оракул для інкрементального;
- незалежне відновлення стану;
- властивості графів і клітинного комплексу.

Наприклад, перевірка інкрементального оновлення через повний перерахунок є корисною, але сама повна реалізація також повинна перевірятися на еталонних позиціях та математичних інваріантах.

## 2.3. DO NOT COLLAPSE — CONTEXTUALIZE

Тестова система повинна перевіряти, що реалізація не зливає:

- WHITE і BLACK;
- геометричну атаку та легальний хід;
- атаку та стратегічний вплив;
- відсутнє значення та нуль;
- точне та евристичне значення;
- поле та його походження;
- шаховий стан та його похідні характеристики;
- позиційну оцінку та пошукове значення.

Кожне таке розрізнення має бути представлене окремими тестами.

# 3. ТЕСТОВА АРХІТЕКТУРА

## 3.1. Рівні тестування

FD-12 встановлює дев'ять рівнів.

### T1 — UNIT TESTS

Перевірка окремих функцій, операторів і структур даних.

### T2 — PROPERTY-BASED TESTS

Перевірка математичних властивостей на множині автоматично згенерованих вхідних даних.

### T3 — INVARIANT TESTS

Перевірка властивостей, які повинні залишатися незмінними за допустимих перетворень.

### T4 — DIFFERENTIAL TESTS

Порівняння незалежних реалізацій або способів обчислення одного результату.

### T5 — INTEGRATION TESTS

Перевірка взаємодії польових модулів між собою та із шаховим станом.

### T6 — SEARCH TESTS

Перевірка впливу FIELD DYNAMICS на пошукове ядро.

### T7 — REGRESSION TESTS

Перевірка того, що зміни коду не порушили раніше підтверджені властивості.

### T8 — PERFORMANCE TESTS

Вимірювання часу, пам'яті, кількості операцій та ефективності кешування.

### T9 — AUTONOMY AND REPRODUCIBILITY TESTS

Перевірка автономності реалізації, відтворюваності результатів та незалежності від зовнішніх шахових рушіїв і зовнішніх ігрових баз.

# 5. ТЕСТУВАННЯ ШАХОВОЇ ГЕОМЕТРІЇ

## 5.1. Канонічна система координат

Координати:

`x ∈ {0,...,7}`

`y ∈ {0,...,7}`

`index(x,y)=8y+x`

Напрямки:

- EAST = (+1,0);
- WEST = (−1,0);
- NORTH = (0,+1);
- SOUTH = (0,−1);
- NORTH_EAST = (+1,+1);
- NORTH_WEST = (−1,+1);
- SOUTH_EAST = (+1,−1);
- SOUTH_WEST = (−1,−1).

### GEO-001 — Кути дошки

Перевірити всі чотири кути:

- a1;
- h1;
- a8;
- h8.

Очікування: жоден напрямок не виходить за межі дошки як допустима клітина.

### GEO-002 — Межі координат

Для кожної клітини перевірити:

`0 ≤ x ≤ 7`

`0 ≤ y ≤ 7`

`0 ≤ index(x,y) ≤ 63`

### GEO-003 — Взаємна оберненість координат

Для всіх 64 клітин:

`decode(index(x,y))=(x,y)`

### GEO-004 — Напрямлена симетрія

Перевірити:

`EAST = −WEST`

`NORTH = −SOUTH`

`NORTH_EAST = −SOUTH_WEST`

`NORTH_WEST = −SOUTH_EAST`

Це стосується геометричних напрямків, а не семантики пішаків.

### GEO-005 — Геометричні промені

Для кожної клітини й кожного з восьми напрямків перевірити:

- послідовність клітин;
- відсутність повторів;
- завершення на межі дошки;
- правильну відстань між сусідніми клітинами.

# 6. ТЕСТУВАННЯ ВЕКТОРНОГО ПРЕДСТАВЛЕННЯ

## 6.1. Загальний принцип

Шахові вектори є дискретними напрямленими переміщеннями або відношеннями.

Вони не повинні трактуватися як фізичні сили.

### VEC-001 — Ортогональні вектори

Перевірити вісім напрямків для кожної клітини.

### VEC-002 — Вектори коня

Перевірити всі допустимі зміщення:

`(±1,±2)` та `(±2,±1)`.

Очікування: максимум вісім геометричних клітин призначення.

### VEC-003 — Геометрія короля

Перевірити всі сусідні клітини без урахування рокіровки.

### VEC-004 — Напрямок білого пішака

Білий пішак рухається в напрямку `+Y`.

### VEC-005 — Напрямок чорного пішака

Чорний пішак рухається в напрямку `−Y`.

### VEC-006 — Напрямок атак пішаків

Атаки білого й чорного пішаків повинні бути діагональними та протилежно орієнтованими.

### VEC-007 — Геометрична атака проти легального ходу

Побудувати позицію, де фігура геометрично атакує клітину, але не може легально перейти на неї через шах власному королю.

Очікування: геометричне поле зберігає атаку, а генератор легальних ходів відхиляє відповідний хід.

### VEC-008 — Збереження джерела

Якщо кілька фігур впливають на одну клітину, система повинна зберігати кожне джерело.

# 7. ТЕСТУВАННЯ ОНТОЛОГІЇ ПОЛІВ

### GEO-FIELD-001 — Тип поля

Кожне поле повинно мати визначений тип.

### GEO-FIELD-002 — Сторона

WHITE, BLACK, SHARED і NEUTRAL повинні залишатися розрізненими.

### GEO-FIELD-003 — Джерело

Кожне активне відношення повинно мати визначене джерело або явно позначену відсутність джерела.

### GEO-FIELD-004 — Ціль

Ціль повинна належати задекларованому домену:

- клітина;
- фігура;
- зона;
- лінія;
- структурне відношення.

### GEO-FIELD-005 — Provenance

Похідне значення повинно зберігати посилання на джерельні компоненти.

### GEO-FIELD-006 — Unknown ≠ Zero

Створити поле, яке ще не обчислювалося.

Очікування:

`NOT_COMPUTED ≠ ZERO`

### GEO-FIELD-007 — Blocked ≠ Inactive

Перевірити, що заблокований вплив не ототожнюється з відсутністю джерела.

### GEO-FIELD-008 — Geometric / Legal / Strategic Separation

Три рівні повинні повертати окремі результати та мати окремі статуси точності.

# 8. ТЕСТУВАННЯ НАПРЯМЛЕНИХ ОПЕРАТОРІВ

### DIR-001 — Орієнтація ребра

Для ребра `u→v` перевірити, що зворотне ребро має протилежну орієнтацію.

### DIR-002 — Межі дошки

Оператор не повинен створювати ребро за межами 64 клітин.

### DIR-003 — Блокування

Променевий оператор повинен зупинятися на першому блокері відповідно до семантики конкретного поля.

### DIR-004 — Власна фігура

Геометричне поле може позначати клітину власної фігури як контрольовану, але генератор легальних ходів не повинен трактувати це як можливість взяття.

### DIR-005 — Ворожа фігура

Клітина ворожої фігури повинна оброблятися відповідно до типу операції: атака, взяття або переміщення.

### DIR-006 — Відкриття лінії

Після усунення блокера відповідний промінь повинен оновитися.

### DIR-007 — Закриття лінії

Після появи нового блокера дальні клітини повинні втратити відповідний променевий вплив.

# 9. ТЕСТУВАННЯ ГРАДІЄНТА

Нехай граф позиції має вершини V та орієнтовані ребра E.

Для потенціалу `φ:V→ℝ`:

`Gradφ(u→v)=φ(v)−φ(u)`

### GRD-001 — Нульовий потенціал

Якщо `φ(q)=0` для всіх q, градієнт дорівнює нулю на всіх ребрах.

### GRD-002 — Сталий потенціал

Якщо потенціал однаковий для всіх вершин, градієнт дорівнює нулю.

### GRD-003 — Лінійний потенціал

Для контрольного потенціалу, залежного від координати x, горизонтальні ребра повинні мати передбачуваний знак, а вертикальні — нульове значення.

### GRD-004 — Зворотне ребро

`Gradφ(v→u)=−Gradφ(u→v)`

### GRD-005 — Циркуляція градієнта

Для будь-якого замкненого циклу C:

`Circ(Gradφ,C)=0`

### GRD-006 — Локальне оновлення

Зміна потенціалу однієї вершини повинна змінювати лише інцидентні ребра, якщо структура графа незмінна.

### GRD-007 — Незалежність сторін

Потенціали WHITE та BLACK не повинні змішуватися без явного оператора порівняння.

# 10. ТЕСТУВАННЯ ДИВЕРГЕНЦІЇ

Для напрямленого потоку J на ребрах:

`Div J(v)=Σ outgoing J − Σ incoming J`

Конкретна нормалізація повинна відповідати визначенню FD-06.

### DIV-001 — Нульовий потік

Нульовий потік дає нульову дивергенцію.

### DIV-002 — Єдине джерело

Потік, спрямований від однієї вершини до сусідньої, створює відповідні додатне й від'ємне значення.

### DIV-003 — Єдине поглинання

Зворотний напрямок змінює знаки.

### DIV-004 — Баланс потоку

Для скінченного графа без зовнішніх потоків:

`Σᵥ Div J(v)=0`

### DIV-005 — Циклічний потік

Ненульовий потік по замкненому циклу може мати нульову дивергенцію в усіх вершинах циклу.

### DIV-006 — Зміна одного ребра

Зміна потоку на одному ребрі повинна змінити дивергенцію лише його кінцевих вершин.

### DIV-007 — Незалежні канали

Дивергенція атакувального поля WHITE не повинна змінювати дивергенцію BLACK.

# 11. ТЕСТУВАННЯ РОТОРА ТА ЦИРКУЛЯЦІЇ

### CUR-001 — Квадратний цикл

Для циклу d4→e4→e5→d5→d4 обчислити циркуляцію за визначеним напрямком.

### CUR-002 — Зворотна орієнтація

`Circ(J,reverse(C))=−Circ(J,C)`

### CUR-003 — Нульовий потік

Нульовий потік дає нульову циркуляцію.

### CUR-004 — Нульова циркуляція з ненульовим потоком

Побудувати ненульовий потік уздовж циклу, сума якого дорівнює нулю.

### CUR-005 — Градієнтний потік

Для `J=Gradφ` циркуляція кожного замкненого циклу повинна дорівнювати нулю.

### CUR-006 — Локальний ротор

Перевірити циркуляцію на межі кожної одиничної грані.

### CUR-007 — Інцидентність

Для матриць інцидентності перевірити:

`D₁ · Bᵀ = 0`

### CUR-008 — Розмірність циклічного простору

Для зв'язного ортогонального графа дошки:

`β₁=|E|−|V|+1`

Для 64 вершин і 112 ортогональних ребер:

`β₁=49`

### CUR-009 — Теорема дискретного Стокса

Для кожної тестової області перевірити:

`Σ Curl(J,f)·Area(f)=Circ(J,∂Z)`

### CUR-010 — Потік після блокування

Зміна блокера повинна оновлювати залежні потоки та циркуляції, але не повинна змінювати незалежні цикли.

### CUR-011 — Невизначена циркуляція

Якщо частина ребер невідома, результат не повинен мовчки трактуватися як точний нуль.

### CUR-012 — Цикл і шахова послідовність

Цикл графа не повинен автоматично трактуватися як послідовність легальних шахових ходів.

# 12. ТЕСТУВАННЯ ВЗАЄМОДІЇ ПОЛІВ

### INT-001 — Сумісність типів

Несумісні типи полів не можуть автоматично агрегуватися.

### INT-002 — Сумісність одиниць

Значення з різними шкалами не додаються без явного перетворення.

### INT-003 — Незалежність порядку

Якщо операція визначена як комутативна, зміна порядку аргументів не повинна змінювати результат.

### INT-004 — Напрямленість

Для напрямлених відношень зміна порядку джерела й цілі повинна змінювати семантику відповідно до визначення.

### INT-005 — Reinforcement

Підтверджується на контрольній позиції, де кілька незалежних джерел підсилюють одну структурну характеристику.

### INT-006 — Opposition

Перевірити протилежні впливи без автоматичного взаємного знищення їхніх джерел.

### INT-007 — Blocking

Перевірити, що блокування змінює доступність, але не знищує існування заблокованого джерела.

### INT-008 — Dependency

Зміна первинного поля повинна інвалідовувати залежні взаємодії.

### INT-009 — Unknown Propagation

Невідоме значення повинно передаватися відповідно до правил невизначеності оператора.

### INT-010 — Duplicate Source

Повторне включення того самого джерела не повинно непомітно подвоювати його внесок.

### INT-011 — Provenance Preservation

Після агрегування повинна залишатися можливість визначити первинні джерела.

### INT-012 — Interaction Cycle

Циклічні залежності повинні бути виявлені або явно дозволені визначеним алгоритмом.

# 13. ТЕСТУВАННЯ ІНТЕГРАЦІЇ З ОЦІНЮВАННЯМ

### EVA-001 — Незалежність компонентів

Оцінка повинна зберігати окремі складові до виконання явної агрегувальної операції.

### EVA-002 — WHITE / BLACK Separation

Поля сторін не повинні зливатися до застосування визначеної функції оцінювання.

### EVA-003 — Контекст сторони ходу

Зміна сторони ходу повинна впливати лише на компоненти, які залежать від цього контексту.

### EVA-004 — Геометрична атака не дорівнює стратегічній перевазі

Наявність геометричної атаки сама по собі не повинна автоматично створювати позитивну стратегічну оцінку.

### EVA-005 — Блокована фігура

Перевірити розрізнення між геометричним потенціалом і фактичною доступністю.

### EVA-006 — Зміна позиції

Після легального ходу оцінка повинна оновлюватися відповідно до змінених полів.

### EVA-007 — Оцінка проти пошукового значення

`StaticEvaluation` не повинна ототожнюватися з `SearchValue`.

### EVA-008 — Детермінованість

Однакова позиція та однакові параметри повинні давати однакову детерміновану оцінку.

# 14. ТЕСТУВАННЯ ПОШУКОВОЇ ІНТЕГРАЦІЇ

### SEA-001 — Легальна генерація

FIELD DYNAMICS не повинна змінювати множину легальних ходів.

### SEA-002 — Move Ordering

Зміна польового пріоритету може змінювати порядок ходів, але не повинна змінювати множину ходів.

### SEA-003 — Повний пошук

За незмінної функції оцінювання й повного перегляду всіх ходів перестановка ходів не повинна змінювати точне мінімаксне значення.

### SEA-004 — Alpha-Beta

Перевірити коректність меж alpha і beta за різного порядку ходів.

### SEA-005 — Quiescence

Польова інформація не повинна приховувати обов'язкові тактичні продовження, які передбачені правилами пошуку.

### SEA-006 — Transposition

Однакова позиція повинна використовувати кеш лише за сумісності релевантного контексту.

### SEA-007 — Search Extension

Розширення пошуку не повинно створювати неконтрольовану рекурсію.

### SEA-008 — No Field-Only Pruning

Ходи з низьким польовим пріоритетом не вилучаються лише на цій підставі.

### SEA-009 — Search Reproducibility

За однакових умов пошук повинен бути відтворюваним, якщо не ввімкнено явно задекларовану стохастичність.

### SEA-010 — Baseline Comparison

Порівняти базовий пошук і пошук із польовим впорядкуванням.

Оцінювати окремо:

- кількість вузлів;
- час;
- глибину;
- стабільність найкращого ходу;
- тактичну коректність;
- точне пошукове значення там, де його можна незалежно встановити.

# 18. PROPERTY-BASED TESTING

## 18.1. Призначення

Property-based testing перевіряє загальні властивості, а не лише заздалегідь визначені позиції.

Генератор повинен створювати внутрішньо допустимі шахові стани й легальні послідовності ходів.

## 18.2. Обов'язкові властивості

**PBT-001 — Coordinate Round Trip**

`decode(encode(q))=q`

**PBT-002 — Edge Reversal**

`J(v→u)=−J(u→v)` для одного й того самого напрямленого потоку, представленого у зворотній орієнтації.

**PBT-003 — Gradient Cycle**

`Circ(Gradφ,C)=0`

**PBT-004 — Divergence Balance**

Сума дивергенцій дорівнює сумарному зовнішньому потоку.

**PBT-005 — Curl of Gradient**

`Curl(Gradφ)=0` для відповідного дискретного комплексу.

**PBT-006 — Stokes Consistency**

Локальна сума ротора відповідає циркуляції межі області.

**PBT-007 — Incremental Equivalence**

Інкрементальне оновлення дорівнює повному обчисленню.

**PBT-008 — Make/Unmake Identity**

`Unmake(Make(S,m))=S`

**PBT-009 — Determinism**

Однаковий вхід дає однаковий точний результат.

**PBT-010 — Provenance Completeness**

Кожне агреговане точне значення має відновлюване походження відповідно до визначення оператора.

## 18.3. Shrinking

Якщо генератор виявив помилку на довгій послідовності ходів, тестова система повинна скорочувати приклад до мінімальної послідовності, що відтворює помилку.

Це необхідно для локалізації причин:

- помилка геометрії;
- неправильна інвалідація;
- помилка make/unmake;
- stale cache;
- неправильна взаємодія полів;
- помилка спеціального ходу.

# 19. DIFFERENTIAL TESTING

FD-12 передбачає порівняння незалежних способів обчислення.

## 19.1. Повний проти інкрементального

Основна пара:

`FullFieldBuilder` проти `IncrementalFieldUpdater`.

## 19.2. Попередньо обчислена геометрія проти прямої геометрії

Порівняти таблиці променів і масок із простою координатною реалізацією.

## 19.3. Bitboard проти множин

Якщо існують дві реалізації множин клітин, їхні результати повинні збігатися.

## 19.4. Cached проти Uncached

Кешований і некешований обчислювач повинні повертати однакові точні результати.

## 19.5. Optimized проти Reference Operator

Кожен оптимізований оператор повинен мати просту контрольну реалізацію для тестування.

Reference implementation може бути повільною. Її призначення — ясність і незалежна перевірка, а не продуктивність.

# 22. REGRESSION TESTING

## 22.1. Regression Suite

Кожен підтверджений тест стає частиною регресійного набору.

Регресійний набір повинен включати:

- координатні тести;
- тести всіх фігур;
- геометричні атаки;
- градієнт;
- дивергенцію;
- циркуляцію;
- взаємодію полів;
- інкрементальні оновлення;
- кешування;
- make/unmake;
- пошук;
- продуктивність.

## 22.2. Regression Gate

Зміна не може бути прийнята, якщо вона:

- порушує раніше підтверджений інваріант;
- змінює точний результат без зміни специфікації;
- створює нові stale-cache випадки;
- порушує відновлення стану;
- зменшує повноту легальної генерації;
- погіршує продуктивність за межі встановленого бюджету без обґрунтування.

## 22.3. Specification Change

Якщо змінюється математичне визначення оператора, необхідно:

1. змінити специфікацію;
2. визначити вплив на залежні модулі;
3. оновити еталонні результати;
4. оновити тести;
5. зафіксувати версію;
6. повторно виконати повний регресійний набір.

`TestRun = (runId,commit,specVersion,seed,config,environment,results,timestamp)`
