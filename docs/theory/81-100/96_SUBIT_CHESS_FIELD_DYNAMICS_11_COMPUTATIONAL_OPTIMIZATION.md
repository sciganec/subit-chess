# 1. ПРИЗНАЧЕННЯ

FD-11 визначає обчислювальну архітектуру, необхідну для ефективного виконання SUBIT-CHESS FIELD DYNAMICS у межах шахового пошукового дерева.

Попередні специфікації визначили математичні та структурні принципи польової системи:

- FD-01 — фундаментальна транспозиція;
- FD-02 — онтологія структурних полів;
- FD-03 — векторне представлення впливів;
- FD-04 — напрямлені оператори;
- FD-05 — градієнт;
- FD-06 — дивергенція;
- FD-07 — ротор і циркуляція;
- FD-08 — взаємодія полів і суперпозиція;
- FD-09 — інтеграція з оцінюванням позиції;
- FD-10 — інтеграція з пошуком.

FD-11 вирішує наступну проблему:

**Як обчислювати, оновлювати, зберігати та використовувати польову інформацію з мінімальними витратами часу й пам'яті, не втрачаючи математичної коректності, шахової семантики та контексту?**

Основний принцип:

**OPTIMIZE COMPUTATION — PRESERVE STRUCTURE.**

Оптимізація не повинна знищувати відмінності між типами полів, сторонами, контекстами, походженням або рівнями точності.

# 2. ОСНОВНІ ЦІЛІ

FD-11 встановлює такі цілі.

## 2.1. Обчислювальна ефективність

Зменшити кількість повторних обчислень польових характеристик під час:

- побудови початкової позиції;
- генерації кандидатних ходів;
- виконання шахового ходу;
- повернення попереднього стану;
- оцінювання позиції;
- розширення пошукового дерева;
- повторного відвідування транспозицій.

## 2.2. Інкрементальність

Після легального ходу перераховувати лише ті компоненти FIELD DYNAMICS, які справді залежать від змінених елементів позиції.

## 2.3. Контекстна цілісність

Не допускати використання застарілих польових даних, отриманих для іншого шахового стану або контексту.

## 2.4. Детермінованість

Для однакової позиції, контексту, версії операторів та параметрів точні обчислення повинні давати однакові результати.

## 2.5. Масштабованість

Архітектура повинна підтримувати:

- локальне обчислення;
- повне обчислення позиції;
- інкрементальне оновлення;
- пошукове використання;
- подальше розширення типів польових операторів.

## 2.6. Автономність

Оптимізація реалізується власними алгоритмами SUBIT-CHESS.

Не використовуються сторонні шахові рушії, їхні внутрішні структури або зовнішні шахові бази як заміна власним алгоритмам.

# 3. ЗАГАЛЬНА ОБЧИСЛЮВАЛЬНА МОДЕЛЬ

Визначимо:

`S` — шахова позиція.

`F(S)` — набір польових характеристик.

`I(S)` — набір взаємодій між полями.

`E(S)` — структурна оцінка позиції.

`D(S)` — граф залежностей польових компонентів.

Повне обчислення:

`FD_full(S) = E(F(S), I(S))`

Інкрементальне обчислення після ходу:

`S₁ = Tₘ(S₀)`

`ΔS = Difference(S₀,S₁)`

`ΔF = UpdateFields(F₀,ΔS,D₀)`

`ΔI = UpdateInteractions(I₀,ΔF,D₀)`

`E₁ = UpdateEvaluation(E₀,ΔF,ΔI)`

Основна вимога:

`FD_incremental(S₀,m) = FD_full(Tₘ(S₀))`

Для всіх компонентів, які оголошені точними, результати інкрементального обчислення повинні збігатися з результатами повного перерахунку.

Евристичні компоненти можуть мати окремі правила точності, але не можуть непомітно підміняти точні дані.

# 4. АРХІТЕКТУРА ПРЕДСТАВЛЕННЯ ДАНИХ

## 4.1. Загальний принцип

Необхідно розділити:

1. первинний шаховий стан;
2. геометричні структури;
3. напрямлені відношення;
4. польові значення;
5. взаємодії;
6. похідні характеристики;
7. пошукові метадані.

Ці структури мають різні життєві цикли й не повинні зберігатися як один надмірно великий об'єкт.

## 4.2. Board Representation

Базова множина клітин:

`Q = {0,1,...,63}`

Індекс клітини:

`index(x,y)=8y+x`

де:

- `x=0...7`;
- `y=0...7`.

Координатна відповідність:

- a1 = 0;
- b1 = 1;
- h1 = 7;
- a2 = 8;
- h8 = 63.

Первинний стан повинен дозволяти швидко визначати:

- тип фігури на клітині;
- сторону фігури;
- зайнятість клітини;
- розташування всіх фігур;
- множину клітин кожної сторони;
- множини клітин кожного типу фігур.

Вибір між масивом клітин, bitboard-представленням або гібридною структурою залишається рішенням реалізації.

FD-11 не нав'язує конкретну мову програмування або конкретний формат внутрішньої пам'яті.

## 4.3. Square Sets

Множина клітин повинна підтримувати операції:

- UNION;
- INTERSECTION;
- DIFFERENCE;
- COMPLEMENT;
- MEMBERSHIP;
- COUNT;
- ITERATION.

За можливості використовується компактне бітове представлення.

Для 64 клітин природним кандидатом є 64-бітна маска.

Однак конкретна реалізація залежить від мови програмування та її числової моделі.

Наприклад, у JavaScript необхідно враховувати обмеження точного представлення цілих чисел і семантику побітових операторів. Можливі рішення:

- BigInt;
- два 32-бітні слова;
- масиви компактних цілих чисел.

Вибір визначається бенчмарками, а не припущенням про перевагу певного формату.

## 4.4. Piece Representation

Фігури повинні мати стабільні внутрішні ідентифікатори протягом конкретного стану пошуку.

`PieceRecord = (pieceId,type,side,square,status)`

Структура повинна дозволяти швидко визначати:

- клітину фігури;
- її тип;
- її сторону;
- її поточний статус;
- залежні від неї польові компоненти.

Максимальна кількість фігур на дошці обмежена правилами шахів, тому фіксовані або компактні масиви можуть бути ефективнішими за динамічні структури.

# 5. ОПТИМІЗОВАНЕ ПРЕДСТАВЛЕННЯ ПОЛІВ

## 5.1. Dense та Sparse Representation

FD-11 розрізняє два типи представлення.

### Dense Representation

Значення зберігаються для всіх можливих комбінацій:

`Field[type][side][square][direction]`

Переваги:

- швидкий доступ;
- проста індексація;
- передбачуваний розмір;
- зручність повного перерахунку.

Недоліки:

- зберігання багатьох нульових або неактивних значень;
- надмірне використання пам'яті;
- зайве копіювання під час пошуку.

### Sparse Representation

Зберігаються лише активні відношення та значення.

`SparseField = {active_relations,values,metadata}`

Переваги:

- компактність;
- менше зайвих записів;
- ефективне зберігання розріджених відношень;
- зручність локальних оновлень.

Недоліки:

- складніший доступ;
- необхідність підтримувати індекси;
- можливі витрати на пошук і видалення елементів.

## 5.2. Гібридне представлення

Рекомендована архітектура:

- базова геометрія — попередньо обчислені компактні структури;
- множини клітин — бітові маски;
- атаки й захист — компактні маски або лічильники з provenance;
- структурні відношення — розріджені списки;
- взаємодії — розріджений граф;
- градієнт, дивергенція та циркуляція — обчислювані або кешовані похідні значення.

Це не обов'язкова єдина реалізація. Остаточний формат визначається вимірюваннями.

## 5.3. Збереження provenance

Оптимізація не повинна знищувати походження значення.

Якщо клітина атакована трьома фігурами, система повинна мати змогу відновити три окремі джерела.

Лічильник `attackCount=3` не є повною заміною списку джерел.

Рекомендована модель:

`InfluenceSummary = (count,sourceMask,sourceIds,fieldType,side)`

Частина цих полів може обчислюватися ліниво.

# 6. ПОПЕРЕДНЬО ОБЧИСЛЕНА ГЕОМЕТРІЯ

## 6.1. Призначення

Геометрія шахових фігур багаторазово використовується під час побудови польових структур.

Тому незмінні геометричні залежності доцільно обчислювати один раз.

## 6.2. Precomputed Tables

Рекомендовано передбачити таблиці:

- `KING_ATTACKS[square]`;
- `KNIGHT_ATTACKS[square]`;
- `WHITE_PAWN_ATTACKS[square]`;
- `BLACK_PAWN_ATTACKS[square]`;
- `ORTHOGONAL_RAYS[square][direction]`;
- `DIAGONAL_RAYS[square][direction]`;
- `QUEEN_RAYS[square]`;
- `BETWEEN_MASK[squareA][squareB]`;
- `LINE_MASK[squareA][squareB]`.

Таблиці геометрії не повинні містити залежностей від поточного розташування фігур, якщо ці залежності не передбачені конкретною таблицею.

## 6.3. Sliding Pieces

Для тури, слона та ферзя геометричні промені визначаються координатами.

Фактичний вплив залежить від зайнятості клітин.

`RayReach = GeometryRay − CellsBeyondFirstBlocker`

Потрібно розрізняти:

- клітини до першого блокера;
- саму клітину першого блокера;
- клітини за блокером.

Правила включення клітини блокера залежать від типу поля:

- геометрична атака може включати клітину першого блокера;
- переміщення на зайняту власною фігурою клітину заборонене;
- взяття ворожої фігури може бути дозволене;
- клітини за блокером недосяжні для відповідного променевого впливу.

## 6.4. Незмінність геометричних таблиць

Попередньо обчислена геометрія є незмінною для конкретної версії правил і координатної системи.

Зміна стану позиції не повинна спричиняти повторне створення таких таблиць.

# 7. INCREMENTAL FIELD UPDATE

## 7.1. Основний принцип

Після ходу не потрібно автоматично перераховувати всі поля дошки.

Необхідно визначити множину змінених залежностей.

`AffectedSet(m,S₀) = {components affected by move m}`

Далі:

`F₁ = F₀ − F_affected_old + F_affected_new`

Це концептуальна форма. Фактична реалізація може використовувати дельти, заміну записів або локальну реконструкцію.

## 7.2. Класифікація змін

Кожен хід може змінити:

- початкову клітину фігури;
- кінцеву клітину фігури;
- клітину взятої фігури;
- зайнятість клітин;
- променеві відношення;
- підтримку;
- доступність;
- мобільність;
- атакувальні й захисні поля;
- похідні градієнти;
- дивергенцію;
- циркуляцію;
- взаємодії;
- оцінку позиції.

Спеціальні ходи потребують окремої обробки.

## 7.3. Move Dependency Map

`MoveDelta = (removedPieces,addedPieces,changedSquares,changedRights,changedHistory)`

Для кожного зміненого елемента визначаються залежні компоненти.

Приклад:

Переміщення тури з a1 на a4:

1. змінюється зайнятість a1;
2. змінюється зайнятість a4;
3. можуть змінитися вертикальні промені через a1 та a4;
4. можуть змінитися горизонтальні промені через a1 та a4;
5. змінюються відповідні атакувальні відношення;
6. можуть змінитися підтримка, доступність і взаємодії;
7. оновлюються лише залежні похідні оператори.

## 7.4. Slider Ray Invalidation

Особливе значення мають тури, слони та ферзі.

Зміна зайнятості однієї клітини може змінити довгі променеві відношення багатьох фігур.

Тому для кожної зміненої клітини необхідно визначити потенційно залежні променеві джерела.

`AffectedSliders(q,S)`

має повертати фігури, чиї промені можуть перетинати клітину `q`.

Оновлення повинно враховувати:

- відкриття променя;
- закриття променя;
- зміну першого блокера;
- появу нового доступного сегмента;
- втрату доступного сегмента.

## 7.5. Special Moves

Інкрементальна система повинна окремо підтримувати:

### Castling

Змінюються позиції короля та тури. Необхідно оновити обидві початкові й кінцеві клітини та залежні променеві відношення.

### En Passant

Клітина взяття не збігається з клітиною вилученої фігури. Потрібно оновити три клітини та залежні поля.

### Promotion

Пішак замінюється фігурою нового типу. Необхідно перебудувати геометричні й польові характеристики відповідно до нового типу.

### Capture

Вилучення фігури змінює зайнятість клітини та потенційно відкриває лінії.

### Double Pawn Move

Оновлюється контекст можливості en passant, навіть якщо геометричні поля інших фігур не змінилися.

# 8. DEPENDENCY GRAPH

## 8.1. Призначення

Для коректного інкрементального обчислення необхідний граф залежностей.

`D_FD=(V_D,E_D)`

Вузли — обчислювані компоненти:

- occupancy;
- piece geometry;
- attack field;
- defense field;
- mobility field;
- accessibility field;
- support field;
- obstruction field;
- gradient;
- divergence;
- curl;
- interactions;
- evaluation.

Ребро `A→B` означає, що зміна A може вимагати оновлення B.

## 8.2. Dependency Propagation

Якщо змінюється вузол A:

1. визначити його безпосередніх залежних;
2. побудувати множину потенційно застарілих вузлів;
3. визначити порядок оновлення;
4. оновити лише необхідні вузли;
5. позначити незмінені компоненти як актуальні;
6. перевірити цілісність версій.

## 8.3. Cycle Detection

Граф залежностей не повинен створювати неконтрольовані цикли обчислень.

Якщо взаємодія двох компонентів має циклічну залежність, необхідно:

- визначити її як спільний обчислювальний вузол;
- або задати явний ітераційний алгоритм із критерієм завершення;
- або заборонити таку залежність.

Нескінченне повторне оновлення неприпустиме.

# 9. LAZY EVALUATION

## 9.1. Принцип

Не всі польові характеристики потрібні для кожного вузла пошуку.

Тому дозволяється відкладене обчислення.

`LazyFieldState ∈ {NOT_COMPUTED, COMPUTING, VALID, INVALID, UNKNOWN}`

Коли компонент потрібен:

1. перевірити актуальність;
2. перевірити кеш;
3. обчислити залежності;
4. отримати значення;
5. зберегти provenance;
6. позначити компонент VALID.

## 9.2. Пріоритети обчислення

Першими обчислюються компоненти, які:

- необхідні для легальних правил або тактичної перевірки;
- потрібні поточному оцінювачу;
- потрібні для впорядкування кандидатних ходів;
- часто використовуються повторно;
- мають невисоку вартість обчислення.

Дорогі похідні компоненти можуть обчислюватися лише за запитом.

## 9.3. Обмеження

Lazy evaluation не повинна створювати ситуацію, коли відсутнє значення мовчки трактується як нуль.

Якщо поле не обчислене, воно має залишатися `NOT_COMPUTED` або `UNKNOWN`.

# 10. CACHING ARCHITECTURE

## 10.1. Окремі рівні кешу

Рекомендовано розділити:

- `GeometryCache`;
- `AttackFieldCache`;
- `DefenseFieldCache`;
- `MobilityCache`;
- `AccessibilityCache`;
- `GradientCache`;
- `DivergenceCache`;
- `CurlCache`;
- `InteractionCache`;
- `EvaluationCache`.

Не всі рівні обов'язково повинні бути реалізовані як окремі фізичні сховища. Важливе розділення їхньої семантики й залежностей.

## 10.2. Cache Key

Ключ кешу повинен містити всі дані, від яких залежить конкретний результат.

Загальна форма:

`FieldCacheKey = (positionKey,contextKey,fieldType,side,operatorVersion,ruleVersion)`

Історичні характеристики включаються лише тоді, коли вони впливають на результат.

Не потрібно без необхідності включати всю історію до кешу чисто геометричного поля.

## 10.3. Cache Invalidation

Після зміни позиції:

- залежні компоненти інвалідуються;
- незалежні компоненти залишаються чинними;
- версії компонентів оновлюються;
- stale-значення не повертаються як актуальні.

## 10.4. Collision Handling

Якщо використовується хеш, необхідно враховувати можливість колізій.

Хеш може бути індексом пошуку, але критичні результати повинні мати механізм підтвердження тотожності стану або достатньо надійного ключа.

## 10.5. Transposition Reuse

Однакова шахова позиція може зустрічатися в різних гілках пошуку.

Польові результати можуть повторно використовуватися, якщо збігаються:

- релевантний стан;
- контекст;
- правила;
- тип поля;
- версія оператора;
- параметри обчислення.

Збіг лише розташування фігур не завжди достатній.

---

# 11. MAKE / UNMAKE OPTIMIZATION

## 11.1. Основна вимога

Пошукове дерево не повинно вимагати повного копіювання всіх польових структур у кожному дочірньому вузлі.

Рекомендована модель:

`MakeMove → RecordDelta → UpdateFields`

`UnmakeMove → RestoreDelta → RestoreFields`

## 11.2. Undo Record

`FieldUndoRecord` може містити:

- змінені клітини;
- попередні значення occupancy;
- попередні польові значення;
- змінені відношення;
- змінені взаємодії;
- попередні версії кешу;
- попередній стан залежностей;
- посилання на тимчасові записи.

## 11.3. Branch Safety

Відновлення повинно бути незалежним від того, скільки дочірніх ходів було досліджено.

Після повернення до батьківського вузла:

`State_after_unmake == State_before_make`

`Fields_after_unmake == Fields_before_make`

`Interactions_after_unmake == Interactions_before_make`

Це точні вимоги для компонентів, які визначені як точні.

## 11.4. Stack Discipline

Undo-записи повинні мати суворо контрольований порядок.

Заборонено:

- відновлювати записи в неправильному порядку;
- використовувати undo-запис іншої гілки;
- залишати активні посилання на тимчасові об'єкти;
- повторно використовувати пам'ять до завершення залежних операцій.

---

# 12. MEMORY LAYOUT

## 12.1. Принцип

Обчислювальна вартість залежить не лише від кількості операцій, але й від організації пам'яті.

Потрібно мінімізувати:

- надлишкові об'єкти;
- часті heap allocations;
- копіювання великих структур;
- pointer chasing;
- неефективне зберігання малих значень;
- непотрібне дублювання provenance.

## 12.2. Array of Structures vs Structure of Arrays

Два підходи:

`AoS: [Record₁, Record₂, Record₃...]`

`SoA: {field₁:[...], field₂:[...], field₃:[...]}`

AoS зручний для доступу до повного запису.

SoA може бути ефективнішим, коли алгоритм обробляє одне поле для великої кількості елементів.

Вибір визначається фактичними сценаріями доступу та профілюванням.

## 12.3. Fixed-Size Buffers

Для обмежених структур можна використовувати фіксовані буфери:

- 64 клітини;
- максимум 32 фігури;
- 8 основних напрямків;
- обмежені списки джерел;
- фіксовані масиви геометричних залежностей.

Переповнення буфера має бути виявлюваним. Тихе обрізання даних неприпустиме.

## 12.4. Allocation Strategy

Для тимчасових пошукових структур можуть застосовуватися:

- stack allocation;
- arena allocation;
- object pools;
- reusable buffers.

Ці механізми дозволені лише за умови контрольованого життєвого циклу й коректного відновлення стану.

---

# 13. NUMERICAL OPTIMIZATION

## 13.1. Типи числових значень

Кожен оператор декларує числову семантику.

Наприклад:

- цілочисельні лічильники;
- бітові маски;
- фіксована точність;
- floating-point значення;
- категоріальні стани.

## 13.2. Fixed-Point

Для окремих польових величин може використовуватися fixed-point представлення.

Переваги:

- детермінованість у відповідних реалізаціях;
- контрольоване округлення;
- можливість швидких цілочисельних операцій;
- прогнозовані межі значень.

Недоліки:

- необхідність визначення масштабу;
- ризик переповнення;
- похибка округлення;
- обмежений динамічний діапазон.

## 13.3. Overflow Protection

Кожне числове поле визначає:

- мінімальне значення;
- максимальне значення;
- правило переповнення;
- правило округлення;
- допустимість від'ємних значень.

Непомітне переповнення заборонене.

## 13.4. Floating-Point

Якщо використовуються числа з плаваючою комою:

- порядок накопичення має бути визначеним;
- порівняння повинно враховувати числову точність;
- NaN та Infinity повинні оброблятися явно;
- результати повинні мати контрольовану детермінованість.

---

# 14. VECTOR AND BITBOARD OPTIMIZATION

## 14.1. Bitwise Operations

Для множин клітин бажано використовувати бітові операції, якщо вони забезпечують перевагу в конкретному середовищі.

Типові операції:

`A ∩ B`

`A ∪ B`

`A \ B`

`COUNT(A)`

`IS_EMPTY(A)`

`CONTAINS(A,q)`

## 14.2. Attack Aggregation

Атакувальні множини можуть представлятися як:

`AttackMask[side]`

Однак для збереження кількості атак і provenance необхідні додаткові структури.

Маска показує факт наявності атаки, але не завжди відповідає на запитання:

- скільки джерел атакують клітину;
- які саме фігури є джерелами;
- чи має хоча б одна атака тактичну ефективність;
- чи є атака легальною в конкретному контексті.

## 14.3. SIMD

SIMD може бути використаний для паралельної обробки незалежних значень.

Однак SIMD не є обов'язковою вимогою.

Він впроваджується лише після профілювання, коли визначено конкретний обчислювальний bottleneck.

---

# 15. FIELD OPERATOR OPTIMIZATION

## 15.1. Directional Operators

FD-04 може використовувати попередньо обчислені напрямлені маски й геометричні таблиці.

Повторне обчислення координатних зміщень для кожного вузла пошуку слід уникати, якщо це не дає переваги за вимірюваннями.

## 15.2. Gradient

FD-05 може кешувати потенціали та локальні різниці між суміжними вузлами.

Після зміни потенціалу `φ(q)` оновлюються лише ребра, інцидентні клітині `q`, якщо домен і оператор залишаються незмінними.

## 15.3. Divergence

FD-06 може використовувати локальні суми потоків.

Якщо змінюється потік на ребрі `u→v`, потенційно змінюються дивергенції лише у вузлах `u` та `v`.

Це правило діє за незмінних орієнтації, метрики та структури графа.

## 15.4. Curl / Circulation

FD-07 може використовувати індексацію граней і циклів за ребрами.

Якщо змінюється потік на ребрі, перераховуються лише грані й цикли, що містять це ребро.

Для базового ортогонального комплексу кожне внутрішнє ребро належить обмеженій кількості квадратних граней.

## 15.5. Field Interaction

FD-08 може використовувати індекс залежностей:

`InteractionIndex[fieldId] → affectedInteractions`

Після зміни поля оновлюються лише взаємодії, які залежать від цього поля.

# 16. SEARCH-SPECIFIC OPTIMIZATION

## 16.1. Search Node Footprint

Пошуковий вузол не повинен зберігати повну копію всіх польових структур, якщо їх можна відновити або представити компактною дельтою.

`SearchNode = (positionRef,fieldDeltaRef,evaluationRef,searchMetadata)`

Це концептуальна модель, а не обов'язкова структура конкретного коду.

## 16.2. Move Ordering

Для впорядкування ходів використовуються лише ті польові характеристики, обчислення яких виправдане на поточному рівні пошуку.

Рекомендовано розділяти:

- дешеві ознаки;
- середньої вартості ознаки;
- дорогі структурні ознаки.

Дорогі оператори можуть обчислюватися лише для обмеженої множини кандидатів.

## 16.3. Search Depth Awareness

Глибина пошуку може впливати на бюджет обчислення FIELD DYNAMICS.

Наприклад:

- на верхніх рівнях — ширший структурний аналіз;
- на середніх рівнях — інкрементальні характеристики;
- на глибоких рівнях — дешеві локальні ознаки.

Це не повинно впливати на повноту генерації легальних ходів.

## 16.4. No Field-Only Pruning

FD-11 не дозволяє вилучати легальні ходи лише через низький польовий пріоритет.

Оптимізація обчислень не є дозволом на втрату пошукової повноти.

# 20. FAILURE CONDITIONS

Реалізація не проходить приймання, якщо:

1. інкрементальні результати відрізняються від повних без задекларованої причини;
2. make/unmake залишає залишкові зміни;
3. кеш повертає застаріле значення;
4. хеш-колізія призводить до неперевіреного використання чужого стану;
5. втрачається provenance;
6. атакувальні канали сторін зливаються;
7. невідоме значення автоматично стає нульовим;
8. спеціальний хід оновлює лише частину залежних клітин;
9. оптимізація змінює семантику оператора;
10. продуктивність заявляється без відтворюваного benchmark;
11. пошук втрачає легальні ходи через польову евристику;
12. тимчасові структури використовуються після завершення їхнього життєвого циклу.

`ChessState`
→ `MoveDelta`
→ `Dependency Resolution`
→ `Incremental Field Update`
→ `Interaction Update`
→ `Derived Operator Update`
→ `Evaluation Update`
→ `Search`

При поверненні:

`Search`
→ `Undo Record`
→ `Restore Field State`
→ `Restore Interaction State`
→ `Restore Cache Versions`
→ `Parent Position`

SUBIT-контекст може зберігатися як окремий метарівень, але не повинен змінювати шахову семантику координат, кольорів фігур або легальності ходів.

# 24. КРИТИЧНІ АРХІТЕКТУРНІ ОБМЕЖЕННЯ

1. Оптимізація не змінює визначення польових операторів.
2. Швидкість не має пріоритету над точністю.
3. Інкрементальність повинна перевірятися повним перерахунком.
4. Кеш не є джерелом істини — він зберігає похідні дані.
5. Геометричні маски не замінюють легальну генерацію ходів.
6. Bitboard не замінює provenance.
7. Лічильник атак не замінює список джерел.
8. Lazy evaluation не перетворює невідоме значення на нуль.
9. Польова евристика не вилучає легальні ходи.
10. SIMD та інші низькорівневі оптимізації впроваджуються лише після профілювання.
11. Повторне використання транспозицій допускається лише за сумісності контексту.
12. Кожне оптимізоване представлення повинно мати тест на семантичну еквівалентність.
