# 1. МЕТА СПЕЦИФІКАЦІЇ

FD-08 визначає механізм взаємодії між різними структурними полями шахової позиції.

Попередні специфікації визначили окремі типи полів, їхні джерела, цілі, напрямки, градієнти, дивергенцію, циркуляцію та локальні характеристики.

Однак у реальній шаховій позиції ці поля не існують ізольовано.

Наприклад:

- атака однієї фігури може посилюватися підтримкою іншої;
- відкриття вертикалі може збільшувати доступність проникнення;
- блокування діагоналі може одночасно зменшувати активність слона та захищати короля;
- контроль центрального поля може підтримувати мобільність декількох фігур;
- одна фігура може одночасно створювати загрозу та обмежувати власні фігури;
- переміщення однієї фігури може змінити декілька взаємозалежних полів.

Тому двигуну потрібна окрема система визначення взаємодій.

Основний принцип:

**SUPERPOSITION MUST NOT ERASE CONTEXT.**

Накладання полів не повинно знищувати інформацію про їхнє походження, тип, напрямок, сторону, контекст і функціональне значення.

FD-08 має забезпечити перехід від набору незалежних полів до структурованої системи їхніх взаємодій.

# 2. ОСНОВНІ ПРИНЦИПИ

## 2.1. Розділення поля та взаємодії

Поле є самостійною структурою впливу.

Взаємодія — це відношення між двома або більше полями.

Отже:

Fᵢ ≠ I(Fᵢ,Fⱼ)

де:

- Fᵢ — окреме поле;
- I(Fᵢ,Fⱼ) — взаємодія між полями.

Взаємодія не повинна змінювати вихідні поля.

Вона створює новий аналітичний об'єкт, який посилається на вихідні структури.

Це дозволяє зберігати первинні характеристики та незалежно перевіряти результати взаємодії.

## 2.2. Розділення суперпозиції та взаємодії

Суперпозиція — це операція об'єднання сумісних внесків.

Взаємодія — це визначення відношень між полями, включно з нелінійними та контекстуальними залежностями.

Ці операції не є тотожними.

Для сумісних полів може застосовуватися:

F_total(q) = Σ Fᵢ(q)

Але це допустимо лише тоді, коли всі компоненти мають сумісну семантику.

Наприклад, два незалежні внески до поля геометричної атаки можуть бути об'єднані в одну структуру атакованості.

Проте безпосереднє додавання:

ATTACK + MOBILITY + DEFENSE + ACCESSIBILITY

не має визначеного математичного значення без спеціально встановленого перетворення.

Тому FD-08 забороняє автоматичне додавання різнорідних полів.

## 2.3. Збереження контексту

Кожна взаємодія повинна зберігати:

- типи вихідних полів;
- сторону або власника;
- джерела впливу;
- цільові об'єкти;
- просторову локалізацію;
- напрямок;
- рівень інтерпретації;
- стан достовірності;
- походження даних;
- версію оператора;
- шахову позицію, у якій взаємодію було обчислено.

Це реалізує принцип:

**DO NOT COLLAPSE — CONTEXTUALIZE.**

# 3. ФОРМАЛЬНА МОДЕЛЬ ВЗАЄМОДІЇ

Нехай:

F = {F₁,F₂,...,Fₙ}

— множина полів поточної шахової позиції S.

Визначимо взаємодію:

Iᵢⱼ = I(Fᵢ,Fⱼ | S,C)

де:

- Fᵢ, Fⱼ — вихідні поля;
- S — поточний шаховий стан;
- C — контекст взаємодії;
- Iᵢⱼ — результат визначення відношення між полями.

Контекст:

C = (Cₛ,Cₜ,Cₕ,Cᵣ,Cₚ)

де:

- Cₛ — статичний контекст дошки;
- Cₜ — контекст сторони, що ходить;
- Cₕ — історичний контекст;
- Cᵣ — контекст шахових правил;
- Cₚ — контекст походження та достовірності даних.

Результатом взаємодії є не обов'язково число.

Загальна структура:

Interaction = (Type, Sources, Targets, Relation, Scope, Context, Evidence, Confidence)

де:

- Type — тип взаємодії;
- Sources — вихідні поля;
- Targets — об'єкти впливу;
- Relation — встановлене відношення;
- Scope — область дії;
- Context — контекст;
- Evidence — підстави визначення;
- Confidence — достовірність результату.

Confidence не повинна підміняти собою шахову оцінку.

Вона характеризує надійність аналітичного висновку, а не силу позиції.

# 4. СУМІСНІСТЬ ПОЛІВ

Перед будь-якою операцією суперпозиції система повинна перевірити сумісність вихідних полів.

Визначимо:

Compatible(Fᵢ,Fⱼ) ∈ {TRUE,FALSE,UNKNOWN}

Сумісність повинна перевірятися за такими критеріями.

## 4.1. Семантична сумісність

Поля повинні описувати однаковий тип характеристики або мати явно визначене перетворення між ними.

Наприклад:

ATTACK + ATTACK → допустима суперпозиція.

DEFENSE + DEFENSE → допустима суперпозиція.

ATTACK + DEFENSE → не є безпосередньо сумісною суперпозицією.

ATTACK + MOBILITY → не є безпосередньо сумісною суперпозицією.

Останні дві пари можуть взаємодіяти через окремі оператори.

## 4.2. Сумісність одиниць та шкал

Якщо поле має числову інтенсивність, необхідно знати:

- одиницю вимірювання;
- нормалізацію;
- діапазон;
- напрямок збільшення;
- семантику нульового значення;
- спосіб отримання величини.

Числові значення з різних шкал не можна додавати без обґрунтованого перетворення.

## 4.3. Просторова сумісність

Поля повинні мати сумісну область визначення.

Наприклад:

- квадрат → квадрат;
- фігура → квадрат;
- лінія → лінія;
- зона → зона;
- фігура → зона.

Різні просторові типи можуть взаємодіяти, але для цього необхідний оператор просторового відображення.

## 4.4. Часова сумісність

Поля, обчислені для різних позицій, не можна безпосередньо об'єднувати.

Для порівняння необхідно встановити відповідність між станами:

F₀ = Φ(S₀)

F₁ = Φ(S₁)

ΔF = Difference(F₀,F₁)

Різниця визначається лише за сумісної семантики та відомого перетворення позиції.

## 4.5. Сумісність власника

Необхідно зберігати канали:

WHITE  
BLACK  
SHARED  
NEUTRAL

Не допускається автоматичне взаємне погашення впливів білих і чорних фігур.

Наприклад, дві протилежні атаки на одне поле не означають відсутності атаки.

Вони означають конфлікт двох незалежних впливів.

## 4.6. Повний предикат сумісності

Визначимо:

Compatible(Fᵢ,Fⱼ) =

SemanticCompatible  
∧ ScaleCompatible  
∧ DomainCompatible  
∧ ContextCompatible  
∧ TemporalCompatible  
∧ OwnershipCompatible  
∧ ProvenanceCompatible

Якщо хоча б одна необхідна умова невідома, результат повинен бути UNKNOWN, а не TRUE.

# 5. КЛАСИ ВЗАЄМОДІЙ

FD-08 визначає базову таксономію взаємодій.

## 5.1. REINFORCEMENT — ПІДСИЛЕННЯ

Два або більше полів підтримують одну функціональну характеристику.

Приклад:

- біла тура атакує вертикаль;
- білий ферзь підтримує проникнення;
- білий кінь контролює поле входу.

Результатом є структурне підсилення потенційного проникнення.

Формально:

I(Fᵢ,Fⱼ) = REINFORCEMENT

Підсилення не означає автоматичної стратегічної переваги.

Воно лише визначає взаємне посилення певної характеристики.

## 5.2. OPPOSITION — ПРОТИДІЯ

Поля створюють протилежно спрямовані впливи.

Приклад:

- біла фігура атакує поле;
- чорна фігура його захищає.

Результат:

I(Fᵢ,Fⱼ) = OPPOSITION

Необхідно зберігати обидва вихідні поля.

Не можна трактувати протидію як нульовий вплив.

## 5.3. BLOCKING — БЛОКУВАННЯ

Одне поле або структурний елемент обмежує дію іншого.

Приклад:

- чорний пішак блокує білу туру;
- блокування діагоналі обмежує слона;
- фігура перекриває лінію атаки.

Формально:

Fᵢ → BLOCKS → Fⱼ

Блокування може мати подвійне значення.

Воно може обмежувати власну фігуру, але водночас перешкоджати атаці суперника.

Тому оцінка блокування повинна залежати від контексту.

## 5.4. ENABLING — УМОЖЛИВЛЕННЯ

Одне поле створює умови для активації іншого.

Приклад:

- звільнення вертикалі створює доступність для тури;
- підтримка поля дозволяє коню зайняти центральну позицію;
- усунення блокатора відкриває діагональ слона.

Відношення:

Fᵢ → ENABLES → Fⱼ

Уможливлення не означає, що відповідна дія вже сталася.

Необхідно розділяти фактичну та потенційну активацію.

## 5.5. OVERLAP — НАКЛАДАННЯ

Два поля мають спільну просторову область.

Наприклад, декілька фігур контролюють один квадрат.

OVERLAP не обов'язково означає підсилення.

Воно лише фіксує просторове накладання.

## 5.6. INTERSECTION — ПЕРЕТИН

Два поля мають спільний елемент або спільну структурну ціль.

Наприклад:

- атака тури перетинається з контролем ферзя;
- поле підтримки коня перетинається з полем атаки пішака.

Перетин повинен бути відокремлений від накладання.

OVERLAP описує спільну область.

INTERSECTION описує конкретну структуру перетину.

## 5.7. COMPLEMENTARITY — ДОПОВНЮВАЛЬНІСТЬ

Поля виконують різні, але взаємодоповнювальні функції.

Наприклад:

- слон контролює діагональ;
- кінь контролює сусідні центральні поля;
- тура забезпечує горизонтальну підтримку.

Ці поля не обов'язково мають спільні квадрати.

Їхня взаємодія полягає у функціональному доповненні.

## 5.8. DEPENDENCY — ЗАЛЕЖНІСТЬ

Одне поле залежить від існування або стану іншого.

Наприклад:

- доступність поля залежить від відсутності блокатора;
- мобільність тури залежить від стану вертикалі;
- підтримка фігури залежить від геометрії атаки іншої фігури.

Формально:

Fᵢ → DEPENDS_ON → Fⱼ

Залежність повинна мати визначений напрямок.

## 5.9. TRANSFORMATION — ТРАНСФОРМАЦІЯ

Взаємодія призводить до зміни стану іншого поля після шахового ходу.

Наприклад:

- переміщення пішака відкриває діагональ;
- розмін змінює структуру контролю;
- відхід фігури відкриває приховану атаку;
- переміщення тури змінює доступність горизонталі.

Трансформація повинна бути прив'язана до конкретного переходу:

S₀ → S₁

## 5.10. COMPETITION — КОНКУРЕНЦІЯ

Декілька полів претендують на обмежений ресурс.

Приклад:

- дві фігури потребують одного центрального поля;
- декілька фігур використовують одну лінію;
- різні плани потребують одного темпу або одного структурного ресурсу.

Конкуренція не обов'язково є конфліктом.

Вона може бути допустимою альтернативністю.

## 5.11. CONFLICT — КОНФЛІКТ

Взаємодія, за якої поля створюють несумісні вимоги або структурні стани.

Наприклад:

- фігура одночасно має підтримувати захист короля та атакувати іншу ділянку;
- блокування однієї лінії захищає одну структуру, але послаблює іншу;
- два потенційні плани потребують несумісних ходів.

CONFLICT не повинен автоматично перетворюватися на числовий штраф.

Спочатку необхідно визначити природу конфлікту.

# 6. РІВНІ ВЗАЄМОДІЇ

Взаємодії повинні класифікуватися за просторовим масштабом.

## 6.1. SQUARE-LEVEL

Локальна взаємодія на одному квадраті.

Приклади:

- атака;
- захист;
- контроль;
- блокування;
- накладання.

## 6.2. PIECE-LEVEL

Взаємодія між конкретними фігурами.

Приклади:

- підтримка;
- зв'язування;
- координація;
- взаємне обмеження;
- залежність мобільності.

## 6.3. LINE-LEVEL

Взаємодія на вертикалі, горизонталі або діагоналі.

Приклади:

- відкриття вертикалі;
- блокування діагоналі;
- подвійний контроль лінії;
- проникнення;
- перехресна атака.

## 6.4. ZONE-LEVEL

Взаємодія в межах структурної зони.

Приклади:

- контроль центру;
- тиск на королівський фланг;
- обмеження ферзевого флангу;
- підтримка проходження пішака.

## 6.5. POSITION-LEVEL

Глобальна взаємодія полів усієї позиції.

Приклади:

- координація фігур;
- баланс атаки та захисту;
- взаємозалежність королівської безпеки й активності;
- структурна цілісність;
- конфлікт стратегічних планів.

Рівні не повинні зливатися.

Локальна взаємодія може бути частиною глобального процесу, але глобальний висновок потребує окремого оператора агрегації.

# 7. МОДЕЛЬ ГРАФА ВЗАЄМОДІЙ

Для представлення взаємодій визначимо:

Gᵢ = (Vᵢ,Eᵢ)

де:

- Vᵢ — множина полів та їхніх структурних компонентів;
- Eᵢ — множина взаємодій.

Вузлами можуть бути:

- окремі поля;
- джерела поля;
- цільові квадрати;
- фігури;
- лінії;
- зони;
- структурні характеристики.

Ребро:

e = (Fₐ,Type,Fᵦ)

Наприклад:

ROOK_ATTACK  
→ REINFORCEMENT  
→ QUEEN_ATTACK

Або:

PAWN_BLOCK  
→ BLOCKING  
→ BISHOP_ACCESSIBILITY

## 7.1. Орієнтованість

Взаємодії можуть бути:

- спрямованими;
- двоспрямованими;
- симетричними;
- асиметричними.

Наприклад:

A ENABLES B

не означає:

B ENABLES A

Тому напрямок повинен зберігатися.

## 7.2. Гіперграф

Деякі взаємодії не можуть бути повноцінно представлені одним ребром.

Наприклад, координація трьох фігур або взаємодія декількох полів навколо короля.

Для таких випадків вводиться гіперграф:

HG = (V,H)

де H — множина гіперребер, кожне з яких може поєднувати більше двох вузлів.

Приклад:

H₁ = {ROOK_FIELD, QUEEN_FIELD, KNIGHT_FIELD, KING_ZONE}

Такий гіперзв'язок може описувати багатофігурну координацію.

Гіперграф не є обов'язковим для першої реалізації FD-08.

Початковою реалізацією може бути звичайний орієнтований граф із можливістю подальшого розширення.

# 8. СУПЕРПОЗИЦІЯ ПОЛІВ

## 8.1. Базова операція

Для сумісних полів одного типу:

F_total(q) = Σᵢ Fᵢ(q)

Ця операція допустима лише за умови, що:

1. поля мають однакову семантику;
2. їхні числові шкали сумісні;
3. вони належать до одного контексту;
4. вони мають сумісну просторову область;
5. відсутні дубльовані внески;
6. збережено походження кожного внеску.

## 8.2. Канали сторін

Суперпозиція виконується окремо:

F_WHITE(q) = Σ Fᵢ(q), owner=WHITE

F_BLACK(q) = Σ Fⱼ(q), owner=BLACK

F_SHARED(q) = Σ Fₖ(q), owner=SHARED

F_NEUTRAL(q) = Σ Fₘ(q), owner=NEUTRAL

Загальний показник може бути побудований пізніше.

Він не повинен знищувати вихідні канали.

## 8.3. Заборона передчасного взаємного погашення

Неприпустимо:

F_WHITE(q) − F_BLACK(q) = 0

і на цій підставі робити висновок про відсутність впливу.

Правильний результат:

FieldState(q) = CONTESTED

із збереженням обох каналів.

Наприклад:

WHITE_ATTACK(q) = 2

BLACK_DEFENSE(q) = 2

Це не означає відсутності атаки та захисту.

Це означає, що поле має два конкуруючі впливи.

## 8.4. Зважена суперпозиція

Зважене об'єднання:

F_total(q) = Σᵢ wᵢ · Fᵢ(q)

можливе лише після:

- визначення спільної шкали;
- нормалізації;
- калібрування коефіцієнтів;
- визначення цільової функції;
- перевірки чутливості результату.

Коефіцієнти wᵢ не повинні вводитися довільно.

Вони мають бути окремо обґрунтовані та перевірені.

FD-08 не визначає універсальні ваги шахових полів.

# 9. НЕЛІНІЙНІ ВЗАЄМОДІЇ

Лінійна суперпозиція не може описати всі шахові відношення.

Наприклад, підтримка фігури може мати різне значення залежно від:

- наявності блокатора;
- можливості розміну;
- зв'язування;
- королівської безпеки;
- черговості ходу;
- тактичної послідовності.

Тому вводиться окремий оператор:

I(Fᵢ,Fⱼ | S,C)

Його результат може бути категоріальним або числовим.

Для кількох полів:

Iₙ(F₁,...,Fₙ | S,C)

Це дозволяє описувати складні взаємозалежності.

## 9.1. Відсутність автоматичної адитивності

Загалом:

I(F₁,F₂) ≠ F₁ + F₂

Взаємодія може створювати нову властивість, яка не присутня в кожному полі окремо.

Наприклад, окремі атаки двох фігур можуть утворювати подвійний удар.

Подвійний удар є структурним результатом взаємодії, а не просто сумою двох атак.

## 9.2. Контекстуальна залежність

Одна й та сама пара полів може мати різні результати в різних позиціях.

Тому:

I(F₁,F₂ | S₀) ≠ I(F₁,F₂ | S₁)

Навіть якщо вихідні геометричні характеристики частково збігаються.

---

# 10. РОЗДІЛЕННЯ АНАЛІТИЧНИХ РІВНІВ

FD-08 встановлює обов'язкове розділення чотирьох рівнів.

## 10.1. GEOMETRIC INTERACTION

Описує геометричні відношення.

Наприклад:

- дві фігури контролюють один квадрат;
- фігура перекриває лінію;
- дві лінії перетинаються.

## 10.2. LEGAL INTERACTION

Враховує правила шахів.

Наприклад:

- фігура геометрично атакує квадрат, але не може виконати певний хід через шах королю;
- зв'язана фігура має обмежену множину легальних ходів;
- рокіровка змінює доступність королівських полів.

## 10.3. TACTICAL INTERACTION

Визначає тактичні наслідки.

Наприклад:

- подвійний удар;
- зв'язування;
- відкритий напад;
- відволікання;
- перевантаження;
- матова загроза.

## 10.4. STRATEGIC INTERACTION

Описує довгострокові структурні наслідки.

Наприклад:

- контроль відкритої вертикалі;
- координація фігур;
- обмеження суперника;
- створення слабкостей;
- підтримка проходження пішака.

## 10.5. PREDICTED INTERACTION

Описує можливу взаємодію після майбутнього ходу.

Вона повинна мати статус прогнозу, а не факту.

Жодна геометрична взаємодія не повинна автоматично перетворюватися на легальний хід, тактичну можливість або стратегічну перевагу.

# 11. СТАНИ ВЗАЄМОДІЇ

Кожна взаємодія повинна мати один із таких станів:

ACTIVE  
INACTIVE  
LATENT  
BLOCKED  
TRANSFORMED  
CONFLICTED  
UNRESOLVED  
UNKNOWN  
STALE

Значення:

ACTIVE — взаємодія підтверджена в поточному контексті.

INACTIVE — взаємодія не діє.

LATENT — існує потенційно, але ще не активована.

BLOCKED — взаємодія обмежена перешкодою.

TRANSFORMED — її структура змінилася після ходу.

CONFLICTED — виявлено несумісні впливи.

UNRESOLVED — взаємодія визначена частково, але висновок не завершений.

UNKNOWN — даних недостатньо.

STALE — результат належить до застарілого стану позиції.

Критичне правило:

UNKNOWN ≠ ZERO.

Відсутність даних не є доказом відсутності взаємодії.

# 12. ПОХОДЖЕННЯ ТА ЗАПОБІГАННЯ ДУБЛЮВАННЮ

Один із ризиків суперпозиції — подвійний підрахунок одного джерела.

Наприклад, одна геометрична атака може бути відображена:

- у полі атаки;
- у полі доступності;
- у похідному полі контролю;
- у полі стратегічного впливу.

Ці структури можуть посилатися на одну первинну подію.

Якщо всі вони будуть додані як незалежні внески, двигун отримає штучне збільшення впливу.

Тому кожне поле повинно мати:

SourceID  
FieldID  
DerivationID  
ParentFieldIDs  
PositionHash  
OperatorVersion

Для похідних полів необхідно зберігати зв'язок із первинними джерелами.

Правило:

Один первинний факт не повинен автоматично враховуватися декілька разів лише тому, що він представлений у різних аналітичних структурах.

Для об'єднання необхідна перевірка походження.

## 13.2. Етап 1 — перевірка цілісності

Перевірити:

- чи існують усі посилання;
- чи відповідають поля поточній позиції;
- чи узгоджені їхні типи;
- чи не є дані застарілими;
- чи збережено походження.

## 13.3. Етап 2 — визначення кандидатів

Створити множину потенційних взаємодій.

Не потрібно перевіряти кожне поле з кожним.

Кандидати відбираються за:

- просторовим перетином;
- спільними джерелами;
- спільними цілями;
- структурною залежністю;
- напрямком;
- належністю до однієї зони;
- відомими правилами взаємодії.

## 13.4. Етап 3 — перевірка сумісності

Для кожної пари:

Compatible(Fᵢ,Fⱼ)

Результат:

TRUE — дозволити сумісні операції.

FALSE — заборонити безпосередню суперпозицію.

UNKNOWN — зберегти невизначеність.

## 13.5. Етап 4 — класифікація взаємодії

Визначити один або декілька типів:

REINFORCEMENT  
OPPOSITION  
BLOCKING  
ENABLING  
OVERLAP  
INTERSECTION  
COMPLEMENTARITY  
DEPENDENCY  
TRANSFORMATION  
COMPETITION  
CONFLICT

Одна пара полів може мати декілька незалежних відношень.

Наприклад, одна фігура може одночасно блокувати лінію та захищати короля.

## 13.6. Етап 5 — побудова Interaction Graph

Створити вузли та ребра.

Зберегти:

- напрямок;
- тип;
- рівень;
- контекст;
- походження;
- стан;
- докази.

## 13.7. Етап 6 — суперпозиція сумісних полів

Виконати об'єднання лише для тих полів, для яких:

Compatible = TRUE.

Несумісні поля залишаються окремими, але можуть бути пов'язані через Interaction Graph.

## 13.8. Етап 7 — перевірка результату

Перевірити:

- відсутність подвійного підрахунку;
- збереження каналів сторін;
- коректність напрямків;
- сумісність шкал;
- актуальність контексту;
- цілісність походження.

## 13.9. Етап 8 — формування результату

Результат:

FieldInteractionState = (F,Gᵢ,A,U,P)

де:

- F — вихідні поля;
- Gᵢ — граф взаємодій;
- A — допустимі агреговані структури;
- U — невизначені та конфліктні стани;
- P — походження й докази.

# 14. ОНОВЛЕННЯ ПІСЛЯ ШАХОВОГО ХОДУ

Нехай:

S₀ → S₁

Після виконання ходу не потрібно безумовно перебудовувати всі взаємодії.

Необхідно визначити залежності між полями.

Для кожного ходу:

1. визначити змінені фігури;
2. визначити змінені квадрати;
3. визначити змінені лінії;
4. визначити змінені поля;
5. визначити залежні взаємодії;
6. позначити застарілі результати;
7. перебудувати лише необхідні компоненти;
8. перевірити узгодженість інкрементального результату.

Визначимо:

Affected(Fᵢ,m)

як предикат, що показує, чи впливає хід m на поле Fᵢ.

Тоді:

Affected(Iᵢⱼ,m) =
Affected(Fᵢ,m) ∨ Affected(Fⱼ,m) ∨ Affected(C,m)

де C — контекст взаємодії.

Особливо важливо враховувати приховані залежності.

Наприклад, переміщення фігури може змінити поле тури, яка стоїть на іншому кінці вертикалі.

Тому оновлення лише локального квадрата є недостатнім.

# 18. ОБЧИСЛЮВАЛЬНА СКЛАДНІСТЬ

Нехай:

n = кількість полів.

Наївна перевірка всіх пар має складність:

O(n²)

Проте для практичного використання це не обов'язково.

Можна використовувати:

- просторову індексацію;
- індекси джерел;
- індекси цільових квадратів;
- індекси ліній;
- індекси зон;
- граф залежностей;
- інкрементальне оновлення.

Тоді перевірка обмежується множиною потенційно пов'язаних полів.

Якщо k — кількість кандидатів для взаємодії, то основна складність становить:

O(k)

для вже сформованого набору кандидатів.

Суперпозиція сумісних числових полів має складність, пропорційну кількості їхніх внесків.

Побудова повного гіперграфа може бути значно дорожчою, тому вона не повинна бути обов'язковою для кожної позиції.

# 19. ВИМОГИ ДО ТЕСТУВАННЯ

## 19.1. Тест сумісності

Два поля однакового типу, шкали й контексту повинні бути сумісними.

Поля різних семантичних типів не повинні безпосередньо додаватися.

## 19.2. Тест незалежності порядку

Для сумісної адитивної суперпозиції:

F₁ + F₂ = F₂ + F₁

Результат не повинен залежати від порядку надходження полів.

## 19.3. Тест збереження сторін

WHITE та BLACK повинні залишатися окремими каналами.

Протилежні впливи не повинні автоматично взаємно погашатися.

## 19.4. Тест невідомого значення

UNKNOWN не повинно інтерпретуватися як ZERO.

Відсутність поля не повинна створювати штучне нульове значення.

## 19.5. Тест походження

Два похідні поля, що представляють один первинний факт, не повинні автоматично рахуватися як два незалежні внески.

## 19.6. Тест блокування

Блокування лінії повинно змінювати відповідні взаємодії, але не знищувати первинне геометричне походження поля.

## 19.7. Тест подвійної атаки

Дві незалежні атаки на різні цілі повинні зберігатися як окремі поля та формувати відповідну тактичну взаємодію лише за наявності необхідних умов.

## 19.8. Тест зв'язаної фігури

Геометрична атака зв'язаної фігури не повинна автоматично інтерпретуватися як повноцінна легальна дія.

## 19.9. Тест перетворення

Після переміщення пішака необхідно оновити залежні поля, зокрема відкриті діагоналі та вертикалі.

## 19.10. Тест інкрементального оновлення

Результат інкрементального оновлення повинен збігатися з результатом повного перерахунку:

IncrementalUpdate(S₀,m) = FullRecompute(S₁)

за однакової версії операторів та однакового контексту.

## 19.11. Тест конфлікту

Наявність двох протилежних полів повинна створювати CONFLICTED або інший відповідний стан, а не автоматично ZERO.

## 19.12. Тест збереження семантики

Суперпозиція не повинна перетворювати геометричне поле на тактичне або стратегічне без відповідного оператора.

# 23. НАСТУПНИЙ ЕТАП

## FD-09 — FIELD DYNAMICS INTEGRATION INTO POSITION EVALUATION

Після визначення полів, їхніх операторів, циркуляції та взаємодій необхідно перейти до питання, як ці структури можуть впливати на оцінювання шахової позиції.

FD-09 має визначити:

1. як представити результати FD-01 — FD-08 у системі оцінювання;
2. як зберегти незалежність різних характеристик позиції;
3. як відокремити опис поля від його стратегічної інтерпретації;
4. як визначити внесок поля в оцінювання;
5. як враховувати взаємодії без подвійного підрахунку;
6. як враховувати сторону, що ходить;
7. як оцінювати зміну структури після ходу;
8. як передавати результати до пошукового механізму;
9. як перевіряти стабільність оцінювання;
10. як уникнути довільної вагової функції.

Ключове питання FD-09:

**Як перетворити структурний опис шахової позиції на обґрунтовану оцінку, не втрачаючи інформації, з якої ця оцінка була отримана?**

Це наступний перехід від FIELD DYNAMICS до POSITION EVALUATION.
