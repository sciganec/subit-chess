# 1. Мета FD-02

FD-01 встановив фундаментальну відповідність між векторним аналізом та структурою шахової позиції.

FD-02 переходить до наступного рівня: формального визначення того, що саме є шаховим структурним полем, з яких елементів воно складається, як формується, які властивості має та яким чином взаємодіє з іншими полями.

Головне завдання — створити онтологію, придатну для безпосереднього програмного представлення.

Ми повинні перейти від загального твердження:

> Шахова позиція породжує множину структурних полів.

до конкретної моделі:

> Кожне поле має тип, джерело, ціль, напрямок, інтенсивність, контекст, набір відношень та правила трансформації.

Це дозволить FIELD DYNAMICS стати обчислювальним шаром SUBIT-CHESS, а не лише концептуальною моделлю.

# 2. Fundamental Ontological Model

Визначимо шахове структурне поле:

**F = (τ, S, X, Y, D, I, R, C, P)**

де:

- τ — тип поля;
- S — шаховий стан, з якого поле формується;
- X — множина джерел;
- Y — множина цілей;
- D — напрямлені відношення;
- I — інтенсивність впливу;
- R — структурні відношення;
- C — контекст;
- P — provenance.

Поле не є самостійним шаховим об'єктом.

Воно є похідною структурою, що формується з конкретного стану.

Отже:

F = Φ(S, τ, C)

де Φ — функція побудови поля.

Для однієї позиції S можуть існувати різні поля:

F₁ = Φ(S, ATTACK, C)

F₂ = Φ(S, DEFENSE, C)

F₃ = Φ(S, MOBILITY, C)

F₄ = Φ(S, ACCESSIBILITY, C)

F₅ = Φ(S, SUPPORT, C)

F₆ = Φ(S, OBSTRUCTION, C)

Кожне поле описує окремий аспект позиційної структури.

---

# 3. Chess State Dependency

Побудова поля повинна спиратися на повний шаховий стан.

Визначимо:

S = (B, W, K, E, H, T)

де:

- B — конфігурація фігур на дошці;
- W — сторона, що має виконати хід;
- K — права рокірування;
- E — можливість взяття на проході;
- H — історія ходів, релевантна для правил і повторень;
- T — лічильники та інші часові параметри.

Для FIELD DYNAMICS особливо важливо розділяти два типи інформації.

### 3.1. Static Position Context

Включає:

- розташування фігур;
- типи фігур;
- колір;
- зайнятість квадратів;
- геометричні відношення;
- актуальні лінії атаки;
- актуальні блокування.

### 3.2. Dynamic Position Context

Включає:

- сторону ходу;
- легальні трансформації;
- історично залежні права;
- можливі наступні стани;
- попередні переміщення;
- контекст повторення;
- часові обмеження партії.

Не всі поля потребують усіх компонентів контексту.

Наприклад, геометричне поле атак не повинно змінюватися лише через те, що змінилася сторона ходу, якщо розташування фігур залишилося тим самим.

Але поле легальних можливостей може змінюватися залежно від сторони ходу.

Тому кожен тип поля повинен визначати власну залежність від компонентів S.

# 4. Field Types

FD-02 встановлює розширену класифікацію структурних полів.

## 4.1. ATTACK FIELD

**ID:** FD-FIELD-001

Описує атакуючі відношення між фігурами та квадратами.

Формально:

AF(q, c, S)

де:

- q — цільовий квадрат;
- c — сторона;
- S — шаховий стан.

Початкове визначення:

AF(q, c, S) = Σᵢ Aᵢ(q, S)

де Aᵢ — внесок окремої фігури сторони c у контроль квадрата q.

Важливе розрізнення:

**Attack ≠ Legal Move.**

Фігура може атакувати квадрат, на який не може легально переміститися.

Наприклад, король атакує сусідні квадрати, навіть якщо вони контролюються фігурами суперника.

Це розрізнення критично важливе для коректного визначення шаху, захисту короля та легальності ходів.

---

## 4.2. DEFENSE FIELD

**ID:** FD-FIELD-002

Описує відношення захисної підтримки.

DF(q, c, S)

Визначає, які фігури сторони c контролюють квадрат q з погляду атакувальної геометрії.

Проте захист не можна зводити лише до кількості захисників.

Необхідно враховувати:

- цінність захищеної фігури;
- цінність атакуючої фігури;
- кількість атак і захистів;
- порядок взяттів;
- можливість тактичного перевантаження;
- абсолютні та відносні зв'язки;
- pinned pieces;
- королівські обмеження.

Тому DEFENSE FIELD на першому етапі повинен описувати геометричну підтримку, а тактичну ефективність захисту передавати спеціалізованому аналізатору.

---

## 4.3. MOBILITY FIELD

**ID:** FD-FIELD-003

Описує потенціал зміни положення фігур.

MF(p, S)

де p — конкретна фігура.

Визначимо:

M(p, S) = |L(p, S)|

де L(p, S) — множина допустимих легальних ходів фігури p.

Однак для FIELD DYNAMICS кількість ходів є лише одним із показників.

Додатково враховуються:

- доступність центральних квадратів;
- відкритість ліній;
- можливість проникнення;
- обмеження маршрутів;
- кількість стратегічно релевантних цілей;
- можливість зміни напрямку впливу.

Необхідно розрізняти:

**Geometric Mobility** — геометричні можливості переміщення.

**Legal Mobility** — легальні ходи.

**Strategic Mobility** — позиційна корисність доступних переміщень.

Ці величини не є взаємозамінними.

---

## 4.4. ACCESSIBILITY FIELD

**ID:** FD-FIELD-004

Описує структурну доступність квадратів для фігур.

ACF(q, p, S)

На відміну від Mobility Field, який описує можливості фігури, Accessibility Field характеризує доступність конкретної цілі.

Приклади:

- чи може кінь потрапити на центральний квадрат;
- чи має тура відкриту вертикаль;
- чи може слон проникнути на діагональ;
- чи може ферзь досягти слабкого квадрата;
- чи доступна фігурі зона короля суперника.

Для дальніх фігур доступність повинна враховувати блокування.

Для коней — специфічну геометрію ходів.

Для пішаків — напрямок руху, зайнятість та правила взяття.

---

## 4.5. SUPPORT FIELD

**ID:** FD-FIELD-005

Описує відношення взаємної підтримки.

SF(pᵢ, pⱼ, S)

Тут джерелом є фігура pᵢ, а ціллю — фігура pⱼ.

Базова підтримка існує, якщо pᵢ атакує квадрат, на якому розташована pⱼ.

Однак необхідно відрізняти:

- геометричну підтримку;
- легальну можливість захисту;
- тактично ефективну підтримку;
- стратегічну взаємозалежність.

Наприклад, фігура може геометрично захищати іншу, але бути зв'язаною і не мати можливості легально виконати відповідне взяття.

Тому SUPPORT FIELD повинен зберігати тип підтримки, а не лише бінарне значення.

---

## 4.6. OBSTRUCTION FIELD

**ID:** FD-FIELD-006

Описує перешкоди, які обмежують структурний вплив.

OF(p, q, S)

де p — фігура або джерело, q — цільовий квадрат.

Обструкція може виникати через:

- зайняті квадрати;
- власні фігури;
- фігури суперника;
- блоковані лінії;
- пішакові ланцюги;
- обмеження руху;
- королівські заборони.

Особливо важливе розрізнення:

**Obstruction ≠ Negative Influence.**

Перешкода може бути як негативною, так і позитивною.

Наприклад, власний пішак може блокувати слона, але одночасно забезпечувати захист короля.

Отже, значення обструкції залежить від контексту та цілі аналізу.

---

# 5. Field Source Ontology

Кожне поле повинно мати визначене джерело впливу.

Визначимо множину джерел:

X = P ∪ Z ∪ R

де:

- P — шахові фігури;
- Z — групи квадратів або позиційні зони;
- R — структурні відношення.

### 5.1. Piece Sources

Окрема шахова фігура.

Наприклад:

SOURCE = White Bishop on c4.

### 5.2. Zone Sources

Структурна область.

Наприклад:

SOURCE = White kingside pawn structure.

### 5.3. Relational Sources

Відношення між фігурами.

Наприклад:

SOURCE = rook battery on the open file.

Це дозволяє надалі розширити FIELD DYNAMICS від геометрії окремих фігур до аналізу цілих структур.

---

# 6. Field Target Ontology

Ціллю поля може бути:

- окремий квадрат;
- фігура;
- множина квадратів;
- лінія;
- діагональ;
- вертикаль;
- зона;
- король;
- структурне відношення;
- потенційний маршрут.

Формально:

Y = Q ∪ P ∪ Z ∪ L ∪ R

де:

- Q — квадрати;
- P — фігури;
- Z — позиційні зони;
- L — шахові лінії;
- R — структурні відношення.

Це принципове розширення.

Поле атаки може бути спрямоване на квадрат, а поле підтримки — на фігуру.

Поле проникнення може бути спрямоване на зону.

Поле блокування може бути спрямоване на маршрут.

Отже, універсальна модель повинна підтримувати різні типи цілей.

---

# 7. Directionality Ontology

Напрямок є фундаментальною характеристикою FIELD DYNAMICS.

Визначимо:

D = (source, target, orientation, relation)

Напрямок може бути:

1. Геометричним.
2. Атакувальним.
3. Захисним.
4. Мобільним.
5. Стратегічним.
6. Потенційним.

Наприклад, біла тура на a1 може мати геометричний напрямок впливу вздовж першої горизонталі та вертикалі a.

Але стратегічний напрямок її використання може бути спрямований на проникнення через відкриту вертикаль.

Тому геометричний напрямок і стратегічний напрямок повинні зберігатися окремо.

---

# 8. Field Intensity

Інтенсивність характеризує силу структурного відношення.

I(x, y, S, τ)

де:

- x — джерело;
- y — ціль;
- S — стан;
- τ — тип поля.

Важливо не використовувати одну універсальну шкалу для всіх типів полів.

Наприклад:

- кількість атак — натуральне число;
- доступність — може бути дискретною або нормованою величиною;
- підтримка — може враховувати кілька параметрів;
- блокування — може бути категоріальним;
- стратегічний потенціал — може бути оцінювальною функцією.

Отже, тип інтенсивності повинен визначатися типом поля.

Рекомендоване представлення:

FieldValue = (magnitude, scale, semantics)

де:

- magnitude — значення;
- scale — шкала;
- semantics — значення та правила інтерпретації.

---

# 9. Field Ownership

Кожне поле повинно мати належність до сторони.

Визначимо:

Owner(F) ∈ {WHITE, BLACK, SHARED, NEUTRAL}

Це дозволяє представляти:

- поле білого впливу;
- поле чорного впливу;
- спільно контрольовану область;
- нейтральну структурну область.

Проте спільний контроль не обов'язково означає рівність сил.

Наприклад, квадрат може атакуватися обома сторонами, але мати різну кількість атак і захистів.

Тому:

Owner(F) не замінює Intensity(F).

Належність та інтенсивність — різні характеристики.

---

# 10. Field Relations

Поля повинні мати можливість взаємодіяти.

Визначимо множину відношень:

R = {
SUPPORTS,
ATTACKS,
BLOCKS,
ENABLES,
RESTRICTS,
INTERSECTS,
OVERLAPS,
REINFORCES,
OPPOSES,
DEPENDS_ON
}

Приклади:

- ATTACK FIELD атакує квадрат.
- DEFENSE FIELD підтримує фігуру.
- OBSTRUCTION FIELD блокує маршрут.
- MOBILITY FIELD забезпечує доступність.
- SUPPORT FIELD підсилює локальну структуру.

Ці відношення утворюють основу майбутнього графа взаємодії полів.

Важливе правило:

Не всі відношення є симетричними.

Наприклад:

A SUPPORTS B

не означає:

B SUPPORTS A.

Так само:

A BLOCKS B

не означає:

B BLOCKS A.

Тому граф FIELD DYNAMICS повинен підтримувати напрямлені відношення.

---

# 11. Field Interaction

Взаємодія полів може бути:

### 11.1. Reinforcement

Одне поле підсилює інше.

Наприклад, атака тури підтримується слоном.

### 11.2. Opposition

Поля створюють протилежний вплив.

Наприклад, атака однієї сторони нейтралізується захистом іншої.

### 11.3. Blocking

Одне поле обмежує інше.

### 11.4. Complementarity

Два поля створюють спільний ефект, який не виникає від кожного окремо.

Наприклад, ферзь і слон координують атаку на короля.

### 11.5. Dependency

Одне поле існує лише за певних структурних умов.

Наприклад, атака тури по вертикалі залежить від відсутності блокуючих фігур.

### 11.6. Transformation

Зміна одного поля спричиняє зміну іншого.

Наприклад, переміщення пішака відкриває діагональ слону, змінюючи поле атаки.

---

# 12. Field Context Ontology

Кожне поле повинно зберігати контекст.

Визначимо:

C(F) = (Cₛ, Cₜ, Cₕ, Cᵣ)

де:

- Cₛ — статичний контекст;
- Cₜ — контекст сторони ходу;
- Cₕ — історичний контекст;
- Cᵣ — контекст шахових правил.

Не всі компоненти обов'язкові для кожного поля.

Наприклад, геометричне поле атак залежить передусім від розташування фігур.

Поле легальних можливостей залежить також від сторони ходу, шахових обмежень та спеціальних правил.

Таким чином, FIELD DYNAMICS повинна використовувати контекстну залежність, а не одну універсальну функцію.

---

# 13. Field State

Поле може перебувати в одному з кількох структурних станів.

**ACTIVE** — поле має актуальний вплив.

**INACTIVE** — поле не має актуального впливу.

**BLOCKED** — потенційний вплив обмежений.

**LATENT** — поле може активуватися після певної трансформації.

**TRANSFORMED** — поле змінило свою структуру.

**CONFLICTED** — поле взаємодіє з протилежним полем.

**UNRESOLVED** — інформації недостатньо для визначення стану.

Останній стан важливий: двигун не повинен автоматично прирівнювати відсутність обчисленого результату до нульового впливу.

---

# 14. Field Transformation

Поле змінюється внаслідок шахового ходу.

Нехай:

S₀ — початкова позиція.

m — легальний хід.

S₁ = Tₘ(S₀) — позиція після ходу.

Тоді:

F₀ = Φ(S₀, τ)

F₁ = Φ(S₁, τ)

Зміна поля:

ΔF = F₁ − F₀

Ця різниця може характеризувати:

- появу нових атак;
- втрату контролю;
- відкриття ліній;
- зміну підтримки;
- появу блокувань;
- зміну доступності;
- виникнення нових структурних можливостей.

Проте віднімання можливе лише для полів із сумісними числовими представленнями.

Для категоріальних полів необхідно використовувати операцію структурної різниці:

ΔₛF = Difference(F₀, F₁)

Це важливе розрізнення для подальшої реалізації.

Структура цілі:

```text
FieldTarget
│
├── target_id
├── target_type
├── square
├── piece_id
├── zone_id
└── structural_reference
```

Це логічна схема даних, а не вимога використовувати саме таку структуру типів у фінальній мові програмування.

---

# 16. Field Graph

Онтологія дозволяє сформувати граф структурних полів.

Позначимо:

G_F(S) = (V_F, E_F)

де:

- V_F — вузли, що представляють поля, джерела та цілі;
- E_F — напрямлені структурні відношення.

Приклад:

White Rook  
↓ ATTACKS  
Open File  
↓ ENABLES  
Penetration Square  
↓ THREATENS  
Black Pawn

Інший приклад:

White Bishop  
↓ SUPPORTS  
White Knight  
↓ CONTROLS  
Central Square

Граф повинен зберігати походження кожного відношення.

Це дозволить у наступних етапах застосувати мережевий аналіз та топологічні методи без необхідності повторно будувати всю шахову геометрію.

Водночас FD-02 лише визначає можливість такого представлення. Повноцінна мережева аналітика буде розроблятися окремо.

---

# 17. Separation of Geometric and Strategic Fields

Це одна з найважливіших архітектурних вимог.

Необхідно розділяти:

**Geometric Field**

Описує фактичні геометричні відношення між фігурами та квадратами.

**Legal Field**

Описує допустимість конкретних ходів згідно з шаховими правилами.

**Strategic Field**

Описує потенційну позиційну цінність структурних відношень.

**Predicted Field**

Описує очікувану структуру після потенційної трансформації.

Наприклад, тура може геометрично контролювати вертикаль, але її проникнення може бути тактично неможливим.

Отже, геометричний вплив не гарантує стратегічної ефективності.

FIELD DYNAMICS повинна зберігати ці рівні окремо.

# 19. Computational Efficiency Requirements

Повна побудова всіх можливих відношень для кожного квадрата та кожної фігури на кожному вузлі пошуку може бути надмірно дорогою.

Тому FD-02 встановлює такі принципи.

### 19.1. Incremental Construction

Після ходу не обов'язково перебудовувати всі поля з нуля.

Можна оновлювати лише поля, на які вплинула трансформація.

### 19.2. Lazy Evaluation

Поля, які не потрібні для поточного аналізу, можуть обчислюватися за запитом.

### 19.3. Shared Representation

Геометричні відношення повинні використовуватися кількома полями, щоб уникнути дублювання.

### 19.4. Contextual Caching

Кешування допускається лише за умови коректного врахування залежностей від стану та контексту.

### 19.5. Exactness Separation

Точні шахові характеристики не повинні змішуватися з евристичними стратегічними оцінками.

Наприклад, факт атаки квадрата повинен залишатися точним результатом геометричного аналізу, тоді як стратегічна цінність контролю цього квадрата може бути евристичною.

**FD02-R001.** Кожне поле повинно мати тип.

**FD02-R002.** Кожне поле повинно мати визначене джерело або набір джерел.

**FD02-R003.** Кожне поле повинно підтримувати визначені цілі.

**FD02-R004.** Напрямлені відношення повинні зберігатися явно.

**FD02-R005.** Інтенсивність повинна мати типізовану шкалу.

**FD02-R006.** Належність до сторони повинна бути відокремлена від інтенсивності.

**FD02-R007.** Поле повинно зберігати контекст.

**FD02-R008.** Поле повинно мати визначений структурний стан.

**FD02-R009.** Поле повинно підтримувати трансформацію між шаховими станами.

**FD02-R010.** Геометричні та стратегічні поля повинні бути розділені.

**FD02-R011.** Геометрична атака не повинна ототожнюватися з легальним ходом.

**FD02-R012.** Поля повинні підтримувати структурні відношення.

**FD02-R013.** Взаємодії полів повинні підтримувати напрямленість.

**FD02-R014.** Структура повинна підтримувати provenance.

**FD02-R015.** Система повинна підтримувати інкрементальне оновлення.

**FD02-R017.** Різниця між полями повинна враховувати сумісність їхніх типів.

**FD02-R018.** Поля повинні бути похідними від шахового стану, а не замінювати його.

# 21. Validation Scenarios

Перед переходом до FD-03 онтологія повинна пройти такі концептуальні перевірки.

### Test 01 — Open File

Тура отримує відкриту вертикаль.

Очікувано:

- ATTACK FIELD відображає контроль відповідних квадратів;
- ACCESSIBILITY FIELD відображає можливість проникнення;
- OBSTRUCTION FIELD не повинно показувати неіснуюче блокування;
- STRATEGIC FIELD може оцінити потенціал проникнення окремо.

### Test 02 — Blocked Bishop

Слон має заблоковану діагональ.

Очікувано:

- геометричний вплив обмежується блокуванням;
- OBSTRUCTION FIELD фіксує перешкоду;
- ACCESSIBILITY FIELD не трактує заблоковані квадрати як безумовно доступні;
- зміна позиції після переміщення пішака породжує відповідну трансформацію полів.

### Test 03 — Double Attack

Дві фігури атакують один квадрат.

Очікувано:

- обидва джерела зберігаються;
- інтенсивність не втрачає інформацію про походження;
- агреговане значення не замінює індивідуальні відношення.

### Test 04 — Pinned Piece

Фігура геометрично атакує квадрат, але не може легально виконати відповідне переміщення через зв'язку.

Очікувано:

- геометричне поле зберігає атаку;
- легальне поле відображає обмеження;
- стратегічна інтерпретація не плутає ці два результати.

### Test 05 — King Attack

Король атакує сусідній квадрат, який контролюється суперником.

Очікувано:

- ATTACK FIELD відображає контроль;
- LEGAL FIELD не допускає відповідний хід короля.

### Test 06 — Field Transformation

Після переміщення фігури відкривається нова лінія.

Очікувано:

- попереднє поле зберігається для порівняння;
- нове поле формується для наступного стану;
- ΔF відображає зміну;
- provenance дозволяє визначити причину трансформації.
