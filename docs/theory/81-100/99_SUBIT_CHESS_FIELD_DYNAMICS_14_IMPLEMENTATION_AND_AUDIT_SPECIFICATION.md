# 1. ПРИЗНАЧЕННЯ

FD-14 завершує специфікаційний цикл FIELD DYNAMICS і визначає процедуру переходу від теоретичної архітектури до реалізованої, протестованої та перевіреної підсистеми SUBIT-CHESS.

Попередні документи FD-01—FD-13 визначили математичні основи, структури даних, оператори, взаємодії, оцінювання, пошукову інтеграцію, оптимізацію, тестування та системні інтерфейси.

Однак специфікація сама по собі не підтверджує існування відповідного програмного забезпечення.

FD-14 встановлює механізм, за допомогою якого кожне положення специфікації має бути зіставлене з:

- конкретним модулем;
- конкретною функцією або структурою даних;
- відповідним тестом;
- результатом виконання;
- доказом відповідності;
- версією коду;
- статусом реалізації.

Основна вимога:

**EVERY SPECIFICATION REQUIREMENT MUST HAVE AN IMPLEMENTATION TRACE AND A VERIFICATION RESULT.**

# 2. ПРИНЦИПИ РЕАЛІЗАЦІЇ

## 2.1. Specification ≠ Implementation ≠ Verification

Необхідно розділяти три незалежні сутності.

**Specification**

Визначає, що система повинна робити.

**Implementation**

Визначає, як вимоги реалізовані в коді.

**Verification**

Підтверджує, що реалізація відповідає вимогам.

Статус одного рівня не переноситься автоматично на інші.

Наприклад:

- специфікація існує;
- відповідний код може бути відсутнім;
- тест може бути написаний, але не виконаний;
- тест може бути виконаний, але не пройти;
- тест може пройти, але не покривати всю вимогу.

Ці стани повинні бути розрізненими.

## 2.2. DO NOT COLLAPSE — CONTEXTUALIZE

Аудит не повинен зводити складну відповідність до одного показника на кшталт «готово на 80%».

Кожна вимога має окремі статуси:

- specification status;
- implementation status;
- test status;
- verification status;
- performance status;
- integration status.

## 2.3. Інкрементальна реалізація

FIELD DYNAMICS повинна впроваджуватися послідовно.

Забороняється інтегрувати всі оператори, взаємодії та пошукові механізми одночасно без перевірки проміжних етапів.

## 2.4. Автономність реалізації

SUBIT-CHESS залишається автономним шаховим рушієм.

Реалізація FIELD DYNAMICS не повинна залежати від:

- сторонніх шахових рушіїв;
- імпортованих шахових партій як навчального джерела;
- зовнішніх оцінок ходів;
- зовнішніх пошукових алгоритмів як компонентів рушія;
- сторонніх бібліотек, які підміняють власну реалізацію шахового ядра.

Внутрішньо згенеровані позиції, самостійний аналіз і self-play можуть використовуватися для тестування та контрольованого вдосконалення.

# 4. TRACEABILITY MATRIX

## 4.1. Призначення

Traceability Matrix забезпечує простежуваність кожної вимоги від специфікації до тесту.

Формат запису:

`TraceRecord = (RequirementId, SpecificationVersion, ModuleId, SymbolId, TestIds, Evidence, Status)`

Де:

- `RequirementId` — ідентифікатор вимоги;
- `SpecificationVersion` — версія документа;
- `ModuleId` — відповідальний модуль;
- `SymbolId` — функція, тип або інший програмний символ;
- `TestIds` — пов'язані тести;
- `Evidence` — результати перевірки;
- `Status` — актуальний статус відповідності.

## 4.2. Напрямки простежуваності

Повна простежуваність повинна працювати в обох напрямках.

**Forward traceability:**

Вимога → модуль → код → тест → результат.

**Backward traceability:**

Код → вимога → тест → обґрунтування існування.

Другий напрямок виявляє код, який не має чіткого архітектурного призначення.

## 4.3. Обов'язкові статуси

`NOT_SPECIFIED`

Вимога ще не визначена.

`SPECIFIED`

Вимогу формалізовано.

`PLANNED`

Реалізацію заплановано.

`IMPLEMENTED`

Код реалізований, але відповідність ще не підтверджена.

`TESTED`

Тест виконаний.

`VERIFIED`

Відповідність підтверджена визначеним набором доказів.

`PARTIAL`

Реалізовано лише частину вимоги.

`BLOCKED`

Реалізація заблокована залежністю або помилкою.

`DEPRECATED`

Вимогу або реалізацію виведено з використання.

`NOT_APPLICABLE`

Вимога обґрунтовано не застосовується до конкретної конфігурації.

Статус `VERIFIED` повинен мати посилання на докази.

# 7. CODE AUDIT PROTOCOL

## 7.1. Перевірка кожного модуля

Для кожного модуля аудит повинен відповісти на такі питання:

1. Яку вимогу він реалізує?
2. Які дані отримує?
3. Які дані повертає?
4. Які припущення використовує?
5. Які інваріанти зобов'язаний зберігати?
6. Які модулі від нього залежать?
7. Які тести перевіряють його поведінку?
8. Які помилки він може створити?
9. Як відновлюється після помилки?
10. Чи можна незалежно перевірити результат?

## 7.2. Static Audit

Перевіряються:

- дублювання коду;
- недосяжні гілки;
- невикористані функції;
- неузгоджені типи;
- приховані глобальні змінні;
- неконтрольовані побічні ефекти;
- небезпечні числові операції;
- помилки керування пам'яттю;
- неузгоджені інтерфейси;
- неявні залежності.

## 7.3. Dynamic Audit

Перевіряються:

- фактична поведінка функцій;
- послідовність викликів;
- узгодженість станів;
- make/unmake;
- кешування;
- помилки після спеціальних ходів;
- пошукові гілки;
- поведінка під навантаженням.

## 7.4. Semantic Audit

Особлива увага приділяється відповідності коду математичній семантиці.

Наприклад, функція з назвою `curl()` не вважається реалізацією ротора лише через назву.

Аудит повинен перевірити:

- домен;
- орієнтацію;
- формулу;
- нормалізацію;
- знаки;
- одиниці;
- обробку невизначених значень;
- граничні випадки.

# 8. КОНТРОЛЬ МАТЕМАТИЧНОЇ КОРЕКТНОСТІ

## 8.1. Геометрія

## 8.2. Градієнт

Для потенціалу φ:

`Gradφ(u→v)=φ(v)−φ(u)`

Контроль:

`Circ(Gradφ,C)=0`

для кожного замкненого циклу C.

## 8.3. Дивергенція

Для скінченного графа перевірити баланс:

`Σᵥ Div J(v) = сумарний зовнішній потік`

За відсутності зовнішніх потоків:

`Σᵥ Div J(v)=0`

## 8.4. Ротор

Перевірити орієнтацію граней, знаки ребер і відповідність циркуляції.

## 8.5. Дискретний Стокс

Для кожної тестової області:

`Σ Curl(J,f)·Area(f)=Circ(J,∂Z)`

## 8.6. Інкрементальна тотожність

Для точних компонентів:

`FD_incremental(S,m)=FD_full(Tₘ(S))`

## 8.7. Make/Unmake

`Unmake(Make(S,m))=S`

Для всіх релевантних польових даних:

`Field_after_undo=Field_before_move`

Ці властивості є обов'язковими контрольними інваріантами.

## 10.4. Незалежність перевірки

Критичні оператори повинні мати контрольну реалізацію або математичний оракул, незалежний від оптимізованого коду.

# 11. PERFORMANCE AUDIT

## 11.1. Базова лінія

До оптимізації необхідно виміряти:

- повний час побудови полів;
- час кожного оператора;
- час оцінювання;
- час оновлення після ходу;
- час пошуку;
- пам'ять.

## 11.2. Порівняння режимів

Порівнюються:

- baseline chess engine;
- full field computation;
- incremental field computation;
- cached computation;
- lazy computation;
- field-assisted search;
- integrated field evaluation.

## 11.3. Контроль коректності

Кожен performance benchmark повинен одночасно контролювати правильність результату.

Швидкість не є доказом коректності.

## 11.4. Оптимізаційні ризики

Особливо перевіряються:

- застарілі кеші;
- некоректна інвалідація;
- помилки при make/unmake;
- повторне використання несумісних станів;
- втрати provenance;
- зміни порядку числового накопичення;
- переповнення;
- надмірна пам'ять;
- надмірна кількість структурних об'єктів.

# 12. RELEASE GATE

FIELD DYNAMICS не може бути оголошена інтегрованою та перевіреною лише на підставі завершення програмування.

Встановлюються чотири рівні приймання.

## LEVEL 1 — MODULE ACCEPTANCE

Кожен окремий модуль:

- реалізований;
- має визначений контракт;
- проходить unit tests;
- має provenance;
- не порушує власних інваріантів.

## LEVEL 2 — INTEGRATION ACCEPTANCE

Модулі:

- працюють із сумісними станами;
- використовують узгоджені контексти;
- коректно передають дані;
- проходять integration tests;
- підтримують відновлення.

## LEVEL 3 — SEARCH ACCEPTANCE

Польова підсистема:

- не порушує легальність;
- не вилучає легальні ходи;
- коректно впливає на move ordering;
- проходить пошукові тести;
- не створює неприпустимого погіршення продуктивності.

## LEVEL 4 — SYSTEM ACCEPTANCE

Система:

- проходить повний regression suite;
- проходить differential testing;
- має відтворювані результати;
- має виміряну продуктивність;
- має повну traceability matrix;
- має задокументовані обмеження.

Лише після LEVEL 4 допускається статус:

`FIELD_DYNAMICS_SYSTEM = VERIFIED`

Цей статус не означає математичного доведення всіх властивостей системи. Він означає проходження визначеного набору перевірок.

Модульна структура та контракти.

Програмна реалізація.

**Testing**

Перевірка функціональної поведінки.

**Audit**

Перевірка коду та відповідності вимогам.

**Verification**

Підтвердження визначених властивостей.

**Release**

Контрольоване включення в рушій.

Жоден етап не може автоматично замінити наступний.
