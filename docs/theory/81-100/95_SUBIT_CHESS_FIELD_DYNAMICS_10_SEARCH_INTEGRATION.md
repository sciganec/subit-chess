# 1. ПРИЗНАЧЕННЯ

FD-10 визначає інтеграцію SUBIT-CHESS FIELD DYNAMICS із пошуковим механізмом шахового двигуна.

Попередні специфікації створили систему, яка дозволяє:

- представляти структурні поля шахової позиції;
- визначати напрямлений вплив;
- обчислювати градієнтні характеристики;
- визначати дивергенцію;
- аналізувати циркуляцію;
- встановлювати взаємодії між полями;
- формувати структуровану оцінку позиції.

FD-10 переводить ці результати в контекст пошуку.

Основне завдання полягає не просто в тому, щоб оцінювати позицію після кожного ходу.

Необхідно визначити, як структурні поля можуть допомагати двигуну:

1. знаходити перспективні кандидатні ходи;
2. встановлювати порядок їх перевірки;
3. визначати структурні наслідки кожного ходу;
4. розпізнавати критичні зміни позиції;
5. зменшувати непотрібні обчислення;
6. зберігати повноту пошуку;
7. підвищувати якість вибору ходів.

Основний принцип:

**FIELD DYNAMICS GUIDES SEARCH — IT DOES NOT REPLACE SEARCH CORRECTNESS.**

Поля допомагають визначати пріоритети аналізу, але не можуть самостійно доводити, що хід є найкращим.

# 2. АРХІТЕКТУРНЕ РОЗДІЛЕННЯ

FD-10 визначає шість окремих компонентів.

## 2.1. LEGAL MOVE GENERATION

Генерація легальних ходів.

Позначення:

L(S) = {m₁,m₂,...,mₙ}

Цей компонент повинен визначати повну множину легальних ходів для позиції S.

Він відповідає за:

- правила руху фігур;
- зайнятість квадратів;
- шах королю;
- зв'язування;
- рокіровку;
- взяття на проході;
- перетворення пішака;
- інші спеціальні правила.

FIELD DYNAMICS не повинна змінювати правила легальності.

## 2.2. FIELD ANALYSIS

Структурний аналіз позиції:

F(S) = Φ(S)

Він визначає поля, які можуть бути використані для оцінювання та аналізу кандидатних ходів.

## 2.3. MOVE STRUCTURAL ANALYSIS

Аналіз структурних наслідків конкретного ходу:

MFD(S,m) = ΔF(S,m)

Визначає:

- які поля виникають;
- які поля зникають;
- які поля змінюються;
- які взаємодії трансформуються;
- які залежності виникають або припиняються.

## 2.4. MOVE ORDERING

Впорядкування кандидатних ходів.

Визначає пріоритет перевірки ходів, не змінюючи їхньої легальності.

## 2.5. SEARCH ENGINE

Пошуковий механізм досліджує дерево легальних ходів.

Він визначає наслідки послідовностей ходів, а не лише окремих переходів.

## 2.6. POSITION EVALUATION

Оцінює позиції за FD-09.

Вона є джерелом статичної оцінки листових або граничних позицій пошуку.

# 3. ЗАГАЛЬНА АРХІТЕКТУРА

Для позиції S:

1. Генеруються легальні ходи L(S).
2. Визначається структурний стан F(S).
3. Для кандидатів формується структурний прогноз.
4. Ходи впорядковуються.
5. Пошуковий алгоритм досліджує їх.
6. Для необхідних позицій виконується оцінювання FD-09.
7. Результати повертаються пошуковому механізму.
8. Найкраща послідовність визначається відповідно до пошукової функції.

Формально:

S → L(S) → MFD(S,m) → Ordering(S) → Search(S) → Evaluation(S)

Важливо, що ця схема не означає повного обчислення всіх полів для кожного кандидатного ходу.

Структурний аналіз повинен підтримувати інкрементальне оновлення.

---

# 4. ПРЕДСТАВЛЕННЯ ПОШУКОВОГО СТАНУ

Визначимо:

SearchState = (S,F,I,E,D)

де:

- S — шахова позиція;
- F — структурні поля;
- I — взаємодії;
- E — результат оцінювання;
- D — залежності та метадані.

Кожен пошуковий вузол повинен мати власний логічний контекст.

Не допускається неконтрольоване використання структурних даних батьківського вузла після зміни позиції.

## 4.1. Position Identity

Для кожної позиції необхідно мати стабільний ідентифікатор.

PositionKey повинен враховувати всі параметри, які впливають на легальні ходи та релевантний стан гри:

- розташування фігур;
- сторону, що ходить;
- права на рокіровку;
- можливість взяття на проході.

Для правил повторення та завершення партії необхідно окремо зберігати відповідну історію.

Однакове розташування фігур не завжди означає однаковий шаховий стан.

## 4.2. Search Node

```text
SearchNode {
    position
    positionKey

    parentNodeId
    incomingMove

    fieldStateId
    interactionStateId
    evaluationStateId

    depth
    alpha
    beta

    nodeType
    searchStatus

    bestMove
    bestScore

    provenance
}
```

## 4.3. Ізоляція станів

Кожен вузол повинен отримувати коректний стан полів для своєї позиції.

Допустимі підходи:

- незалежне обчислення;
- копіювання з контрольованим оновленням;
- незмінні структури;
- стек змін із гарантованим відновленням.

Головна вимога — відсутність витоку змін між гілками пошуку.

# 5. СТРУКТУРНИЙ АНАЛІЗ КАНДИДАТНОГО ХОДУ

Для кожного легального ходу:

m ∈ L(S)

визначимо:

S₁ = T(S,m)

Далі:

ΔF = F(S₁) − F(S)

ΔI = I(S₁) − I(S)

ΔE = E(S₁) − E(S)

Однак ці різниці повинні зберігати типи та походження.

## 5.1. Категорії структурних змін

### A. FIELD_CREATION

Створення нового поля або його активація.

Приклад: переміщення пішака відкриває діагональ слона.

### B. FIELD_REMOVAL

Припинення існування або дії поля.

Приклад: усунення фігури, яка створювала певний контроль.

### C. FIELD_MODIFICATION

Зміна інтенсивності, напрямку, області або контексту поля.

### D. INTERACTION_CREATION

Виникнення нової взаємодії.

Приклад: дві фігури починають координовано атакувати одну ціль.

### E. INTERACTION_REMOVAL

Припинення попередньої взаємодії.

### F. INTERACTION_TRANSFORMATION

Зміна типу або функції взаємодії.

Наприклад, структурне блокування перетворюється на підтримку.

### G. DEPENDENCY_CHANGE

Зміна залежностей між структурними елементами.

### H. IRREVERSIBLE_CHANGE

Зміна, яка не може бути безпосередньо скасована звичайним поверненням фігури.

Приклад: хід пішака або взяття.

---

# 6. ПЕРЕДБАЧЕННЯ СТРУКТУРНИХ НАСЛІДКІВ

Для впорядкування ходів можна використовувати прогноз структурних змін.

Визначимо:

PredictedFieldState(S,m)

Це прогноз стану полів після ходу m.

Він може мати різні рівні достовірності.

## 6.1. EXACT

Точний результат, отриманий через фактичне застосування ходу та перерахунок відповідних полів.

## 6.2. INCREMENTAL_EXACT

Результат інкрементального оновлення, перевірений відповідно до формальних інваріантів.

## 6.3. HEURISTIC

Наближений прогноз, отриманий без повного обчислення всіх залежних структур.

## 6.4. UNKNOWN

Прогноз не сформований або недостатньо даних.

Критичне правило:

HEURISTIC ≠ EXACT.

Пошуковий механізм повинен знати, чи спирається він на точний стан, чи на попередню оцінку.

---

# 7. FIELD-BASED MOVE ORDERING

Впорядкування ходів є першим основним застосуванням FIELD DYNAMICS у пошуку.

Його мета — перевірити перспективні ходи раніше.

Для кожного ходу визначимо:

Priority(m | S)

Це пріоритет пошукової перевірки.

Він не є доказом найкращості ходу.

## 7.1. Джерела пріоритету

Пріоритет може враховувати:

- безпосередні тактичні можливості;
- шах королю;
- взяття;
- загрозу мату;
- створення підтримки;
- відкриття ліній;
- поліпшення доступності;
- зменшення обмежень;
- зміну контролю;
- створення структурних взаємодій;
- нейтралізацію критичних загроз;
- результати попередніх пошукових ітерацій.

## 7.2. Базова модель

Priority(m | S) =

P_tactical  
+ P_field_change  
+ P_interaction  
+ P_history  
+ P_search_context

Це концептуальна декомпозиція.

Вона не встановлює конкретних числових коефіцієнтів.

## 7.3. Тактичний пріоритет

Тактичні ознаки повинні мати окремий канал.

Наприклад:

- шах;
- взяття;
- безпосередня загроза мату;
- форсована відповідь;
- виграш матеріалу.

Структурна оцінка не повинна послаблювати пріоритет перевірки критичного тактичного ходу.

## 7.4. Структурний пріоритет

Структурний пріоритет може підвищувати позиції ходів, які:

- відкривають важливі лінії;
- створюють підтримку;
- активують фігури;
- покращують доступність;
- усувають блокування;
- змінюють несприятливі взаємодії;
- створюють критичні структурні умови.

## 7.5. Історичний пріоритет

Можуть використовуватися результати попередніх ітерацій пошуку:

- найкращий хід із попередньої ітерації;
- killer moves;
- history heuristic;
- результати попереднього аналізу аналогічних позицій.

Ці механізми не повинні змінювати правила легальності.

---

# 8. РОЗДІЛЕННЯ MOVE ORDERING ТА MOVE PRUNING

Це принципова вимога.

MOVE ORDERING змінює порядок перевірки ходів.

MOVE PRUNING може виключати частину ходів із пошуку.

Ці операції мають різні наслідки.

FD-10 встановлює:

**FIELD-BASED ORDERING IS ALLOWED BY DEFAULT. FIELD-BASED PRUNING REQUIRES SEPARATE VALIDATION.**

Структурний показник не є достатньою підставою для виключення ходу.

Наприклад, хід із негативною локальною структурною оцінкою може бути:

- єдиним захистом від мату;
- тактичною жертвою;
- проміжним ходом;
- форсованим розміном;
- способом уникнути повторення.

Тому початкова реалізація повинна використовувати FIELD DYNAMICS для впорядкування, а не для відсікання легальних ходів.

---

# 9. ІНТЕГРАЦІЯ З ALPHA-BETA SEARCH

FD-10 передбачає можливість використання класичного alpha-beta minimax.

Нехай:

V(S,d,α,β)

— значення пошуку позиції S на глибині d з межами α та β.

Для сторони, що максимізує:

V(S) = max V(Sᵢ)

Для сторони, що мінімізує:

V(S) = min V(Sᵢ)

з урахуванням рекурсивного пошуку.

## 9.1. Роль FIELD DYNAMICS

FIELD DYNAMICS впливає на:

- порядок перевірки ходів;
- вибір глибини додаткового аналізу;
- виявлення критичних змін;
- оцінювання листових позицій;
- визначення кандидатів для розширення пошуку.

Вона не повинна змінювати математичну логіку minimax.

## 9.2. Alpha-Beta Correctness

Якщо всі легальні ходи досліджуються, а листові оцінки однакові, зміна порядку ходів не повинна змінювати точний minimax-результат.

Вона може змінювати кількість відвіданих вузлів.

Це один із головних тестів коректності інтеграції.

## 9.3. Pruning

Відсікання, засноване на структурних евристиках, не повинно вводитися в базову реалізацію без окремого доказового або експериментального обґрунтування.

---

# 10. ІНТЕГРАЦІЯ З QUIESCENCE SEARCH

Статичне оцінювання позиції може бути ненадійним, якщо сторона перебуває в тактично нестабільному стані.

Тому передбачено quiescence search.

Його завдання — продовжити пошук у позиціях, де тактичні зміни ще не завершилися.

FIELD DYNAMICS може допомагати визначати:

- активні атакувальні поля;
- відкриті лінії;
- нестабільність короля;
- тактичні взаємодії;
- зміни матеріального балансу;
- наявність критичних загроз.

Але структурна нестабільність не повинна автоматично означати необхідність нескінченного розширення.

Необхідно встановити контрольовані умови продовження пошуку.

## 10.1. Tactical Stability

Введемо:

TacticalStability(S)

Можливі стани:

QUIET  
TACTICALLY_UNSTABLE  
CHECK  
FORCING_SEQUENCE  
UNKNOWN

Остаточна класифікація повинна залежати від шахових правил і тактичного аналізу, а не лише від геометричних полів.

---

# 11. ІНТЕГРАЦІЯ З ITERATIVE DEEPENING

Пошук повинен підтримувати поступове збільшення глибини.

Наприклад:

Depth 1  
Depth 2  
Depth 3  
...  
Depth N

Результат попередньої ітерації використовується для покращення наступної.

FIELD DYNAMICS може забезпечити додаткові дані:

- структурний опис найкращого ходу;
- стабільність його оцінки;
- зміни критичних полів;
- альтернативні кандидатні ходи;
- структурні причини зміни пріоритетів.

## 11.1. Стабільність найкращого ходу

Введемо:

BestMoveStability(d)

Вона показує, наскільки стабільним є найкращий хід зі збільшенням глибини.

Зміна найкращого ходу між ітераціями може свідчити про:

- недостатню глибину;
- тактичну нестабільність;
- зміну оцінки;
- виявлення прихованої відповіді.

Цей показник може впливати на планування подальшого аналізу.

Він не є доказом правильності ходу.

---

# 12. STRUCTURAL SEARCH EXTENSION

FD-10 вводить концепцію структурного розширення пошуку.

Мета — збільшувати глибину аналізу в тих випадках, коли хід створює значущу структурну трансформацію.

Наприклад:

- відкривається лінія на короля;
- змінюється контроль критичного поля;
- виникає нова тактична взаємодія;
- руйнується важлива підтримка;
- змінюється пішакова структура;
- виникає потенційне проходження пішака.

Визначимо:

StructuralExtension(S,m)

Вона може повертати:

- NO_EXTENSION;
- LIMITED_EXTENSION;
- TACTICAL_EXTENSION;
- STRUCTURAL_EXTENSION;
- UNKNOWN.

## 12.1. Обмеження

Структурне розширення не повинно застосовуватися до кожної зміни поля.

Інакше пошукове дерево може неконтрольовано розростатися.

Потрібні:

- максимальна кількість додаткових напівходів;
- обмеження повторних розширень;
- перевірка тактичної значущості;
- обмеження сумарного бюджету;
- захист від циклічних структурних змін.

---

# 13. FIELD-BASED REDUCTION

Зменшення глибини пошуку для окремих ходів є ризикованішим за їхнє впорядкування.

Можливі кандидати:

- тихі ходи без помітної структурної зміни;
- ходи, які не впливають на критичні поля;
- повторювані позиційні зміни;
- ходи з низьким попереднім пріоритетом.

Однак:

LOW_STRUCTURAL_PRIORITY ≠ BAD_MOVE.

Тому FD-10 не дозволяє використовувати лише FIELD DYNAMICS як підставу для скорочення пошуку.

Будь-яке скорочення повинно бути частиною окремого механізму з незалежною перевіркою.

Для першої версії рекомендовано:

- повне легальне генерування;
- FIELD-BASED MOVE ORDERING;
- стандартне alpha-beta pruning;
- обмежені структурні розширення;
- відсутність самостійного FIELD-BASED MOVE PRUNING.

# 14. ІНКРЕМЕНТАЛЬНЕ ОНОВЛЕННЯ В ПОШУКОВОМУ ДЕРЕВІ

Повний перерахунок усіх полів у кожному вузлі може бути дорогим.

Тому необхідно використовувати залежності.

Для ходу m:

S₀ → S₁

визначаємо:

AffectedFields(m)

AffectedInteractions(m)

AffectedEvaluationComponents(m)

Після цього:

1. зберегти попередній стан;
2. застосувати хід;
3. оновити шаховий стан;
4. оновити залежні поля;
5. оновити взаємодії;
6. оновити компоненти оцінки;
7. перевірити узгодженість;
8. виконати пошук;
9. відновити стан після повернення з рекурсії.

## 14.1. Make/Unmake

Пошуковий механізм повинен підтримувати контрольовані операції:

makeMove(S,m)

unmakeMove(S,m)

Структурні зміни повинні бути сумісні з цим механізмом.

Після unmakeMove стан полів та взаємодій повинен точно відповідати початковій позиції.

## 14.2. Delta State

Для зменшення копіювання можна зберігати лише зміни:

FieldDelta = {
    added,
    removed,
    modified,
    transformed
}

InteractionDelta = {
    added,
    removed,
    modified,
    transformed
}

Відновлення повинно виконуватися у зворотному порядку.

- взаємодії;

Однаковий ключ не повинен використовуватися без урахування відмінностей контексту.

Особливо важливо враховувати історію для правил повторення та лічильники, що впливають на завершення партії.

## 15.3. Повторне використання структурних результатів

Кешування допускається лише за умови:

- однакової позиції;

- однакової версії операторів;
- однакової семантики полів;
- відсутності застарілих залежностей.

# 16. ПРІОРИТЕТИ ПОШУКУ ТА SUBIT

SUBIT-CHESS повинен використовувати структурні характеристики не як ізольовані числові оцінки, а як контекстуалізовані відношення.

Для кожного кандидатного ходу можна формувати:

MoveStructuralProfile = (
    WHO,
    WHERE,
    WHEN,
    FieldChanges,
    InteractionChanges,
    TacticalContext,
    StrategicContext
)

Це не означає, що кожен хід повинен отримувати один із 64 архетипів як остаточну шахову характеристику.

SUBIT-64 може бути додатковим контекстуальним шаром.

Він не повинен підміняти повний стан шахової позиції.

Основний принцип:

SUBIT classification supplements chess state; it does not replace chess state.

## 16.1. WHO

Визначає перспективу учасника:

- ME;
- WE;
- YOU;
- THEY.

Для шахового двигуна це може використовуватися як контекстуальний шар суб'єктної перспективи, але не як заміна WHITE/BLACK.

## 16.2. WHERE

Визначає просторову орієнтацію:

- EAST;
- SOUTH;
- WEST;
- NORTH.

Вона може допомагати групувати напрямлені структурні зміни.

Але координати дошки залишаються основною геометричною системою.

## 16.3. WHEN

Визначає часовий або фазовий контекст:

- SPRING;
- SUMMER;
- AUTUMN;
- WINTER.

Це може використовуватися як додаткова категоризація станів або процесів.

Не слід без окремої специфікації ототожнювати ці чотири категорії з дебютом, мітельшпілем, ендшпілем та іншою фазою гри.

# 17. ПОШУК ЯК ПРОЦЕС СТРУКТУРНОЇ ТРАНСФОРМАЦІЇ

Кожен хід змінює не лише розташування фігур.

Він може змінювати систему відношень.

Тому пошук можна представити як:

S₀ → S₁ → S₂ → ... → Sₙ

одночасно:

F₀ → F₁ → F₂ → ... → Fₙ

I₀ → I₁ → I₂ → ... → Iₙ

E₀ → E₁ → E₂ → ... → Eₙ

Це дозволяє аналізувати не лише окремі позиції, а й траєкторії структурних змін.

Наприклад:

1. Відкриття вертикалі.
2. Переміщення тури.
3. Створення підтримки.
4. Проникнення на сьому горизонталь.
5. Виникнення тактичної загрози.

Окремий хід може мати невелику статичну вигоду, але бути необхідним елементом довшої послідовності.

Тому FIELD DYNAMICS повинна підтримувати аналіз траєкторій, а не лише локальних змін.

# 18. ПОШУКОВА ОЦІНКА ТА СТРУКТУРНА ОЦІНКА

Необхідно розділяти:

StaticEvaluation(S)

і:

SearchValue(S,d)

Перша оцінює поточну позицію.

Друга визначається пошуком послідовностей ходів.

Загалом:

SearchValue(S,d) ≠ StaticEvaluation(S)

Статична оцінка є лише одним із джерел інформації для пошуку.

Вона не може замінити аналіз відповідей суперника.

## 18.1. Причинний ланцюг

Пошуковий результат повинен зберігати:

BestMove  
→ PrincipalVariation  
→ ResultingPositions  
→ FieldChanges  
→ InteractionChanges  
→ EvaluationChanges

Це створює основу для пояснення вибраної послідовності.

# 20. ВИМОГИ ДО ПРОДУКТИВНОСТІ

FIELD DYNAMICS не повинна робити пошук повільнішим без вимірюваної компенсації у якості.

Необхідно вимірювати:

- вузли за секунду;
- кількість відвіданих вузлів;
- кількість оцінених позицій;
- час побудови полів;
- час побудови взаємодій;
- кількість інкрементальних оновлень;
- кількість повних перерахунків;
- ефективність впорядкування;
- частоту відсічень alpha-beta;
- якість вибору ходів.

## 20.1. Режими пошуку

Пропонується три режими.

### BASELINE SEARCH

Пошук без структурного впорядкування.

Використовується як контрольний режим.

### FIELD-ASSISTED SEARCH

Пошук із використанням структурних характеристик для впорядкування ходів.

### ADVANCED FIELD SEARCH

Пошук із додатковими структурними розширеннями, прогнозуванням змін та інкрементальним аналізом.

Усі три режими повинні використовувати однакові правила легальності.

# 21. ТЕСТОВА СПЕЦИФІКАЦІЯ

## 21.1. Тест повноти генерації

FIELD DYNAMICS не повинна змінювати множину легальних ходів.

## 21.2. Тест еквівалентності minimax

Для однакової глибини, однакової оцінки листових позицій і повного пошуку зміна порядку ходів не повинна змінювати точний результат.

## 21.3. Тест впорядкування

Структурно перспективний хід може отримати вищий пріоритет, але це не повинно автоматично робити його найкращим.

## 21.4. Тест тактичного пріоритету

Шах, матова загроза або критичне взяття не повинні бути витіснені звичайною структурною евристикою.

## 21.5. Тест заблокованої фігури

Структурний аналіз повинен визначати обмеження, але не повинен неправильно виключати легальні ходи.

## 21.6. Тест відкритої вертикалі

Відкриття вертикалі повинно впливати на структурний пріоритет відповідних кандидатів.

## 21.7. Тест discovered attack

Відкриття прихованої атаки повинно бути виявлене як структурна трансформація та перевірене тактичним аналізом.

## 21.8. Тест make/unmake

Після послідовності makeMove/unmakeMove стан позиції, полів та взаємодій повинен точно відновлюватися.

## 21.9. Тест транспозиції

Однакова позиція повинна отримувати узгоджені структурні характеристики за однакового контексту та версій операторів.

## 21.10. Тест застарілого кешу

Зміна контексту або версії оператора повинна блокувати некоректне повторне використання кешованих результатів.

## 21.11. Тест структурного розширення

Додаткове розширення не повинно створювати необмежене зростання глибини.

## 21.12. Тест quiescence

Тактично нестабільна позиція не повинна передчасно оцінюватися як завершена лише через статичний результат.

## 21.13. Тест незалежності

Пошук без FIELD DYNAMICS і пошук із FIELD DYNAMICS повинні мати однакову множину легальних ходів.

## 21.14. Тест відтворюваності

За однакової позиції, конфігурації, глибини та бюджету результати повинні бути відтворюваними, якщо не ввімкнено явно недетермінований режим.
