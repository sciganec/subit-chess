# 1. Основна методологія розробки

Кожен фундаментальний принцип повинен проходити повний цикл транспозиції до того, як ми переходимо до наступного.

## Етап 1. Fundamental Principle

Визначаємо оригінальний принцип у його первинній науковій дисципліні.

Не використовуємо лише популярну аналогію. Потрібно розуміти, що саме принцип математично або функціонально описує.

## Етап 2. Structural Extraction

Виділяємо структуру, яка може бути перенесена в шаховий двигун.

Наприклад, з векторного аналізу Максвелла ми не переносимо електромагнетизм.

Ми виділяємо:

- поле;
- локальне значення;
- напрямок;
- градієнт;
- дивергенцію;
- циркуляцію;
- взаємодію локальних і глобальних структур.

## Етап 3. Chess Transposition

Визначаємо відповідність шаховій позиції.

Наприклад:

- поле → шахове поле стратегічного впливу;
- вектор → напрямок позиційного впливу;
- градієнт → зміна позиційного потенціалу;
- циркуляція → циклічність локальних взаємодій;
- дивергенція → локальне розходження або концентрація структурних потоків.

На цьому етапі формується власна шахова інтерпретація принципу.

## Етап 4. Mathematical Formalization

Транспозиція повинна отримати формальний математичний опис.

Якщо принцип неможливо формалізувати достатньо точно, він поки залишається концептуальною ідеєю, а не компонентом двигуна.

## Етап 5. Engine Operator

Створюємо конкретний оператор, який виконує визначену функцію.

Оператор повинен мати:

- вхідні дані;
- математичну модель;
- процедуру обчислення;
- вихід;
- обчислювальну складність;
- критерії правильності;
- тестові сценарії.

## Етап 6. Engine Integration

Визначаємо, де оператор розташовується в архітектурі SUBIT-CHESS:

- генерація ходів;
- аналіз позиції;
- оцінювання;
- пошук;
- селекція кандидатів;
- управління пошуком;
- стратегічна адаптація.

## Етап 7. Verification

Перевіряємо:

1. математичну коректність;
2. функціональну коректність;
3. шахову релевантність;
4. computational cost;
5. вплив на інші модулі;
6. наявність регресій;
7. фактичну ефективність.

## Етап 8. Stabilization

Після завершення транспозиції:

- фіксуємо версію;
- документуємо оператора;
- визначаємо API;
- проводимо аудит;
- встановлюємо статус інтеграції.

Лише після цього переходимо до наступного фундаментального принципу.

# 3. Критичне правило розробки

У процесі транспозиції необхідно уникнути трьох основних помилок.

### Помилка 1 — Metaphorical Implementation

Не створювати модуль лише тому, що його назва звучить фундаментально.

Наприклад, назва THERMODYNAMIC STRUCTURE не має сенсу, якщо вона лише дублює стандартний evaluation під іншою назвою.

Кожен оператор повинен виконувати окрему функцію.

### Помилка 2 — Architectural Duplication

Якщо два принципи транспонуються в механізми, які фактично виконують однакову функцію, необхідно дослідити їхню відмінність.

Можливо:

- один принцип є фундаментальним оператором;
- інший — його контекстуальним розширенням;
- третій — механізмом управління.

Не потрібно автоматично створювати 29 незалежних модулів.

### Помилка 3 — Premature Integration

Не інтегрувати оператор у повний двигун до завершення його локальної перевірки.

Спочатку:

**Theory → Formalization → Operator → Unit Tests → Position Tests → Benchmark → Audit**

Після цього:

**Integration → Regression → Engine Evaluation**
