# SUBIT-CHESS PARAMETER OPTIMIZATION v1.0

## Математична архітектура оптимізації параметрів автономного шахового двигуна

**Статус:** концептуальна технічна специфікація  
**Версія:** 1.0  
**Система:** SUBIT-CHESS  
**Залежності:** SPVT, SRA, SUBIT-SEARCH, LEARNING ARCHITECTURE, SELF-PLAY & EVALUATION PROTOCOL  
**Принцип:** DO NOT COLLAPSE — CONTEXTUALIZE

---

# 1. Анотація

SUBIT-CHESS PARAMETER OPTIMIZATION визначає математичну систему вдосконалення внутрішніх параметрів шахового двигуна.

Мета — створити механізм, який дозволяє двигуну самостійно досліджувати різні конфігурації оцінювання, порівнювати їхні результати, знаходити ефективніші комбінації параметрів і приймати зміни лише після контрольованої перевірки.

Основна проблема полягає в тому, що шахова позиція не має одного простого параметра якості.

Її оцінювання залежить від:

- матеріального співвідношення;
- мобільності;
- структурних відносин;
- контролю простору;
- безпеки короля;
- тактичних можливостей;
- фази партії;
- потенціалу майбутніх трансформацій;
- якості пошуку.

Тому оптимізація повинна бути багатопараметричною та контекстуальною.

Документ визначає:

1. Вектор параметрів двигуна.
2. Структуру функції оцінювання.
3. Обмеження допустимих параметрів.
4. Цільові функції оптимізації.
5. Багатокритеріальне оцінювання.
6. Еволюційну оптимізацію.
7. Локальний пошук.
8. Адаптивне коригування.
9. Захист від перенавчання.
10. Процедуру прийняття нової конфігурації.

Усі методи оптимізації мають бути реалізовані власним кодом SUBIT-CHESS. Зовнішні шахові рушії, оцінки та партії не використовуються.

# 2. Основна математична постановка

Нехай:

`P` — шахова позиція.

`Ω(P)` — її структурне представлення.

`C(P)` — контекст позиції.

`θ` — вектор параметрів двигуна.

Тоді функцію оцінювання визначимо як:

`E(P, s; θ)`

де s — сторона, з перспективи якої оцінюється позиція.

Завдання оптимізації:

`θ* = arg maxθ J(θ)`

де J — цільова функція, що характеризує якість конфігурації.

Однак максимізація J не повинна відбуватися без обмежень.

Потрібно також забезпечити:

- коректність шахових правил;
- стабільність оцінювання;
- обчислювальну ефективність;
- відсутність критичних регресій;
- достатню різноманітність поведінки.

Отже, повна постановка:

`maxθ J(θ)`

за умов:

`θ ∈ Θ_valid`

`Rules(θ) = TRUE`

`Regression(θ) = PASS`

`Stability(θ) ≥ τ_s`

де Θ_valid — множина допустимих конфігурацій, а τ_s — мінімальний поріг стабільності.

Важливо: параметри оцінювання не повинні впливати на визначення легальних ходів.

# 3. Вектор параметрів

## 3.1. Загальна структура

Вектор параметрів:

`θ = (θ_M, θ_A, θ_R, θ_T, θ_C, θ_D, θ_S)`

де:

- θ_M — матеріальні параметри;
- θ_A — параметри активності;
- θ_R — структурні параметри;
- θ_T — тактичні параметри;
- θ_C — контекстуальні параметри;
- θ_D — динамічні параметри;
- θ_S — параметри пошуку.

Це дозволяє розділяти функціональні групи та проводити незалежне тестування.

## 3.2. Матеріальні параметри

`θ_M = (v_P, v_N, v_B, v_R, v_Q)`

де:

- v_P — вага пішака;
- v_N — вага коня;
- v_B — вага слона;
- v_R — вага тури;
- v_Q — вага ферзя.

Матеріальні параметри можуть залежати від фази партії.

Наприклад:

`v_P = v_P(Φ)`

Це дозволяє відрізняти цінність пішака в мітельшпілі та ендшпілі.

Однак базові матеріальні параметри повинні залишатися в обґрунтованих межах.

## 3.3. Параметри активності

`θ_A = (a_m, a_c, a_k, a_d)`

де:

- a_m — мобільність;
- a_c — контроль полів;
- a_k — координація;
- a_d — динамічна активність.

Ці параметри характеризують здатність фігур брати участь у грі.

Важливо не ототожнювати кількість доступних ходів із якістю позиції.

Мобільність може бути високою, але тактично небезпечною.

## 3.4. Структурні параметри

`θ_R = (r_s, r_p, r_l, r_f, r_c)`

де:

- r_s — стійкість;
- r_p — підтримка;
- r_l — зв'язність;
- r_f — функціональна залежність;
- r_c — контроль критичних полів.

Вони пов'язані з SRA.

Структурні відносини повинні зберігати типову семантику.

Наприклад, DEFEND не можна трактувати як тотожне SUPPORT, а ATTACK — як тотожне CONTROL.

Оптимізація змінює вагу відносин, але не їхнє значення.

## 3.5. Тактичні параметри

`θ_T = (t_k, t_p, t_f, t_m, t_o)`

де:

- t_k — безпека короля;
- t_p — зв'язування;
- t_f — вилка;
- t_m — матові загрози;
- t_o — перевантаження.

Ці параметри впливають на оцінювання тактичних можливостей.

Точні шахові факти не повинні замінюватися евристичними вагами.

Наприклад, факт шаху визначається правилами, а не значенням t_k.

## 3.6. Контекстуальні параметри

`θ_C = W(I, Z, Φ)`

де:

- I — функціональний контекст;
- Z — просторова зона;
- Φ — фаза партії.

Для прикладної шахової моделі:

`I = {QUIET, DEFENCE, ATTACK, PRESSURE}`

`Z = {GLOBAL, QUEENSIDE, KING, CENTER}`

`Φ = {OPENING, MIDDLEGAME, ENDGAME, TRANSITION}`

Отримуємо 64 контекстні комбінації.

Контекстуальні параметри можуть модифікувати ваги інших характеристик.

Наприклад, безпека короля може мати різну вагу в різних фазах.

Однак контекст не повинен перетворюватися на жорстку класифікацію, яка відкидає інші характеристики позиції.

## 3.7. Динамічні параметри

`θ_D = (d_Δ, d_u, d_h, d_q)`

де:

- d_Δ — чутливість до структурної зміни;
- d_u — чутливість до невизначеності;
- d_h — історична залежність;
- d_q — потенціал майбутньої трансформації.

Ця група пов'язує оцінювання окремої позиції з її можливим розвитком.

Наприклад, хід може тимчасово погіршити матеріальну або просторову оцінку, але створити сильніший довгостроковий потенціал.

Це потрібно враховувати через пошук, а не лише через статичну оцінку.

## 3.8. Пошукові параметри

`θ_S = (s_d, s_q, s_l, s_r, s_b)`

де:

- s_d — стратегія розподілу глибини;
- s_q — параметри quiescence search;
- s_l — параметри move ordering;
- s_r — параметри selective search;
- s_b — розподіл обчислювального бюджету.

Параметри пошуку повинні бути відокремлені від параметрів оцінювання.

Це дозволяє визначити, чи покращення виникає через якість оцінювання, чи через ефективніший пошук.

# 4. Структура функції оцінювання

## 4.1. Базова модель

Визначимо:

`E(P, s; θ) = Σᵢ wᵢ(P; θ) · fᵢ(P, s)`

де:

- fᵢ — окремі характеристики позиції;
- wᵢ — відповідні ваги.

До характеристик можуть належати:

- матеріальний баланс;
- мобільність;
- контроль центру;
- безпека короля;
- активність фігур;
- пішакова структура;
- координація;
- обмеження суперника;
- структурна стійкість;
- тактичні можливості.

Це початкова параметрична модель, а не остаточна формула SUBIT-CHESS.

## 4.2. Контекстуальне зважування

Вага характеристики може залежати від контексту:

`wᵢ(P; θ) = gᵢ(C(P), Ω(P); θ)`

Отже, оцінка не повинна використовувати незмінні ваги для всіх позицій.

Наприклад:

- мобільність може бути особливо важливою в закритих позиціях;
- безпека короля — під час атакувальної напруги;
- активність короля — в ендшпілі;
- пішакова структура — у довгостроковій позиційній боротьбі.

Це приклади можливих залежностей, які потрібно перевіряти, а не наперед вважати правильними.

## 4.3. Перспектива сторони

Оцінювання повинно бути симетричним щодо перспективи.

Якщо E_abs(P) — оцінка з абсолютної перспективи, тоді:

`E(P, s) = sign(s) · E_abs(P)`

де sign(s) залежить від сторони, для якої обчислюється оцінка.

Для negamax це особливо важливо.

Після кожного ходу перспектива змінюється:

`V(P, d) = maxₘ [−V(T(P,m), d−1)]`

Невідповідність перспективи є критичною помилкою.

# 5. Нормалізація параметрів

## 5.1. Проблема різних масштабів

Матеріальні оцінки, мобільність, структурні характеристики та контекстні інтенсивності можуть мати різні числові масштаби.

Якщо їх оптимізувати без нормалізації, одна група може домінувати лише через масштаб значень.

## 5.2. Нормалізована характеристика

Для характеристики fᵢ можна визначити:

`fᵢ_norm = Normalize(fᵢ)`

Нормалізація повинна зберігати зміст характеристики та не створювати втрату важливих крайніх значень.

Наприклад, для обмеженої характеристики:

`f_norm ∈ [0,1]`

Для симетричної характеристики:

`f_norm ∈ [−1,1]`

Не всі характеристики потрібно нормалізувати однаково.

## 5.3. Відсутність семантичного згортання

Нормалізація не повинна перетворювати різні структурні характеристики на один універсальний показник.

Наприклад:

- мобільність;
- захищеність;
- зв'язність;
- контроль;

залишаються різними величинами навіть тоді, коли мають однаковий числовий діапазон.

---

# 6. Обмеження простору параметрів

Визначимо допустиму множину:

`Θ_valid = {θ | Constraints(θ) = TRUE}`

Вона повинна містити:

## 6.1. Межі

Для кожного параметра:

`θᵢ_min ≤ θᵢ ≤ θᵢ_max`

Межі визначаються на основі семантики параметра та числової стабільності.

## 6.2. Залежності

Деякі параметри можуть бути пов'язані.

Наприклад, якщо матеріальні ваги мають певний масштаб, то інші евристичні компоненти повинні використовувати сумісний масштаб.

Необхідно уникати ситуації, коли оптимізатор компенсує помилку одного параметра необмеженим зростанням іншого.

## 6.3. Симетрія

Параметри не повинні створювати штучну перевагу кольору.

Для колірно-обернених позицій повинна виконуватися відповідна симетрія:

`E(P, WHITE) = −E(ColorReverse(P), BLACK)`

Ця властивість застосовується за умови коректного перетворення всієї позиції та її стану.

## 6.4. Числова стабільність

Не допускаються:

- NaN;
- нескінченні значення;
- неконтрольоване переповнення;
- нестабільні числові перетворення;
- непередбачувані стрибки оцінювання.

# 7. Цільова функція

## 7.1. Багатокомпонентна модель

Замість однієї метрики визначимо вектор цілей:

`J(θ) = (J_game, J_tactical, J_structural, J_efficiency, J_stability)`

де:

- J_game — результативність у матчах;
- J_tactical — тактична надійність;
- J_structural — якість структурного оцінювання за визначеними внутрішніми критеріями;
- J_efficiency — обчислювальна ефективність;
- J_stability — стабільність.

Ці компоненти не обов'язково мають однакову важливість.

## 7.2. Результативність

`J_game = (W + 0.5D) / N`

Це середня кількість очок на партію.

## 7.3. Тактична надійність

`J_tactical = N_pass / N_tests`

де:

- N_pass — кількість пройдених тактичних тестів;
- N_tests — загальна кількість тестів.

Ця метрика має сенс лише для тестів із коректно встановленою очікуваною властивістю.

## 7.4. Обчислювальна ефективність

Можна визначити:

`J_efficiency = UsefulSearchWork / ComputationalCost`

Однак коректне визначення корисної роботи пошуку потребує окремого дослідження.

Просте збільшення кількості вузлів не означає покращення.

Тому практично потрібно вимірювати:

- вузли за секунду;
- глибину;
- час пошуку;
- стабільність головного варіанта;
- результативність за однакового бюджету.

## 7.5. Стабільність

Стабільність можна оцінювати через варіативність результатів на різних наборах позицій і seeds.

Наприклад:

`J_stability = 1 / (1 + Var(Score))`

Це лише одна можлива форма показника.

Вона не повинна винагороджувати систему за стабільне, але слабке відтворення помилок.

# 8. Багатокритеріальна оптимізація

## 8.1. Проблема зведення до одного числа

Якщо звести всі характеристики до однієї суми:

`J = αJ_game + βJ_tactical + γJ_efficiency + δJ_stability`

можна отримати ситуацію, коли сильне покращення однієї характеристики приховує критичне погіршення іншої.

Наприклад, висока швидкість може компенсувати в агрегованому показнику падіння тактичної надійності.

Це небажано.

## 8.2. Ієрархічна оптимізація

Рекомендована структура:

**Рівень 1 — обов'язкові умови**

- правила шахів;
- легальність ходів;
- коректність переходів;
- відсутність критичних регресій.

**Рівень 2 — шахова результативність**

- результати матчів;
- тактична надійність;
- якість гри в різних фазах.

**Рівень 3 — ефективність**

- швидкість;
- пам'ять;
- пошуковий бюджет.

**Рівень 4 — структурна якість**

- різноманітність;
- контекстуальна узгодженість;
- пояснюваність;
- стабільність.

Перший рівень не може бути компенсований жодним показником другого, третього або четвертого рівня.

## 8.3. Pareto-підхід

Конфігурація θ₁ домінує θ₂, якщо:

- вона не гірша за всіма визначеними критеріями;
- вона краща принаймні за одним критерієм.

Множина конфігурацій, які не домінуються іншими, утворює Pareto Frontier.

Це дозволяє зберігати різні перспективні конфігурації.

Наприклад:

- одна версія може бути швидшою;
- інша — тактично надійнішою;
- третя — краще грати в ендшпілі.

Не обов'язково негайно зводити всі ці варіанти до одного переможця.

# 9. Метод 1 — контрольований локальний пошук

## 9.1. Принцип

Змінювати невелику кількість параметрів за один цикл.

Нехай:

`θ' = θ + Δθ`

де Δθ — обмежений вектор змін.

## 9.2. Процедура

1. Вибрати параметр.
2. Змінити його в допустимих межах.
3. Запустити контрольні матчі.
4. Порівняти результати.
5. Прийняти або відхилити зміну.
6. Перейти до наступного параметра.

## 9.3. Переваги

- простота;
- відтворюваність;
- зрозуміле походження змін;
- легкість діагностики.

## 9.4. Недоліки

- повільність;
- залежність від початкової конфігурації;
- ризик пропустити взаємодії параметрів.

Цей метод рекомендовано використовувати на ранніх етапах.

# 10. Метод 2 — еволюційна оптимізація

## 10.1. Популяція

Створюється набір конфігурацій:

`Θ = {θ₁, θ₂, ..., θₙ}`

Кожна конфігурація проходить оцінювання.

## 10.2. Відбір

Відбираються конфігурації, які демонструють перспективні результати.

Відбір повинен враховувати не тільки загальний результат, а й окремі критерії.

## 10.3. Мутація

Мутація змінює один або декілька параметрів:

`θ' = Mutate(θ, ε)`

де ε — контрольована величина зміни.

Мутації повинні залишатися в допустимій області.

## 10.4. Рекомбінація

Можна комбінувати частини двох конфігурацій:

`θ_child = Combine(θ_a, θ_b)`

Наприклад, матеріальні параметри беруться з однієї конфігурації, а контекстуальні — з іншої.

Але комбінування не гарантує збереження якості, оскільки параметри можуть взаємодіяти.

Кожен нащадок повинен проходити повний цикл перевірки.

## 10.5. Збереження різноманітності

Не потрібно залишати лише конфігурації з найвищим поточним результатом.

Інакше популяція може надто швидко втратити різноманітність.

Доцільно зберігати декілька різних перспективних конфігурацій.

---

# 11. Метод 3 — оптимізація за градієнтом

Якщо функція оцінювання має диференційовну параметричну форму, можна досліджувати градієнтні методи.

`∇θ J(θ)`

Тоді оновлення:

`θ' = θ + η∇θJ(θ)`

де η — швидкість навчання.

Однак у шахах результат партії є дискретним, а пошук містить нелінійні та негладкі операції.

Тому градієнтна оптимізація безпосередньо за результатами партій може бути складною.

Її доцільніше використовувати для внутрішніх параметричних моделей оцінювання, де можна визначити придатний диференційовний навчальний сигнал.

Необхідно чітко розрізняти:

- оптимізацію функції оцінювання;
- оптимізацію політики вибору ходів;
- оптимізацію результату повної партії.

Це різні задачі.

---

# 12. Метод 4 — адаптивний пошук параметрів

Поточна конфігурація може бути стабільною в одних позиціях і недостатньо ефективною в інших.

Тому система може змінювати інтенсивність аналізу залежно від характеристик позиції.

Наприклад:

`Budget(P) = B₀ + λ·U(P) + μ·T(P)`

де:

- B₀ — базовий бюджет;
- U(P) — оцінка невизначеності;
- T(P) — тактична складність;
- λ, μ — параметри.

Ця формула є концептуальною.

Вона не повинна дозволяти необмежене збільшення бюджету.

Потрібно визначити:

`B_min ≤ Budget(P) ≤ B_max`

Адаптивний пошук повинен оцінюватися за однакового загального обчислювального бюджету, інакше порівняння буде некоректним.

---

# 13. Виявлення взаємодії параметрів

Оптимізація одного параметра за раз може пропустити важливі взаємодії.

Наприклад:

- підвищення ваги мобільності може бути корисним лише за певної ваги безпеки короля;
- структурна активність може бути корисною лише за відповідного контексту;
- контекстуальна вага може залежати від матеріального співвідношення.

Для параметрів θᵢ та θⱼ потрібно досліджувати:

`Interaction(θᵢ, θⱼ)`

Це можна робити через контрольовані експерименти:

1. Базова конфігурація.
2. Зміна θᵢ.
3. Зміна θⱼ.
4. Одночасна зміна θᵢ та θⱼ.

Різниця між очікуваним та фактичним спільним ефектом дає сигнал про взаємодію.

Необхідно уникати припущення, що внесок кожного параметра незалежний.

---

# 14. Захист від перенавчання

## 14.1. Причина

Якщо параметри оптимізуються на одному наборі позицій, двигун може навчитися краще грати саме на ньому.

Це не гарантує покращення на нових позиціях.

## 14.2. Заходи

- розділення навчальних і контрольних наборів;
- періодична генерація нових позицій;
- окремі генератори;
- різні seeds;
- різні структурні профілі;
- контрольні партії з іншими конфігураціями;
- обмеження кількості циклів налаштування на одному наборі.

## 14.3. Ознака перенавчання

Якщо:

`J_train ↑`

але:

`J_validation ↓`

це свідчить про можливе перенавчання.

## 14.4. Принцип

Покращення на навчальному наборі не є достатньою умовою прийняття нової версії.

---

# 15. Захист від деградації

Кожен кандидат проходить перевірку на:

- числову стабільність;
- симетрію кольорів;
- тактичну надійність;
- структурні регресії;
- обчислювальну ефективність;
- результати матчів;
- відсутність критичних помилок.

Потрібно також перевіряти крайні конфігурації параметрів.

Наприклад, якщо оптимізатор встановлює нульову вагу важливої характеристики, це не обов'язково помилка, але така зміна потребує окремого аналізу.

Не можна автоматично вважати, що оптимізатор знайшов правильне рішення лише тому, що він максимізував задану функцію.

Він міг знайти недолік самої цільової функції.

---

# 16. Механізм прийняття параметрів

Визначимо процедуру:

`Accept(θ_candidate)`

Вона повертає:

- ACCEPT;
- REJECT;
- INCONCLUSIVE.

## 16.1. ACCEPT

Кандидат приймається, якщо:

- усі критичні тести пройдені;
- відсутні неприйнятні регресії;
- контрольні результати відповідають критеріям;
- покращення має достатню статистичну підтримку;
- походження параметрів зафіксовано.

## 16.2. REJECT

Кандидат відхиляється, якщо:

- порушено інваріанти;
- виникли критичні помилки;
- спостерігається значна деградація;
- параметри виходять за допустимі межі.

## 16.3. INCONCLUSIVE

Кандидат залишається експериментальним, якщо:

- вибірки недостатньо;
- довірчий інтервал надто широкий;
- результати нестабільні;
- різні метрики демонструють суперечливі тенденції.

Цей третій стан важливий.

Система не повинна примусово приймати рішення, коли доказів недостатньо.

# 17. Формальні інваріанти

## OPT-INV-001 — Parameter Separation

Параметри оцінювання та параметри пошуку зберігаються окремо.

## OPT-INV-002 — Legal Independence

Оптимізація не змінює правила визначення легальних ходів.

## OPT-INV-003 — Bounded Parameters

Усі параметри мають допустимі межі.

## OPT-INV-004 — Color Symmetry

Оцінювання зберігає визначені властивості колірної симетрії.

## OPT-INV-005 — Context Preservation

Контекстуальні параметри не знищують інші структурні характеристики.

## OPT-INV-006 — Objective Separation

Результативність, тактична надійність, структурна якість та ефективність вимірюються окремо.

## OPT-INV-007 — Validation Separation

Контрольні дані не використовуються безпосередньо для оптимізації.

## OPT-INV-008 — Reproducibility

Кожна оптимізація має відтворювані параметри.

## OPT-INV-009 — No Uncontrolled Update

Параметри активного пошукового процесу незмінні.

## OPT-INV-010 — Rollback

Кожна прийнята версія допускає відкат.

## OPT-INV-011 — No External Teacher

Зовнішні шахові оцінки не використовуються як цільові мітки.

## OPT-INV-012 — Multiobjective Integrity

Покращення однієї метрики не може автоматично компенсувати порушення критичного інваріанта.

# 20. Підсумкова архітектурна теза

Оптимізація SUBIT-CHESS повинна бути не просто пошуком найбільшого числового результату.

Вона повинна бути дослідженням взаємодії параметрів, структурних характеристик і наслідків шахових трансформацій.

Вектор параметрів описує внутрішню конфігурацію двигуна.

Функція оцінювання визначає спосіб інтерпретації позиції.

Пошук досліджує можливі трансформації.

Самогра створює досвід.

Оптимізатор пропонує зміни.

Валідація визначає, чи можна ці зміни прийняти.

Повний цикл:

`POSITION → STRUCTURE → EVALUATION → SEARCH → EXPERIENCE → OPTIMIZATION → VALIDATION`

У цій системі є принципова відмінність між двома поняттями:

**Оптимізувати те, що ми вимірюємо, — не означає автоматично покращити те, що ми прагнемо отримати.**

Тому SUBIT-CHESS повинен не лише оптимізувати власні параметри, а й постійно перевіряти адекватність критеріїв, за якими він оцінює власний розвиток.

Це є математичною основою контрольованої автономної еволюції двигуна.
