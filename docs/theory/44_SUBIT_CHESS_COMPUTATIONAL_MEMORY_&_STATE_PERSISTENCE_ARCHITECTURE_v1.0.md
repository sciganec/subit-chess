# 1. Призначення документа

Цей документ визначає архітектуру пам’яті SUBIT-CHESS та принципи збереження станів, обчислювальних результатів, структурних конфігурацій, стратегічних гіпотез і досвіду автономної роботи двигуна.

Мета полягає у створенні системи, яка дозволяє двигуну:

1. зберігати повний шаховий стан;
2. відновлювати незавершені обчислення;
3. повторно використовувати перевірені результати;
4. зберігати структурний та стратегічний контекст;
5. накопичувати досвід власного пошуку;
6. розрізняти актуальні та історичні знання;
7. виявляти застарілі висновки;
8. зберігати походження кожного значущого результату;
9. підтримувати контрольоване навчання;
10. забезпечувати відтворюваність експериментів;
11. захищати пам’ять від суперечностей і самопідтвердження;
12. зберігати незалежність шахової логіки від механізмів навчання.

Основна проблема, яку вирішує ця специфікація:

**Як накопичувати знання про шахові позиції та власний досвід, не перетворюючи пам’ять на неконтрольоване сховище застарілих оцінок і помилкових узагальнень?**

# 2. Фундаментальне розмежування: стан, пам’ять і знання

SUBIT-CHESS повинен розрізняти три поняття.

## 2.1. Шаховий стан

Шаховий стан описує конкретну позицію та необхідну інформацію для визначення легальних продовжень.

Позначимо:

P = (B, s, CR, EP, H, N, 𝓗)

де:

- B — розташування фігур;
- s — сторона, що має хід;
- CR — права на рокіровку;
- EP — можливість взяття на проході;
- H — лічильник напівходів;
- N — номер повного ходу;
- 𝓗 — необхідна історія позицій та подій.

Шаховий стан є первинним об'єктом обчислення.

Його не можна замінювати оцінкою, стратегічним описом або записом у пам’яті.

## 2.2. Обчислювальна пам’ять

Обчислювальна пам’ять зберігає результати виконання алгоритмів:

- геометричні характеристики;
- структурні відносини;
- тактичні конфігурації;
- оцінки;
- пошукові результати;
- стратегічні плани;
- контекстні профілі;
- обчислювальні журнали;
- метадані перевірки.

Ці результати є похідними від шахового стану.

## 2.3. Знання

Знання — це результат, який має визначене значення, контекст, походження та статус доказовості.

Формально:

K = (X, C, Pᵣ, V, E, T, S)

де:

- X — твердження або результат;
- C — контекст;
- Pᵣ — походження;
- V — версія;
- E — доказова основа;
- T — часова актуальність;
- S — статус.

Не кожен збережений результат є знанням.

Наприклад, незавершена оцінка позиції є записом обчислення, але не обов'язково надійним знанням.

# 3. Загальна модель пам’яті

Архітектура пам’яті визначається як:

CM = (M₀, M₁, M₂, M₃, M₄, M₅, M₆)

де кожний рівень має окрему функцію.

## 3.1. M₀ — WORKING MEMORY

Робоча пам’ять.

Містить дані, необхідні для поточного обчислення:

- активну позицію;
- поточний пошуковий вузол;
- проміжні результати;
- активні залежності;
- чергу завдань;
- локальні зміни;
- тимчасові оцінки.

Особливості:

- висока швидкість доступу;
- короткий життєвий цикл;
- можливість очищення після завершення обчислення;
- суворий контроль відповідності поточному стану.

Робоча пам’ять не повинна бути єдиним місцем зберігання важливих результатів.

## 3.2. M₁ — POSITION MEMORY

Пам’ять шахових позицій.

Містить:

- повний шаховий стан;
- ідентифікатор позиції;
- історичні умови;
- легальні ходи;
- термінальний статус;
- зв'язок із попередньою позицією;
- походження позиції.

Основна функція — відновлення точного шахового контексту.

## 3.3. M₂ — STRUCTURAL MEMORY

Структурна пам’ять.

Містить:

- структурні графи;
- відносини між фігурами;
- конфігурації пішаків;
- мережі захисту;
- контроль полів;
- структурні слабкості;
- структурні трансформації;
- локальні та глобальні характеристики.

Структурна пам’ять не повинна трактувати однакову геометричну конфігурацію як повністю тотожну шахову позицію.

## 3.4. M₃ — STRATEGIC MEMORY

Стратегічна пам’ять.

Містить:

- цілі;
- плани;
- умови реалізації;
- причинні залежності;
- альтернативні маршрути;
- ризики;
- результати перевірки планів;
- історію зміни стратегічних режимів.

Стратегічний план має часову та позиційну прив'язку.

Він не повинен автоматично переноситися на нову позицію лише через поверхневу схожість.

## 3.5. M₄ — EXPERIENTIAL MEMORY

Пам’ять досвіду.

Містить результати власної діяльності двигуна:

- зіграні в контрольованому self-play партії;
- результати пошуку;
- виявлені тактичні помилки;
- позиції з невдалими рішеннями;
- результати внутрішніх експериментів;
- статистику ефективності алгоритмів;
- результати порівняння версій.

Це джерело матеріалу для внутрішнього вдосконалення.

Але досвід не є автоматичним доказом.

## 3.6. M₅ — RESEARCH MEMORY

Дослідницька пам’ять.

Містить:

- гіпотези;
- експериментальні протоколи;
- набори внутрішньо згенерованих позицій;
- результати перевірок;
- статистичні висновки;
- відхилені гіпотези;
- невирішені питання;
- версії дослідницьких моделей.

Цей рівень забезпечує накопичення знань про власні алгоритми.

## 3.7. M₆ — META-MEMORY

Мета-пам’ять.

Містить інформацію про саму пам’ять:

- структуру сховищ;
- версії схем;
- політики збереження;
- політики інвалідації;
- індекси;
- залежності;
- контроль цілісності;
- журнали міграцій;
- статистику використання.

Мета-пам’ять дозволяє системі контролювати власну інформаційну організацію.

# 4. Ідентичність об'єктів пам’яті

Одна з основних проблем шахового двигуна — правильне визначення того, що саме є однаковим між двома обчисленнями.

Необхідно розрізняти кілька типів ідентичності.

## 4.1. Board Identity

Ідентичність розташування фігур.

Враховує:

- тип фігури;
- колір;
- поле.

Не враховує автоматично всі умови шахового стану.

## 4.2. Position Identity

Ідентичність повного шахового стану.

Враховує:

- розташування фігур;
- сторону ходу;
- права на рокіровку;
- можливість взяття на проході;
- необхідні лічильники та історичні умови.

## 4.3. Structural Identity

Ідентичність структурної конфігурації.

Визначається через типізовані вузли, відносини та їхні атрибути.

Дві позиції можуть мати подібні структурні характеристики, але різний шаховий стан.

## 4.4. Strategic Identity

Ідентичність стратегічної ситуації.

Враховує:

- активні цілі;
- плани;
- причинні залежності;
- горизонт;
- умови реалізації;
- ризики.

## 4.5. Computational Identity

Ідентичність обчислювального результату.

Визначається не лише позицією, а й:

- алгоритмом;
- версією;
- параметрами;
- залежностями;
- глибиною;
- контекстом;
- бюджетом обчислень.

Таким чином:

BoardIdentity ≠ PositionIdentity ≠ StructuralIdentity ≠ StrategicIdentity ≠ ComputationalIdentity.

Це розмежування запобігає некоректному повторному використанню результатів.

Фактичний вміст запису.

## 5.4. Context

Умови, за яких запис має значення.

## 5.5. Identity

Ідентифікатор відповідного типу об'єкта.

## 5.6. Provenance

Походження:

- джерело даних;
- алгоритм;

- експериментальний запуск.

Версія схеми та змісту.

## 5.8. Dependencies

Список залежностей, необхідних для інтерпретації запису.

## 5.9. Evidence

Статус доказовості.

## 5.10. Validity

Часова та контекстна актуальність.

## 5.11. Timestamp

Час створення, оновлення та перевірки.

## 5.12. Status

Поточний стан запису.

# 6. Життєвий цикл запису

Кожний запис пам’яті проходить контрольований життєвий цикл.

CREATED  
↓  
VALIDATED  
↓  
STORED  
↓  
INDEXED  
↓  
RETRIEVED  
↓  
REVALIDATED  
↓  
USED / REJECTED / SUPERSEDED  
↓  
ARCHIVED

Можливі статуси:

- DRAFT;
- VALID;
- ACTIVE;
- CONTEXT_DEPENDENT;
- STALE;
- INVALID;
- SUPERSEDED;
- ARCHIVED;
- QUARANTINED.

## 6.1. CREATED

Запис створений, але ще не пройшов перевірку.

## 6.2. VALIDATED

Перевірено структуру, типи та необхідні передумови.

## 6.3. ACTIVE

Запис може використовуватися в межах визначеного контексту.

## 6.4. CONTEXT_DEPENDENT

Запис допустимий лише за конкретних умов.

## 6.5. STALE

Запис більше не можна використовувати без повторної перевірки.

## 6.6. INVALID

Запис містить помилку або порушує визначені інваріанти.

## 6.7. SUPERSEDED

Існує новіша версія, яка замінила цей запис.

Стару версію не потрібно автоматично видаляти: вона може бути важливою для відтворення попередніх експериментів.

## 6.8. QUARANTINED

Запис ізольований через суперечність, пошкодження або невідоме походження.

# 7. Пам’ять шахових позицій

Кожна позиція повинна зберігатися з достатньою інформацією для коректного відновлення.

PositionRecord = (
    PositionID,
    Board,
    SideToMove,
    CastlingRights,
    EnPassant,
    HalfmoveClock,
    FullmoveNumber,
    RelevantHistory,
    ParentPosition,
    Move,
    RuleVersion,
    Timestamp
)

## 7.1. Відновлення позиції

Restore(PositionRecord) → P

Після відновлення необхідно перевірити:

1. коректність представлення дошки;
2. відповідність фігур полям;
3. сторону ходу;
4. права на рокіровку;
5. умови взяття на проході;
6. історичні умови;
7. узгодженість із правилами.

## 7.2. Історія позицій

Історія не повинна зводитися до простого списку FEN-подібних представлень.

Для окремих правил нічиєї важливий контекст попередніх позицій.

Тому пам’ять повинна підтримувати:

- послідовність ходів;
- необхідні ідентифікатори позицій;
- дані для повторення позицій;
- відповідні лічильники;
- походження історичного стану.

Збереження лише розташування фігур може бути недостатнім для повного відновлення шахового контексту.

# 8. Структурна пам’ять

Структурна пам’ять зберігає не просто опис дошки, а результати аналізу її організації.

StructuralRecord = (
    StructuralID,
    PositionIdentity,
    Nodes,
    Relations,
    Attributes,
    Context,
    StructuralVersion,
    Provenance,
    EvidenceStatus
)

## 8.1. Типи структурних записів

- PIECE_RELATION;
- PAWN_STRUCTURE;
- KING_SAFETY_STRUCTURE;
- ATTACK_NETWORK;
- DEFENCE_NETWORK;
- CONTROL_MAP;
- SPACE_CONFIGURATION;
- WEAKNESS_CONFIGURATION;
- STRUCTURAL_COMPLEX;
- STRUCTURAL_TRANSFORMATION.

## 8.2. Локальна структурна пам’ять

Може зберігати:

- пішакові конфігурації;
- взаємне розташування фігур;
- локальні мережі захисту;
- конфігурації атак;
- заблоковані лінії.

## 8.3. Глобальна структурна пам’ять

Може зберігати:

- загальний розподіл простору;
- координацію фігур;
- структуру королівського захисту;
- загальні обмеження мобільності;
- баланс активності.

## 8.4. Правило структурного повторного використання

Структурний результат може бути повторно використаний для іншої позиції лише після перевірки всіх його залежностей.

Наприклад, однакова пішакова структура не гарантує однакової оцінки, оскільки:

- розташування фігур може відрізнятися;
- сторона ходу може бути іншою;
- тактичні умови можуть змінитися;
- права на рокіровку можуть відрізнятися;
- часовий контекст може бути іншим.

Структурна схожість є підставою для пошуку аналогії, але не для автоматичного перенесення висновку.

# 9. Стратегічна пам’ять

Стратегічний запис:

StrategicMemoryRecord = (
    PlanID,
    PositionIdentity,
    Goal,
    DesiredStructure,
    ActionConditions,
    Dependencies,
    Risks,
    Horizon,
    Alternatives,
    Uncertainty,
    Provenance,
    Status
)

## 9.1. Збереження цілей

Ціль повинна мати:

- опис бажаного результату;
- початковий стан;
- умови досягнення;
- залежності;
- горизонт;
- критерії перевірки.

## 9.2. Збереження планів

План не повинен зберігатися лише як послідовність ходів.

Його потрібно представляти як умовну структуру:

Plan = (Goal, Conditions, Actions, Dependencies, Risks, Horizon)

Це дозволяє зберігати стратегічний намір, не припускаючи, що суперник обов'язково дозволить виконати заплановану послідовність.

## 9.3. Повторна перевірка

Перед використанням старого плану необхідно:

1. відновити поточну позицію;
2. перевірити актуальність цілі;
3. перевірити причинні залежності;
4. перевірити тактичні умови;
5. перевірити доступні легальні ходи;
6. перевірити альтернативні плани;
7. оновити невизначеність.

Статуси плану:

- ACTIVE;
- PRESERVED;
- MODIFIED;
- SUSPENDED;
- REPLACED;
- ABANDONED;
- COMPLETED;
- REFUTED.

# 10. Пам’ять пошукового досвіду

Пошуковий досвід — це історія того, як двигун досліджував позиції.

SearchExperienceRecord = (
    SearchID,
    PositionIdentity,
    SearchConfiguration,
    Depth,
    Nodes,
    PrincipalVariation,
    Evaluation,
    Bounds,
    Alternatives,
    Cutoffs,
    Uncertainty,
    TerminationStatus,
    Provenance
)

## 10.1. Що потрібно зберігати

- початкову позицію;
- конфігурацію пошуку;
- версію алгоритму;
- глибину;
- кількість вузлів;
- головний варіант;
- оцінку;
- тип межі;
- завершені альтернативи;
- причини завершення;
- часові та ресурсні обмеження.

## 10.2. Що не можна припускати

Попередній пошуковий результат не є автоматично правильним для нової конфігурації.

Наприклад, результат може бути непридатним після:

- зміни позиції;
- зміни параметрів;
- зміни алгоритму;
- зміни глибини;
- зміни історичного контексту;
- зміни пошукового режиму.

## 10.3. Пошукова пам’ять і транспозиції

Транспозиційна таблиця може бути реалізована як спеціалізований механізм пошукової пам’яті.

Однак вона повинна зберігати необхідну інформацію про:

- позицію;
- глибину;
- оцінку;
- тип межі;
- найкращий хід;
- версію пошуку;
- умови повторного використання.

Застосування результату меншої глибини до більшої потребує окремої логіки. Не можна автоматично трактувати будь-який попередній результат як точний.

---

# 11. Пам’ять навчання

Навчальна пам’ять зберігає результати контрольованого вдосконалення двигуна.

TrainingRecord = (
    TrainingID,
    DatasetIdentity,
    ParameterVersion,
    CandidateVersion,
    TrainingProcedure,
    Objective,
    InitialState,
    FinalState,
    ValidationResults,
    Decision,
    Provenance
)

## 11.1. Джерела навчального досвіду

Дозволені джерела:

- власні self-play партії;
- внутрішньо згенеровані позиції;
- власні результати пошуку;
- власні помилки;
- контрольовані експерименти;
- результати незалежної внутрішньої валідації.

Не допускається використання:

- зовнішніх шахових партій як навчальних прикладів;
- сторонніх шахових двигунів як учителів;
- зовнішніх оцінок ходів як цільових сигналів;
- запозичених модулів шахових двигунів.

Загальні шахові математичні знання можуть вивчатися, але реалізація алгоритмів та механізм прийняття рішень залишаються власними.

## 11.2. Розділення даних

Необхідно розділяти:

- TRAINING MEMORY;
- DEVELOPMENT MEMORY;
- VALIDATION MEMORY;
- REGRESSION MEMORY;
- EXPERIMENTAL MEMORY.

Позиції, використані для налаштування параметрів, не повинні автоматично ставати незалежним доказом якості цих параметрів.

## 11.3. Версії параметрів

Кожний навчальний цикл повинен мати незмінний знімок параметрів.

Параметри не можна змінювати посеред активного пошуку.

Нова версія повинна пройти контрольований процес:

CANDIDATE → REGRESSION → VALIDATION → CHAMPION / REJECTED.

# 12. Пам’ять невизначеності та доказовості

Пам’ять повинна зберігати не лише висновок, а й те, наскільки він обґрунтований.

UncertaintyRecord = (
    ClaimID,
    Claim,
    Context,
    UncertaintyType,
    ConfidenceProfile,
    Evidence,
    Dependencies,
    Horizon,
    Provenance,
    Status
)

## 12.1. Типи невизначеності

- SEARCH_UNCERTAINTY;
- TACTICAL_UNCERTAINTY;
- EVALUATION_UNCERTAINTY;
- STRUCTURAL_UNCERTAINTY;
- STRATEGIC_UNCERTAINTY;
- TEMPORAL_UNCERTAINTY;
- MODEL_UNCERTAINTY;
- CONTEXTUAL_UNCERTAINTY.

## 12.2. Статуси знання

- KNOWN;
- COMPUTATION_DERIVED;
- SEARCH_SUPPORTED;
- STRONGLY_SUPPORTED;
- HYPOTHESIZED;
- UNKNOWN;
- REFUTED;
- FORMALLY_VERIFIED.

`UNKNOWN` не означає `FALSE`.

`SEARCH_SUPPORTED` не означає `FORMALLY_VERIFIED`.

`FORMALLY_VERIFIED` допускається лише за наявності перевіреного формального доказу.

## 12.3. Збереження суперечностей

Якщо два записи містять несумісні висновки, пам’ять повинна зберегти обидва до завершення процедури перевірки.

Не можна видаляти один запис лише тому, що інший новіший.

Необхідно порівняти:

- контексти;
- версії;
- вхідні дані;
- методи;
- горизонт;
- доказовість.

Суперечність може бути наслідком різних умов, а не помилки.

# 13. Пошук у пам’яті

Пошук повинен бути контекстним.

MemoryQuery = (
    QueryType,
    PositionIdentity,
    StructuralProfile,
    Context,
    RequiredEvidence,
    VersionConstraints,
    TimeConstraints
)

## 13.1. Рівні пошуку

**EXACT RETRIEVAL**

Пошук за точним ідентифікатором або повною ідентичністю.

**STRUCTURAL RETRIEVAL**

Пошук за структурними характеристиками.

**TACTICAL RETRIEVAL**

Пошук аналогічних тактичних конфігурацій.

**STRATEGIC RETRIEVAL**

Пошук стратегічних ситуацій і планів.

**EXPERIENTIAL RETRIEVAL**

Пошук попереднього досвіду.

**RESEARCH RETRIEVAL**

Пошук результатів внутрішніх експериментів.

## 13.2. Аналогічний пошук

Аналогічний пошук не повинен повертати старий результат як готову відповідь.

Він повинен повертати:

- подібну конфігурацію;
- спільні ознаки;
- відмінності;
- умови аналогії;
- потенційно релевантні висновки;
- необхідні перевірки.

## 13.3. Профіль подібності

Можна використовувати вектор:

Sim(P,Q) = (
    S_board,
    S_structure,
    S_tactics,
    S_context,
    S_strategy,
    S_history
)

Кожна компонента має власне визначення.

Загальний скаляр подібності допустимий лише після калібрування та збереження компонентного профілю.

Необхідно уникати хибного висновку:

Similarity(P,Q) ⇒ Equivalence(P,Q).

Подібність не доводить тотожності.

---

# 14. Часова актуальність пам’яті

Пам’ять повинна розрізняти історичне існування запису та його актуальність.

ValidityRecord = (
    CreatedAt,
    UpdatedAt,
    VerifiedAt,
    ValidFrom,
    ValidUntil,
    Conditions,
    Status
)

## 14.1. CURRENT

Запис відповідає актуальному контексту.

## 14.2. HISTORICAL

Запис зберігається для історичного відтворення.

## 14.3. EXPIRED

Умови застосування більше не виконуються.

## 14.4. SUPERSEDED

Запис замінений новішою версією.

## 14.5. CONTEXT_DEPENDENT

Запис залишається придатним лише за визначених умов.

## 14.6. UNKNOWN

Актуальність не встановлена.

Часова давність сама по собі не робить математичний або шаховий факт неправильним.

Водночас стратегічний план може втратити актуальність одразу після зміни позиції.

Отже, строк придатності повинен визначатися типом інформації, а не лише датою створення.

---

# 15. Збереження стану та відновлення

Система повинна підтримувати контрольоване збереження стану.

Snapshot = (
    SnapshotID,
    PositionState,
    ActiveTasks,
    CompletedResults,
    DependencyState,
    SearchState,
    MemoryReferences,
    ParameterVersion,
    AlgorithmVersions,
    Timestamp
)

## 15.1. Snapshot

Знімок повинен представляти узгоджений стан системи на конкретний момент.

Не допускається збереження такого знімка, в якому різні компоненти належать до несумісних версій позиції.

## 15.2. Checkpoint

Контрольна точка зберігає мінімально необхідний стан для відновлення довготривалого обчислення.

## 15.3. Recovery

Відновлення:

1. завантажити знімок;
2. перевірити цілісність;
3. перевірити версії;
4. відновити шаховий стан;
5. відновити активні залежності;
6. перевірити проміжні результати;
7. відкинути недійсні результати;
8. відновити допустимі завдання;
9. продовжити обчислення.

## 15.4. Безпечне відновлення

Не всі незавершені обчислення потрібно продовжувати з того самого внутрішнього кроку.

Якщо проміжний стан алгоритму неможливо надійно відновити, завдання повинно бути перезапущене.

Коректність важливіша за збереження кожного проміжного обчислення.

---

# 16. Цілісність та захист пам’яті

Пам’ять повинна мати механізми виявлення пошкодження.

Основні механізми:

- контрольні суми;
- перевірка типів;
- перевірка схем;
- перевірка залежностей;
- контроль версій;
- атомарне збереження;
- журнали змін;
- резервні копії;
- контроль міграцій.

## 16.1. Атомарність

Запис повинен або зберігатися повністю, або не зберігатися взагалі.

Частково записаний об'єкт не повинен ставати доступним як валідний.

## 16.2. Ізоляція

Пошкоджений або суперечливий запис повинен бути ізольований.

Він не повинен впливати на основний пошуковий процес.

## 16.3. Відновлення

Відновлення повинно спиратися на останню перевірену контрольну точку та журнал змін.

---

# 17. Управління обсягом пам’яті

Пам’ять не повинна безконтрольно зростати.

Для кожного класу записів визначається політика збереження.

## 17.1. PERMANENT RECORDS

Дані, необхідні для коректності та відтворюваності:

- правила;
- версії алгоритмів;
- версії параметрів;
- важливі експериментальні результати;
- регресійні приклади;
- походження критичних висновків.

## 17.2. LONG-TERM RECORDS

Дані довготривалої користі:

- перевірені структурні конфігурації;
- дослідницькі результати;
- підтверджені алгоритмічні поліпшення;
- важливі пошукові випадки.

## 17.3. SHORT-TERM RECORDS

Тимчасові дані:

- локальні оцінки;
- проміжні результати;
- короткочасні пошукові записи;
- тимчасові графи.

## 17.4. COMPRESSION

Стиснення допускається за умови збереження семантично необхідних даних.

Не можна стискати:

- історичний контекст;
- походження;
- доказовість;
- версії;
- критичні залежності.

## 17.5. ARCHIVING

Архівування не означає видалення.

Архівний запис повинен залишатися доступним для відтворення, якщо це необхідно для аудиту.

---

# 18. Пам’ять та автономний розвиток

Пам’ять є важливою складовою автономного розвитку SUBIT-CHESS.

Однак необхідно розрізняти:

- накопичення досвіду;
- формування гіпотез;
- зміну параметрів;
- зміну алгоритмів;
- підтвердження поліпшення.

Це окремі процеси.

## 18.1. Навчальний цикл

OBSERVATION  
↓  
MEMORY STORAGE  
↓  
PATTERN RETRIEVAL  
↓  
HYPOTHESIS FORMATION  
↓  
INTERNAL EXPERIMENT  
↓  
VALIDATION  
↓  
PARAMETER OR ALGORITHM CANDIDATE  
↓  
CHAMPION–CHALLENGER  
↓  
ACCEPT / REJECT / INCONCLUSIVE  
↓  
MEMORY UPDATE

## 18.2. Захист від самопідтвердження

Якщо двигун використовує власні попередні оцінки як єдине джерело істини, він може закріпити власні помилки.

Тому необхідно:

1. зберігати походження кожного навчального сигналу;
2. відокремлювати тренувальні та валідаційні позиції;
3. перевіряти результати на незалежно сформованих внутрішніх позиціях;
4. проводити регресійні тести;
5. зберігати відхилені кандидати;
6. дозволяти результату експерименту бути INCONCLUSIVE.

## 18.3. Пам’ять не навчає автоматично

Сам факт збереження результату не повинен змінювати параметри двигуна.

Будь-яка зміна параметрів повинна проходити окремий контрольований цикл.

---

# 19. Інтеграція з обчислювальним графом

Computational Memory та Computational Graph повинні працювати як взаємопов'язані, але окремі підсистеми.

Обчислювальний граф створює результати.

Пам’ять зберігає їх, індексує, перевіряє та повертає для повторного використання.

Загальна схема:

COMPUTATIONAL GRAPH  
↓  
RESULT VALIDATION  
↓  
PROVENANCE REGISTRATION  
↓  
MEMORY WRITE  
↓  
INDEXING  
↓  
PERSISTENCE  
↓  
MEMORY QUERY  
↓  
REVALIDATION  
↓  
COMPUTATIONAL GRAPH INPUT

## 19.1. Заборона циклічного самопідтвердження

Результат, отриманий із пам’яті, не повинен автоматично підтверджувати сам себе.

Якщо попередній результат використано як евристичну підказку, це має бути явно зазначено в походженні нового результату.

## 19.2. Контроль версій

Пам’ять повинна зберігати версії:

- шахових правил;
- алгоритмів;
- параметрів;
- схем даних;
- структурних моделей;
- пошукової конфігурації.

Результати різних версій можна порівнювати, але не можна безумовно змішувати.

**CM-INV-017 — TRAINING ISOLATION**

Навчальні та валідаційні дані розділені.

**CM-INV-018 — IMMUTABLE PARAMETER SNAPSHOT**

Параметри не змінюються під час активного пошуку.

**CM-INV-019 — AUTONOMOUS DATA ORIGIN**

Навчальний досвід походить із дозволених внутрішніх процесів.

**CM-INV-020 — AUDITABILITY**

# 26. Архітектурні принципи

**1. MEMORY IS NOT TRUTH**

Збережений результат не стає істинним лише через факт збереження.

**2. STATE BEFORE INTERPRETATION**

Первинний шаховий стан має пріоритет над похідними інтерпретаціями.

**3. CONTEXT BEFORE REUSE**

Жоден результат не переноситься без перевірки контексту.

**4. PROVENANCE BEFORE TRUST**

Походження є необхідною умовою оцінювання надійності.

**5. HISTORY WITHOUT FALSE GENERALIZATION**

Історичний досвід не повинен перетворюватися на універсальне правило без доказів.

**6. PRESERVE CONTRADICTIONS**

Суперечності потрібно аналізувати, а не приховувати.

**7. VERSIONED KNOWLEDGE**

Кожне значуще знання має версію.

**8. CONTROLLED PERSISTENCE**

Збереження даних повинно бути контрольованим і відтворюваним.

**9. SAFE RECOVERY**

Відновлення не повинно жертвувати коректністю заради швидкості.

**10. AUTONOMOUS EXPERIENCE**

Двигун накопичує власний досвід через власні обчислення, внутрішньо створені позиції та контрольований self-play.

# 27. Підсумкова архітектурна теза

Пам’ять SUBIT-CHESS не повинна бути просто базою шахових позицій або сховищем попередніх оцінок.

Вона має стати багаторівневою системою збереження та перевірки досвіду, у якій кожен запис має:

- визначений тип;
- ідентичність;
- контекст;
- походження;
- версію;
- залежності;
- часову актуальність;
- статус доказовості.

Це дозволяє розрізняти те, що двигун обчислив, те, що він перевірив, те, що він лише припускає, і те, що він ще не знає.

У ширшій архітектурі SUBIT-CHESS пам’ять забезпечує зв'язок між окремими рішеннями та довготривалим розвитком системи.

Вона не повинна диктувати рішення на основі минулого досвіду. Її функція — надавати релевантний досвід для нового аналізу, зберігаючи можливість його перевірити, відхилити або переосмислити.

**Пам’ять повинна зберігати не тільки те, що двигун знає, але й те, за яких умов, на підставі чого та з якими обмеженнями він це знає.**

Це є практичним застосуванням принципу:

**DO NOT COLLAPSE — CONTEXTUALIZE.**
