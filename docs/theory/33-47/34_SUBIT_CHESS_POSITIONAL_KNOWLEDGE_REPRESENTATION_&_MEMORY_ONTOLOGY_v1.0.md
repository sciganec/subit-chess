# PART I. ФУНДАМЕНТАЛЬНА ПРОБЛЕМА

## 1. Від позиційної інформації до шахового знання

Шаховий двигун традиційної архітектури переважно оперує такими об'єктами:

- позиція;
- фігура;
- поле;
- хід;
- оцінка;
- пошукова гілка;
- найкращий хід.

Цього достатньо для реалізації базового шахового пошуку.

Однак SUBIT-CHESS має ширшу архітектурну мету.

Він повинен оперувати не лише позиціями, а й знанням про них:

- які об'єкти існують;
- які відношення між ними виникають;
- які структурні конфігурації формуються;
- які залежності підтримують ці конфігурації;
- які зміни відбулися після конкретного ходу;
- які можливості виникли або зникли;
- які стратегічні цілі стали доступними;
- які плани були перевірені;
- які висновки виявилися правильними або помилковими;
- за яких умов попередній досвід залишається релевантним.

Це вимагає єдиної системи представлення знань.

## 2. Центральна теза

Знання про шахову позицію не можна зводити до одного числового значення.

Нехай:

K(P) = (S,C,R,D,G,E,M,U).

Де:

- S — стан;
- C — контекст;
- R — відношення;
- D — структурна динаміка;
- G — цілі та стратегічні конфігурації;
- E — докази та походження;
- M — пам'ять;
- U — невизначеність.

Це багатовимірне представлення.

Його компоненти повинні залишатися семантично розділеними, але мати можливість взаємодіяти через типізовані інтерфейси.

## 3. Принцип DO NOT COLLAPSE — CONTEXTUALIZE

SUBIT-CHESS не повинен перетворювати різні види знання на одну універсальну оцінку.

Наприклад:

- матеріальна перевага не тотожна позиційній перевазі;
- атака не тотожна загрозі;
- загроза не тотожна форсованому виграшу;
- геометрична можливість не тотожна легальному ходу;
- структурна залежність не тотожна причинності;
- стратегічний план не тотожний доведеному варіанту;
- подібність позицій не доводить тотожності їхніх наслідків.

Онтологія повинна зберігати ці відмінності.

# PART II. ONTOLOGY FOUNDATIONS

## 4. Визначення онтології

**SUBIT-CHESS Knowledge Ontology (SCKO)** — це формальна система типів об'єктів, відношень, подій, станів, контекстів, доказів і правил інтерпретації, призначена для представлення та використання шахового знання.

Онтологія визначає:

1. які об'єкти існують у моделі;
2. які характеристики вони мають;
3. які відношення між ними допустимі;
4. які події змінюють їхній стан;
5. як знання залежить від контексту;
6. як знання походить із конкретних обчислень;
7. як знання може бути використане повторно;
8. як воно втрачає актуальність;
9. як воно підтверджується або спростовується.

## 5. Онтологічна структура

Визначимо:

O = (𝒞, 𝒪, 𝓡, 𝓔, 𝓐, 𝓥, 𝓟, 𝓘).

Де:

- 𝒞 — класи;
- 𝒪 — об'єкти;
- 𝓡 — відношення;
- 𝓔 — події;
- 𝓐 — атрибути;
- 𝓥 — значення та стани;
- 𝓟 — походження;
- 𝓘 — правила інтерпретації.

## 6. Класи знання

Онтологія розрізняє такі основні класи:

**POSITIONAL KNOWLEDGE**

Знання про стан конкретної шахової позиції.

**GEOMETRIC KNOWLEDGE**

Знання про просторові відношення між фігурами та полями.

**LEGAL KNOWLEDGE**

Знання про правила та легальні переходи.

**STRUCTURAL KNOWLEDGE**

Знання про конфігурації та відношення.

**TACTICAL KNOWLEDGE**

Знання про форсовані можливості, загрози та комбінації.

**STRATEGIC KNOWLEDGE**

Знання про цілі, плани та довгострокові трансформації.

**CAUSAL KNOWLEDGE**

Знання про механізми, залежності та наслідки.

**TEMPORAL KNOWLEDGE**

Знання про послідовність подій, тривалість і часові обмеження.

**EVALUATIVE KNOWLEDGE**

Знання про числові та векторні оцінки.

**EXPERIENTIAL KNOWLEDGE**

Знання, отримане з власного пошуку, внутрішніх експериментів та self-play.

**META-KNOWLEDGE**

Знання про походження, надійність, актуальність і межі інших знань.

Ці класи можуть описувати один об'єкт одночасно, але не повинні втрачати власну семантику.

# PART III. CORE ENTITY ONTOLOGY

## 7. Базова одиниця — Chess Entity

Кожен об'єкт онтології повинен мати визначену ідентичність.

Entity = (ID, Type, Attributes, Context, Provenance, Version, Status).

Де:

- ID — ідентифікатор;
- Type — тип;
- Attributes — характеристики;
- Context — контекст;
- Provenance — походження;
- Version — версія;
- Status — поточний статус.

Ідентичність об'єкта не повинна залежати лише від його текстової назви.

## 8. Основні типи об'єктів

### 8.1. PIECE

Шахова фігура.

Piece = (ID, Color, Kind, Square, State).

Kind:

- KING;
- QUEEN;
- ROOK;
- BISHOP;
- KNIGHT;
- PAWN.

### 8.2. SQUARE

Поле шахівниці.

Square = (File, Rank, Occupancy, Attributes).

### 8.3. POSITION

Повний стан шахової партії.

Position = (Board, Side, Castling, EnPassant, Halfmove, Fullmove, History).

### 8.4. MOVE

Хід як формалізована дія.

Move = (Actor, Source, Target, Promotion, SpecialType).

### 8.5. STRUCTURE

Структурна конфігурація, яка формується з множини об'єктів та відношень.

Structure = (Members, Relations, Conditions, Context).

### 8.6. ZONE

Просторова область.

Приклади:

- KING_ZONE;
- CENTER;
- QUEENSIDE;
- KINGSIDE;
- PAWN_STRUCTURE_ZONE;
- OPEN_FILE;
- DIAGONAL;
- RANK.

### 8.7. GOAL

Стратегічна ціль.

Goal = (DesiredState, Preconditions, Constraints, Horizon, Status).

### 8.8. PLAN

План досягнення цілі.

Plan = (Goals, Actions, Dependencies, Risks, Alternatives, Horizon).

### 8.9. EVENT

Подія, яка змінює стан або знання.

Event = (Type, Time, SourceState, TargetState, Cause, Effects).

### 8.10. HYPOTHESIS

Непідтверджене твердження про позицію, структуру або наслідок.

Hypothesis = (Statement, Conditions, Evidence, Confidence, Status).

### 8.11. EVIDENCE

Доказова інформація.

Evidence = (Source, Method, Scope, Result, Version, Status).

### 8.12. EXPERIENCE

Запис власного досвіду двигуна.

Experience = (InitialPosition, Actions, Outcomes, Analysis, Parameters, Provenance).

# PART IV. RELATIONAL ONTOLOGY

## 9. Відношення як основа знання

Об'єкти самі по собі не формують повного знання.

Фігура має значення не лише через тип і матеріальну вартість, а й через її відношення до інших фігур, полів, зон та структур.

Тому центральним елементом SCKO є типізоване відношення.

Relation = (Source, Type, Target, Conditions, Context, Evidence).

## 10. Геометричні відношення

- OCCUPIES;
- ATTACKS_GEOMETRICALLY;
- REACHES_GEOMETRICALLY;
- BLOCKS_RAY;
- LIES_ON_FILE;
- LIES_ON_RANK;
- LIES_ON_DIAGONAL;
- ADJACENT_TO;
- DISTANT_FROM.

Вони описують геометрію, а не автоматично легальність.

## 11. Правові відношення

- LEGAL_MOVE;
- LEGAL_CAPTURE;
- LEGAL_CASTLING;
- LEGAL_EN_PASSANT;
- LEGAL_PROMOTION;
- CHECKS;
- EXPOSES_KING;

Ці відношення повинні визначатися Rule Engine.

Жодний стратегічний або евристичний модуль не може самостійно змінювати їхню семантику.

## 12. Функціональні відношення

- DEFENDS;
- SUPPORTS;
- PROTECTS;
- CONTROLS;
- RESTRICTS;
- CONNECTS;
- BLOCKS;
- ENABLES;
- DISABLES.

Кожне з них повинно мати власні умови.

Наприклад, SUPPORTS не повинно автоматично виводитися з того, що дві фігури контролюють одне поле.

## 13. Тактичні відношення

- THREATENS;

Тактичне відношення повинно мати доказовий статус.

Наприклад, FORCES_RESPONSE не може бути лише результатом поверхневої геометричної оцінки.

## 14. Стратегічні відношення

- ADVANCES_GOAL;
- SUPPORTS_PLAN;
- WEAKENS_STRUCTURE;
- IMPROVES_ACTIVITY;
- CREATES_OUTPOST;
- RESTRICTS_OPPONENT;

Стратегічні відношення зазвичай мають евристичний або гіпотетичний характер.

Їх не можна автоматично трактувати як доведені наслідки.

## 15. Причинні відношення

- CAUSES;
- ENABLES_CAUSALLY;
- PREVENTS;
- REQUIRES;
- MEDIATES;
- MODERATES;
- DEPENDS_ON;

Наприклад:

A ASSOCIATED_WITH B

не означає:

A CAUSES B.

# PART V. N-ARY RELATIONS AND STRUCTURAL OBJECTS

## 17. Межі бінарної моделі

Бінарні відношення не завжди достатні для представлення шахової структури.

Наприклад, зв'язана комбінація може залежати одночасно від:

- атакувальної фігури;
- цільової фігури;
- проміжного поля;
- заблокованої лінії;
- конкретної відповіді суперника.

Зведення такого явища до набору незалежних пар може втратити його цілісну семантику.

## 18. Гіпервідношення

Визначимо:

H = (X₁, X₂, ..., Xₙ, Type, Conditions, Context, Evidence).

Гіпервідношення пов'язує більше двох об'єктів.

Приклади:

- PIN_CONFIGURATION;
- DISCOVERED_ATTACK_CONFIGURATION;
- FORK_CONFIGURATION;
- MATE_NET;
- PAWN_CHAIN;
- KING_DEFENCE_NETWORK;
- EXCHANGE_DEPENDENCY;
- STRATEGIC_CORRIDOR.

## 19. Структура як окремий об'єкт

Складну конфігурацію доцільно представляти не лише як набір відношень, а й як самостійний об'єкт.

Наприклад:

PawnStructure = (Pawns, Files, Chains, Weaknesses, Breaks, Context).

Така структура має власну ідентичність у межах конкретної позиції та власну історію трансформацій.

## 20. Структурна ідентичність

Структурна ідентичність не означає незмінність усіх її елементів.

Визначимо:

StructuralIdentity(Sₜ,Sₜ₊₁).

Вона може зберігатися, якщо конфігурація проходить трансформацію, але зберігає визначені функціональні властивості.

Це потребує явного критерію.

Не можна вважати дві структури тотожними лише через візуальну схожість.

# PART VI. POSITIONAL KNOWLEDGE GRAPH

## 21. Граф знань

Основне представлення:

KG(P) = (V,E,L,A).

Де:

- V — вузли;
- E — ребра;
- L — типи відношень;
- A — атрибути.

Вузлами можуть бути:

- фігури;
- поля;
- позиції;
- структури;
- події;
- цілі;
- плани;
- гіпотези;
- докази.

## 22. Рівні графа

Граф знань повинен мати логічні рівні.

**LAYER 1 — STATE**

Фактичний стан шахової позиції.

**LAYER 2 — GEOMETRY**

Геометричні відношення.

**LAYER 3 — LEGALITY**

Легальні дії та обмеження.

**LAYER 4 — STRUCTURE**

Структурні конфігурації.

**LAYER 5 — TACTICS**

Тактичні залежності та форсовані можливості.

**LAYER 6 — STRATEGY**

Цілі, плани та стратегічні конфігурації.

**LAYER 7 — CAUSALITY**

Причинні механізми та наслідки.

**LAYER 8 — TEMPORALITY**

Події, тривалість, послідовність і часові горизонти.

**LAYER 9 — EVALUATION**

Оцінки та порівняння.

**LAYER 10 — META-KNOWLEDGE**

Походження, підтвердження, актуальність і невизначеність.

Ці рівні не є незалежними базами даних. Вони утворюють узгоджену онтологію.

## 23. Knowledge Graph Update

Після ходу m:

P' = T(P,m).

Тоді:

KG(P') = Update(KG(P),m).

Оновлення повинно визначати:

- нові вузли;
- видалені вузли;
- змінені атрибути;
- нові відношення;
- втрачені відношення;
- змінені структурні ідентичності;
- нові події;
- інвалідовані знання.

## 24. Full Rebuild Equivalence

Для перевірки коректності:

Update(KG(P),m) ≡ BuildKG(T(P,m)).

Це важливий інваріант.

Він дозволяє перевіряти інкрементальну систему на відповідність повній побудові графа.

# PART VII. CONTEXTUAL KNOWLEDGE

## 25. Контекст як частина змісту

Один і той самий факт може мати різне значення в різних умовах.

Наприклад, відкрита вертикаль може бути:

- важливою для атаки на короля;
- другорядною за наявності форсованої тактики;
- критичною для проникнення тури;
- малоцінною, якщо фігури не можуть використати її.

Отже:

Knowledge ≠ Fact.

Повніше:

Knowledge = Fact + Context + Interpretation + Provenance.

## 26. Контекстна модель

Для SUBIT-CHESS визначаємо окрему шахову модель:

C = I × Z × Φ.

Де:

I — характер ситуації:

- QUIET;
- DEFENCE;
- ATTACK;
- PRESSURE.

Z — просторова зона:

- GLOBAL;
- QUEENSIDE;
- KING;
- CENTER.

Φ — стратегічна фаза:

- OPENING;
- MIDDLEGAME;
- ENDGAME;
- TRANSITION.

Базова комбінаційна модель має 64 можливі контексти.

Це не означає, що конкретна позиція повинна мати лише один контекст.

## 27. Contextual Profile

CP(P) = {c₁,c₂,...,cₙ}.

Для кожного контексту:

ContextRecord = (Type, Intensity, Side, Horizon, Confidence, Provenance).

Контекст може мати різну інтенсивність для білих і чорних.

## 28. Контекстна релевантність знання

Нехай K — одиниця знання.

Визначимо:

Rel(K,P,C).

Це оцінка релевантності знання K для позиції P у контексті C.

Вона не повинна трактуватися як доказ істинності K.

Релевантність визначає доцільність розгляду, а не правильність висновку.

## 29. Context Transfer

Знання може бути перенесене в інший контекст лише після перевірки умов перенесення.

Transfer(K,C₁,C₂).

Можливі результати:

- VALID_TRANSFER;
- CONDITIONAL_TRANSFER;
- PARTIAL_TRANSFER;
- INVALID_TRANSFER;
- UNKNOWN.

Наприклад, знання про типову структуру пішаків може бути корисним у подібній позиції, але конкретна тактична комбінація не повинна переноситися без перевірки легальних ходів.

# PART VIII. TEMPORAL KNOWLEDGE ONTOLOGY

## 30. Часова природа шахового знання

Шахова позиція є станом у часовій послідовності.

Знання про неї також має часову залежність.

Потрібно розрізняти:

- коли факт виник;
- коли його було виявлено;
- коли він був підтверджений;
- коли він перестав бути актуальним;
- коли його було замінено новішим знанням.

## 31. Temporal Knowledge Record

TKR = (Content, ValidFrom, ValidUntil, ObservedAt, ConfirmedAt, Status).

Не всі часові поля обов'язкові для кожного типу знання.

Наприклад, геометричне правило має постійну семантику, а структурна слабкість може існувати лише в конкретному часовому інтервалі партії.

- MOVE_EXECUTED;
- PIECE_CAPTURED;
- CASTLING_RIGHT_LOST;
- PAWN_STRUCTURE_CHANGED;
- CHECK_CREATED;
- THREAT_CREATED;
- THREAT_RESOLVED;
- PLAN_ACTIVATED;
- PLAN_REFUTED;
- STRUCTURE_TRANSFORMED;
- OPPORTUNITY_EXPIRED;
- TERMINAL_STATE_REACHED.

## 33. Event Causality

Подія повинна мати:

Event = (ID, Type, Time, Actor, Preconditions, Effects, Cause, Evidence).

Подія не повинна бути просто записом текстового опису.

Вона повинна мати зв'язок із конкретним переходом стану.

## 34. Temporal Validity

- CURRENT;
- HISTORICAL;
- EXPIRED;
- SUPERSEDED;
- CONTEXT_DEPENDENT;

# PART X. KNOWLEDGE MEMORY ARCHITECTURE

## 40. Визначення пам'яті

SUBIT-CHESS Memory — це система збереження та повторного використання знання, яка враховує його зміст, походження, контекст, часовий статус і доказовість.

Пам'ять не є лише сховищем позицій.

Вона зберігає:

- факти;
- структури;
- події;
- причинні залежності;
- плани;
- результати пошуку;
- досвід;
- параметри;
- гіпотези;
- результати експериментів.

## 41. Логічні рівні пам'яті

### M0 — WORKING MEMORY

Поточний пошуковий процес.

Містить:

- поточну позицію;
- кандидатні ходи;
- активні гілки;
- проміжні оцінки;
- поточні структурні характеристики.

### M1 — POSITION MEMORY

Короткострокова пам'ять позицій.

Містить:

- транспозиції;
- повторно використовувані оцінки;
- результати локального аналізу;
- позиційні ідентифікатори.

### M2 — STRUCTURAL MEMORY

Пам'ять структур.

Містить:

- типові конфігурації;
- структурні трансформації;
- відношення;
- причинні залежності;
- контекстні характеристики.

### M3 — STRATEGIC MEMORY

Пам'ять планів і стратегічних конфігурацій.

Містить:

- цілі;
- плани;
- альтернативні маршрути;
- результати їхньої перевірки;
- умови застосування.

### M4 — EXPERIENTIAL MEMORY

Пам'ять власного досвіду.

Містить:

- self-play;
- внутрішні експерименти;
- помилки;
- невдалі прогнози;
- результати виправлень.

### M5 — RESEARCH MEMORY

Дослідницький архів.

Містить:

- гіпотези;
- експериментальні протоколи;
- результати;
- регресійні набори;
- версії алгоритмів;
- рішення щодо прийняття або відхилення змін.

Ці рівні є логічними. Вони не вимагають шести фізично незалежних баз даних.

## 42. Memory Entry

MemoryEntry = (ID, Type, Content, Context, Provenance, Evidence, Version, Time, Validity).

## 43. Memory Retrieval

Пошук знань повинен враховувати:

1. тотожність позиції;
2. тотожність структури;
3. контекстну подібність;
4. подібність причинних механізмів;
5. часову релевантність;
6. доказовий статус;
7. сумісність версій.

## 44. Retrieval Is Not Validation

Знайдений запис не стає правильним лише через те, що він відповідає пошуковому запиту.

Тому:

RETRIEVED(K) ⇏ VALID(K).

Перед використанням знання необхідно перевірити:

- контекст;
- походження;
- статус;
- актуальність;
- сумісність із поточною позицією.

## 45. Memory Reuse Policy

Знання може бути повторно використане як:

- DIRECT_REUSE;
- CONTEXTUAL_REUSE;
- ANALOGICAL_REUSE;
- HYPOTHESIS_GENERATION;
- SEARCH_GUIDANCE;
- INVALID_FOR_CURRENT_POSITION.

Навіть DIRECT_REUSE не скасовує перевірку шахових правил.

# PART XI. POSITION IDENTITY AND STRUCTURAL SIMILARITY

## 46. Проблема ідентичності позиції

Дві позиції можуть мати однакове розташування фігур, але відрізнятися:

- стороною ходу;
- правами на рокіровку;
- можливістю en passant;
- історією;
- умовами нічиєї;
- іншими релевантними параметрами.

Тому тотожність шахового стану не можна визначати лише за розташуванням фігур.

## 47. Повна ідентичність

PositionIdentity(P₁,P₂) повинна враховувати всі поля, необхідні для конкретної задачі.

Для пошукового повторного використання це може бути один набір полів.

Для історично залежних правил — ширший набір.

Отже, онтологія повинна підтримувати кілька типів ідентичності.

## 48. Identity Classes

**BOARD IDENTITY**

Однакове розташування фігур.

**RULE-STATE IDENTITY**

Однаковий стан, необхідний для визначення легальних ходів.

**HISTORY IDENTITY**

Однаковий релевантний історичний контекст.

**STRUCTURAL IDENTITY**

Однакова визначена структурна конфігурація.

**STRATEGIC IDENTITY**

Еквівалентність визначених стратегічних властивостей.

**EXPERIENTIAL IDENTITY**

Однаковий або зіставний досвід за визначених умов.

Ці ідентичності не взаємозамінні.

## 49. Similarity Model

Для двох позицій:

Sim(P₁,P₂) = (S_B,S_R,S_G,S_T,S_C,S_H).

Де:

- S_B — подібність дошки;
- S_R — подібність відношень;
- S_G — подібність структур;
- S_T — тактична подібність;
- S_C — контекстна подібність;
- S_H — історична сумісність.

Це вектор подібності.

Зведення до одного числа допускається лише за чітко визначеної задачі.

## 50. Similarity Is Not Equivalence

Sim(P₁,P₂) > 0

не означає:

P₁ ≡ P₂.

Навіть висока подібність не гарантує однакових тактичних наслідків.

Тому аналогічні позиції використовуються для формування гіпотез і пошукових пріоритетів, але не як заміна аналізу поточної позиції.

# PART XII. KNOWLEDGE EVOLUTION

## 51. Знання змінюється

Knowledge Lifecycle:

GENERATED  
→ RECORDED  
→ CONTEXTUALIZED  
→ TESTED  
→ SUPPORTED  
→ REUSED  
→ REEVALUATED  
→ SUPERSEDED або REFUTED.

## 52. Knowledge States

- PROPOSED;
- ACTIVE;
- SUPPORTED;
- CONDITIONAL;
- CONFLICTED;
- REFUTED;
- STALE;
- SUPERSEDED;
- ARCHIVED.

## 53. Knowledge Revision

Якщо новий результат суперечить попередньому, система не повинна просто перезаписувати старий запис.

Вона повинна:

1. зберегти старе знання;
2. створити новий запис;
3. встановити конфлікт;
4. порівняти походження;
5. порівняти умови;
6. визначити, чи справді результати суперечать один одному;
7. оновити статуси;
8. зберегти історію зміни.

## 54. Knowledge Versioning

KnowledgeVersion = (ID, Version, ParentVersion, Change, Evidence).

Це забезпечує відстежуваність еволюції знання.

## 55. Knowledge Contradiction

Суперечність може виникати через:

- різні позиції;
- різні контексти;
- різні горизонти;
- різні версії алгоритму;
- різні параметри;
- різну доказову силу;
- справжню помилку.

Тому суперечність не повинна автоматично трактуватися як логічна несумісність.

Спочатку потрібно перевірити сумісність умов.

# PART XIV. KNOWLEDGE QUERY AND INFERENCE

## 60. Запит до онтології

Система повинна підтримувати структуровані запити.

KnowledgeQuery = (Target, RelationTypes, Context, Time, EvidenceConstraints).

Приклади:

- які фігури захищають короля;
- які структури залежать від конкретного пішака;
- які плани використовують відкриту вертикаль;
- які можливості виникли після останнього ходу;
- які стратегічні цілі втратили здійсненність;
- які висновки мають недостатній доказовий статус.

## 61. Query Result

QueryResult = (Matches, Context, Evidence, Completeness, Status).

Результат повинен показувати не лише знайдені записи, а й обмеження пошуку.

## 62. Ontological Inference

Виведення нових знань дозволяється лише за визначеними правилами.

Наприклад:

A SUPPORTS B  
B ENABLES C

не завжди означає:

A ENABLES C.

Для такого висновку потрібні додаткові семантичні умови.

Отже, правила композиції повинні бути типізованими та явно визначеними.

## 63. Inference Levels

- DIRECT_FACT;
- RULE_DERIVED;
- STRUCTURALLY_DERIVED;
- TACTICALLY_DERIVED;
- STRATEGICALLY_INFERRED;
- CAUSALLY_INFERRED;
- ANALOGICALLY_SUGGESTED;
- UNKNOWN.

Результат виведення повинен зберігати посилання на вихідні записи.

## 64. No Unsupported Inference

Онтологія не повинна генерувати твердження, якщо необхідні передумови відсутні.

Якщо висновок не може бути підтверджений, результатом має бути:

UNKNOWN або INCOMPLETE.

Це краще, ніж створювати хибну впевненість.

# PART XV. KNOWLEDGE COMPRESSION AND ABSTRACTION

## 65. Проблема масштабування

Під час розвитку двигуна кількість позиційних записів, структур, подій і досвіду може зростати дуже швидко.

Тому потрібні механізми абстракції.

Однак стиснення не повинно знищувати критичні відмінності.

## 66. Абстракційні рівні

**MICRO**

Окремі фігури, поля, ходи та локальні відношення.

**MESO**

Локальні структури, комплекси фігур, пішакові ланцюги, атаки.

**MACRO**

Загальна позиційна організація, стратегічні плани, баланс сторін.

**META**

Закономірності, класи структур, причинні механізми та принципи аналізу.

## 67. Abstraction Mapping

Абстракція:

α: K → K'.

Вона повинна зберігати визначені властивості.

Не кожна характеристика може бути збережена на кожному рівні.

Тому кожен абстрактний запис повинен містити перелік властивостей, які він зберігає, і властивостей, які втрачає.

## 68. Loss-Aware Compression

CompressedKnowledge = (AbstractContent, PreservedProperties, LostProperties, Scope, Provenance).

Система не повинна використовувати стиснений запис для тверджень, які потребують втраченої інформації.

## 69. Structural Pattern Formation

З багатьох внутрішньо отриманих прикладів система може формувати узагальнені структурні шаблони.

Але шаблон повинен зберігати:

- умови застосування;
- винятки;
- походження;
- кількість спостережень;
- доказовий статус;
- невизначеність.

Частота появи шаблону сама по собі не доводить його стратегічної правильності.

# PART XVI. MEMORY SAFETY AND CONSISTENCY

## 70. Memory Integrity

Кожен запис повинен мати контроль цілісності.

Важливі властивості:

- унікальність ідентифікатора;
- цілісність посилань;
- узгодженість версій;
- збереження походження;
- контроль часу;
- контроль статусу;
- захист від непомітної зміни.

## 71. Memory Isolation

Поточний пошук не повинен отримувати частково записаний або несумісний запис.

Необхідно забезпечити атомарність критичних оновлень.

## 72. Memory Conflict Resolution

За наявності конфлікту:

1. не приховувати суперечність;
2. не перезаписувати джерела;
3. визначити умови кожного твердження;
4. перевірити доказовий статус;
5. виконати повторний аналіз за потреби;
6. зберегти результат узгодження.

## 73. Memory Garbage Collection

Видалення записів повинно враховувати їхню цінність.

Критичні записи:

- формальні визначення;
- регресійні результати;
- історія параметрів;
- доказові ланцюги;
- активні залежності;
- базові конфігурації.

Їх не можна видаляти лише через вік.

## 74. Memory Decay

Деякі записи можуть втрачати актуальність.

Наприклад:

- локальна оцінка позиції;
- поточний план;
- контекстна інтенсивність;
- прогноз доступності можливості.

Однак математичне визначення або підтверджене правило не повинно автоматично втрачати чинність лише через час.
