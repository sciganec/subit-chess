# 1. Призначення документа

Цей документ визначає архітектуру обчислювального графа SUBIT-CHESS — внутрішньої системи організації, координації та виконання аналітичних операцій шахового двигуна.

Мета полягає в тому, щоб сформувати єдину обчислювальну структуру, яка дозволяє:

1. представляти залежності між аналітичними компонентами;
2. визначати порядок виконання обчислень;
3. передавати результати між підсистемами;
4. оновлювати лише ті компоненти, які залежать від зміненої частини позиції;
5. виявляти застарілі або суперечливі результати;
6. координувати паралельні обчислення;
7. керувати пам'яттю проміжних результатів;
8. забезпечувати відтворюваність аналітичного процесу;
9. підтримувати контроль правильності обчислень;
10. інтегрувати пошук, структурний аналіз, оцінювання та стратегічне планування.

Обчислювальний граф повинен забезпечувати не просто швидке виконання окремих алгоритмів, а узгодженість усієї аналітичної системи.

Основна теза:

**SUBIT-CHESS повинен розглядати шахову позицію як об'єкт багаторівневого аналізу, а сам аналіз — як організовану мережу взаємозалежних обчислень.**

# 2. Межі застосування

Обчислювальний граф не замінює:

- шаховий стан;
- правила шахів;
- генератор легальних ходів;
- структурний граф позиції;
- причинний граф;
- стратегічний план;
- пошукове дерево.

Він координує їхню роботу.

Необхідно розрізняти три структури.

## 2.1. Шаховий структурний граф

Структурний граф:

Gₛ(P) = (Vₛ, Eₛ, Lₛ)

Описує шахові об'єкти та відносини між ними.

Наприклад:

- фігура атакує поле;
- фігура захищає іншу фігуру;
- пішак обмежує рух;
- фігура блокує лінію;
- король залежить від захисної конфігурації.

Його призначення — представити організацію позиції.

## 2.2. Причинний граф

Причинний граф:

G꜀(P) = (V꜀, E꜀, L꜀)

Описує залежності між фактами, подіями та наслідками.

Наприклад:

- звільнення вертикалі створює можливість атаки;
- усунення захисника робить фігуру вразливою;
- переміщення фігури відкриває діагональ.

Його призначення — пояснювати механізми зміни позиції.

## 2.3. Обчислювальний граф

Обчислювальний граф:

G𝚌ₒₘₚ = (V𝚌ₒₘₚ, E𝚌ₒₘₚ, D, S)

де:

- V𝚌ₒₘₚ — обчислювальні вузли;
- E𝚌ₒₘₚ — залежності між вузлами;
- D — дані, які передаються;
- S — правила виконання та синхронізації.

Його призначення — визначати, які обчислення необхідно виконати, у якій послідовності та за яких умов їхні результати можна використовувати.

Це принципове розмежування.

Наприклад, вузол `ATTACK_RELATIONS` обчислює атаки фігур, використовуючи геометрію позиції. Вузол `STRUCTURAL_GRAPH` використовує ці результати для побудови структурних відносин. Вузол `STRATEGIC_ANALYSIS` може використовувати структурний граф, але не повинен безпосередньо підміняти результати генератора легальних ходів.

# 3. Загальна формальна модель

Обчислювальний граф визначається як:

CG(P, C, V) = (N, E, A, Q, R)

де:

- P — поточна шахова позиція;
- C — контекст обчислення;
- V — версія конфігурації алгоритмів;
- N — множина обчислювальних вузлів;
- E — множина залежностей;
- A — множина атрибутів вузлів і ребер;
- Q — черга обчислювальних завдань;
- R — реєстр результатів.

Кожний вузол має типізований вхід, алгоритм обчислення та типізований вихід.

Формально:

nᵢ = (IDᵢ, Typeᵢ, Inputᵢ, Functionᵢ, Outputᵢ, Versionᵢ, Statusᵢ)

Стани вузла:

- NOT_INITIALIZED;
- READY;
- RUNNING;
- COMPLETED;
- INVALIDATED;
- FAILED;
- CANCELLED;
- BLOCKED;
- UNKNOWN.

Результат обчислення:

Resultᵢ = (Valueᵢ, Contextᵢ, Provenanceᵢ, Versionᵢ, Statusᵢ)

Результат не може використовуватися лише тому, що він існує в пам'яті. Необхідно перевірити його відповідність поточній позиції, контексту, залежностям та версіям алгоритмів.

# 5. Архітектура залежностей

Обчислювальне ребро визначається як:

eᵢⱼ = (nᵢ, nⱼ, Type, Condition, Version)

Воно означає, що результат вузла nᵢ необхідний вузлу nⱼ.

Основні типи залежностей:

**DATA_DEPENDENCY** — вузол потребує конкретних даних іншого вузла.

**CONTROL_DEPENDENCY** — виконання залежить від умови або рішення іншого вузла.

**VERSION_DEPENDENCY** — результат допустимий лише для визначеної версії.

**CONTEXT_DEPENDENCY** — результат залежить від контексту позиції.

**TEMPORAL_DEPENDENCY** — результат залежить від історії або послідовності подій.

**VALIDATION_DEPENDENCY** — результат потребує незалежної перевірки.

**RESOURCE_DEPENDENCY** — виконання потребує доступного обчислювального ресурсу.

**INVALIDATION_DEPENDENCY** — зміна одного вузла може зробити результат іншого вузла застарілим.

## 5.1. Напрямок залежностей

Якщо вузол B використовує результат вузла A:

A → B

Це означає, що B не може бути коректно виконаний до отримання необхідного результату A.

Наприклад:

BOARD_STATE → OCCUPANCY_MAP

OCCUPANCY_MAP → SLIDING_ATTACKS

SLIDING_ATTACKS → ATTACK_RELATIONS

ATTACK_RELATIONS → STRUCTURAL_GRAPH

STRUCTURAL_GRAPH → STRUCTURAL_EVALUATION

STRUCTURAL_EVALUATION → POSITION_VALUE_AGGREGATION

Цей порядок не є універсальним для всіх обчислень. Незалежні компоненти можуть виконуватися паралельно.

## 5.2. Заборона прихованих залежностей

Алгоритм не повинен використовувати дані, які не задекларовані в його контракті.

Наприклад, стратегічний аналіз не повинен непомітно використовувати застарілий стан короля або попередню версію структурного графа.

Кожний вхід повинен бути явно зазначений.

Це необхідно для:

- відтворюваності;
- тестування;
- локалізації помилок;
- інкрементального оновлення;
- паралельного виконання.

# 6. Граф залежностей як DAG та проблема циклів

У нормальному режимі обчислювальний граф повинен бути спрямованим ациклічним графом:

DAG = (N, E)

Це дозволяє визначати порядок виконання через топологічне сортування.

Проте в SUBIT-CHESS деякі аналітичні компоненти взаємодіють циклічно.

Наприклад:

- стратегічна оцінка впливає на пріоритети пошуку;
- результати пошуку впливають на стратегічну оцінку;
- аналіз невизначеності може збільшити глибину пошуку;
- результати глибшого пошуку змінюють невизначеність.

Якщо безпосередньо з'єднати ці вузли двосторонніми залежностями, утвориться цикл.

## 6.1. Розділення фаз

Циклічні залежності необхідно розділяти на фази.

Наприклад:

1. STRATEGIC_ANALYSIS₀;
2. SEARCH_CONFIGURATION₀;
3. SEARCH_EXECUTION₀;
4. UNCERTAINTY_UPDATE₁;
5. STRATEGIC_REVALIDATION₁.

Тоді залежності стають часово індексованими:

Strategic₀ → Search₀ → Uncertainty₁ → Strategic₁

Це усуває неоднозначність щодо того, який саме результат використовується.

## 6.2. Ітераційні компоненти

Для окремих алгоритмів допускається контрольована ітерація.

Формально:

xₖ₊₁ = F(xₖ, D)

де D — незмінний набір вхідних даних у межах ітераційного циклу.

Умови зупинки:

- досягнення встановленої точності;
- стабілізація результату;
- досягнення обчислювального ліміту;
- виявлення нестабільності;
- скасування завдання.

Необхідно встановити максимальну кількість ітерацій.

Збіжність не можна припускати без математичного обґрунтування.

## 6.3. Правило розділення первинних і похідних даних

Первинний стан не повинен залежати від власних похідних оцінок.

Наприклад:

BOARD_STATE → STRUCTURAL_ANALYSIS

але не:

STRUCTURAL_ANALYSIS → BOARD_STATE.

Це фундаментальний принцип захисту від логічного самопідтвердження.

Також деякі вузли можуть виконуватися повторно після отримання нових результатів пошуку.

# 8. Обчислювальні контракти

Кожний вузол повинен мати формальний контракт.

Контракт визначає:

- тип входу;
- обов'язкові залежності;
- передумови;
- алгоритмічну операцію;
- тип виходу;
- постумови;
- можливі помилки;
- правила кешування;
- правила інвалідації;
- версію алгоритму.

Загальна форма:

Contract(n) = (I, D, Pre, F, O, Post, Err, Cache, Version)

## 8.1. Приклад контракту LEGAL_MOVE_GENERATION

Вхід:

- BOARD_STATE;
- SIDE_TO_MOVE;
- CASTLING_STATE;
- EN_PASSANT_STATE;
- RULE_CONFIGURATION.

Операція:

LegalMoves(P) = L(P)

Вихід:

- повний набір легальних ходів;
- статус шаху;
- необхідні спеціальні умови.

Постумова:

Кожний повернений хід повинен відповідати правилам шахів.

Жодний нелегальний хід не може бути включений до результату.

Повнота набору також повинна бути забезпечена:

∀m ∈ L(P): Legal(P,m)

і

∀m: Legal(P,m) ⇒ m ∈ L(P).

Остання умова означає, що генератор не повинен пропускати легальні ходи.

Це один із найважливіших контрактів двигуна.

## 8.2. Приклад контракту STRUCTURAL_GRAPH

Вхід:

- BOARD_STATE;
- OCCUPANCY_MAP;
- ATTACK_RELATIONS;
- DEFENCE_RELATIONS;
- LEGAL_STATE.

Операція:

Gₛ(P) = BuildStructuralGraph(P)

Вихід:

- вузли позиції;
- типізовані відносини;
- структурні конфігурації;
- атрибути;
- походження кожного твердження.

Постумова:

Усі відносини повинні відповідати типам і правилам їхнього визначення.

Геометричне відношення не може автоматично трактуватися як легальний хід або стратегічна перевага.

## 8.3. Приклад контракту POSITION_VALUE_AGGREGATION

Вхід:

- матеріальна оцінка;
- активність;
- структурна оцінка;
- безпека королів;
- тактичні фактори;
- простір;
- потенціал трансформації.

Операція:

E(P,s;θ) = Aggregate(F(P,s), θ)

Вихід:

- загальна оцінка;
- вектор компонентів;
- контекст;
- версія параметрів;
- невизначеність;
- походження.

Постумови:

- не допускається подвійне врахування одного й того самого фактора без явного обґрунтування;
- точні шахові факти не можуть бути замінені евристиками;
- термінальні результати мають пріоритет над звичайною оцінкою;
- усі параметри повинні належати одній незмінній версії.

---

# 9. Передача результатів між вузлами

Результати повинні передаватися як типізовані об'єкти.

Не рекомендується передавати довільні набори чисел без контексту.

Стандартна структура:

ComputationResult = (
    ResultID,
    NodeID,
    PositionKey,
    ContextKey,
    InputVersions,
    AlgorithmVersion,
    ParameterVersion,
    Value,
    EvidenceStatus,
    Provenance,
    Timestamp
)

Ця структура дозволяє встановити:

- хто створив результат;
- для якої позиції;
- за яких умов;
- на основі яких даних;
- якою версією алгоритму;
- чи залишається результат актуальним.

## 9.1. Статуси доказовості

Результати повинні зберігати свій епістемічний статус:

- EXACT_RULE_FACT;
- COMPUTATION_DERIVED;
- SEARCH_SUPPORTED;
- HEURISTIC;
- HYPOTHESIS;
- UNKNOWN;
- REFUTED;
- FORMALLY_VERIFIED.

`FORMALLY_VERIFIED` допускається лише тоді, коли існує відповідний формальний доказ.

Сам факт успішного виконання програми не є формальним доказом правильності алгоритму.

## 9.2. Незалежність статусів

Необхідно розрізняти:

- обчислення завершено;
- обчислення пройшло перевірку;
- твердження підтверджено пошуком;
- твердження доведено формально.

Це чотири різні стани.

---

# 10. Інкрементальне виконання графа

Повне повторне обчислення всіх вузлів після кожного ходу може бути надлишковим.

Тому обчислювальний граф повинен підтримувати інкрементальне оновлення.

Нехай:

P' = T(P,m)

Після виконання ходу m формується:

ΔP = Change(P,P')

Далі визначається множина безпосередньо залежних вузлів:

Affected₀ = DirectDependents(ΔP)

Після цього обчислюється транзитивне поширення залежностей:

Affected = Closure(Affected₀, E)

Але просте транзитивне поширення не означає, що всі залежні вузли обов'язково потрібно повністю перерахувати.

Для кожного вузла визначається стратегія:

- PRESERVE;
- PATCH;
- RECOMPUTE;
- INVALIDATE;
- VERIFY.

## 10.1. PRESERVE

Результат залишається актуальним.

Це дозволено лише тоді, коли всі його залежності залишилися незмінними або доведено, що зміни не впливають на результат.

## 10.2. PATCH

Результат оновлюється за допомогою локальної зміни.

Наприклад, після переміщення фігури можна оновити лише відповідні геометричні лінії, якщо алгоритм і представлення дозволяють точно визначити область впливу.

## 10.3. RECOMPUTE

Вузол виконується повторно.

Це необхідно, якщо локального оновлення недостатньо або його правильність не доведена.

## 10.4. INVALIDATE

Результат позначається недійсним.

Він не може бути використаний до повторного обчислення.

## 10.5. VERIFY

Результат перевіряється незалежним методом або порівнянням із повним перерахунком.

Це особливо важливо під час розробки інкрементальних алгоритмів.

## 10.6. Основний інваріант

Для кожного інкрементально оновлюваного вузла:

Incremental(Build(P), ΔP) ≡ Build(P')

де еквівалентність визначається семантикою конкретного вузла.

Для точних шахових даних еквівалентність має бути точною.

Для евристичних результатів допускається інша форма порівняння лише за заздалегідь визначеними критеріями.

---

# 11. Паралельне виконання

Обчислювальний граф повинен дозволяти паралельне виконання незалежних завдань.

Нехай множина вузлів:

N = {n₁, n₂, ..., nₖ}

Якщо між nᵢ та nⱼ немає необхідної залежності, вони потенційно можуть виконуватися паралельно.

Однак відсутність прямого ребра не завжди достатня.

Необхідно також перевірити:

- відсутність конфлікту запису;
- узгодженість версій;
- доступність ресурсів;
- відсутність прихованих спільних змінних;
- коректність синхронізації.

## 11.1. Модель виконання

Task = (
    TaskID,
    NodeID,
    Priority,
    Dependencies,
    ResourceCost,
    Deadline,
    State
)

Планувальник повинен запускати завдання лише після завершення всіх обов'язкових залежностей.

## 11.2. Класи паралелізму

**POSITION PARALLELISM**

Незалежний аналіз різних позицій або гілок пошуку.

**FEATURE PARALLELISM**

Паралельне обчислення матеріалу, активності, простору та інших незалежних характеристик.

**SEARCH PARALLELISM**

Паралельне дослідження частин дерева пошуку.

**VALIDATION PARALLELISM**

Незалежні перевірки результатів.

**RESEARCH PARALLELISM**

Паралельне виконання контрольованих внутрішніх експериментів.

## 11.3. Захист від конфліктів

Паралельні вузли не повинні безконтрольно змінювати спільний стан.

Рекомендована модель:

- незмінні вхідні знімки;
- локальні результати;
- контрольоване об'єднання;
- перевірка версій;
- атомарне оприлюднення результату.

Якщо версія позиції змінилася під час виконання вузла, результат повинен бути перевірений або відкинутий.

## 11.4. Пошукова паралельність

Паралельний пошук не повинен порушувати коректність альфа-бета меж.

Результати різних потоків мають бути узгоджені з відповідними межами, глибиною, позицією та параметрами.

Паралельне виконання не гарантує однакової кількості вузлів або ідентичного порядку дослідження гілок.

Тому необхідно розділяти:

- детермінованість шахових правил;
- детермінованість алгоритму;
- детермінованість розкладу потоків;
- відтворюваність експерименту.

---

# 12. Кешування обчислювальних результатів

Кеш повинен зберігати результати, які можна безпечно повторно використовувати.

Однак кешування не повинно перетворюватися на використання застарілих даних.

Ключ кешу:

CacheKey = (
    PositionIdentity,
    ContextIdentity,
    NodeType,
    AlgorithmVersion,
    ParameterVersion,
    DependencySignature
)

Для пошукових результатів можуть бути потрібні додаткові параметри:

- глибина;
- тип межі;
- пошуковий режим;
- необхідні історичні умови;
- версія пошукової конфігурації.

## 12.1. Типи кешу

**STATE CACHE**

Зберігає похідні представлення шахового стану.

**GEOMETRY CACHE**

Зберігає результати геометричного аналізу.

**STRUCTURAL CACHE**

Зберігає структурні графи та їхні атрибути.

**EVALUATION CACHE**

Зберігає компоненти оцінювання.

**SEARCH CACHE**

Зберігає результати пошуку та транспозиційну інформацію.

**PLAN CACHE**

Зберігає стратегічні цілі та плани з обов'язковою перевіркою актуальності.

## 12.2. Правило повторного використання

Результат може бути використаний повторно лише тоді, коли:

ReuseValid(R,P') = TRUE

Це передбачає відповідність:

- позиції;
- контексту;
- залежностей;
- версії алгоритму;
- параметрів;
- історичних умов.

Схожість двох позицій сама по собі не є підставою для прямого повторного використання результату.

## 12.3. Транспозиції

Однакова шахова позиція може виникнути різними послідовностями ходів.

Проте тотожність дошки не завжди означає тотожність повного шахового стану.

Необхідно враховувати:

- сторону ходу;
- права на рокіровку;
- можливість взяття на проході;
- правила нічиєї;
- необхідну історію повторень.

Тому ключ кешу повинен відображати не лише розташування фігур.

---

# 13. Інвалідація результатів

Інвалідація — процес позначення результатів, які більше не можна використовувати без перевірки.

Основні причини:

1. зміна шахового стану;
2. зміна історії;
3. зміна параметрів оцінювання;
4. зміна алгоритму;
5. зміна контексту;
6. зміна залежностей;
7. виявлення помилки;
8. невідповідність версій;
9. зміна пошукового бюджету, якщо результат залежить від нього.

Інвалідація повинна поширюватися лише відповідно до реальних залежностей.

Необхідно уникати двох протилежних помилок:

**UNDER-INVALIDATION** — застарілий результат продовжує використовуватися.

**OVER-INVALIDATION** — без необхідності відкидаються всі результати, включно з тими, що залишаються актуальними.

Обидві помилки знижують ефективність системи.

---

# 14. Обчислювальна узгодженість

SUBIT-CHESS повинен мати окремий механізм перевірки узгодженості графа.

Для кожного вузла необхідно перевіряти:

- чи виконані передумови;
- чи завершені залежності;
- чи збігаються версії;
- чи відповідає результат позиції;
- чи збережено походження;
- чи немає суперечності з точними фактами;
- чи не використано недійсний результат.

## 14.1. Рівні узгодженості

**LEVEL 1 — LOCAL CONSISTENCY**

Перевірка окремого вузла.

**LEVEL 2 — DEPENDENCY CONSISTENCY**

Перевірка відповідності результатів залежних вузлів.

**LEVEL 3 — POSITION CONSISTENCY**

Перевірка відповідності аналітичних результатів поточному шаховому стану.

**LEVEL 4 — GLOBAL CONSISTENCY**

Перевірка всієї системи результатів, що беруть участь у прийнятті рішення.

## 14.2. Суперечності

Якщо два вузли повертають несумісні результати, система не повинна автоматично вибирати один із них.

Вона повинна:

1. встановити тип суперечності;
2. перевірити первинні дані;
3. перевірити залежності;
4. перевірити версії;
5. повторити відповідні обчислення;
6. за необхідності ізолювати помилковий вузол;
7. зберегти запис про інцидент.

Це особливо важливо, коли евристичні результати суперечать точним шаховим фактам.

---

# 15. Інтеграція з пошуковим деревом

Обчислювальний граф повинен підтримувати пошукове дерево:

T(P) = (Nₜ, Eₜ)

де кожний вузол дерева представляє позицію, а ребра — легальні ходи.

Для кожної позиції пошукового дерева може створюватися власний локальний обчислювальний контекст.

Однак не потрібно механічно створювати повну копію всіх аналітичних структур для кожної позиції.

Можна використовувати:

- незмінні спільні структури;
- локальні зміни;
- спільні кеші;
- інкрементальні оновлення;
- окремі версії результатів.

## 15.1. Пошуковий вузол

SearchNode = (
    Position,
    Depth,
    Alpha,
    Beta,
    MoveSet,
    Evaluation,
    StructuralState,
    TacticalState,
    SearchStatus,
    Provenance
)

Це концептуальна структура. Конкретна реалізація може використовувати компактніші представлення.

## 15.2. Межі впливу аналітичних компонентів

Структурний аналіз може впливати на:

- порядок ходів;
- оцінку позиції;
- пріоритет дослідження;
- розподіл ресурсів.

Він не може:

- змінювати шахові правила;
- додавати нелегальні ходи;
- видаляти легальні ходи з повного набору;
- підміняти перевірку шаху;
- скасовувати обов'язкові тактичні відповіді.

## 15.3. Пошукова повнота

Необхідно розрізняти:

- повноту генерації легальних ходів;
- повноту пошуку на заданій глибині;
- повноту вибіркового пошуку;
- повноту тактичної перевірки.

Наявність усіх легальних ходів у генераторі не означає, що пошук досліджує всі можливі продовження.

Це різні характеристики.

---

# 16. Розподіл обчислювальних ресурсів

Обчислювальний граф інтегрується з SUBIT-CHESS COMPUTATIONAL RESOURCE ALLOCATION THEORY.

Для кожного вузла визначається:

ResourceProfile(n) = (
    TimeCost,
    NodeCost,
    MemoryCost,
    ComputeCost,
    Priority,
    Deadline
)

Планувальник повинен враховувати:

- критичність завдання;
- залежності;
- терміновість;
- очікувану користь;
- обчислювальну вартість;
- доступний бюджет;
- вплив на тактичну надійність.

## 16.1. Пріоритети

Найвищий пріоритет мають:

1. коректність шахового стану;
2. генерація легальних ходів;
3. визначення термінального стану;
4. обов'язкова тактична перевірка.

Нижчі за пріоритетом завдання можуть включати:

- поглиблений стратегічний аналіз;
- додаткові контрфактичні сценарії;
- розширене пояснення;
- дослідницькі обчислення.

Це не означає, що стратегічний аналіз неважливий. Його виконання повинно узгоджуватися з доступним бюджетом і критичністю позиції.

## 16.2. Anytime-виконання

Граф повинен підтримувати безпечне переривання.

Проміжний результат можна використовувати лише тоді, коли він має визначений статус і не порушує умов коректності.

Якщо пошук перервано, система повинна зберігати:

- останній завершений результат;
- його глибину;
- головний варіант;
- межі оцінки;
- незавершені завдання;
- невизначеність.

Незавершений результат не можна представляти як завершений доказ.

---

# 17. Пояснюваність обчислювального графа

Кожне рішення SUBIT-CHESS повинно мати можливість відновити ланцюг обчислень, який привів до нього.

Для цього формується:

ComputationTrace = (
    DecisionID,
    PositionID,
    NodesExecuted,
    DependenciesUsed,
    ResultsConsumed,
    Versions,
    SearchTrace,
    ValidationTrace,
    FinalStatus
)

Пояснення повинно дозволяти відповісти на запитання:

- які факти були використані;
- які вузли їх обчислили;
- які залежності вплинули на результат;
- які альтернативи були досліджені;
- які результати були відкинуті;
- які припущення залишилися неперевіреними;
- які обмеження мав пошук.

Це створює основу для аудиту рішень.

Важливо: пояснення повинно відображати реальний обчислювальний процес, а не бути текстом, створеним постфактум без зв'язку з фактичними залежностями.

---

# 18. Помилки обчислювого графа

Вводиться система кодів:

**CG-ERR-001 — MISSING_DEPENDENCY**

Не визначено необхідну залежність.

**CG-ERR-002 — INVALID_INPUT**

Вузол отримав некоректні дані.

**CG-ERR-003 — STALE_RESULT**

Використано застарілий результат.

**CG-ERR-004 — VERSION_MISMATCH**

Версії залежних компонентів не узгоджені.

**CG-ERR-005 — UNDECLARED_DEPENDENCY**

Вузол використав незадекларовані дані.

**CG-ERR-006 — CYCLE_DETECTED**

Виявлено неконтрольований цикл.

**CG-ERR-007 — DEADLOCK**

Обчислювальні завдання не можуть продовжити виконання через взаємне блокування.

**CG-ERR-008 — RESOURCE_EXHAUSTION**

Недостатньо доступних ресурсів.

**CG-ERR-009 — INVALID_CACHE_REUSE**

Кешований результат не відповідає умовам повторного використання.

**CG-ERR-010 — INCONSISTENT_RESULT**

Виявлено суперечність між результатами.

**CG-ERR-011 — PROVENANCE_MISSING**

Відсутня інформація про походження результату.

**CG-ERR-012 — INCOMPLETE_EXECUTION**

Обчислення не було завершене.

**CG-ERR-013 — INVALIDATION_FAILURE**

Не вдалося коректно позначити залежний результат недійсним.

**CG-ERR-014 — CONCURRENT_WRITE_CONFLICT**

Виявлено конфлікт паралельного запису.

**CG-ERR-015 — TRACE_INCOMPLETE**

Неможливо повністю відновити обчислювальний ланцюг.

**CG-ERR-016 — RULE_BOUNDARY_VIOLATION**

Аналітичний вузол намагався змінити або підмінити результат шахових правил.

# 19. Формальні інваріанти

# 22. Метрики ефективності

Вводяться такі показники.

**Graph Execution Time (GET)**

Загальний час виконання графа.

**Dependency Resolution Time (DRT)**

Час визначення та узгодження залежностей.

**Incremental Reuse Ratio (IRR)**

Частка результатів, які вдалося коректно повторно використати.

**Invalidation Precision (IP)**

Точність інвалідації результатів.

**Cache Validity Rate (CVR)**

Частка коректно повторно використаних кешованих результатів.

**Parallel Efficiency (PE)**

Ефективність паралельного виконання відносно обраного базового режиму.

**Memory Overhead (MO)**

Додаткові витрати пам'яті на представлення графа та його метаданих.

**Trace Completeness (TC)**

Повнота відновлення обчислювального процесу.

**Consistency Failure Rate (CFR)**

Частота виявлених порушень узгодженості.

**Recovery Time (RT)**

Час відновлення після помилки.

Жодна з цих метрик окремо не визначає якість шахової гри.

Наприклад, висока ефективність кешу не означає сильнішої гри, а швидше виконання графа не доводить правильності його результатів.

Причинна теорія описує залежності шахових подій та наслідків.

Обчислювальний граф описує залежності між алгоритмами, які встановлюють ці факти та формують висновки.

## 23.3. Зв'язок із теорією невизначеності

Теорія невизначеності визначає, наскільки обґрунтованими є результати.

Обчислювальний граф визначає, які додаткові перевірки необхідні для зменшення невизначеності.

## 23.4. Зв'язок із ресурсною теорією

Ресурсна теорія визначає бюджет обчислень.

Обчислювальний граф визначає структуру завдань, між якими цей бюджет розподіляється.

## 23.5. Зв'язок із теорією автономного розвитку

Автономний дослідницький механізм може аналізувати ефективність графа, формувати гіпотези оптимізації та порівнювати альтернативні архітектури.

Але зміна алгоритмів повинна відбуватися через контрольований цикл:

HYPOTHESIS → IMPLEMENTATION CANDIDATE → TEST → VALIDATION → ACCEPT / REJECT / INCONCLUSIVE.

Автоматична зміна критичних алгоритмів без незалежної перевірки не допускається.

# 26. Принципи архітектури

SUBIT-CHESS COMPUTATIONAL GRAPH повинен дотримуватися таких принципів.

**1. EXPLICIT DEPENDENCIES**

Усі залежності мають бути явними.

**2. TYPED COMPUTATION**

Кожне обчислення має визначену семантику та типізований результат.

**3. CONTEXT PRESERVATION**

Жоден результат не повинен втрачати контекст свого походження.

**4. VERSION CONSISTENCY**

Результати різних версій не можна змішувати без контрольованої процедури сумісності.

**5. SAFE INCREMENTALITY**

Інкрементальне виконання допускається лише за умови збереження правильності.

**6. CONTROLLED PARALLELISM**

Паралельність не повинна створювати неконтрольовані конфлікти.

**7. EVIDENCE SEPARATION**

Обчислений результат, евристичне припущення та формальний доказ залишаються різними категоріями.

**8. TRACEABILITY**

Рішення повинно мати відновлюваний обчислювальний шлях.

**9. RULE IMMUTABILITY**

Шахові правила залишаються незалежними від механізмів оптимізації та навчання.

**10. AUTONOMOUS IMPLEMENTATION**

Внутрішні алгоритми SUBIT-CHESS реалізуються незалежно, без запозичення сторонніх шахових двигунів, бібліотек або їхніх модулів.

# 27. Підсумкова архітектурна теза

Обчислювальний граф SUBIT-CHESS є метарівнем організації інтелектуальної роботи шахового двигуна.

Він не визначає, яка фігура сильніша, який хід легальний або яка стратегія правильна. Він визначає, як відповідні знання формуються, перевіряються, передаються, оновлюються та використовуються в процесі прийняття рішення.

У цій архітектурі:

- шаховий стан є первинним об'єктом;
- правила визначають допустимі трансформації;
- геометрія визначає просторові відносини;
- структурний аналіз описує організацію позиції;
- причинний аналіз досліджує механізми змін;
- стратегічний аналіз формує цілі та плани;
- оцінювання визначає характеристики позиції;
- пошук порівнює можливі продовження;
- теорія невизначеності визначає межі обґрунтованості;
- ресурсний механізм розподіляє обчислювальні можливості;
- обчислювальний граф координує взаємодію всіх цих компонентів.

Таким чином, архітектура SUBIT-CHESS набуває трьох взаємопов'язаних рівнів:

**Перший рівень — REPRESENTATION:** що саме відомо про позицію.

**Другий рівень — REASONING:** які висновки можна отримати з цього знання.

**Третій рівень — COMPUTATION:** як організувати процес отримання, перевірки та оновлення цих висновків.

Їхнє розмежування дозволяє уникнути змішування шахових фактів, аналітичних інтерпретацій та технічних операцій.

Центральний принцип залишається незмінним:

**DO NOT COLLAPSE — CONTEXTUALIZE.**

SUBIT-CHESS повинен не просто обчислювати результати, а зберігати структуру залежностей, завдяки яким ці результати набувають значення.
