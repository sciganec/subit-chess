- Strategic Plan Generation;

Наступна проблема полягає не в додаванні нових теорій, а в їхній обчислювальній інтеграції.

Якщо кожен компонент працюватиме із власною інтерпретацією позиції, виникнуть:

1. суперечливі результати;
2. повторне обчислення однакових характеристик;
3. несумісні формати даних;
4. неконтрольоване передавання евристичних оцінок;

7. складність відтворення рішень;
8. неконтрольоване зростання обчислювальної вартості.

Тому потрібна єдина архітектура, в якій кожний модуль має визначену функцію, вхідні дані, вихідні дані, гарантії та межі відповідальності.

## 2. Центральна теза

SUBIT-CHESS повинен працювати не як сукупність незалежних оцінювачів, а як інтегрована система перетворення позиції на перевірене рішення.

Її основний цикл:

POSITION → REPRESENTATION → STRUCTURE → RELATIONS → DYNAMICS → CONTEXT → TACTICS → EVALUATION → PLANNING → SEARCH → DECISION → AUDIT → EXPERIENCE → LEARNING.

Кожний етап створює результати, які можуть використовуватися наступними етапами.

Однак жоден результат не повинен автоматично набувати вищого доказового статусу лише через те, що він переданий іншому модулю.

## 3. Визначення Unified Computational Architecture

**SUBIT-CHESS Unified Computational Architecture (UCA)** — це формальна організація обчислювальних компонентів двигуна, яка забезпечує узгоджене перетворення шахового стану на рішення, пояснення, досвід і контрольоване оновлення системи.

UCA визначає:

- структуру виконання;
- межі модулів;
- контракти взаємодії;
- життєвий цикл позиції;
- порядок обчислень;
- політику кешування;
- управління ресурсами;
- контроль коректності;
- обробку невизначеності;
- інтеграцію пам'яті;
- механізми навчання;
- відтворюваність результатів.

# PART II. АРХІТЕКТУРНІ ПРИНЦИПИ

## 4. Принцип єдиного авторитету шахових правил

Шахові правила мають єдине джерело істини в межах двигуна.

Rule Engine визначає:

- легальність ходів;
- допустимі перетворення позиції;
- шах;
- мат;
- пат;
- рокіровку;
- взяття на проході;
- перетворення пішака;
- умови завершення партії;
- відповідні правила нічиєї.

Жодний структурний, стратегічний або навчальний модуль не може змінювати ці правила.

## 5. Принцип розділення точності та евристики

Усі результати поділяються на два великі класи.

**Exact Computation**

Результати, які мають формальну або детерміновану основу:

- стан дошки;
- список легальних ходів;
- наслідок легального ходу;
- матеріальна конфігурація;
- геометричні атаки;
- перевірка шаху;
- точні умови завершення партії.

**Heuristic Computation**

Результати, які залежать від моделі оцінювання:

- стратегічна слабкість;
- активність фігури;
- якість плану;
- структурна перевага;
- потенціал позиції;
- стійкість стратегічної конфігурації;
- контекстна важливість поля.

Ці класи можуть взаємодіяти, але не повинні змішуватися.

## 6. Принцип незмінності легального простору

Для позиції P:

L(P) = {m | m є легальним ходом у P}.

Повний пошуковий алгоритм повинен мати доступ до всієї множини L(P).

Структурна оцінка, стратегічний план, історична пам'ять або пріоритет ходу не можуть оголошувати легальний хід недоступним.

Вибірковий пошук може використовувати контрольовані скорочення лише як окремий оптимізаційний механізм із вимірюваним ризиком і можливістю порівняння з повним базовим пошуком.

## 7. Принцип єдиного стану позиції

Усі модулі повинні використовувати узгоджену модель позиції.

P = (B, s, CR, EP, H, N, 𝓗)

де:

- B — розташування фігур;
- s — сторона, яка ходить;
- CR — права на рокіровку;
- EP — можливість взяття на проході;
- H — лічильник напівходів;
- N — номер повного ходу;
- 𝓗 — необхідна історія позицій для історично залежних правил.

Внутрішні представлення можуть відрізнятися за форматом, але повинні відповідати цій семантиці.

## 8. Принцип відтворюваності

Кожне важливе рішення повинно бути відтворюваним за збереженими:

- позицією;
- версією правил;
- версією пошуку;
- версією оцінювання;
- версією структурного аналізу;
- параметрами;
- пошуковим бюджетом;
- контекстом;
- станом пам'яті;
- випадковим seed, якщо він використовується.

# PART IV. CANONICAL POSITION CORE

## 11. Призначення

Canonical Position Core є фундаментом обчислювальної системи.

Він відповідає за представлення шахового стану та його коректні трансформації.

Його функції:

1. зберігання стану;
2. читання стану;
3. перевірка внутрішньої узгодженості;
4. створення легальних ходів;
5. застосування ходу;
6. скасування ходу;
7. перевірка кінцевих станів;
8. забезпечення стабільного ідентифікатора позиції.

## 12. Position State

Position State повинен мати однозначну семантику.

Він повинен містити всю інформацію, необхідну для визначення легальних ходів та застосування історично залежних правил.

Особливо важливо не втратити:

- права на рокіровку;
- можливість взяття на проході;
- лічильник напівходів;
- необхідну історію повторень.

Хеш позиції, який ігнорує важливі поля стану, не може бути єдиною основою для всіх видів кешування.

## 13. Position Identity

Необхідно розрізняти:

**Board Identity**

Ідентичність розташування фігур.

**Rule State Identity**

Ідентичність повного стану, необхідного для правил.

**Historical State Identity**

Ідентичність стану з урахуванням релевантної історії.

**Analytical Identity**

Ідентичність позиції разом із версіями аналітичних моделей, якщо результат залежить від цих моделей.

Це дозволяє уникнути помилок кешування.

## 14. State Transition

Для легального ходу m:

P' = T(P,m).

Трансформація повинна бути детермінованою.

Після виконання ходу система повинна мати можливість:

- отримати новий стан;
- перевірити його коректність;
- відновити попередній стан;
- обчислити різницю між станами;
- оновити залежні структури.

# PART V. RULE ENGINE

## 15. Компоненти

Rule Engine складається з:

- Attack Generator;
- Pseudo-Legal Move Generator;
- Legal Move Filter;
- Special Move Handler;
- Terminal State Detector;
- Draw Condition Evaluator;
- State Transition Executor.

## 16. Генерація ходів

Необхідно розділити:

PseudoLegal(P) — ходи, які відповідають геометрії руху фігур і локальним правилам генерації.

Legal(P) — ходи, які не порушують обов'язкових шахових обмежень.

L(P) = FilterLegal(P, PseudoLegal(P)).

Це концептуальний поділ.

Конкретна реалізація може використовувати оптимізований генератор легальних ходів без окремого матеріалізованого списку псевдолегальних ходів, якщо коректність залишається перевірною.

## 17. Special Moves

Особлива увага:

**Castling**

Потрібно перевіряти права на рокіровку, зайнятість необхідних полів та заборону проходження короля через атаковані поля.

**En passant**

Необхідно враховувати можливість того, що взяття на проході відкриває атаку на власного короля.

**Promotion**

Необхідно генерувати всі допустимі варіанти перетворення пішака.

## 18. Rule Engine як незалежний контур

Rule Engine не повинен залежати від:

- структурної оцінки;
- стратегічного планування;
- параметрів навчання;
- пам'яті аналогічних позицій;
- евристичного пріоритету.

Він повинен залишатися окремим перевірним компонентом.

# PART VII. STRUCTURAL ANALYSIS ENGINE

## 23. Призначення

Structural Analysis Engine будує структурне представлення позиції.

SAE = (Ω, R, H, ΔΩ, C).

Де:

- Ω — Structural Representation;
- R — Typed Relations;
- H — Hyperrelations;
- ΔΩ — Structural Changes;
- C — Structural Constraints.

## 24. Structural Graph

G(P) = (V,E,L).

Де:

- V — об'єкти;
- E — відношення;
- L — мітки та атрибути.

Структурний граф може включати:

- атаки;
- захист;
- підтримку;
- блокування;
- обмеження;
- зв'язність;
- контроль;
- тактичні залежності;
- стратегічні залежності.

## 25. Structural Hypergraph

Деякі явища не можна повноцінно представити одним бінарним зв'язком.

Наприклад:

- подвійна атака;
- зв'язування;
- відкритий напад;
- перевантаження захисника;
- матова сітка.

Тому SAE повинен підтримувати гіпервідношення.

HyperRelation = (Sources, Type, Targets, Conditions, Evidence).

## 26. Structural Delta

Для переходу:

P → P'

визначається:

ΔΩ = (Created, Preserved, Removed, Transformed).

Це дозволяє встановити не лише те, що змінилося, а й те, що залишилося структурно незмінним.

## 27. Інкрементальний аналіз

Після ходу не обов'язково перебудовувати весь структурний граф.

Можна оновлювати залежні вузли та відношення.

Однак повна побудова повинна залишатися еталонним способом перевірки інкрементального результату.

# PART VIII. CONTEXT ENGINE

## 28. Призначення

Context Engine визначає аналітичний контекст позиції.

Використовується модель:

C = I × Z × Φ.

Де:

I = {QUIET, DEFENCE, ATTACK, PRESSURE}

Z = {GLOBAL, QUEENSIDE, KING, CENTER}

Φ = {OPENING, MIDDLEGAME, ENDGAME, TRANSITION}.

Це 64 базові комбінації.

## 29. Багатоконтекстність

Контекст не повинен зводитися до єдиної мітки.

Наприклад, одна позиція може одночасно мати:

- DEFENCE у зоні короля;
- ATTACK у центрі;
- PRESSURE на ферзевому фланзі;
- TRANSITION на стратегічному рівні.

Тому Context Engine формує профіль, а не одну категорію.

## 30. Contextual Weighting

Визначимо:

wᵢ(c,P) ∈ [0,1].

Це контекстна інтенсивність ознаки.

Наприклад, активність фігури може мати різну стратегічну вагу залежно від контексту.

Але контекстна вага не повинна змінювати точні шахові факти.

Де:

- T — Tactical Features;
- F — Forced Lines;
- C — Combinations;

## 32. Тактичні механізми

Модуль аналізує:

- шахи;
- взяття;
- прямі загрози;
- зв'язування;
- подвійні атаки;
- відкриті напади;
- відволікання;
- перевантаження;
- проміжні ходи;
- матові загрози;
- форсовані комбінації.

## 33. Пріоритет тактики

Якщо позиція містить форсовану тактичну можливість, стратегічний план не може ігнорувати її.

Ієрархія:

1. коректність стану;
2. легальність;
3. точні кінцеві результати;
4. форсовані тактичні наслідки;
5. позиційні та структурні оцінки;
6. стратегічні гіпотези.

Це не означає, що тактичний модуль повинен самостійно обирати хід.

Він передає пошуку критичну інформацію.

## 34. Tactical Certificate

Кожен важливий тактичний висновок повинен мати запис:

TC = (Line, Depth, Completeness, Result, Provenance, Status).

Можливі статуси:

- PROVEN_WITHIN_SEARCH_SCOPE;
- FORCED_WITHIN_VERIFIED_DEPTH;
- SEARCH_SUPPORTED;
- INCOMPLETE;
- REFUTED;
- UNKNOWN.

# PART X. EVALUATION ENGINE

## 35. Призначення

Evaluation Engine визначає оцінку позиції з погляду конкретної сторони.

Базова модель:

E(P,s;θ) = Σᵢ wᵢ(P;θ) · fᵢ(P,s).

Де:

- fᵢ — ознаки;
- wᵢ — параметри;
- θ — конфігурація моделі.

## 36. Структурна оцінка

Використовуємо сім вимірів:

Vₛ(P) = (M,A,R,K,T,Q,X).

Де:

- M — Material;
- A — Activity;
- R — Relations;
- K — King Safety;
- T — Tactical Potential;
- Q — Space;
- X — Transformation Potential.

Це вектор характеристик, а не обов'язково готова числова оцінка.

## 37. Розділення оцінок

Необхідно розрізняти:

**Static Evaluation**

Оцінка поточної позиції.

**Search Evaluation**

Результат пошуку продовжень.

**Structural Value**

Оцінка структурних характеристик.

**Strategic Value**

Оцінка цілей та планів.

**Robustness Value**

Оцінка стійкості стратегічних механізмів.

Ці величини не повинні механічно підміняти одна одну.

## 38. Відсутність подвійного врахування

Якщо одна й та сама характеристика впливає на декілька компонентів, необхідно перевірити подвійне врахування.

Наприклад, активність фігури може вже впливати на контроль поля, а контроль поля — на оцінку простору.

Безконтрольне додавання всіх трьох оцінок може штучно збільшувати вагу одного явища.

## 39. Невизначеність

Оцінка повинна супроводжуватися окремою інформацією про невизначеність.

U(P) ≠ E(P).

Невизначеність не є негативною оцінкою позиції.

Вона характеризує обмеження знань або пошуку.

Potentiality Engine досліджує не лише наявну структуру, а й допустимі майбутні трансформації.

- CONDITIONALLY_REACHABLE;
- FORCEABLE;

Можливість існування послідовності ходів не означає, що суперник дозволить її реалізувати.

Тому Potentiality Engine повинен передавати результати до пошуку для перевірки опором суперника.

## 42. Контрфактичні сценарії

- інший стратегічний план;
- інший часовий горизонт.

Аналітичне видалення фігури для оцінювання залежності не повинно трактуватися як легальний шаховий хід.

# PART XIII. CAUSAL AND RESILIENCE ENGINE

## 48. Causal Analysis

Causal Engine визначає механізми, через які зміна позиції породжує наслідки.

CG(P) = (V꜀, E꜀, H꜀).

Основні типи зв'язків:

- ENABLES;
- REQUIRES;
- BLOCKS;
- PREVENTS;
- TRIGGERS;
- PRODUCES;
- WEAKENS;
- STRENGTHENS;
- MEDIATES;
- DEPENDS_ON;
- TRANSFORMS.

## 49. Причинний ланцюг

Наприклад:

MOVE  
→ DEFENDER DISPLACEMENT  
→ LOSS OF CONTROL  
→ WEAK SQUARE  
→ INVASION POSSIBILITY  
→ STRUCTURAL CONSEQUENCE.

Кожний зв'язок повинен мати умови та доказовий статус.

## 50. Strategic Resilience

Resilience Engine аналізує, чи здатний план зберігати функцію після протидії.

SR = (S_struct, S_causal, S_tactical, S_adaptive, S_recovery).

Де:

- S_struct — структурна стійкість;
- S_causal — причинна стійкість;
- S_tactical — тактична надійність;
- S_adaptive — здатність адаптуватися;
- S_recovery — здатність відновити стратегічну функцію.

Ці характеристики не є заміною мінімаксного пошуку.

# PART XIV. SEARCH ENGINE

## 51. Центральна роль пошуку

Search Engine залишається основним механізмом порівняння легальних продовжень.

Він отримує:

- позицію;
- повний набір легальних ходів;
- оцінку;
- тактичну інформацію;
- структурні характеристики;
- контекст;
- плани;
- релевантні записи пам'яті.

Але остаточна перевірка шахових наслідків відбувається через пошук у дереві легальних ходів.

## 52. Базова модель

Negamax:

V(P,d) = maxₘ [−V(T(P,m),d−1)].

Базовий випадок:

V(P,0) = E(P,s).

Точні кінцеві стани обробляються окремо від евристичної оцінки.

## 53. Основні компоненти пошуку

- Move Generator;
- Search Controller;
- Negamax;
- Alpha-Beta;
- Iterative Deepening;
- Principal Variation;
- Transposition Table;
- Quiescence Search;
- Move Ordering;
- Search Budget Manager;
- Terminal Evaluator.

## 54. Move Ordering

Пріоритет ходу може залежати від:

- попередньої головної лінії;
- результату таблиці транспозицій;
- тактичних характеристик;
- структурної зміни;
- контексту;
- історичної ефективності;
- стратегічної мети.

Але пріоритет не дорівнює коректності.

## 55. Quiescence Search

У позиції шаху stand-pat не допускається.

Якщо король перебуває під шахом, необхідно аналізувати всі легальні відповіді, а не лише взяття або шахи.

Це критичний інваріант коректності.

## 56. Selective Search

Null Move, Late Move Reductions, Futility Pruning та інші скорочення можуть розглядатися лише після створення надійного базового пошуку.

Вони повинні мати:

- визначені передумови;
- контрольовану область застосування;
- вимірюваний ризик;
- регресійні тести;
- можливість відключення;
- порівняння з базовим алгоритмом.

Null Move є аналітичним прийомом пошуку, а не легальним шаховим ходом.

# PART XV. KNOWLEDGE AND MEMORY RUNTIME

## 57. Призначення

Knowledge Runtime забезпечує доступ до пам'яті під час аналізу.

Він не повинен блокувати критичний пошук через повільні або надмірні операції з пам'яттю.

Основні функції:

- retrieval;
- context matching;
- structural matching;
- causal matching;
- temporal validation;
- provenance retrieval;
- contradiction checking;
- knowledge update.

## 58. Рівні доступу

**L0 — Immediate Memory**

Поточна позиція та активний пошук.

**L1 — Local Memory**

Нещодавно використані структурні та стратегічні записи.

**L2 — Persistent Memory**

Довготривалі знання та епізоди.

**L3 — Research Archive**

Експерименти, гіпотези, результати та історія версій.

Це логічні рівні, які можуть бути реалізовані різними структурами даних.

## 59. Retrieval Budget

Пошук пам'яті повинен мати обмежений бюджет.

Якщо пошук знань не дає результату в межах бюджету, це не повинно блокувати основний шаховий пошук.

Memory Retrieval Failure ≠ Search Failure.

## 60. Кешування

Необхідно розділяти:

- Position Cache;
- Evaluation Cache;
- Structural Cache;
- Tactical Cache;
- Knowledge Retrieval Cache;
- Search Transposition Table.

Кожний кеш повинен мати власні правила ідентичності та інвалідації.

Наприклад, результат оцінювання може залежати від версії параметрів, навіть якщо сама позиція не змінилася.

# PART XVI. META-CONTROL ENGINE

## 61. Призначення

Meta-Control Engine контролює якість роботи всієї системи.

Він не повинен виконувати кожну операцію замість профільних модулів.

Його завдання — перевіряти узгодженість, достатність пошуку та надійність висновків.

## 62. Основні функції

- перевірка цілісності позиції;
- перевірка повноти легальних ходів;
- перевірка узгодженості структурного графа;
- перевірка актуальності планів;
- виявлення суперечностей;
- оцінка достатності пошуку;
- виявлення помилок пам'яті;
- перевірка походження результатів;
- контроль впевненості;
- рішення про додаткові обчислення.

## 63. Meta-Reasoning Loop

```text
ANALYSIS RESULT
      ↓
CLAIM EXTRACTION
      ↓
PROVENANCE CHECK
      ↓
CONSISTENCY AUDIT
      ↓
TACTICAL AUDIT
      ↓
STRUCTURAL AUDIT
      ↓
PLAN AUDIT
      ↓
SEARCH ADEQUACY
      ↓
UNCERTAINTY CALIBRATION
      ↓
ACCEPT / REVISE / SEARCH MORE / UNKNOWN
```

## 64. Adaptive Computation

Нехай:

B = B₀ + Bₐ.

Де:

- B₀ — базовий пошуковий бюджет;
- Bₐ — додатковий бюджет.

Додаткові обчислення можуть запускатися, коли:

- оцінка нестабільна;
- найкращі ходи близькі за значенням;
- є форсована тактика;
- виявлено суперечність;
- стратегічний план залежить від критичної умови;
- результат чутливий до горизонту;
- пам'ять містить релевантний контрприклад.

Це архітектурна гіпотеза, ефективність якої потрібно перевіряти експериментально.

- головну лінію;
- оцінку;
- кількість вузлів;
- час;
- статус повноти;
- версію пошуку.

Незавершений результат не повинен подаватися як повністю перевірений.

# PART XVIII. PARALLELISM AND CONCURRENCY

## 68. Загальний принцип

Паралельність може підвищити ефективність, але створює ризики:

- конфліктів стану;
- гонок даних;
- некоректного кешування;
- невідтворюваності;
- неузгоджених оновлень пам'яті.

Тому паралельність повинна бути підпорядкована чіткій моделі власності даних.

## 69. Immutable Position Snapshot

Кожен аналітичний процес повинен працювати з узгодженим знімком позиції.

PositionSnapshot = (P, PositionVersion, RulesVersion).

Після створення знімка його стан не змінюється.

Новий хід породжує новий знімок.

## 70. Parallel Analysis Tasks

Можливі паралельні завдання:

- генерація структурного графа;
- аналіз тактики;
- контекстна класифікація;
- пошук релевантних знань;
- генерація стратегічних цілей;
- попереднє оцінювання.

Результати збираються через визначений інтерфейс.

## 71. Deterministic Aggregation

Якщо порядок завершення паралельних завдань впливає на результат, необхідно визначити стабільне правило агрегування.

Не можна дозволяти випадковому порядку виконання змінювати семантику рішення.

# PART XX. ПОВНИЙ RUNTIME CYCLE

## 79. Початок аналізу

Після отримання позиції:

1. перевіряється формат;
2. створюється PositionSnapshot;
3. перевіряється стан;
4. визначаються кінцеві умови;
5. генерується повний список легальних ходів.

Якщо позиція некоректна, аналіз не повинен продовжуватися так, ніби вона правильна.

## 80. Первинний аналіз

Далі система:

1. формує об'єкти;
2. будує геометричні відношення;
3. визначає структурні характеристики;
4. формує контекст;
5. перевіряє тактичні загрози;
6. отримує релевантні знання;
7. виконує первинне оцінювання.

## 81. Планування

На основі результатів:

1. генеруються цілі;
2. визначаються структурні результати;
3. формуються плани;
4. аналізуються залежності;
5. визначаються ризики;
6. оцінюється адаптивність.

## 82. Пошук

Search Engine:

1. отримує повну множину легальних ходів;
2. встановлює базовий бюджет;
3. визначає порядок ходів;
4. виконує пошук;
5. зберігає головну лінію;
6. перевіряє тактичну стабільність;
7. повертає результат.

## 83. Метааудит

Meta-Control:

1. перевіряє завершеність;
2. перевіряє походження оцінки;
3. аналізує суперечності;
4. оцінює достатність пошуку;
5. перевіряє критичні стратегічні передумови;
6. визначає необхідність додаткових обчислень.

## 84. Остаточний вибір

Вибір ходу повинен базуватися на результаті пошуку серед легальних ходів.

Decision(P) = argmaxₘ RobustSearchValue(P,m).

Для стандартного мінімаксного пошуку оцінка повинна бути приведена до узгодженої перспективи сторони, яка ходить.

Результати структурного аналізу, контексту та пам'яті можуть впливати на оцінку й порядок пошуку, але не можуть підміняти перевірку шахових наслідків.

## 85. Після вибору

Після визначення ходу:

1. формується пояснення;
2. зберігається рішення;
3. оновлюється епізодична пам'ять;
4. реєструються зміни структури;
5. оновлюються стратегічні плани;
6. зберігаються результати пошуку;
7. визначаються потенційні навчальні випадки.

Навчання параметрів не повинно непомітно змінювати модель посеред активного пошуку.

# PART XXI. DECISION EXPLANATION SYSTEM

## 86. Призначення

SUBIT-CHESS повинен уміти пояснювати, чому обрав конкретний хід.

Пояснення не повинно створюватися незалежно від реального процесу вибору.

Воно повинно спиратися на збережені результати аналізу.

## 87. Decision Record

DR = (P, M, A, T, S, C, E, U, V).

Де:

- P — позиція;
- M — вибраний хід;
- A — альтернативи;
- T — тактичні підстави;
- S — структурні підстави;
- C — причинні залежності;
- E — пошукові докази;
- U — невизначеність;
- V — версії компонентів.

## 88. Рівні пояснення

**LEVEL 1 — MOVE**

Вибраний хід.

**LEVEL 2 — SEARCH**

Оцінка, глибина, головна лінія.

**LEVEL 3 — TACTICAL**

Тактичні наслідки.

**LEVEL 4 — STRUCTURAL**

Структурні зміни.

**LEVEL 5 — STRATEGIC**

Цілі та плани.

**LEVEL 6 — CAUSAL**

Причинні механізми.

**LEVEL 7 — EPISTEMIC**

Невизначеність, межі перевірки, статус доказів.

## 89. Пояснення не дорівнює доказу

Переконливе пояснення не робить хід правильним.

Правильність повинна підтверджуватися відповідними обчисленнями.

Якщо пояснення має лише евристичну основу, це повинно бути зазначено.

# PART XXII. FAILURE MANAGEMENT

## 90. Типи помилок

**POSITION ERROR**

Некоректний стан.

**RULE ERROR**

Неправильна генерація або перевірка ходу.

**STRUCTURAL ERROR**

Некоректне структурне відношення.

**EVALUATION ERROR**

Помилкова оцінка.

**SEARCH ERROR**

Некоректний пошуковий результат.

**MEMORY ERROR**

Використання застарілого або неправильного знання.

**CONTEXT ERROR**

Невідповідний контекст.

**PLANNING ERROR**

Нереалістичний стратегічний план.

**META-REASONING ERROR**

Неправильна оцінка надійності власного аналізу.

## 91. Error Containment

Помилка одного модуля не повинна автоматично заражати всю систему.

Для цього:

- результати мають бути типізовані;
- критичні переходи повинні перевірятися;
- помилки повинні локалізуватися;
- статуси повинні передаватися явно;
- недостовірні результати повинні ізолюватися;
- система повинна мати можливість повернутися до базового пошуку.

## 92. Graceful Degradation

Якщо стратегічний модуль недоступний, двигун повинен продовжити базовий шаховий пошук.

Якщо Knowledge Engine не відповідає, це не повинно блокувати генерацію легальних ходів.

Якщо структурний аналіз неповний, його результат не повинен подаватися як повний.

Якщо метааналіз перевищив бюджет, двигун може повернути найкращий завершений пошуковий результат із позначкою обмежень.

- що структурний аналіз покращить гру;
- що пам'ять зменшить пошукову вартість;
- що причинні моделі підвищать точність;
- що стратегічне планування покращить вибір ходів;
- що метарівень завжди знаходить помилки;
- що автономне навчання стабільно підвищуватиме силу двигуна.

Ці твердження є дослідницькими гіпотезами.

## 142. Принцип незалежності

SUBIT-CHESS не повинен використовувати сторонні шахові двигуни як джерело рішень, навчальні вчителі або компоненти власного обчислювального ядра.

Не повинні використовуватися сторонні шахові бібліотеки чи запозичені модулі реалізації шахової логіки.

Дозволено вивчати загальні математичні, алгоритмічні та наукові концепції, але власна реалізація повинна бути незалежною.

Внутрішній self-play та внутрішньо згенеровані позиції залишаються допустимими джерелами досвіду.

# PART XXVII. ПІДСУМКОВИЙ АРХІТЕКТУРНИЙ СИНТЕЗ

## 143. Єдина система

SUBIT-CHESS тепер концептуально визначається як система з дванадцяти взаємопов'язаних рівнів:

1. POSITION — формальний стан шахової дошки.
2. RULES — точні правила та легальні трансформації.
3. PERCEPTION — ідентифікація об'єктів і базових характеристик.
4. STRUCTURE — структурні відношення та конфігурації.
5. DYNAMICS — зміни структури в часі.
6. CONTEXT — ситуаційна інтерпретація.
7. POTENTIALITY — можливі та умовні трансформації.
8. REASONING — причинний аналіз і стратегічні плани.
9. SEARCH — перевірка легальних продовжень.
10. KNOWLEDGE — пам'ять і накопичений досвід.
11. META-CONTROL — самокритика та контроль надійності.
12. EVOLUTION — навчання, експерименти та контрольоване вдосконалення.

Це не послідовність незалежних фільтрів.

Це багаторівнева обчислювальна архітектура зі зворотними зв'язками та чіткими межами авторитетності.

## 144. Єдиний принцип прийняття рішення

Двигун не повинен обирати хід лише тому, що:

- він відповідає знайомому шаблону;
- він узгоджується зі стратегічним планом;
- він отримав високу структурну оцінку;
- він часто приводив до перемоги в self-play;
- він рекомендується пам'яттю.

Хід повинен бути легальним і оціненим через наслідки, які дослідив пошук.

Інші компоненти допомагають системі краще організувати аналіз, сформувати кандидатів, розподілити ресурси та зрозуміти позицію.

## 145. Фінальна формула

**SUBIT-CHESS = RULES × STRUCTURE × CONTEXT × DYNAMICS × REASONING × SEARCH × MEMORY × META-CONTROL × EVOLUTION.**

Знак множення тут означає архітектурну взаємозалежність, а не арифметичну операцію.

Якщо відсутній один із фундаментальних компонентів, повноцінність відповідного рівня системи обмежується.

Правила забезпечують коректність.

Структура забезпечує представлення.

Контекст забезпечує ситуаційну інтерпретацію.

Динаміка забезпечує розуміння змін.

Міркування забезпечує формування цілей і пояснень.

Пошук забезпечує перевірку наслідків.

Пам'ять забезпечує накопичення досвіду.

Мета контроль забезпечує перевірку надійності.

Еволюція забезпечує контрольоване вдосконалення.

## 146. Заключна теза

SUBIT-CHESS повинен бути не просто шаховою програмою, яка обчислює найкращий хід.

Його цільова архітектура — це автономна обчислювальна система, яка:

- формально представляє позицію;
- виявляє її внутрішню структуру;
- встановлює відношення;
- аналізує трансформації;
- досліджує потенційні стани;
- формує стратегічні гіпотези;
- перевіряє їх пошуком;
- пояснює власні рішення;
- зберігає досвід;
- виявляє власні помилки;
