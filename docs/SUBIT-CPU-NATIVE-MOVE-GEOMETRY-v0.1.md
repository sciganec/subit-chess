# SUBIT-CPU Native Move Geometry v0.1

**Status:** CPU-executed piece geometry and intermediate-square occupancy validation, using a static relation ROM assembled in JavaScript.

## Purpose

The geometry stage follows Move Preflight and precedes staged Move Apply. It answers two questions:

1. Is the source piece type geometrically allowed to move from the decoded source square to the decoded destination square?
2. If the move follows a ray or is a pawn's initial double advance, are all intermediate squares empty?

The stage does not use the chess engine's legal-move API. The SUBIT-CPU computes the pair index, reads the relation mask, selects the source piece type, and checks live board occupancy.

## Relation ROM

The table has 64 × 64 source/destination records. Each record occupies eight 16-bit words:

- word 0: piece-type mask — bit 0 pawn, 1 knight, 2 bishop, 3 rook, 4 queen, 5 king;
- word 1: number of intermediate squares;
- words 2–7: ordered intermediate square indices, padded with 0xFFFF.

The side-specific ROM is generated at assembly time. Runtime record address:

`tableBase + 8 × (64 × from + to)`

A 16-word one-hot lookup maps the exact Chess Unit piece code to the corresponding geometry-mask bit. White piece codes 1–6 and black codes 9–14 map to the same six type bits.

Default memory:
- relation ROM: 0x4000–0xBFFF (32,768 words);
- one-hot map: 0x3F00–0x3F0F;
- geometry status: 0x034C;
- program start: 0xD000.

The staged board at 0x0500 does not overlap the relation ROM.

## Implemented geometry

- **Pawn:** one-square advance, diagonal capture geometry, initial two-square advance in the side-specific direction. The middle square of a double advance is checked at runtime.
- **Knight:** all eight L-shaped displacements.
- **Bishop:** nonzero diagonal displacement.
- **Rook:** same-file or same-rank displacement.
- **Queen:** bishop or rook displacement.
- **King:** one-square Chebyshev neighborhood.

For bishops, rooks, and queens, all intermediate squares are checked in order. The same runtime path scan is used for the intermediate square of a pawn double advance. Destination occupancy and source ownership remain the responsibility of Move Preflight.

## Status codes

| Code | Meaning |
|---:|---|
| 0 | Not run |
| 1 | Geometry and path accepted |
| 2 | Piece cannot make this displacement |
| 3 | Intermediate square is occupied |
| 4 | Nonzero promotion field is unsupported by this pipeline stage |
| 5 | Reserved for execution-level failure reporting |

## Pipeline

The composed king-safety pipeline now runs:

`MOVE_PREFLIGHT → MOVE_GEOMETRY → MOVE_APPLY → ATTACK_MAP × 5 → KING_SAFETY`

A geometry rejection prevents Move Apply and all subsequent attack-map work.

## Validation

Regressions cover:
- legal and illegal knight displacement;
- clear and blocked rook rays;
- clear and blocked bishop rays;
- legal pawn double advance and blocked intermediate square;
- black pawn double advance;
- invalid pawn displacement;
- explicit rejection of a nonzero promotion field.

The composed pipeline's discovered-check and safe-blocker cases continue to pass with geometry inserted before application.

## Limits and next steps

This stage is a geometry/path validator, not a full chess legality validator. It does not currently enforce:
- promotion rank/choice semantics or promoted-piece replacement;
- en passant (including removal of the captured pawn);
- castling (including rook movement and attacked transit squares);
- all special move metadata, clocks, castling rights, hash/repetition updates;
- whether a move resolves an existing check beyond the subsequent king-safety probe.

The ROM is generated by JavaScript as immutable static data; the runtime decision and path reads are performed by SUBIT-CPU. JavaScript still sequences the component programs. The next step is promotion-aware move application and special-move transformations, followed by differential testing of generated candidates against the reference chess engine.
