# SUBIT-CHESS ∞
## Foundational Ontology & Mathematical Architecture
### Розділ II. Від базового простору станів до динамічної системи

## 1. Фундаментальна проблема: що саме ми моделюємо?

Почнемо з розрізнення трьох об'єктів, які традиційна шахова архітектура часто об'єднує.

**Простір.**

Множина 64 незмінних адрес, які відповідають клітинам шахівниці.

**Стан.**

Сукупність властивостей, які характеризують конкретну клітину в конкретний момент.

**Конфігурація.**

Сукупність станів усіх клітин разом із відношеннями між ними.

Це три різні математичні об'єкти.

Позначимо:

```text
S = SUBIT-64
C = {c₀, c₁, ..., c₆₃}
P = Position
```

Де:

- S — множина 64 станів SUBIT;
- C — множина 64 клітин;
- P — повна конфігурація шахової системи.

Між C та S визначаємо бієкцію:

```text
φ : C ↔ S
```

Кожна клітина отримує один конкретний код SUBIT-64.

Однак потрібно зафіксувати важливе уточнення.

Ця бієкція не означає, що фізичне розташування фігури визначається значенням WHO, WHERE або WHEN. Вони залишаються компонентами ідентичності базового SUBIT-стану.

Фізична геометрія шахівниці визначається окремим відношенням між клітинами.

Таким чином, ми не підміняємо SUBIT-64 шаховими координатами.

# 2. SUBIT-64: точна адресна структура

Використовуємо канонічну специфікацію:

```text
WHO:
ME    = 10
WE    = 11
YOU   = 01
THEY  = 00

WHERE:
EAST  = 10
SOUTH = 11
WEST  = 01
NORTH = 00

WHEN:
SPRING = 10
SUMMER = 11
AUTUMN = 01
WINTER = 00
```

Кожен стан має шість бітів:

```text
SUBIT = WHO + WHERE + WHEN
```

Ідентифікатор:

```text
ID = 32b1 + 16b2 + 8b3 + 4b4 + 2b5 + b6
```

Отримуємо:

```text
|S| = 2⁶ = 64
```

Тепер необхідно зробити ще один крок.

Визначити канонічну функцію відображення:

```text
φ(cᵢ) = sᵢ
```

Для першої реалізації пропоную:

```text
a1 → 000000
b1 → 000001
c1 → 000010
...
h8 → 111111
```

Це лише початкове адресне відображення. Його можна замінити іншою бієкцією без зміни самої шахової системи, якщо зберігається семантика базових станів.

Принципово важливо: **SUBIT-код клітини є незмінним, але вміст клітини може змінюватися необмежену кількість разів.**

# 3. CELL: клітина як структурний носій

Тепер визначимо клітину.

У традиційній архітектурі:

```text
board[square] = piece
```

У SUBIT-CHESS ∞ це недостатньо.

Пропоную:

```text
CELL = {
    IDENTITY,
    SUBIT_STATE,
    GEOMETRY,
    CONTENT,
    RELATIONS,
    CONTEXT,
    HISTORY
}
```

Розглянемо компоненти.

### IDENTITY

Незмінна ідентичність клітини.

```text
CELL_ID = 0...63
```

### SUBIT_STATE

Базовий код SUBIT-64.

```text
SUBIT_STATE = φ(CELL_ID)
```

### GEOMETRY

Відношення клітини до інших клітин.

```text
NORTH
SOUTH
EAST
WEST
DIAGONAL
DISTANCE
```

### CONTENT

Поточний вміст:

```text
EMPTY
OCCUPIED
```

Якщо клітина зайнята, вона посилається на конкретного агента.

### RELATIONS

Відношення до інших клітин та агентів.

### CONTEXT

Контекстуальні характеристики.

### HISTORY

Історія змін конкретної клітини.

Останні три компоненти не обов'язково повинні зберігатися безпосередньо в кожному об'єкті CELL. Їх можна представляти централізованими структурами з посиланнями на клітини.

Це важливо для продуктивності.

---

# 4. AGENT: шахова фігура як автономний структурний об'єкт

Тепер перейдемо до фігур.

Я пропоную принципово відмовитися від ототожнення фігури з клітиною.

Фігура існує незалежно від свого поточного розташування.

Визначимо:

```text
AGENT = {
    ID,
    COLOR,
    TYPE,
    LOCATION,
    OPERATORS,
    CONSTRAINTS,
    STATE
}
```

Наприклад:

```text
AGENT:
    ID: WN1
    COLOR: WHITE
    TYPE: KNIGHT
    LOCATION: b1
```

Після ходу:

```text
LOCATION: c3
```

Але:

```text
ID = WN1
```

залишається незмінним.

Це дозволяє відстежувати історію конкретної фігури, її відносини та вплив на структуру позиції.

Важливе уточнення: ідентичність агента потрібна для внутрішнього структурного аналізу, але не повинна впливати на шахову тотожність позиції. Дві позиції з однаковим розташуванням однакових типів фігур можуть бути шахово еквівалентними, навіть якщо внутрішні ID агентів відрізняються.

---

# 5. PIECE OPERATORS: фігури як оператори

Тепер визначимо спосіб взаємодії фігур із простором.

Кожен тип фігури має набір операторів.

```text
OPERATOR = {
    MOVE,
    ATTACK,
    INTERACTION
}
```

Розділення MOVE та ATTACK є обов'язковим.

Наприклад, пішак може рухатися вперед, але атакувати по діагоналі.

### KNIGHT

Нехай координати клітини:

```text
(x,y)
```

Тоді множина потенційних переходів:

```text
ΔKNIGHT = {
    (+1,+2),
    (+2,+1),
    (+2,-1),
    (+1,-2),
    (-1,-2),
    (-2,-1),
    (-2,+1),
    (-1,+2)
}
```

### BISHOP

Діагональний оператор:

```text
ΔBISHOP = {
    (+1,+1),
    (+1,-1),
    (-1,+1),
    (-1,-1)
}
```

### ROOK

Ортогональний оператор:

```text
ΔROOK = {
    (+1,0),
    (-1,0),
    (0,+1),
    (0,-1)
}
```

### QUEEN

Композиція:

```text
QUEEN = BISHOP ∪ ROOK
```

### KING

Локальний оператор:

```text
max(|Δx|,|Δy|) = 1
```

З окремими обмеженнями безпеки та спеціальним оператором рокіровки.

### PAWN

Спрямований асиметричний оператор:

```text
MOVE ≠ ATTACK
```

Із правилами першого подвійного ходу, перетворення, en passant та обмеженнями напрямку.

Зверни увагу: ми поки що визначаємо геометричну можливість переходу, а не його легальність.

Це два різні рівні.

# 6. RELATIONAL TOPOLOGY: геометрія як система відносин

Тепер можемо побудувати одну з найважливіших складових нової архітектури.

Шахівниця — це граф.

```text
G = (V,E)
```

Де:

```text
V = C
```

А E — множина геометричних відношень.

Проте звичайного графа недостатньо.

Я пропоную використовувати типізований орієнтований граф:

```text
G = (V,E,τ)
```

Де τ визначає тип кожного ребра.

Наприклад:

```text
τ(e) ∈ {
    ORTHOGONAL,
    DIAGONAL,
    KNIGHT,
    ADJACENT,
    SAME_FILE,
    SAME_RANK,
    SAME_DIAGONAL
}
```

Це дає можливість описувати геометрію через відношення.

Але тут є ще один цікавий момент.

**Геометрія шахівниці є незмінною, тоді як доступність відношень залежить від конфігурації.**

Наприклад, між a1 та a8 існує геометрична вертикальна лінія незалежно від фігур.

Але тура може мати або не мати доступ до a8 залежно від проміжних зайнятих клітин.

Тому:

```text
GEOMETRIC_RELATION ≠ AVAILABLE_TRANSITION
```

Це розрізнення має стати одним із базових інваріантів SUBIT-CHESS.

# 7. OCCUPANCY: перше динамічне розгортання

Тепер, коли ми маємо 64 стани, геометрію та агентів, можна визначити зайнятість.

```text
OCCUPANCY : C → AGENT ∪ {EMPTY}
```

Для будь-якої клітини:

```text
OCCUPANCY(c) =
    agent, якщо клітина зайнята
    EMPTY, якщо клітина вільна
```

Важливий інваріант:

```text
∀a,b ∈ AGENTS:
    LOCATION(a) = LOCATION(b) → a = b
```

Тобто одна клітина не може містити дві фігури одночасно.

Далі визначаємо проєкції:

```text
WHITE_OCCUPANCY
BLACK_OCCUPANCY
TOTAL_OCCUPANCY
EMPTY_SQUARES
```

Ці проєкції вже можна реалізувати за допомогою Bitboards.

Але тепер Bitboards отримують інше місце в архітектурі.

Вони не є первинною онтологією.

Вони є ефективними обчислювальними проєкціями множини SUBIT-станів.

Це суттєва відмінність від попередньої концепції SUBIT-BITBOARD.

# 8. TRANSFORMATION: хід як формальна зміна системи

Тепер можемо визначити шаховий хід.

Нехай P — поточна позиція.

Хід m є трансформацією:

```text
Tₘ : P → P'
```

Але не кожна трансформація допустима.

Визначимо:

```text
L(P) = {m | m задовольняє правила шахів}
```

Тоді:

```text
P' = Tₘ(P), m ∈ L(P)
```

Кожна трансформація повинна бути атомарною.

Тобто або всі її компоненти застосовуються, або жодна.

Наприклад, рокіровка — це не один незалежний перехід короля.

Вона змінює розташування двох агентів, права на рокіровку та інші характеристики стану.

En passant також потребує спеціальної трансформації.

Просування пішака змінює тип агента відповідно до правил гри.

Тому пропоную:

```text
TRANSFORMATION =
    PREPARE
    → VALIDATE
    → COMMIT
```

У разі невідповідності:

```text
ABORT
```

Це добре узгоджується з транзакційним підходом SUBIT-CPU, але не означає, що шаховий рушій повинен механічно використовувати всю архітектуру SUBIT-CPU.

# 9. SUBIT-CONTEXT: повернення до початкової філософії

Тепер ми маємо геометрію, агентів, відносини та трансформації.

Але цього недостатньо.

Одна й та сама геометрична конфігурація може мати різне стратегічне значення залежно від:

- сторони, що ходить;
- фази партії;
- історії;
- наявних загроз;
- можливих відповідей;
- часових обмежень.

Тому визначимо:

```text
CONTEXT(P) =
    WHO × WHERE × WHEN
```

Тут потрібно зробити важливе розрізнення.

SUBIT-64, призначений клітині, — її незмінна адресна ідентичність.

SUBIT-контекст позиції — динамічний опис ситуації.

Ці два рівні не можна ототожнювати.

Для шахового рушія я пропоную зберігати контекст у вигляді багатовимірного профілю, а не одного коду.

Наприклад:

```text
CONTEXT:
    INTENT:
        QUIET
        DEFENCE
        ATTACK
        PRESSURE

    ZONE:
        GLOBAL
        QUEENSIDE
        KING
        CENTER

    PHASE:
        OPENING
        MIDDLEGAME
        ENDGAME
        TRANSITION
```

Отримуємо 64 контекстуальні комбінації.

Але позиція не обов'язково належить лише одній комірці цього простору.

Вона може мати декілька одночасно релевантних контекстів.

Це дозволяє уникнути примусового зведення складної позиції до одного ярлика.

# 10. Важливе розширення: SUBIT-∞ як простір розрізнень

Тепер я хочу запропонувати дещо принциповіше.

До цього моменту ми будували систему навколо 64 базових клітин.

Але SUBIT-∞ дозволяє поставити інше питання:

Чи повинні всі характеристики шахової позиції мати ту саму просторову розмірність?

Очевидно, ні.

Просторовий субстрат має 64 клітини.

Але відносини між клітинами можуть мати значно більшу кількість комбінацій.

Відносини між агентами — ще іншу структуру.

Історія трансформацій — ще іншу.

Тому пропоную визначити:

```text
SUBIT-∞ =
    BASE STATES
    + STRUCTURAL DISTINCTIONS
    + RELATIONAL DISTINCTIONS
    + CONTEXTUAL DISTINCTIONS
    + TEMPORAL DISTINCTIONS
    + META-DISTINCTIONS
```

Це не просто розширення кількості бітів.

Це розширення множини типів інформації, які система здатна розрізняти.

Наприклад, одна клітина може одночасно:

- бути зайнятою білим конем;
- атакувати чорного пішака;
- захищати білого пішака;
- контролювати центральне поле;
- бути частиною потенційної комбінації;
- мати різне значення залежно від відповіді суперника.

Жодна одна бітова характеристика не здатна адекватно представити всю цю інформацію.

# 11. Перша математична модель нового рушія

На цьому етапі можна сформулювати базову модель.

```text
SUBIT-CHESS ∞ = (C,S,A,G,R,O,T,H,K)
```

Де:

- C — множина клітин;
- S — множина базових станів SUBIT-64;
- A — множина шахових агентів;
- G — геометрична топологія;
- R — система відносин;
- O — функція зайнятості;
- T — множина допустимих трансформацій;
- H — історія;
- K — контекст.

Повний стан позиції:

```text
P = (O,A,R,K,H)
```

Геометрія G та базове відображення φ залишаються незмінними.

Трансформація:

```text
Tₘ(P) = P'
```

Функція легальності:

```text
LEGAL(P,m) ∈ {TRUE,FALSE}
```

Умовою переходу є:

```text
LEGAL(P,m) = TRUE
```

А вже після цього система може аналізувати:

```text
STRUCTURAL_DELTA(P,P')
```

Ця модель поки що є фундаментальним контрактом. Вона ще не визначає повністю всі правила шахів, але створює місце для їхнього точного формального вираження.

# 12. Що я пропоную зробити далі

На цьому етапі я б не поспішав переходити до пошукових алгоритмів.

Є три фундаментальні напрями, які необхідно опрацювати.

**Перший — SUBIT-64 Spatial Mapping.**

Потрібно математично визначити, як саме 64 стани SUBIT відповідають 64 клітинам, як формується геометрія і які властивості є інваріантними.

**Другий — SUBIT Piece Ontology.**

Потрібно визначити фігури як структурні агенти, їхні оператори, обмеження та взаємодію.

**Третій — SUBIT Transformation Algebra.**

Потрібно формалізувати легальні трансформації, їхні наслідки, оборотність, композицію та історичну залежність.

Я пропоную наступним кроком перейти до першого напряму й дослідити одну особливо цікаву можливість:

**Чи можна вивести геометрію шахівниці безпосередньо з внутрішньої структури шести бітів SUBIT-64?**

Тобто не просто призначити 64 коди 64 клітинам, а спробувати побудувати математичне відображення, у якому бітові відмінності, тривимірна структура WHO × WHERE × WHEN та шахова геометрія утворюють узгоджену систему.

Це може виявитися найважливішим фундаментальним експериментом у всьому проєкті.

Але його результат не слід припускати наперед: потрібно перевірити, чи здатна структура SUBIT-64 породити шахову геометрію зі збереженням усіх її властивостей, чи для цього потрібен додатковий оператор просторового відображення.

Саме це і варто дослідити наступним.
